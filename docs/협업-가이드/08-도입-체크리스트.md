## GitHub Actions / Ruleset

- [ ] 실제 Backend/Frontend 프로젝트 구조가 들어온 뒤 GitHub Actions CI를 구성한다.
- [ ] CI의 정상 코드 성공을 샘플 PR에서 확인한다.
- [ ] 의도적으로 실패하는 코드/테스트에서 CI가 실패하는지 확인한다.
- [ ] GitHub에 표시된 실제 check 이름을 기록한다.
- [ ] 문서-only / FE-only / BE-only PR에서 검사가 Pending으로 멈추지 않는지 확인한다.
- [ ] 검증된 CI check를 `main` Ruleset의 Required Status Check로 등록한다.
- [ ] `main` Ruleset에서 PR 필수, 사람 승인 1명, conversation resolution, force push/삭제 금지, linear history를 적용한다.
- [ ] Ruleset 적용 후 작은 실제 PR로 전체 흐름을 다시 검증한다.

## 팀원 합류 전 마무리

- [ ] `.gitmessage.txt`를 저장소에 추가하고 팀원 초기 설정 문서를 최종 검토한다.
- [ ] Linear ↔ GitHub 연결과 이슈 상태 전환 동작을 실제 이슈로 검증한다.
- [ ] Slack `#dev` 공지, GitHub 협업 문서, Linear 프로젝트 운영 설명의 표현을 최종 일치시킨다.
- [ ] 모든 자동화/보호 설정 검증이 끝난 뒤 Organization에 팀원을 초대한다.
- [ ] 팀원 모두 자신의 clone에 초기 설정을 적용하고 결과를 확인한다.
- [ ] 팀원과 함께 실제 PR 하나를 작성 → CI → CodeRabbit → Human Review → Squash Merge → 브랜치 삭제까지 수행한다.

Ruleset과 CI는 순서를 바꾸지 않는다. **CI를 먼저 실제 PR에서 검증하고, 그 다음 Required Status Check와 `main` Ruleset을 완성한다.**
