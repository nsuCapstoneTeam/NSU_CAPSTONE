# 실제 개발 작업 절차

← [가이드 목차](README.md)

이 문서는 실제 기능·버그 작업 하나를 시작해서 Linear Issue를 닫을 때까지 팀원이 따라야 하는 표준 순서를 정한다.

## 전체 흐름

```text
Slack #dev Root Message + Thread 논의
        ↓
@Claude 논의 요약 / 문서 초안 / 설계 검토
        ↓
Human Confirm
        ↓
@Linear Issue 생성
        ↓
Linear Issue 내용 확인
        ↓
작업 시작 시 In Progress
        ↓
최신 main에서 작업 Branch 생성
        ↓
Linear 확정 내용을 기준으로 필요한 README / docs/ / API / ADR 갱신
        ↓
AI Agent 또는 Human 구현·검증
        ↓
GitHub PR
        ↓
CodeRabbit 자동 PR Review
        ↓
Human Review
- Linear 요구사항 / Acceptance Criteria
- 코드 / 테스트 / 보안 / 권한 / 예외처리
- README / docs/ / API / ADR 정합성
        ↓
작성자 외 팀원 1명 이상 승인
        ↓
Squash Merge
        ↓
@Linear로 Done 처리
```

현재 Linear 상태는 `Backlog / In Progress / Done / Canceled / Duplicate`를 사용한다. 별도의 `Approved` 상태는 두지 않는다. 요구사항 승인은 Slack Thread의 Human Confirm에서 이루어지고, Linear에서는 생성된 Issue가 그 확정 내용과 일치하는지 확인한다.

## 1. Slack에서 논의 시작

하나의 기능·버그는 `#dev`의 Root Message 하나로 시작하고 관련 논의는 같은 Thread에서 진행한다.

예시:

```text
[FEATURE] 이메일 로그인 구현

논의할 내용
- 로그인 성공/실패 응답
- 비밀번호 정책
- 계정 잠금 여부
- 필요한 API / DB 변경
```

## 2. Claude로 논의 정리

팀 논의가 충분히 진행되면 Slack에서 Claude를 호출한다.

```text
@Claude
위 Thread 논의를 우리 프로젝트 MVP 기준으로 정리해줘.

- 확정된 요구사항
- 정책
- 예외 상황
- 필요한 API
- DB 변경사항
- 관련 Requirement ID
- Linear Issue 제목/Description/Acceptance Criteria 초안
- 결정되지 않은 사항

팀에서 결정하지 않은 내용은 임의로 결정하지 말고 "결정 필요"로 표시해줘.
```

Claude의 결과는 초안이다. 팀원이 검토하기 전에는 확정 요구사항으로 취급하지 않는다.

## 3. Human Confirm

팀원이 Claude 결과를 검토하고 최종 요구사항을 같은 Thread에 명시한다.

```text
[Human Confirm]
이 Thread의 최종 요구사항을 아래와 같이 확정합니다.
- 이메일/비밀번호 로그인
- 로그인 실패 시 401
- 계정 잠금은 이번 MVP에서 제외
- 관련 Requirement: AUTH-xxx
```

결정하지 않은 정책을 AI가 임의로 확정하지 않는다.

## 4. Linear Issue 생성

Human Confirm 이후 `@Linear`로 실제 Issue를 만든다.

```text
@Linear
위 Human Confirm 내용을 기준으로 Linear 프로젝트
`아티스트-행사 매칭 플랫폼 MVP`에 Issue 1개를 만들어줘.

포함할 내용:
- 제목
- 목표
- 관련 Requirement ID
- Acceptance Criteria
- 담당자
- Priority
- 일정(확정된 경우만)
- 결정 필요 사항이 있으면 별도 표시

임의로 정책을 추가하지 말고, 생성 후 실제 Issue 키와 링크를 이 Thread에 알려줘.
```

Linear Bot이 반환한 Issue 링크를 열어 다음을 확인한다.

- 제목과 작업 범위가 Human Confirm과 같은가?
- Acceptance Criteria가 구현 완료 조건으로 충분한가?
- 관련 Requirement ID가 맞는가?
- 담당자 / Priority / 일정이 맞는가?
- 결정되지 않은 정책이 임의로 추가되지 않았는가?

잘못된 부분이 있으면 구현 전에 Linear를 수정한다. Issue 생성 직후에는 `Backlog`, 실제 개발을 시작하는 시점에는 `In Progress`로 변경한다.

## 5. Branch 생성과 GitHub 문서 반영

Linear Issue가 확인되면 최신 `main`에서 작업 Branch를 만든다.

```bash
git switch main
git pull origin main
git switch -c feat/NSU-123-email-login
```

브랜치 이름에는 실제 Linear Issue 키를 사용한다. 없는 Issue 번호를 임의로 만들지 않는다.

Linear의 확정 내용이 장기 문서에 영향을 주면 같은 작업 Branch에서 필요한 문서를 먼저 또는 구현과 함께 갱신한다.

- API 변경: `docs/api/`
- 중요한 기술 결정: `docs/adr/`
- 장기 설계·정책·운영 규칙: `docs/`
- 프로젝트 진입 정보: `README.md`

GitHub 문서는 Linear 내용을 그대로 복제하는 두 번째 요구사항 원본이 아니다. 제품 요구사항 자체가 바뀌면 GitHub 문서에서 먼저 확정하지 않고 Slack 논의 → Human Confirm → Linear 갱신을 먼저 한다.

## 6. 구현과 PR

AI Agent 또는 사람이 Linear Issue와 Acceptance Criteria를 기준으로 구현하고 검증한다.

PR 제목 예시:

```text
[NSU-123] 이메일 로그인 구현
```

PR 본문에는 최소한 다음을 남긴다.

- Linear Issue 링크
- 관련 Requirement ID
- 실제 변경 내용
- 실행한 테스트와 결과
- README / `docs/` / API / ADR 영향
- 리뷰어가 집중해서 확인할 부분

구현 중 새로운 요구사항이 발견되면 PR 안에서 임의로 정책을 정하지 않고 다시 Slack Thread → Human Confirm → Linear 갱신 절차로 돌아간다.

## 7. CodeRabbit Review

PR을 열면 CodeRabbit 자동 Review를 기다린다. CodeRabbit은 Advisory이며 사람 승인을 대체하지 않는다.

자동 Review를 놓쳤거나 전체 재검토가 필요한 경우 GitHub PR 댓글에서 사용할 수 있다.

```text
@coderabbitai review
```

또는:

```text
@coderabbitai full review
```

Slack `@CodeRabbit`은 공식 필수 단계가 아니라 보조 조사용이다.

```text
@CodeRabbit
GitHub PR #123에서 지적된 내용을 요약하고,
버그/보안/데이터 정합성 문제와 단순 스타일 제안을 구분해줘.
```

Slack의 CodeRabbit 답변만으로 Merge 여부를 결정하지 않는다.

## 8. Human Review와 승인

사람 리뷰어는 반드시 다음 세 가지를 확인한다.

1. **Linear** — Issue 목표와 Acceptance Criteria를 실제 구현이 충족하는가?
2. **Code** — 코드, 테스트, 보안, 권한, 예외 처리와 변경 영향이 적절한가?
3. **Documentation** — README, `docs/`, API, ADR이 필요한 만큼 갱신되었고 Linear의 확정 내용과 충돌하지 않는가?

작성자 외 팀원 1명 이상이 승인한 뒤 사람이 Squash Merge한다.

## 9. Merge 후 Linear 종료

현재 GitHub PR Merge 후 Linear 상태 자동 전환은 신뢰하지 않는다. Merge 후 Slack에서 `@Linear`로 명시적으로 종료한다.

```text
@Linear
GitHub PR #123이 Squash Merge됐어.
연결된 NSU-123 Issue의 Acceptance Criteria가 완료된 것을 기준으로 상태를 Done으로 변경해줘.
상태 변경 후 결과만 알려줘.
```

취소된 작업은 `Canceled`, 중복 작업은 `Duplicate`를 사용한다.

마지막으로 다음을 확인한다.

```text
Linear Issue: Done
GitHub PR: Squash Merge 완료
원격 작업 Branch: 삭제 확인
필요 문서: 반영 완료
Slack Thread: 중요한 결정이 Linear/GitHub에 남아 있음
```

병합 이후 로컬 정리는 [7. 병합 이후 정리와 되돌리기](07-병합-이후-정리와-되돌리기.md)를 따른다.
