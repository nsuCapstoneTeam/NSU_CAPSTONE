# 로컬 설정과 일상 작업

← [가이드 목차](README.md)

아래 명령은 저장소 안에서 실행한다. macOS·Linux·Git Bash 기준이다. 예시 브랜치 이름과 파일 경로는 실제 작업에 맞게 바꾼다. **명령은 한 단계씩 실행하고, 실패하거나 예상과 다른 결과가 나오면 다음 단계로 넘어가지 않는다.**

## 팀원 초기 설정

### 저장소를 clone한 뒤 한 번 설정

`.gitmessage.txt`가 저장소에 추가된 다음 실행한다. 템플릿 내용은 [커밋 전략과 메시지](03-커밋-전략과-메시지.md#공통-gitmessagetxt-제안)에 있다.

```bash
git config --local commit.template "$(git rev-parse --show-toplevel)/.gitmessage.txt" # 이 저장소의 커밋 템플릿을 등록한다.
git config --local --get commit.template # 템플릿의 실제 경로를 확인한다.
```

`--local` 설정은 각 clone의 로컬 Git 설정에 저장된다. 팀원이 새로 clone하면 다시 실행해야 한다. 템플릿을 절대 경로로 등록하므로 저장소 폴더를 옮겼을 때도 템플릿 경로를 다시 등록한다. 이 설정은 GitHub에 push되지 않는다. [Git 설정 범위][G4]

### pull 전에 확인할 것

`pull`은 원격 정보를 fetch한 뒤 현재 브랜치에 통합한다. 통합 과정에서 merge 커밋이 생기거나 충돌이 발생할 수 있으므로, 커밋하지 않은 변경이 있으면 **먼저 커밋하거나 따로 보존한 뒤** 실행한다. 작업을 버리는 명령으로 정리하지 않는다.

| 현재 상태 | 팀 대응 |
|---|---|
| 로컬이 원격보다 뒤에 있고 이력이 이어짐 | 그대로 pull해 갱신 |
| 이미 동일한 이력 | 추가 통합 없음 |
| 로컬에만 추가 커밋이 있고 원격은 그 조상 | 원격에서 합칠 새 변경이 없으며 로컬 커밋은 유지 |
| 로컬·원격에 각각 다른 커밋이 생김 | merge 커밋이 생기거나 충돌이 날 수 있음. 결과를 확인하고 필요하면 담당자와 처리 방식 결정 |
| 커밋하지 않은 변경이 있음 | 팀 규칙상 먼저 보존·정리한 뒤 실행 |

충돌이 발생하면 아래 [충돌 해결 또는 중단](#충돌-해결-또는-중단) 절차를 따른다. [pull 동작][G5]

## 일상 작업 절차

### 최신 `main`에서 새 작업 시작

먼저 진행 중인 merge·rebase와 저장하지 않은 변경이 없는지 확인한다. 변경이 있으면 현재 작업 브랜치에 필요한 변경을 커밋하거나 내용을 확인해 따로 보존한다.

```bash
git status # 현재 브랜치와 커밋하지 않은 변경, 진행 중인 작업을 확인한다.
git switch main # 깨끗한 작업 상태에서 기준 브랜치로 이동한다.
git pull origin main # 원격 main을 로컬 main에 반영한다.
git switch -c feat/DEV-123-user-signup # 실제 이슈와 작업명으로 새 브랜치를 만든다.
```

`main`의 pull에서 예상하지 못한 merge 커밋이나 충돌이 발생하면 작업 브랜치 생성으로 넘어가지 않는다. 로컬 `main`에 실수로 커밋했는지 등을 먼저 확인한다. 필요한 로컬 커밋을 보존하기 전에는 이력을 초기화하지 않는다.

### 변경 확인, 커밋, push

```bash
git diff # 수정한 내용을 검토한다.
git add -p # 이미 추적 중인 파일에서 이번 목적에 맞는 변경을 선택한다.
git diff --cached # 실제 커밋될 변경을 다시 확인한다.
git commit # 편집기에서 팀 규칙에 맞는 제목과 한국어 본문을 작성한다.
git push -u origin feat/DEV-123-user-signup # 실제 작업 브랜치를 처음 push하고 추적 대상을 설정한다.
```

`git add -p`는 새 파일을 자동으로 포함하지 않는다. 새 파일은 내용을 확인한 뒤 다음처럼 정확한 경로를 지정한다. 아래는 경로를 바꿔서 사용하는 예시다.

```bash
git add -- '실제/새파일/경로' # 예시를 실제 파일 경로로 바꿔 새 파일을 추가한다.
```

새 파일도 커밋 전에 `git diff --cached`로 확인한다. 작업 브랜치에서 리뷰 수정 커밋을 추가한 뒤에는 다음과 같이 push한다.

```bash
git push # 현재 브랜치의 등록된 원격 추적 대상으로 후속 커밋을 올린다.
```

### 작업 브랜치에 최신 `main` 반영

이번 문서에서는 **작업 브랜치에서 fetch 후 merge하는 방식**을 기본 운영값으로 제안한다. 이미 공유한 커밋을 다시 쓰지 않아 팀원이 함께 다루기 쉽다. 이는 GitHub Flow 자체가 의무화하는 단일 방식은 아니다.

다음 명령은 작업 브랜치에 있고 작업 상태가 깨끗할 때 실행한다.

```bash
git status # 작업 브랜치인지, 커밋하지 않은 변경이 없는지 확인한다.
git fetch origin # 원격 브랜치의 최신 정보를 가져온다.
git merge origin/main # 최신 main을 현재 작업 브랜치에 명시적으로 통합한다.
```

이력이 갈라져 있으면 작업 브랜치에 merge 커밋이 생길 수 있다. 편집기가 열리면 `최신 main 변경을 작업 브랜치에 반영한다`처럼 목적을 적는다. `main`에는 PR을 Squash Merge하므로 이 작업 브랜치의 merge 커밋이 그대로 추가되는 것은 아니다. [merge][G6] · [Squash Merge][G2]

개인 로컬 브랜치의 rebase가 필요한 경우에는 이력 변경을 이해한 사람이 별도로 처리한다. 공유한 브랜치의 rebase·강제 push를 기본 절차로 사용하지 않는다. 통합 실패를 무시하고 자동으로 rebase나 강제 초기화를 실행하는 스크립트도 만들지 않는다.

### 충돌 해결 또는 중단

위 merge에서 충돌이 발생한 경우에만 다음 절차를 따른다.

```bash
git status # 충돌과 merge 진행 상태를 확인한다.
git diff --name-only --diff-filter=U # 아직 해결되지 않은 파일 목록을 확인한다.
```

양쪽 변경 의도를 확인하고, 필요하면 상대 변경 작성자와 합의해 파일을 수정한다. 충돌 표시만 제거하는 것으로 끝내지 말고 결과 동작을 검증한다. 모든 파일을 일괄적으로 "내 것" 또는 "상대 것"으로 선택하지 않는다.

```bash
git add -- '실제/해결한/파일경로' # 예시를 실제 경로로 바꿔 해결한 파일마다 추가한다.
git diff --cached # 자동 통합된 변경과 직접 해결한 변경을 함께 검토한다.
git status # 해결되지 않은 파일이 없는지 확인한다.
git commit # merge 결과의 목적과 필요한 설명을 기록한다.
git push # 검증한 통합 결과를 작업 브랜치에 올린다.
```

계속 진행하지 않기로 했다면 **위 완료 절차 대신** 다음 명령을 쓴다.

```bash
git merge --abort # 진행 중인 merge를 중단하고 시작 전 상태로 복구를 시도한다.
```

이 명령은 진행 중인 merge에 사용한다. 실제 rebase 진행 중에는 다음 명령을 사용한다.

```bash
git rebase --abort # 실제로 진행 중인 rebase를 중단할 때만 사용한다.
```

시작 전 미커밋 변경이 있으면 merge 중단만으로 원래 상태를 완전히 복구하지 못할 수 있으므로, 팀 규칙은 통합 전에 작업을 보존하고 깨끗한 상태를 확인하는 것이다. [충돌·중단 동작][G6]
