# 커밋 전략과 메시지

← [가이드 목차](README.md)

## 커밋을 나누는 기준

**작업 브랜치에는 여러 개의 의미 있는 커밋을 남기고, `main`에는 PR 하나를 Squash 커밋 하나로 남긴다.** Squash Merge는 PR의 변경을 하나의 새 커밋으로 합친다. [병합 방식 참고][G2]

| 상황 | 권장 단위 |
|---|---|
| 버그 수정과 그 버그의 재현 테스트 | 같은 목적의 커밋 / PR에 함께 포함 |
| 한 기능의 API와 화면 구현 | 같은 기능의 PR 안에서 BE·FE를 이해 가능한 커밋으로 분리 가능 |
| 서로 독립적으로 배포할 수 있는 API와 화면 작업 | 계약을 먼저 합의하고 별도 PR 가능 |
| 기능 추가 중 발견한 무관한 리팩터링 | 별도 PR로 분리 |
| 리뷰에서 받은 수정 요청 | 같은 PR 브랜치에 후속 커밋 추가 |
| 문서 오타 한 건 | 작은 커밋 하나와 PR 하나로 처리 |

커밋 크기를 줄 수나 파일 수로 강제하지 않는다. 변경 목적을 한 문장으로 설명할 수 있는지, 리뷰어가 이해할 수 있는지, 필요하면 그 목적만 되돌릴 수 있는지로 판단한다. 관련 테스트는 변경과 함께 작성하고, 단순 문서 수정에 불필요한 테스트를 추가하지 않는다.

예를 들어 회원가입 PR은 다음처럼 구성할 수 있다.

| 작업 브랜치의 커밋 | 변경 의도 |
|---|---|
| `회원가입 입력값 검증을 추가한다` | 잘못된 입력을 거부하는 로직과 관련 테스트 |
| `회원가입 API를 구현한다` | 합의한 API 계약과 서버 동작 |
| `회원가입 화면을 API와 연결한다` | 화면 입력·요청·오류 안내 |
| `중복 이메일 오류 안내를 수정한다` | 리뷰 피드백 반영 |

`main`의 최종 Squash 커밋은 PR 전체 목적을 설명하는 `회원가입 기능을 구현한다`처럼 작성한다. 위 기능과 이슈 번호는 설명용 예시이며 실제 완료된 작업이 아니다.

## 커밋 메시지 규칙

기존 인수인계 문서의 다음 일곱 규칙을 유지한다.

1. 제목과 본문 사이에 빈 줄을 둔다.
2. 제목은 50자 이내로 작성한다.
3. 제목 끝에 마침표를 붙이지 않는다.
4. 제목은 변경 동작을 드러내는 명령형으로 작성한다. 팀 예시는 `추가한다`, `수정한다`, `제거한다` 형식이다.
5. 본문은 한 줄을 72자 이내로 줄바꿈한다.
6. 구현 방법을 나열하기보다 **무엇을 바꿨고 왜 필요한지** 설명한다.
7. 본문은 한국어로 작성한다.

50자·72자는 팀 작성 규칙이며 Git 자체가 자동으로 검사하는 제한이 아니다. 이번 도입에서는 `feat:`·`fix:` 같은 Conventional Commits 접두사를 필수로 추가하지 않는다. 필요해지면 자동 릴리스 등 사용 목적과 함께 별도 결정한다.

### 메시지 예시

```text
커밋 메시지 규칙을 추가한다

팀원마다 커밋 메시지 형식이 달라질 경우 Git 기록의 일관성이
떨어지고 변경 의도를 파악하기 어려울 수 있다.

공통 커밋 템플릿과 작성 규칙을 추가해 모든 개발자가 동일한
기준으로 변경 목적과 이유를 기록할 수 있도록 한다.
```

`수정`, `작업 완료`, `여러 가지 개선`처럼 대상을 알 수 없는 제목은 피한다. API 키·토큰·비밀번호는 파일뿐 아니라 커밋 메시지와 PR 본문에도 넣지 않는다.

## 공통 `.gitmessage.txt` 제안

다음 내용을 저장소 루트의 `.gitmessage.txt`에 추가하는 PR을 만든다. 현재 문서에는 템플릿 내용을 제공하며, 실제 저장소 파일 생성은 도입 작업에 포함한다.

```text
# 첫 줄: 변경 동작을 설명하는 제목, 50자 이내, 끝에 마침표 없음
# 예시: 커밋 메시지 규칙을 추가한다
# 제목 다음에는 빈 줄을 한 줄 둔다.
# 본문: 무엇을 바꿨는지, 왜 필요한지 한국어로 설명한다.
# 본문은 한 줄을 72자 이내로 줄바꿈한다.
# 필요하면 마지막 문단에 실제 이슈 키를 적는다.
# 이 안내를 참고해 위쪽에 실제 메시지를 작성한다.
```

기본 Git 편집 설정에서는 `#`로 시작하는 안내가 최종 메시지에서 제외된다. 별도 주석·정리 설정을 사용하는 사람은 안내가 남지 않는지 확인한다. 템플릿은 작성 안내이며 규칙을 강제하는 검사기는 아니다. `git commit -m`은 템플릿 편집을 거치지 않으므로 기본 작성 방식은 `git commit`으로 한다. [템플릿 동작][G3]

템플릿을 각자의 clone에 등록하는 방법은 [로컬 설정과 일상 작업](04-로컬-설정과-일상-작업.md#팀원-초기-설정)에 있다.
