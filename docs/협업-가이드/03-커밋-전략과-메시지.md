# 커밋 전략과 메시지

← [가이드 목차](README.md)

## 커밋을 나누는 기준

**작업 브랜치에는 여러 개의 의미 있는 커밋을 남기고, `main`에는 PR 하나를 Squash 커밋 하나로 남긴다.** Squash Merge는 PR의 변경을 하나의 새 커밋으로 합친다. [병합 방식 참고][G2]

| 상황 | 권장 단위 |
|---|---|
| 버그 수정과 그 버그의 재현 테스트 | 같은 목적의 커밋 / PR에 함께 포함 |
| 한 기능의 API와 화면 구현 | 같은 기능의 PR 안에서 BE·FE를 이해 가능한 커밋으로 분리 가능 |
| 서로 독립적으로 배포할 수 있는 API와 화면 작업 | 계약을 먼저 합의하고 별도 PR 가능 |
| 기능 추가 중 발견한 무관한 리팩터링 | 별도 PR로 분리 |
| 리뷰에서 받은 수정 요청 | 같은 PR 브랜치에 후속 커밋 추가 |
| 문서 오타 한 건 | 작은 커밋 하나와 PR 하나로 처리 |

커밋 크기를 줄 수나 파일 수로 강제하지 않는다. 변경 목적을 한 문장으로 설명할 수 있는지, 리뷰어가 이해할 수 있는지, 필요하면 그 목적만 되돌릴 수 있는지로 판단한다. 관련 테스트는 변경과 함께 작성하고, 단순 문서 수정에 불필요한 테스트를 추가하지 않는다.

예를 들어 회원가입 PR은 다음처럼 구성할 수 있다.

| 작업 브랜치의 커밋 | 변경 의도 |
|---|---|
| `feat(auth): 회원가입 입력값 검증 추가` | 잘못된 입력을 거부하는 로직과 관련 테스트 |
| `feat(auth): 회원가입 API 구현` | 합의한 API 계약과 서버 동작 |
| `feat(auth): 회원가입 화면을 API와 연결` | 화면 입력·요청·오류 안내 |
| `fix(auth): 중복 이메일 오류 안내 수정` | 리뷰 피드백 반영 |

`main`의 최종 Squash 커밋은 PR 전체 목적을 설명하는 `feat(auth): 회원가입 기능 구현`처럼 작성한다. 위 기능과 이슈 번호는 설명용 예시이며 실제 완료된 작업이 아니다.

## 커밋 메시지 규칙

### 기본 일곱 규칙

1. 제목과 본문을 빈 행으로 구분한다.
2. 제목은 50글자 이내로 제한한다.
3. 제목의 첫 글자는 대문자로 작성한다.
4. 제목 끝에는 마침표를 넣지 않는다.
5. 제목은 명령문으로 사용하며 과거형을 사용하지 않는다.
6. 본문의 각 행은 72글자 내로 제한한다.
7. 어떻게 보다는 무엇과 왜를 설명한다.

**타입을 제외한 주제와 본문은 한국어로 작성한다.** 이 팀의 적용 기준은 다음과 같다.

- 3번 규칙은 한국어에 대문자가 없으므로, **타입은 항상 소문자**로 쓰고 주제의 첫 글자가 영문일 때만 대문자로 적는다. 예: `fix: Safari 모달 스크롤 이슈 수정`
- 5번 규칙은 한국어에서 **명사형 종결**로 적용한다. `추가`, `수정`, `제거`처럼 끝내고 `수정했다`, `수정함` 같은 과거형·완료형을 쓰지 않는다.
- 50글자·72글자는 팀 작성 규칙이며 Git 자체가 자동으로 검사하는 제한이 아니다.

### 커밋 구조

Header, Body, Footer는 빈 행으로 구분한다.

```text
타입(스코프): 주제        // Header(헤더)

본문                      // Body(바디)

바닥글                    // Footer
```

Header는 필수이며 스코프는 생략 가능하다.

### 타입

타입은 해당 커밋의 성격을 나타내며 아래 중 하나여야 한다.

| 타입 이름 | 내용 |
|---|---|
| `feat` | 새로운 기능에 대한 커밋 |
| `fix` | 버그 수정에 대한 커밋 |
| `build` | 빌드 관련 파일 수정 / 모듈 설치 또는 삭제에 대한 커밋 |
| `chore` | 그 외 자잘한 수정에 대한 커밋 |
| `ci` | ci 관련 설정 수정에 대한 커밋 |
| `docs` | 문서 수정에 대한 커밋 |
| `style` | 코드 스타일 혹은 포맷 등에 관한 커밋 |
| `refactor` | 코드 리팩토링에 대한 커밋 |
| `test` | 테스트 코드 수정에 대한 커밋 |
| `perf` | 성능 개선에 대한 커밋 |

한 커밋이 여러 타입에 걸치면 커밋을 나눈다. 그래도 하나로 묶어야 하면 변경의 주된 목적에 해당하는 타입을 고른다.

### 스코프

스코프는 변경이 닿은 범위를 괄호 안에 적으며 생략할 수 있다. `auth`, `signup`, `frontend`, `backend`처럼 팀이 알아볼 수 있는 짧은 이름을 쓴다. 범위가 넓거나 애매하면 넣지 않는다.

```text
feat(auth): 소셜 로그인 추가
docs: 커밋 메시지 규칙 문서화
```

### Body

Body는 Header에서 표현할 수 없는 상세한 내용을 적는다. Header에서 충분히 표현할 수 있다면 생략 가능하다. 구현 방법을 나열하기보다 **무엇을 바꿨고 왜 필요한지** 한국어로 설명하고, 한 줄을 72글자 이내로 줄바꿈한다.

### Footer와 Linear 연결

Footer는 어떤 이슈에서 왔는지 같은 참조 정보를 추가하는 용도로 사용하며 생략 가능하다. **이 저장소는 GitHub Issues 대신 Linear를 쓰므로 `#1234` 대신 Linear 이슈 키를 적는다.**

Linear의 GitHub 통합은 커밋 메시지의 이슈 키를 인식하며, 앞에 붙인 단어에 따라 동작이 달라진다. [Linear GitHub 통합][G13]

| Footer 예시 | 동작 |
|---|---|
| `Fixes DEV-123` | 커밋이 기본 브랜치에 도달하면 이슈를 완료 상태로 옮긴다 |
| `Ref DEV-123` | 상태를 바꾸지 않고 이슈에 링크만 남긴다 |
| `DEV-123` | 상태를 바꾸지 않고 링크만 남긴다 |

완료로 옮기는 단어는 `close`, `fix`, `resolve`, `complete`, `implement` 계열이고, 링크만 남기는 단어는 `ref`, `references`, `part of`, `contributes to` 계열이다.

**적용할 때 반드시 아는 점이 있다.**

- 이 자동 연결은 Linear의 GitHub 통합이 이 저장소에 연결되어 있어야 동작한다. **아직 연결 여부를 확인하지 않았다.** 확인 전에는 Footer를 사람이 읽는 참조 표기로만 취급하고, 이슈 상태는 사람이 직접 옮긴다.
- 이 팀은 Squash Merge를 쓴다. 작업 브랜치의 개별 커밋은 `main`에 그대로 남지 않으므로, 이슈를 완료로 옮기려면 **최종 Squash 커밋 메시지의 Footer**에 magic word를 넣어야 한다. 작업 브랜치 커밋의 Footer만으로는 완료 처리가 되지 않는다.
- Linear가 가장 확실하게 인식하는 경로는 **브랜치 이름과 PR 제목**이다. 이 팀은 [브랜치 이름](02-github-flow와-브랜치.md#브랜치-이름) 규칙(`feat/DEV-123-user-signup`)과 PR 제목 형식(`[DEV-123] ...`)에 이미 이슈 키를 넣으므로, Footer는 이를 보조하는 수단이다.
- 이슈가 없는 Level 0 작업은 Footer를 생략한다. 없는 이슈 키를 지어내지 않는다.

### 작성 예시

```text
fix: Safari에서 모달을 띄웠을 때 스크롤 이슈 수정

모바일 사파리에서 Carousel 모달을 띄웠을 때,
모달 밖의 상하 스크롤이 움직이는 이슈 수정.

Fixes DEV-1137
```

`수정`, `작업 완료`, `여러 가지 개선`처럼 대상을 알 수 없는 주제는 피한다. API 키·토큰·비밀번호는 파일뿐 아니라 커밋 메시지와 PR 본문에도 넣지 않는다.

`git commit -m`은 여러 줄 작성과 템플릿 편집에 불편하므로 기본 작성 방식은 `git commit`으로 한다.

## 공통 `.gitmessage.txt` 제안

다음 내용을 저장소 루트의 `.gitmessage.txt`에 추가하는 PR을 만든다. 현재 문서에는 템플릿 내용을 제공하며, 실제 저장소 파일 생성은 도입 작업에 포함한다.

```text
# <타입>(<스코프>): <주제>
# 제목은 50글자 이내, 끝에 마침표 없음, 한국어 명사형으로 종결한다.
# 타입: feat fix build chore ci docs style refactor test perf
# 스코프는 생략 가능하다. 예: feat(auth): 소셜 로그인 추가
#
# 제목과 본문 사이에 빈 행을 한 줄 둔다.
#
# 본문: 어떻게보다 무엇을 왜 바꿨는지 한국어로 설명한다.
# 한 줄을 72글자 이내로 줄바꿈한다. 제목으로 충분하면 생략 가능하다.
#
# 본문과 바닥글 사이에도 빈 행을 한 줄 둔다.
#
# 바닥글: Linear 이슈 참조. 예: Fixes DEV-123 또는 Ref DEV-123
# 이슈가 없으면 생략한다.
#
# 이 안내를 참고해 위쪽에 실제 메시지를 작성한다.
```

기본 Git 편집 설정에서는 `#`로 시작하는 안내가 최종 메시지에서 제외된다. 별도 주석·정리 설정을 사용하는 사람은 안내가 남지 않는지 확인한다. 템플릿은 작성 안내이며 규칙을 강제하는 검사기는 아니다. [템플릿 동작][G3]

템플릿을 각자의 clone에 등록하는 방법은 [로컬 설정과 일상 작업](04-로컬-설정과-일상-작업.md#팀원-초기-설정)에 있다.
