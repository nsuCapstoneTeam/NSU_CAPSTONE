# PR 작성과 리뷰

## 제목과 본문

PR의 base는 `main`, compare는 해당 작업 브랜치로 지정한다. 제목은 기존 형식인 `[이슈키] 변경 요약`을 사용한다. 이슈가 없는 Level 0 작업은 키를 생략한다.

- 기존 형식 예시: `[DEV-123] Implement user signup`
- 한국어 예시: `[DEV-123] 회원가입 기능을 구현한다`
- 이슈 없는 예시: `커밋 메시지 규칙을 문서화한다`

저장소에는 `.github/pull_request_template.md`가 이미 있으므로 PR을 열면 해당 양식이 자동으로 채워진다. 다음은 그 양식을 작성할 때 반드시 담아야 할 내용이다. 항목에는 실제 결과를 적고, 해당하지 않으면 이유를 적는다.

```markdown
## 관련 작업

- Linear: 실제 이슈 링크 또는 이슈 생략 사유

## 변경 이유

- 해결하려는 문제와 완료 조건

## 변경 내용

- 사용자 동작 또는 코드의 달라진 점
- FE / BE / API 계약에 미치는 영향

## 확인 결과

- 실제 실행한 테스트·빌드·정적 검사와 결과
- 화면 변경이 있으면 확인 방법과 필요한 스크린샷
- 미실행 또는 해당 없음인 항목과 이유

## 리뷰 요청

- 중점적으로 봐야 할 부분
- DB·설정·호환성 영향, 필요한 배포 순서
```

Linear 링크를 PR에 적었다는 이유만으로 자동 연동이나 상태 변경이 완료되었다고 간주하지 않는다. 연동이 검증되기 전에는 사람이 이슈 상태를 관리한다.

## 병합 조건

| 조건 | 확인 방법 |
|---|---|
| 작업 범위와 완료 조건 충족 | 이슈·PR 설명과 실제 변경 비교 |
| 변경 검증 | 해당 변경에 필요한 테스트·빌드·검사를 실행하고 결과 기록 |
| 사람 승인 | PR 작성자 외 권한 있는 팀원 1명 이상 승인 |
| 수정 요청 처리 | 사람 리뷰의 미해결 요청을 반영하거나 리뷰어와 합의 |
| 필수 CI | 등록된 필수 검사가 병합 가능한 상태이며 필요한 검사가 실제 수행됐는지 확인 |
| 충돌 해소 | GitHub가 병합 가능 상태인지 확인 |
| 최종 메시지 | Squash 커밋 제목·본문을 팀 규칙에 맞게 검토 |

CodeRabbit의 초기 리뷰는 참고 의견이다. AI의 통과·승인 표시만으로 사람 승인 조건을 충족하지 않는다. 리뷰 이후 변경이 추가되면 변경된 내용을 다시 검토받는다.

일반 작업은 PR 리뷰 단계에서 Linear의 `In Review`, 병합 후 완료 조건까지 충족했을 때 `Done`으로 옮기는 흐름을 사용한다. 상태 이름은 실제 Linear 설정에 맞춘다. 배포가 완료 조건이면 병합만으로 `Done` 처리하지 않는다.

## Squash Merge 메시지

병합하는 사람이 GitHub의 최종 커밋 제목과 본문을 확인한다. 로컬 `.gitmessage.txt`는 GitHub 웹의 Squash 메시지에 자동 적용되지 않는다. 제목은 50자 이내로 다듬고 본문에 PR 전체의 What/Why를 한국어로 적는다. 필요한 실제 이슈 키는 본문에 남길 수 있다.

GitHub의 기본 Squash 메시지는 PR 제목·본문을 바탕으로 설정할 수 있지만, PR의 체크리스트 전체를 최종 커밋에 그대로 남길 필요는 없다. PR 제목과 최종 커밋 제목이 반드시 같아야 하는 것은 아니다. [메시지 설정][G7]

병합 이후 정리 절차는 [병합 이후 정리와 되돌리기](07-병합-이후-정리와-되돌리기.md)에 있다.
