# PR 작성과 리뷰

← [가이드 목차](README.md)

## PR 제목

PR의 base는 `main`, compare는 해당 작업 브랜치로 지정한다. Linear 이슈가 있는 일반 작업은 `[이슈키] 변경 요약` 형식을 사용한다. 이슈가 없는 Level 0 docs/chore 작업은 이슈 키를 생략한다.

예시:

- `[DEV-123] 로그인 기능 구현`
- `[DEV-245] Refresh Token 검증 오류 수정`
- `협업 가이드의 PR 규칙 정리`

`DEV-123`은 형식 예시이며 실제 작업에서는 현재 Linear의 실제 이슈 키를 사용한다.

## PR 템플릿

이 저장소는 PR 목적에 따라 두 템플릿을 사용한다.

| 템플릿 | 경로 | 사용 기준 |
|---|---|---|
| 문서 PR | `.github/PULL_REQUEST_TEMPLATE/문서_PR.md` | 운영 가이드, ADR, API 문서, 오타·링크·정책 문서 변경 |
| 구현 PR | `.github/PULL_REQUEST_TEMPLATE/구현_PR.md` | 기능, 버그, 리팩터링, 테스트, DB, 설정, CI, 런타임 코드 변경 |

GitHub에서 여러 PR 템플릿을 사용할 때는 생성 URL의 `template` 파라미터로 원하는 파일을 선택할 수 있다. PR을 열었는데 본문이 자동으로 채워지지 않았다면 아래처럼 템플릿 이름을 지정하거나 해당 파일 내용을 기준으로 본문을 작성한다.

```text
?template=문서_PR.md
?template=구현_PR.md
```

문서와 구현이 서로 독립적으로 리뷰 가능한 경우 PR을 분리한다. 구현의 동작을 이해하는 데 반드시 필요한 API/설계 문서는 같은 구현 PR에 포함할 수 있다.

## 구현 PR에서 반드시 확인할 내용

- 해결하려는 문제와 완료 조건
- 실제 변경 사항
- Frontend / Backend / API Contract / Database / Infrastructure 영향
- 실제 실행한 테스트·빌드·Lint·Type Check와 결과
- API·DB·환경변수·배포 순서 변경 여부
- Breaking Change와 migration/호환 전략
- 리뷰어가 집중해서 확인할 보안·권한·트랜잭션·동시성·예외·성능 영역

미실행한 검증 항목은 빈칸으로 숨기지 말고 이유를 적는다.

## 문서 PR에서 반드시 확인할 내용

- 문서를 변경하는 이유
- 바뀐 운영 규칙 또는 설명
- 영향을 받는 다른 문서
- 링크·파일 경로·명령·설정 화면이 실제 값과 일치하는지
- 아직 적용하지 않은 설정을 적용 완료처럼 표현하지 않았는지

## Linear 연결

PR 본문에는 관련 Linear 이슈 키 또는 링크를 남긴다. 단순히 링크를 적었다는 이유만으로 자동 상태 변경이 된다고 간주하지 않는다.

Linear ↔ GitHub 연동이 실제 저장소에서 검증되기 전에는 사람이 상태를 관리한다. 브랜치 이름과 PR 제목에도 실제 이슈 키를 넣어 추적 가능성을 높인다.

CodeRabbit에서 Linear 연계를 사용하려면 CodeRabbit 쪽 Integration/Knowledge Base 설정도 별도로 필요하다. 특히 공개 저장소에서는 CodeRabbit의 Linear `auto` 설정이 기본적으로 활성화되지 않을 수 있으므로, 실제 연계가 필요할 때는 [CodeRabbit 운영 문서](10-coderabbit-review와-slack-agent.md#linear-연계)를 확인한다.

## PR 검증 순서

PR을 열면 아래 순서로 확인한다.

```text
Pull Request
   ↓
GitHub Actions CI
   ↓
CodeRabbit 자동 PR Review
   ↓
필요 시 작성자가 수정하고 재검증
   ↓
필요 시 Slack Thread에서 @CodeRabbit 후속 조사
   ↓
Human Review
   ↓
Squash Merge
```

CI가 실패하면 사람 리뷰에 들어가기 전에 원인을 우선 수정한다. CodeRabbit의 자동 리뷰에서 지적이 나와도 무조건 수용하지 않고 근거와 실제 요구사항을 확인한다.

복잡한 지적이나 CI 실패는 Slack의 기존 기능 Thread에서 CodeRabbit Agent를 선택적으로 호출할 수 있다.

예시:

```text
@CodeRabbit 이 PR의 변경과 현재 Thread의 확정 요구사항을 함께 보고,
리뷰 지적 중 실제 버그 가능성이 높은 항목만 우선순위대로 정리해줘.
아직 코드는 수정하지 말고 근거와 수정 방향만 제안해줘.
```

```text
@CodeRabbit 이 PR의 실패한 CI와 관련 코드를 조사해서
원인 후보, 재현 방법, 최소 수정안을 정리해줘.
확실하지 않은 내용은 추측이라고 표시해줘.
```

Slack Agent 호출은 모든 PR의 필수 단계가 아니다. GitHub의 CodeRabbit Review가 자동 1차 리뷰를 담당하고, Slack Agent는 저장소 전체 맥락이 필요한 조사·설명·계획을 확장할 때 사용한다.

## 병합 조건

| 조건 | 확인 방법 |
|---|---|
| 작업 범위와 완료 조건 충족 | Linear 이슈·PR 설명과 실제 변경 비교 |
| 변경 검증 | 필요한 테스트·빌드·정적 검사를 실제 실행하고 결과 기록 |
| 사람 승인 | PR 작성자 외 권한 있는 팀원 1명 이상 승인 |
| 수정 요청 처리 | 사람 리뷰의 미해결 요청을 반영하거나 리뷰어와 합의 |
| 필수 CI | Ruleset에 등록된 필수 검사가 모두 통과 |
| 충돌 해소 | GitHub가 병합 가능한 상태인지 확인 |
| 최종 메시지 | Squash 커밋 제목·본문을 커밋 규칙에 맞게 검토 |

CodeRabbit의 초기 리뷰는 **Advisory**다. CodeRabbit의 승인/통과 표시만으로 사람 승인 조건을 충족하지 않는다. CodeRabbit의 `request changes` 자동화는 초기에는 사용하지 않는다. 리뷰 이후 코드가 바뀌면 변경된 내용을 다시 확인한다.

## Squash Merge

저장소는 다음 병합 정책을 사용한다.

```text
Allow squash merging  ON
Allow merge commits   OFF
Allow rebase merging  OFF
Auto merge            OFF (초기 운영)
Delete head branch    ON
```

따라서 최종 병합은 사람이 `Squash and merge`로 수행한다. GitHub 웹의 Squash 메시지에는 로컬 `.gitmessage.txt`가 자동 적용되지 않으므로 병합하는 사람이 최종 메시지를 직접 확인한다.

최종 Squash 커밋 제목은 [커밋 메시지 규칙](03-커밋-전략과-메시지.md#커밋-메시지-규칙)의 `타입(스코프): 주제` 형식을 따른다.

예시:

```text
feat(auth): 로그인 기능 구현

이메일과 비밀번호 기반 로그인 흐름과 인증 실패 처리를 추가한다.
인증 관련 API 계약에 맞춰 백엔드 동작을 구성한다.

Fixes DEV-123
```

Linear 자동 완료 기능을 사용할 경우 `Fixes DEV-123` 같은 Footer는 **최종 Squash 커밋**에 남아야 한다. 자동 연동을 검증하기 전에는 사람이 이슈 상태를 옮긴다.

병합 이후 정리 절차는 [병합 이후 정리와 되돌리기](07-병합-이후-정리와-되돌리기.md)에 있다.
