# PR 작성과 리뷰

← [가이드 목차](README.md)

## PR 제목

PR의 base는 `main`, compare는 해당 작업 브랜치로 지정한다. Linear 이슈가 있는 일반 작업은 `[이슈키] 변경 요약` 형식을 사용한다. 이슈가 없는 Level 0 docs/chore 작업은 이슈 키를 생략한다.

예시:

- `[DEV-123] 로그인 기능 구현`
- `[DEV-245] Refresh Token 검증 오류 수정`
- `협업 가이드의 PR 규칙 정리`

`DEV-123`은 형식 예시이며 실제 작업에서는 현재 Linear의 실제 이슈 키를 사용한다.

## PR 템플릿

이 저장소는 PR 목적에 따라 두 템플릿을 사용한다.

| 템플릿 | 경로 | 사용 기준 |
|---|---|---|
| 문서 PR | `.github/PULL_REQUEST_TEMPLATE/문서_PR.md` | 운영 가이드, ADR, API 문서, 오타·링크·정책 문서 변경 |
| 구현 PR | `.github/PULL_REQUEST_TEMPLATE/구현_PR.md` | 기능, 버그, 리팩터링, 테스트, DB, 설정, CI, 런타임 코드 변경 |

GitHub에서 여러 PR 템플릿을 사용할 때는 생성 URL의 `template` 파라미터로 원하는 파일을 선택할 수 있다.

```text
?template=문서_PR.md
?template=구현_PR.md
```

문서와 구현이 서로 독립적으로 리뷰 가능한 경우 PR을 분리한다. 구현의 동작을 이해하는 데 반드시 필요한 API/설계 문서는 같은 구현 PR에 포함할 수 있다.

## 구현 PR에서 반드시 확인할 내용

- 해결하려는 문제와 동기화된 Linear / GitHub Issue의 Acceptance Criteria
- 관련 Requirement ID와 요구사항 변경 여부
- 실제 변경 사항
- Frontend / Backend / API Contract / Database / Infrastructure 영향
- 실제 실행한 테스트·빌드·Lint·Type Check와 결과
- API·DB·환경변수·배포 순서 변경 여부
- Breaking Change와 migration/호환 전략
- README / `docs/` / ADR / API 문서 변경 필요 여부와 반영 결과
- 리뷰어가 집중해서 확인할 보안·권한·트랜잭션·동시성·예외·성능 영역

미실행한 검증 항목은 빈칸으로 숨기지 말고 이유를 적는다.

## 문서 PR에서 반드시 확인할 내용

- 문서를 변경하는 이유
- 바뀐 운영 규칙 또는 설명
- 영향을 받는 다른 문서
- 제품 요구사항 영향 여부와 관련 Requirement ID
- `docs/요구사항/` 변경이면 Slack Human Confirm과 일치하는 확정 내용인지
- 링크·파일 경로·명령·설정 화면이 실제 값과 일치하는지
- 아직 적용하지 않은 설정을 적용 완료처럼 표현하지 않았는지

## GitHub 문서 / Linear / GitHub Issue 연결

요구사항의 Source of Truth는 GitHub `docs/`다. **일반 작업의 PR 본문에는** 관련 GitHub 문서, Linear 이슈 키, 동기화된 GitHub Issue 링크를 남긴다. 두 이슈의 제목·Description·Acceptance Criteria는 동일하게 유지하며, Human Reviewer가 문서와 실제 구현을 직접 비교한다.

제품 요구사항과 직접 관련된 구현 작업은 GitHub `docs/`의 고정 Requirement ID도 PR에 연결한다. 구현 중 제품 요구사항 자체가 변경되었다면 코드를 먼저 확정하지 않고, Slack 논의와 Human Confirm을 거쳐 GitHub 문서를 PR로 먼저 갱신한 뒤 동기화된 Issue의 Acceptance Criteria를 수정하고 구현한다.

Linear 이슈가 없는 Level 0 `docs` / `chore` 작업은 이슈 키를 생략하거나 `N/A`로 표시할 수 있다. 이 경우 추적을 위해 가짜 Linear Issue 또는 가짜 Requirement ID를 만들지 않는다.

Linear ↔ GitHub Issues Two-way Sync와 PR Merge 자동화가 실제 저장소에서 검증되기 전에는 자동 종료를 완료로 간주하지 않는다. 이슈가 있는 작업은 브랜치 이름과 PR 제목에 실제 Linear 이슈 키를 넣고 PR 본문에는 두 이슈 링크를 함께 남긴다.

CodeRabbit과 Linear의 직접 연동은 이 팀의 공식 Workflow에 필수로 사용하지 않는다. CodeRabbit은 GitHub PR 변경을 검토하고, GitHub 문서와 Issue의 요구사항 충족 여부는 Human Review에서 확인한다.

## PR 검증 순서

현재 GitHub Actions CI는 도입 예정이다. CI 도입 전과 도입 후의 검증 흐름을 구분한다.

```text
현재
Pull Request
   ↓
CodeRabbit 자동 PR Review
   ↓
필요 시 작성자가 수정하고 재검증
   ↓
Human Review 3종 체크
   ↓
Squash Merge

GitHub Actions CI 도입 완료 후
Pull Request
   ↓
GitHub Actions CI
   ↓
CodeRabbit 자동 PR Review
   ↓
필요 시 작성자가 수정하고 재검증
   ↓
Human Review 3종 체크
   ↓
Squash Merge
```

CI 도입 후 CI가 실패하면 사람 리뷰에 들어가기 전에 원인을 우선 수정한다. CodeRabbit의 자동 리뷰에서 지적이 나와도 무조건 수용하지 않고 근거와 실제 요구사항을 확인한다.

## Human Review 필수 확인 3가지

### 1. Requirement / Issue — 요구사항

- GitHub `docs/`의 확정 요구사항이 실제 구현에 반영되었는가?
- Linear와 GitHub Issue의 제목·Description·Acceptance Criteria가 동일한가?
- Acceptance Criteria를 모두 충족했는가?
- 관련 Requirement ID와 실제 구현 범위가 일치하는가?
- 구현 중 요구사항이 바뀌었다면 GitHub 문서를 먼저 갱신하고 두 Issue도 함께 맞췄는가?

### 2. Code — 구현 품질

- 코드와 테스트가 의도대로 동작하는가?
- 보안, 권한, 예외 처리, 트랜잭션, 동시성 등 변경 영향이 적절한가?
- 현재 구성된 검증과 필요한 로컬 검증이 통과했는가?
- CI 도입 후에는 관련 GitHub Actions CI가 통과했는가?
- CodeRabbit 지적 중 실제 문제가 있는 항목이 적절히 처리되었는가?

### 3. Documentation — 문서 영향

- README 변경이 필요한가?
- `docs/`의 운영·API·설계 문서 변경이 필요한가?
- 제품 요구사항이 변경되었다면 Slack Human Confirm 이후 GitHub `docs/`가 먼저 갱신되었는가?
- Linear를 요구사항 문서 저장소처럼 사용하지 않았는가?
- 중요한 기술 결정이라면 `docs/adr/`를 작성하거나 수정해야 하는가?
- 문서 변경이 필요한데 누락했다면 Merge 전에 반영한다.

## 병합 조건

| 조건 | 확인 방법 |
|---|---|
| 요구사항 충족 | GitHub `docs/`, 두 Issue의 Acceptance Criteria와 실제 변경 비교 |
| Requirement 추적 | 제품 요구사항 관련 작업이면 PR의 Requirement ID와 실제 변경 범위 비교 |
| 구현 검증 | 필요한 테스트·빌드·정적 검사를 실제 실행하고 결과 기록 |
| 문서 영향 확인 | README / `docs/` / ADR / API 문서 변경 필요 여부 확인 및 필요 시 반영 |
| 사람 승인 | PR 작성자 외 권한 있는 팀원 1명 이상 승인 |
| 수정 요청 처리 | 사람 리뷰의 미해결 요청을 반영하거나 리뷰어와 합의 |
| 필수 CI | CI 도입 후 Ruleset에 실제 등록된 필수 검사가 모두 통과 |
| 충돌 해소 | GitHub가 병합 가능한 상태인지 확인 |
| 최종 메시지 | Squash 커밋 제목·본문을 커밋 규칙에 맞게 검토 |

현재 CI 도입 전에는 `필수 CI` 조건을 적용하지 않는다. 실제 CI 워크플로와 check 이름을 성공/실패 PR로 검증한 뒤 Ruleset에 등록한 시점부터 병합 조건으로 적용한다.

CodeRabbit의 초기 리뷰는 **Advisory**다. CodeRabbit의 승인/통과 표시만으로 사람 승인 조건을 충족하지 않는다. CodeRabbit의 `request changes` 자동화는 초기에는 사용하지 않는다. 리뷰 이후 코드가 바뀌면 변경된 내용을 다시 확인한다.

## Squash Merge

저장소는 다음 병합 정책을 사용한다.

```text
Allow squash merging  ON
Allow merge commits   OFF
Allow rebase merging  OFF
Auto merge            OFF (초기 운영)
Delete head branch    ON
```

따라서 최종 병합은 사람이 `Squash and merge`로 수행한다. GitHub 웹의 Squash 메시지에는 로컬 `.gitmessage.txt`가 자동 적용되지 않으므로 병합하는 사람이 최종 메시지를 직접 확인한다.

최종 Squash 커밋 제목은 [커밋 메시지 규칙](03-커밋-전략과-메시지.md#커밋-메시지-규칙)의 `타입(스코프): 주제` 형식을 따른다.

예시:

```text
feat(auth): 로그인 기능 구현

이메일과 비밀번호 기반 로그인 흐름과 인증 실패 처리를 추가한다.
인증 관련 API 계약에 맞춰 백엔드 동작을 구성한다.

Fixes DEV-123
Closes #42
```

PR 본문에는 `Fixes DEV-123`과 `Closes #42`처럼 Linear 이슈 키와 동기화된 GitHub Issue 번호를 함께 적는다. Squash Merge를 완료 이벤트로 삼아 Linear는 `Done`, GitHub Issue는 `Closed`로 자동 전환한다. Two-way Sync가 중복 전환을 일으키더라도 최종 상태는 동일해야 하며, 실제 테스트가 끝나기 전에는 [도입 체크리스트](08-도입-체크리스트.md)의 검증 상태를 확인한다.

병합 이후 정리 절차는 [병합 이후 정리와 되돌리기](07-병합-이후-정리와-되돌리기.md)에 있다.
