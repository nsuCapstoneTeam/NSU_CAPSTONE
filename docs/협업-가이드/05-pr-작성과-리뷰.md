# PR 작성과 리뷰

← [가이드 목차](README.md)

## PR 제목

PR의 base는 `main`, compare는 해당 작업 브랜치로 지정한다. Linear 이슈가 있는 일반 작업은 `[이슈키] 변경 요약` 형식을 사용한다. 이슈가 없는 Level 0 docs/chore 작업은 이슈 키를 생략한다.

예시:

- `[DEV-123] 로그인 기능 구현`
- `[DEV-245] Refresh Token 검증 오류 수정`
- `협업 가이드의 PR 규칙 정리`

`DEV-123`은 형식 예시이며 실제 작업에서는 현재 Linear의 실제 이슈 키를 사용한다.

## PR 템플릿

이 저장소는 PR 목적에 따라 두 템플릿을 사용한다.

| 템플릿 | 경로 | 사용 기준 |
|---|---|---|
| 문서 PR | `.github/PULL_REQUEST_TEMPLATE/문서_PR.md` | 운영 가이드, ADR, API 문서, 오타·링크·정책 문서 변경 |
| 구현 PR | `.github/PULL_REQUEST_TEMPLATE/구현_PR.md` | 기능, 버그, 리팩터링, 테스트, DB, 설정, CI, 런타임 코드 변경 |

GitHub에서 여러 PR 템플릿을 사용할 때는 생성 URL의 `template` 파라미터로 원하는 파일을 선택할 수 있다.

```text
?template=문서_PR.md
?template=구현_PR.md
```

문서와 구현이 서로 독립적으로 리뷰 가능한 경우 PR을 분리한다. 구현의 동작을 이해하는 데 반드시 필요한 API/설계 문서는 같은 구현 PR에 포함할 수 있다.

## Linear → GitHub 문서 반영 원칙

제품·서비스 요구사항과 실제 작업 완료 조건의 기준은 Linear다.

```text
Slack 논의
   ↓
Claude 요약 / 초안
   ↓
Human Confirm
   ↓
Linear Requirements / Issue 확정
   ↓
작업 Branch 생성
   ↓
필요한 GitHub docs/ / ADR / API 문서 갱신
   ↓
구현
```

GitHub 문서는 Linear 내용을 그대로 복제하는 두 번째 요구사항 원본이 아니다. 다음과 같이 역할을 나눈다.

- Linear Requirements: 제품·서비스 요구사항, 비즈니스 규칙
- Linear Issue: 실제 작업, Acceptance Criteria, 담당자, 우선순위, 일정, 상태
- GitHub `docs/`: 장기 유지할 설계·정책·API·운영 문서
- GitHub `docs/adr/`: 중요한 기술적 결정과 근거
- GitHub Code / PR: 실제 구현과 변경 이력

담당자, 우선순위, 일정, 진행 상태처럼 Linear에서 충분히 관리되는 값은 GitHub 문서에 중복 기록하지 않는다. 요구사항이 변경되면 Linear를 먼저 수정하고, 필요한 GitHub 문서는 같은 작업 Branch에서 함께 갱신한다.

문서 정합성을 검사하는 별도 GitHub Actions는 도입하지 않는다. Linear ↔ GitHub 문서의 일치 여부는 PR Human Review에서 확인한다.

## 구현 PR에서 반드시 확인할 내용

- 해결하려는 문제와 Linear Acceptance Criteria
- 관련 Requirement ID와 요구사항 변경 여부
- 실제 변경 사항
- Frontend / Backend / API Contract / Database / Infrastructure 영향
- 실제 실행한 테스트·빌드·Lint·Type Check와 결과
- API·DB·환경변수·배포 순서 변경 여부
- Breaking Change와 migration/호환 전략
- README / `docs/` / ADR / API 문서 변경 필요 여부와 반영 결과
- 리뷰어가 집중해서 확인할 보안·권한·트랜잭션·동시성·예외·성능 영역

미실행한 검증 항목은 빈칸으로 숨기지 말고 이유를 적는다.

## 문서 PR에서 반드시 확인할 내용

- 문서를 변경하는 이유
- 바뀐 운영 규칙 또는 설명
- 영향을 받는 다른 문서
- 제품 요구사항 영향 여부와 관련 Requirement ID
- Linear의 확정 내용과 모순되지 않는지
- 링크·파일 경로·명령·설정 화면이 실제 값과 일치하는지
- 아직 적용하지 않은 설정을 적용 완료처럼 표현하지 않았는지

## Linear / Requirement 연결

**Linear 이슈가 있는 일반 작업의 PR 본문에는** 관련 Linear 이슈 키 또는 링크를 남긴다. Linear의 **Issue 목표와 Acceptance Criteria가 작업 완료 기준**이며, Human Reviewer가 실제 구현과 직접 비교한다.

제품 요구사항과 직접 관련된 구현 작업은 Linear Requirements의 고정 Requirement ID도 PR에 연결한다. 구현 중 제품 요구사항 자체가 변경되었다면 코드를 먼저 확정하지 않고, Slack 논의와 Human Confirm을 거쳐 Linear Requirements와 관련 Issue의 Acceptance Criteria를 먼저 갱신한 뒤 구현한다.

Linear 이슈가 없는 Level 0 `docs` / `chore` 작업은 이슈 키를 생략하거나 `N/A`로 표시할 수 있다. 이 경우 추적을 위해 가짜 Linear Issue 또는 가짜 Requirement ID를 만들지 않는다.

워크플로우 Smoke Test에서 Slack `@Linear`를 통한 Issue 생성과 Issue 키 기반 Branch/PR 추적은 정상 동작했다. 다만 PR Squash Merge 후 Linear Issue 상태가 자동으로 변경되지는 않았으므로, 현재는 병합 후 `@Linear`로 상태를 명시적으로 정리한다.

CodeRabbit과 Linear의 직접 연동은 이 팀의 공식 Workflow에 필수로 사용하지 않는다. CodeRabbit은 GitHub PR 변경을 검토하고, Linear 요구사항 충족 여부는 Human Review에서 확인한다.

## PR 검증 순서

현재 기본 검증 흐름은 다음과 같다.

```text
Pull Request
   ↓
CodeRabbit 자동 PR Review
   ↓
필요 시 작성자가 수정하고 재검증
   ↓
Human Review 3종 체크
   ↓
작성자 외 팀원 1명 이상 승인
   ↓
Squash Merge
   ↓
@Linear 상태 정리
```

CodeRabbit의 자동 리뷰가 무료 Review 제한 등으로 지연될 수 있다. CodeRabbit은 초기 **Advisory**이므로, 리뷰 제한 자체가 Merge Gate가 되지는 않는다. 다만 실제 리뷰가 도착했다면 Human Reviewer가 유효한 지적을 확인하고 필요한 항목을 반영한다.

실제 Backend/Frontend 코드가 들어온 뒤 빌드·테스트 자동화가 필요하면 애플리케이션 CI를 별도로 도입할 수 있다. 이 CI는 코드 검증을 위한 것이며, 문서 정합성 전용 GitHub Action은 도입하지 않는다.

## Human Review 필수 확인 3가지

### 1. Linear — 요구사항

- Issue의 목표가 실제 구현에 반영되었는가?
- Acceptance Criteria를 모두 충족했는가?
- 관련 Requirement ID와 실제 구현 범위가 일치하는가?
- 구현 중 요구사항이 바뀌었다면 Linear Requirements와 Issue도 먼저 갱신되었는가?

### 2. Code — 구현 품질

- 코드와 테스트가 의도대로 동작하는가?
- 보안, 권한, 예외 처리, 트랜잭션, 동시성 등 변경 영향이 적절한가?
- 필요한 로컬 검증이 실제로 수행되었는가?
- CodeRabbit 지적 중 실제 문제가 있는 항목이 적절히 처리되었는가?
- 향후 애플리케이션 CI가 도입되면 관련 빌드·테스트 검사가 통과했는가?

### 3. Documentation — 문서 영향

- README 변경이 필요한가?
- `docs/`의 운영·API·설계 문서 변경이 필요한가?
- 제품 요구사항이 변경되었다면 Linear Requirements가 먼저 갱신되었는가?
- GitHub 문서가 Linear의 확정 내용과 충돌하거나 오래된 내용을 남기고 있지 않은가?
- 중요한 기술 결정이라면 `docs/adr/`를 작성하거나 수정해야 하는가?
- 담당자·우선순위·일정·상태 같은 Linear 전용 정보를 GitHub 문서에 불필요하게 중복하지 않았는가?

## 병합 조건

| 조건 | 확인 방법 |
|---|---|
| Linear 요구사항 충족 | Linear Issue / Acceptance Criteria와 실제 변경 비교 |
| Requirement 추적 | 제품 요구사항 관련 작업이면 PR의 Requirement ID와 실제 변경 범위 비교 |
| 구현 검증 | 필요한 테스트·빌드·정적 검사를 실제 실행하고 결과 기록 |
| 문서 영향 확인 | README / `docs/` / ADR / API 문서 변경 필요 여부 및 Linear와의 일치 확인 |
| 사람 승인 | PR 작성자 외 권한 있는 팀원 1명 이상 승인 |
| 수정 요청 처리 | 사람 리뷰의 미해결 요청을 반영하거나 리뷰어와 합의 |
| CodeRabbit | 도착한 리뷰가 있다면 유효한 지적 확인. 초기에는 Required Check 아님 |
| 충돌 해소 | GitHub가 병합 가능한 상태인지 확인 |
| 최종 메시지 | Squash 커밋 제목·본문을 커밋 규칙에 맞게 검토 |

향후 애플리케이션 CI가 도입되고 실제 PR에서 검증된 경우에만 해당 CI를 병합 조건에 추가한다.

## Squash Merge

저장소는 다음 병합 정책을 사용한다.

```text
Allow squash merging  ON
Allow merge commits   OFF
Allow rebase merging  OFF
Auto merge            OFF (초기 운영)
Delete head branch    ON
```

따라서 최종 병합은 사람이 `Squash and merge`로 수행한다. GitHub 웹의 Squash 메시지에는 로컬 `.gitmessage.txt`가 자동 적용되지 않으므로 병합하는 사람이 최종 메시지를 직접 확인한다.

최종 Squash 커밋 제목은 [커밋 메시지 규칙](03-커밋-전략과-메시지.md#커밋-메시지-규칙)의 `타입(스코프): 주제` 형식을 따른다.

예시:

```text
feat(auth): 로그인 기능 구현

이메일과 비밀번호 기반 로그인 흐름과 인증 실패 처리를 추가한다.
인증 관련 API 계약에 맞춰 백엔드 동작을 구성한다.

Fixes DEV-123
```

Linear 자동 완료 기능은 현재 확인되지 않았으므로 Merge 후 `@Linear`로 이슈 상태를 정리한다. 자동 상태 전환을 추후 도입하려면 별도 테스트로 동작을 검증한 뒤 운영 문서를 갱신한다.

병합 이후 정리 절차는 [병합 이후 정리와 되돌리기](07-병합-이후-정리와-되돌리기.md)에 있다.
