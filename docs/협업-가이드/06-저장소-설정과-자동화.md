# 저장소 설정과 자동화

← [가이드 목차](README.md)

## 공지와 자동화의 역할

**운영 문서로 기준을 남기고, Slack에는 문서 링크와 적용 방법을 알리며, 저장소가 강제할 수 있는 규칙은 GitHub 설정으로 적용한다.**

| 규칙 | 적용 위치 | 도입 방법 |
|---|---|---|
| 브랜치·커밋·PR 작성 방식 | 문서, 템플릿, 사람 리뷰 | 가이드와 예시 공유 |
| 커밋 템플릿 등록 | 각 팀원의 clone | 초기 설정 실행 및 결과 확인 |
| `main` 직접 push 방지 | GitHub 브랜치 보호 | PR 필수 설정과 우회 권한 확인 |
| 사람 승인 1명 이상 | GitHub + 팀 리뷰 운영 | 승인 수 설정, 실제 사람 승인 확인 |
| 빌드·테스트 기준 | GitHub Actions + 필수 검사 | 워크플로 검증 후 필수화 |
| Squash Merge | GitHub 저장소 설정 | Squash만 병합 방식으로 허용 |
| 작업 브랜치 정리 | GitHub + 각 팀원 PC | 원격 자동 삭제, 로컬 별도 확인 |

GitHub의 CI나 서버 설정은 팀원 PC의 로컬 Git 설정을 통제하지 않는다. 로컬 설정은 사용자가 바꿀 수 있고 clone만으로 공유되지 않는다. 초기에는 위 설정과 확인 절차를 사용하고, 반복적인 설정 누락이 생기면 저장소용 설치 스크립트로 묶는다.

커밋 메시지 검사는 초기 필수 도입 항목으로 추가하지 않는다. 필요해지면 현재 메시지 규칙에 맞는 검사 대상을 정한다. `main`에 Squash 결과를 남기는 구조에서 작업 브랜치의 모든 커밋에 다른 형식을 강제하지 않도록 한다.

## 저장소 소유자의 설정 체크리스트

다음은 **적용해야 할 설정안**이다. 실제 설정 완료 여부는 아직 확인하지 않았다. GitHub의 메뉴·기능 제공 여부는 저장소 공개 범위, 소유 형태와 요금제에 따라 확인한다. 비공개 저장소의 브랜치 보호 기능에는 해당 기능을 제공하는 요금제가 필요하다. [브랜치 보호 조건][G8]

### 병합 방식

저장소 `Settings → General → Pull Requests`에서 확인한다.

- [ ] `Allow squash merging`을 켠다.
- [ ] `Allow merge commits`와 `Allow rebase merging`을 끈다.
- [ ] Squash 기본 메시지는 PR 제목·본문을 사용하는 설정으로 정한다.
- [ ] 병합 담당자가 최종 메시지를 팀 규칙에 맞게 편집한다.
- [ ] 병합 후 작업 브랜치 자동 삭제를 켠다.
- [ ] 최종 병합은 사람이 수행한다. 자동 병합은 초기 운영 범위에 넣지 않는다.

병합 옵션 설정은 GitHub로 PR을 병합할 때 적용된다. `main`의 직접 push를 막으려면 아래 보호 설정도 필요하다. [Squash 설정][G7]

### `main` 보호

브랜치 보호 규칙 또는 저장소에서 제공되는 Ruleset으로 `main`을 대상으로 설정한다. 중복된 규칙을 만들기 전에 기존 규칙과 우회 권한을 먼저 확인한다.

| 설정 | 도입값 / 확인 사항 |
|---|---|
| PR 없이 변경 반영 | 금지 |
| 필수 승인 수 | 최소 1명, 팀 운영상 사람 리뷰어 |
| 새 변경으로 기존 승인이 오래된 경우 | 승인 무효화 후 재승인 요구 권장 |
| 필수 상태 검사 | CI 구축·검증 후 실제 검사 이름을 선택 |
| 병합 전 기준 브랜치 최신 상태 요구 | CI 필수화 시 함께 활성화 권장 |
| 강제 push와 `main` 삭제 | 허용하지 않음 |
| 관리자·앱 등의 규칙 우회 | 일반 작업에서 우회하지 않도록 적용 범위 확인 |
| 선형 이력 | `main`에 활성화 권장. Squash 방식과 함께 사용 |
| CodeRabbit 검사 | 초기에는 필수 검사로 등록하지 않음 |

GitHub의 승인 수 설정과 별개로 사람이 실제 리뷰했는지 확인한다. CodeRabbit이 모든 스레드의 해결을 요구하게 되는 등 Advisory 의견이 우연히 병합 차단 조건이 되지 않도록 앱 설정과 대화 해결 조건도 함께 확인한다. [보호 설정의 동작][G8]

### CI 등록 순서

1. 저장소의 실제 구조와 실행 명령에 맞게 FE·BE 검사를 만든다.
2. 샘플 PR에서 정상 변경의 성공과 실제 오류의 실패를 확인한다.
3. GitHub에 표시된 실제 검사 이름을 확인하고 필수 검사로 등록한다.
4. 문서만 수정한 PR과 FE·BE 각각의 변경에서도 검사 결과가 정상 종료되는지 확인한다.

이 가이드에서는 아직 확인하지 않은 디렉터리, 빌드 명령이나 검사 이름을 실제 값으로 지정하지 않는다. 경로 필터 때문에 워크플로 전체가 생략되면 필수 검사가 대기 상태로 남을 수 있다. 반대로 조건으로 생략된 job은 성공으로 취급될 수 있으므로, 초록 표시만 보고 필요한 테스트가 실행됐다고 판단하지 않는다. [필수 검사 주의점][G9]
