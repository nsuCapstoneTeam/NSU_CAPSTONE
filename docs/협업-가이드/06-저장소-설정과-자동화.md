# 저장소 설정과 자동화

← [가이드 목차](README.md)

## 공지와 자동화의 역할

**운영 문서로 기준을 남기고, Slack에는 문서 링크와 적용 방법을 알리며, 저장소가 강제할 수 있는 규칙은 GitHub 설정으로 적용한다.**

| 규칙 | 적용 위치 | 도입 방법 |
|---|---|---|
| 브랜치·커밋·PR 작성 방식 | 문서, PR 템플릿, 사람 리뷰 | 가이드와 예시 공유 |
| 커밋 템플릿 등록 | 각 팀원의 clone | 초기 설정 실행 및 결과 확인 |
| `main` 직접 push 방지 | GitHub Ruleset | PR 필수 설정과 우회 권한 확인 |
| 사람 승인 1명 이상 | GitHub Ruleset + 팀 리뷰 | 승인 수 설정, 실제 사람 승인 확인 |
| 빌드·테스트 기준 | GitHub Actions + Required Check | 워크플로 검증 후 필수화 |
| Squash Merge | GitHub 저장소 설정 | Squash만 병합 방식으로 허용 |
| 작업 브랜치 정리 | GitHub + 각 팀원 PC | 원격 자동 삭제, 로컬 별도 정리 |
| 이슈 양방향 동기화 | Linear ↔ GitHub Issues | 제목·Description·상태·링크 동기화 검증 |
| PR Merge 후 이슈 종료 | Linear GitHub Integration + Two-way Sync | Linear `Done` / GitHub `Closed` 자동 전환 검증 |
| AI PR 리뷰 | CodeRabbit Review | 초기 Advisory로 운영 |

| 항목 | 현재 상태 |

## Linear ↔ GitHub Issues 자동화

Linear는 이슈·일정 관리에만 사용하고 요구사항 문서는 저장하지 않는다. 확정된 요구사항의 원본은 GitHub `docs/`다.

운영 기준:

1. Linear 상태는 `ToDo` / `In Progress` / `Done`만 사용한다.
2. GitHub Issues Sync는 Two-way로 유지한다.
3. 제품 요구사항·정책·설계를 새로 만들거나 변경할 때는 Slack Human Confirm → GitHub 문서 PR → Human Review → Squash Merge를 먼저 완료한다.
4. 병합된 `main` 문서를 기준으로 Linear 이슈를 `ToDo`로 만들고 동기화된 GitHub Issue의 제목·Description·Acceptance Criteria와 문서 링크를 확인한다.
5. 이미 확정된 요구사항을 그대로 구현하는 작업은 별도 문서 PR 없이 기존 `main` 문서를 기준으로 이슈를 만든다.
6. 최신 `main`에서 작업 브랜치를 만든다. 이슈가 있는 작업은 실제 Linear 이슈 키를 포함하고, 이슈가 없는 Level 0 `docs`·`chore` 작업은 키를 생략할 수 있다.
7. Draft PR은 상태를 바꾸지 않는다. 리뷰 가능한 일반 PR이 열리면 Linear를 `In Progress`로 자동 전환하도록 설정되어 있다.
8. 리뷰 요청·활동과 Ready for merge 이벤트는 상태를 바꾸지 않는다.
9. 커밋 Footer는 `Refs` 참조 전용으로 사용한다. 이슈 종료 자동화의 공식 진입점은 PR 본문이다.
10. 하나의 이슈에 PR 하나만 연결되며 그 PR이 Acceptance Criteria 전체를 완료하면 PR 본문에 `Fixes NSU-123`과 `Closes #123`을 사용한다.
11. 하나의 이슈에 여러 PR이 연결되면 중간 PR은 `Refs NSU-123` / `Refs #123`, Acceptance Criteria를 최종 완료하는 마지막 PR만 `Fixes NSU-123` / `Closes #123`을 사용한다.
12. 사람이 Squash Merge하면 Linear `Done`과 GitHub Issue `Closed`로 맞춰지도록 자동화가 설정되어 있다. 실제 전체 흐름 검증 완료 여부는 [도입 체크리스트](08-도입-체크리스트.md)를 기준으로 한다.

Linear는 여러 PR이 하나의 이슈에 연결된 경우 마지막 연결 PR이 필요한 상태에 도달할 때 상태를 갱신할 수 있지만, GitHub Issue는 `Closes #123`이 들어간 개별 PR 병합만으로 먼저 닫힐 수 있다. 그래서 두 시스템의 완료 시점을 암묵적으로 같다고 가정하지 않고, **중간 PR은 참조만 하고 마지막 완료 PR에서만 종료 키워드를 사용**한다.

Two-way Sync의 이슈 생성과 GitHub Issue Closed → Linear Done 동기화는 실제 이슈로 확인했다. PR 이벤트 자동화는 설정을 완료했지만 실제 PR Squash Merge 전체 흐름은 아직 검증 대기다. 검증 전에는 자동 종료를 완료된 사실로 표현하지 않는다.

## GitHub Actions CI 등록 순서

CI는 저장소의 실제 구현 구조와 실행 명령을 확인한 뒤 만든다.

1. Backend의 실제 Java/Gradle 버전과 테스트·빌드 명령을 확인한다.
2. Frontend의 실제 Node/package manager와 lint/test/build 명령을 확인한다.
3. `.github/workflows/`에 PR 검증 workflow를 추가한다.
4. 샘플 PR에서 정상 변경의 성공과 의도적 오류의 실패를 모두 확인한다.
5. GitHub에 표시된 실제 check 이름을 기록한다.
6. 문서-only, Frontend-only, Backend-only PR에서도 Required Check가 영원히 Pending 상태로 남지 않는지 확인한다.
7. 검증이 끝난 check만 `main` Ruleset의 Required Status Check로 등록한다.

## 마지막 단계: `main` Ruleset

CodeRabbit과 CI를 실제 PR에서 검증한 뒤 `Settings → Rules → Rulesets`에서 `main` 대상 Branch Ruleset을 만든다.

| 설정 | 값 |
|---|---|
| Pull Request 없이 변경 | 금지 |
| Required approvals | 작성자 외 사람 1명 이상 |
| Dismiss stale approvals | ON 권장 |
| Require conversation resolution | ON |
| Required status checks | 검증된 CI check만 등록 |
| Force push | 금지 |
| `main` 삭제 | 금지 |
| Require linear history | ON |
| CodeRabbit | 초기에는 Required Check 아님 |
