# 저장소 설정과 자동화

← [가이드 목차](README.md)

## 공지와 자동화의 역할

**운영 문서로 기준을 남기고, Slack에는 문서 링크와 적용 방법을 알리며, 저장소가 강제할 가치가 큰 규칙만 GitHub 설정으로 적용한다.**

| 규칙 | 적용 위치 | 운영 방식 |
|---|---|---|
| 요구사항·작업 관리 | Linear Requirements / Issue | 제품 요구사항, Acceptance Criteria, 담당자, 우선순위, 일정, 상태 관리 |
| 장기 문서 | GitHub `docs/` / ADR | Linear에서 확정된 내용을 바탕으로 설계·정책·API·운영 문서 유지 |
| 문서 정합성 | Human Review | 별도 GitHub Action을 만들지 않고 PR에서 직접 확인 |
| 브랜치·커밋·PR 작성 방식 | 문서, PR 템플릿, 사람 리뷰 | 가이드와 예시 공유 |
| `main` 직접 push 방지 | GitHub Ruleset | 팀원 합류 후 PR 필수 규칙으로 적용 예정 |
| 사람 승인 1명 이상 | GitHub Ruleset + 팀 리뷰 | 작성자 외 팀원 승인 기준 |
| 애플리케이션 빌드·테스트 | GitHub Actions | 실제 FE/BE 구조가 생긴 뒤 필요 시 도입 |
| Squash Merge | GitHub 저장소 설정 | Squash만 병합 방식으로 허용 |
| 작업 브랜치 정리 | GitHub + 각 팀원 PC | 원격 자동 삭제, 로컬 별도 정리 |
| AI PR 리뷰 | CodeRabbit Review | 초기 Advisory로 운영 |

문서 정합성 전용 CI를 별도로 만들지 않는다. 현재 팀 규모에서는 **Linear를 먼저 확정하고, 같은 작업 Branch에서 필요한 GitHub 문서를 갱신한 뒤 Human Review에서 비교하는 방식**을 기본으로 한다.

## Source of Truth와 문서 반영

```text
Slack Thread
   ↓
Claude 초안 / 영향 분석
   ↓
Human Confirm
   ↓
Linear Requirements / Issue
   ↓
작업 Branch
   ↓
필요한 README / docs/ / API / ADR 갱신
   ↓
구현
   ↓
PR
```

GitHub 문서는 Linear의 복사본이 아니다. 담당자·우선순위·일정·진행 상태는 Linear에만 두고, GitHub에는 코드와 함께 오래 유지해야 할 설계·정책·API·운영 내용을 남긴다.

요구사항이 바뀌면 **Linear를 먼저 수정**한다. 그다음 같은 작업 Branch에서 GitHub 문서와 코드를 필요한 만큼 갱신한다. PR Human Review에서 Linear / Code / Documentation 3가지를 함께 비교한다.

## CodeRabbit 운영

상세 설정은 [10. CodeRabbit PR Review](10-coderabbit-pr-review.md)를 따른다.

초기 원칙:

1. CodeRabbit GitHub App은 `NSU_CAPSTONE`에만 접근하도록 제한한다.
2. Review Profile은 `chill`을 사용한다.
3. Auto Review는 ON으로 사용한다.
4. `request_changes_workflow`는 OFF로 두어 Advisory Reviewer로 유지한다.
5. Path Instructions는 FE/BE 코드가 실제로 들어온 뒤 필요한 규칙만 추가한다.
6. CodeRabbit 자체를 GitHub Ruleset의 Required Check로 사용하지 않는다.
7. 무료 Review 제한으로 리뷰가 지연될 수 있으므로 CodeRabbit 미실행만으로 팀 작업을 막지 않는다.

Linear ↔ CodeRabbit 직접 연동과 Slack `@CodeRabbit` 호출은 공식 Workflow의 필수 단계가 아니다.

## 애플리케이션 GitHub Actions CI — 추후

실제 Backend/Frontend 코드가 들어오기 전에는 빌드 명령과 테스트 명령을 가정해서 CI를 만들지 않는다.

구현 구조가 확정된 뒤 다음을 확인한다.

1. Backend의 실제 Java/Gradle 버전과 테스트·빌드 명령
2. Frontend의 실제 Node/package manager와 lint/test/build 명령
3. 필요한 경우 `.github/workflows/`에 애플리케이션 PR 검증 workflow 추가
4. 정상 PR과 의도적 실패 PR로 동작 검증
5. 충분히 안정화된 check만 Ruleset의 Required Status Check 후보로 검토

이 CI는 **애플리케이션 빌드·테스트 검증용**이다. 문서 정합성을 검사하는 별도 Action은 만들지 않는다.

## 팀원 초대와 FE / BE 작업 책임

팀원 초대 후 Frontend와 Backend의 작업 책임을 명확히 나눈다.

예정 방향:

- Frontend 담당: `frontend/` 중심 작업
- Backend 담당: `backend/` 중심 작업
- 공통 문서, API Contract, 설정 변경은 관련 담당자와 함께 리뷰
- `CODEOWNERS`를 도입해 경로별 필수 리뷰 책임을 나누는 방안을 우선 검토

중요: 현재 저장소는 하나의 **public monorepo**다. 일반적인 Repository write 권한만으로 특정 팀원에게 `frontend/`만 쓰게 하고 다른 경로의 write를 완전히 차단하는 폴더별 ACL을 단순하게 제공하지 않는다. 따라서 목표가 "작업 책임 분리"라면 CODEOWNERS + PR Review가 적합하고, 정말 엄격한 폴더별 write 격리가 필요하면 저장소 분리 같은 구조도 함께 검토해야 한다.

## `main` Ruleset — 추후

팀원 합류와 작업 책임 정리가 끝난 뒤 `main` 보호를 적용한다.

최소 목표:

| 설정 | 목표 |
|---|---|
| Pull Request 없이 `main` 변경 | 금지 |
| Required approvals | 작성자 외 사람 1명 이상 |
| Require conversation resolution | ON 권장 |
| Force push | 금지 |
| `main` 삭제 | 금지 |
| Require linear history | ON 권장 |
| CodeRabbit | Required Check로 사용하지 않음 |
| 문서 정합성 Action | 만들지 않음 |
| 애플리케이션 CI | 실제 도입·검증 후에만 Required Check 여부 결정 |

Ruleset 적용 후 작은 실제 기능 PR에서 **Linear → Branch → docs/코드 → PR → CodeRabbit → Human Review → Squash Merge → Linear 상태 정리** 흐름을 다시 확인한다.
