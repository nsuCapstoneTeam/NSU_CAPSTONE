# 팀 규칙과 역할

## 먼저 읽는 팀 규칙

| 항목 | 운영 기준 | 상태 |
|---|---|---|
| 브랜치 전략 | `main` + 작업별 짧은 브랜치 | 적용 기준 |
| 작업 단위 | 독립적으로 설명·검토·되돌릴 수 있는 변경 하나를 PR 하나로 묶기 | 적용 기준 |
| 커밋 메시지 | `타입(스코프): 주제`, 제목 50글자 이내, 본문 한국어·72글자 이내 | 적용 기준 |
| `main` 반영 | PR → 작성자 외 사람 1명 이상 승인 → 사람이 Squash Merge | 적용 기준 |
| AI PR 리뷰 | CodeRabbit Review는 초기 Advisory, 사람 승인을 대체하지 않음 | 도입·검증 중 |
| Slack Agent | CodeRabbit Agent는 코드/PR/CI 맥락이 필요한 조사·계획에 선택적으로 호출 | 도입·검증 중 |
| CI | 실제 워크플로 실행을 검증한 뒤 필수 검사로 등록 | 도입 예정 |
| 병합 이후 | 원격 작업 브랜치 자동 삭제, 다음 작업은 최신 `main`에서 새로 시작 | 저장소 설정 적용 |

각 항목의 실제 절차는 [GitHub Flow와 브랜치](02-github-flow와-브랜치.md), [커밋 전략과 메시지](03-커밋-전략과-메시지.md), [로컬 설정과 일상 작업](04-로컬-설정과-일상-작업.md), [PR 작성과 리뷰](05-pr-작성과-리뷰.md), [CodeRabbit 운영](10-coderabbit-review와-slack-agent.md)에서 다룬다.

## 협업 도구와 Source of Truth

| 도구 / 담당 | 책임 |
|---|---|
| Slack `#dev` | 팀 논의, Context 공유, AI Agent 호출 시작점 |
| Claude | Slack Thread의 논의 요약, 문서 초안, 설계 검토, 구현 보조 |
| Linear | 확정된 작업 범위·담당자·우선순위·일정·진행 상태 관리 |
| GitHub | 코드, 브랜치, 커밋, PR, 리뷰, CI/CD 기록의 Source of Truth |
| CodeRabbit Review | GitHub PR의 자동 AI 1차 코드 리뷰. 초기에는 Advisory |
| CodeRabbit Slack Agent | 코드베이스 영향 분석, 기존 패턴 조사, 구현 계획, CI 실패·PR 리뷰 후속 분석 |
| `docs/adr/` | 인증, API 계약, DB 구조, 인프라 등 중요한 설계 결정 기록 |
| 사람 리뷰어 | 요구사항·설계·코드·검증 결과 확인 및 최종 승인 |
| 저장소 관리자 | Organization 권한, 병합 방식, `main` Ruleset, GitHub App 및 CodeRabbit 설정 관리 |

Slack에만 남은 대화는 최종 작업 기준으로 보지 않는다. Claude나 CodeRabbit이 Thread를 정리·분석한 결과도 초안이며, 팀원이 검토해 확정된 작업은 Linear와 필요한 경우 GitHub 문서/ADR로 옮긴다.

## 기본 개발 워크플로우

```text
Slack #dev에서 기능/문제 제시
        ↓
같은 Root Message의 Thread에서 팀 논의
        ↓
@Claude 호출
- 논의 요약
- 확정 / 미확정 사항 분리
- 문서 초안
- 설계 검토
- Linear Issue 후보 제안
        ↓
사람이 Claude 결과 검토·확정
        ↓
@Linear
- Issue / 담당자 / 우선순위 / 일정 반영
        ↓
필요 시 @CodeRabbit
- 기존 코드 패턴 조사
- 변경 영향 범위 분석
- 구현 순서와 테스트 포인트 제안
        ↓
최신 main에서 짧은 작업 브랜치 생성
        ↓
AI Agent 또는 사람이 구현·검증
        ↓
GitHub Pull Request
        ↓
GitHub Actions CI + CodeRabbit 자동 PR Review
        ↓
필요 시 Slack Thread에서 @CodeRabbit
- CI 실패 원인 조사
- 리뷰 지적의 타당성/영향 분석
- 최소 수정안 제안
        ↓
작성자 외 사람 리뷰어 승인
        ↓
사람이 Squash Merge
        ↓
main 반영 + 원격 작업 브랜치 삭제
        ↓
Linear 상태 정리
```

## AI Agent 호출 원칙

- Claude는 **논의 → 요구사항/설계 초안** 단계에서 우선 사용한다.
- CodeRabbit Slack Agent는 **코드 저장소의 실제 맥락이 필요한 순간**에 사용한다.
- CodeRabbit GitHub Review는 PR이 열리면 자동으로 수행하는 1차 품질 검토다.
- 자동 PR Review와 Slack Agent는 역할이 겹치므로 매 PR마다 Slack Agent를 의무 호출하지 않는다.
- CodeRabbit이 코드 변경이나 PR 생성을 제안할 수 있어도 영향이 큰 작업은 먼저 분석/계획을 받고 사람이 승인한 뒤 실행한다.
- 최종 Merge 판단은 AI가 아니라 사람 리뷰어가 한다.

핵심 운영 원칙은 **"Slack은 논의하는 곳이고, Linear는 결정된 작업을 관리하며, GitHub는 코드와 변경 이력을 보존하는 곳"**이다.

일반 작업은 Linear 이슈를 연결한다. 오타·주석·간단한 문서 수정 같은 Level 0 작업은 이슈 없이 PR을 만들 수 있다. DB 스키마, 인증, 결제, 운영 환경, 호환성을 깨는 API 변경은 구현 전에 사람이 설계를 검토하고 필요하면 ADR을 작성한다.

`DEV-123` 같은 키는 형식 예시다. 실제 작업에서는 현재 Linear 팀의 실제 이슈 키를 사용하며, 없는 이슈 번호를 만들어 붙이지 않는다.
