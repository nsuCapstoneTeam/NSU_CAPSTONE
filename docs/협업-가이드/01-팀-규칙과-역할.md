## 먼저 읽는 팀 규칙

| 항목 | 운영 기준 | 근거 / 상태 |
|---|---|---|
| 브랜치 전략 | `main` + 작업별 짧은 브랜치 | 기존 합의 |
| 작업 단위 | 독립적으로 설명·검토·되돌릴 수 있는 변경 하나를 PR 하나로 묶기 | 이번 문서의 구체화 제안 |
| 커밋 단위 | 하나의 목적을 가진 변경과 관련 검증을 함께 기록 | 이번 문서의 구체화 제안 |
| 커밋 메시지 | 제목 50자 이내, 본문 한국어·한 줄 72자 이내 | 기존 합의 |
| `main` 반영 | PR → 작성자 외 사람 1명 이상 승인 → 사람이 Squash Merge | 기존 합의 |
| AI 리뷰 | CodeRabbit은 초기 Advisory, 사람의 승인을 대체하지 않음 | 기존 합의 |
| CI | 실제 워크플로 실행을 확인한 뒤 필수 검사로 등록 | 기존 계획 |
| 작업 브랜치 갱신 | 깨끗한 작업 상태에서 최신 `origin/main`을 명시적으로 merge | 이번 문서의 권장 운영값 |
| 병합 이후 | 원격 작업 브랜치 삭제, 다음 작업은 최신 `main`에서 새로 시작 | 기존 합의 |

각 항목의 실제 절차는 [GitHub Flow와 브랜치](02-github-flow와-브랜치.md), [커밋 전략과 메시지](03-커밋-전략과-메시지.md), [로컬 설정과 일상 작업](04-로컬-설정과-일상-작업.md)에서 다룬다.

## 협업 도구와 역할

| 도구 / 담당 | 책임 |
|---|---|
| Slack `#dev` | 요구사항 논의, 막힌 문제 공유, 리뷰 요청 |
| Linear | 작업 범위·담당자·완료 조건·진행 상태 관리 |
| GitHub | 코드, 커밋, PR, 리뷰와 병합 기록 |
| `docs/adr/` | 인증, API 계약, DB 구조, 인프라 등 중요한 설계 결정 기록 |
| PR 작성자 | 변경 범위 정리, 검증, 리뷰 반영, 병합 준비 |
| 사람 리뷰어 | 요구사항·코드·검증 결과를 확인하고 승인 또는 수정 요청 |
| 저장소 소유자 | 병합 방식과 `main` 보호 설정 적용·관리 |
| Claude Code / Codex / CodeRabbit | 구현·검증·리뷰 보조. 최종 승인과 병합은 사람 담당 |

일반 작업은 Linear 이슈를 연결한다. 오타·주석·간단한 문서 수정 같은 Level 0 작업은 기존 합의대로 이슈 없이 PR을 만들 수 있다. DB 스키마, 인증, 결제, 운영 환경, 호환성을 깨는 API 변경은 구현 전에 사람이 설계를 검토한다.

`DEV-123` 같은 키는 형식 예시다. Linear 팀 키와 실제 이슈 생성 여부는 별도 확인이 필요하며, 없는 이슈 번호를 실제 작업에 붙이지 않는다.
