## 먼저 읽는 팀 규칙

| 항목 | 운영 기준 | 상태 |
|---|---|---|
| 브랜치 전략 | `main` + 작업별 짧은 브랜치 | 적용 기준 |
| 작업 단위 | 독립적으로 설명·검토·되돌릴 수 있는 변경 하나를 PR 하나로 묶기 | 적용 기준 |
| 커밋 메시지 | `타입(스코프): 주제`, 제목 50글자 이내, 본문 한국어·72글자 이내 | 적용 기준 |
| `main` 반영 | PR → 작성자 외 사람 1명 이상 승인 → 사람이 Squash Merge | 적용 기준 |
| AI PR 리뷰 | CodeRabbit은 초기 Advisory, 사람 승인을 대체하지 않음 | 적용 기준 |
| 문서 정합성 | 별도 GitHub Action 없이 Linear 기준 + Human Review로 확인 | 적용 기준 |
| 애플리케이션 CI | 실제 FE/BE 구조와 실행 명령이 생긴 뒤 필요 시 구성 | 추후 도입 |
| 병합 이후 | 원격 작업 브랜치 자동 삭제, 다음 작업은 최신 `main`에서 새로 시작 | 저장소 설정 적용 |

각 항목의 실제 절차는 [GitHub Flow와 브랜치](02-github-flow와-브랜치.md), [커밋 전략과 메시지](03-커밋-전략과-메시지.md), [로컬 설정과 일상 작업](04-로컬-설정과-일상-작업.md), [PR 작성과 리뷰](05-pr-작성과-리뷰.md), [CodeRabbit PR Review](10-coderabbit-pr-review.md)에서 다룬다.

## 협업 도구와 Source of Truth

| 도구 / 담당 | 책임 |
|---|---|
| Slack `#dev` | 팀 논의, Context 공유, Claude/Linear 호출 시작점 |
| Claude | Slack Thread의 논의 요약, 문서 초안, 설계 검토, 구현 보조 |
| Linear Requirements | 확정된 제품·서비스 요구사항과 비즈니스 규칙의 기준 원문 |
| Linear Issue | 실제 구현 작업, Acceptance Criteria, 담당자, 우선순위, 일정, 진행 상태 관리 |
| GitHub | 코드, 브랜치, 커밋, PR, 리뷰와 변경 이력의 Source of Truth |
| `docs/` / `docs/adr/` | Linear의 확정 내용을 바탕으로 장기 유지할 설계·정책·API·운영 문서와 중요한 기술 결정 기록 |
| CodeRabbit | GitHub PR의 자동 AI 1차 코드 리뷰. 초기에는 Advisory |
| 사람 리뷰어 | Linear 요구사항, 구현, 문서 영향을 함께 검토하고 최종 승인 |
| 저장소 관리자 | Organization 권한, 병합 방식, `main` Ruleset, GitHub App 및 CodeRabbit 설정 관리 |

Slack에만 남은 대화는 최종 작업 기준으로 보지 않는다. Claude가 Thread를 정리한 결과도 초안이며, 팀원이 검토해 확정한 뒤 Linear에 반영한다. GitHub 문서는 Linear와 동일한 작업 관리 정보를 다시 복제하는 곳이 아니라, 구현과 운영에 장기적으로 필요한 내용을 관리한다.

## 기본 개발 워크플로우

```text
Slack #dev에서 기능/문제 제시
        ↓
같은 Root Message의 Thread에서 팀 논의
        ↓
@Claude 호출
- 논의 요약
- 확정 / 미확정 사항 분리
- 문서 초안
- 설계 검토
- Linear Issue 후보 제안
        ↓
사람이 Claude 결과 검토·확정
        ↓
@Linear
- Issue / Acceptance Criteria
- 담당자 / 우선순위 / 일정 반영
        ↓
최신 main에서 짧은 작업 브랜치 생성
        ↓
Linear 확정 내용을 기준으로 필요한 GitHub 문서 갱신
- README
- docs/
- docs/api/
- docs/adr/
        ↓
AI Agent 또는 사람이 구현·검증
        ↓
GitHub Pull Request
        ↓
CodeRabbit 자동 PR Review
        ↓
Human Review
- Linear 요구사항 / Acceptance Criteria 충족 확인
- 코드 / 테스트 / 보안 / 예외처리 확인
- README / docs/ / ADR이 확정된 요구사항과 일치하는지 확인
        ↓
작성자 외 사람 리뷰어 1명 이상 승인
        ↓
사람이 Squash Merge
        ↓
main 반영 + 원격 작업 브랜치 삭제
        ↓
@Linear 상태 정리
```

GitHub 문서를 수정해야 하는 작업이라면 **작업 Branch를 만든 뒤 같은 Branch에서 문서와 구현을 함께 갱신**한다. 문서만 독립적으로 리뷰할 필요가 있을 때만 별도의 문서 PR로 분리한다.

문서 정합성을 위한 별도 GitHub Actions는 도입하지 않는다. 요구사항 변경은 Linear를 먼저 갱신하고, GitHub 문서 반영 여부와 정합성은 PR의 Human Review에서 확인한다. 실제 Backend/Frontend 코드가 들어온 뒤 빌드·테스트 자동화가 필요하면 애플리케이션 CI를 별도로 구성한다.

## Human Review 필수 확인 3가지

1. **Linear**: Issue의 목표와 Acceptance Criteria를 실제 구현이 충족하는가?
2. **Code**: 코드, 테스트, 보안, 권한, 예외 처리와 변경 영향이 적절한가?
3. **Documentation**: README, `docs/`, ADR이 필요한 만큼 갱신되었고 Linear의 확정 내용과 충돌하지 않는가?

CodeRabbit은 이 검토를 보조하는 PR Reviewer이며 사람의 최종 판단을 대체하지 않는다. 무료 Review 제한 등으로 실제 리뷰가 지연될 수 있으므로 CodeRabbit 자체를 Merge Gate로 사용하지 않는다. Linear ↔ CodeRabbit 직접 연동이나 Slack `@CodeRabbit` 호출도 공식 Workflow의 필수 단계가 아니다.

핵심 운영 원칙은 **"Slack은 논의하는 곳, Linear는 요구사항과 작업을 확정하는 곳, GitHub는 코드와 변경 이력을 보존하는 곳, docs/ADR은 확정된 내용을 장기 문서로 유지하는 곳"**이다.

일반 작업은 Linear 이슈를 연결한다. 오타·주석·간단한 문서 수정 같은 Level 0 작업은 이슈 없이 PR을 만들 수 있다. DB 스키마, 인증, 결제, 운영 환경, 호환성을 깨는 API 변경은 구현 전에 사람이 설계를 검토하고 필요하면 ADR을 작성한다.

`DEV-123` 같은 키는 형식 예시다. 실제 작업에서는 현재 Linear 팀의 실제 이슈 키를 사용하며, 없는 이슈 번호를 만들어 붙이지 않는다.
