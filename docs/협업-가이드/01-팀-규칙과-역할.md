# 팀 규칙과 역할

← [가이드 목차](README.md)

## 먼저 읽는 팀 규칙

| 항목 | 운영 기준 | 상태 |
|---|---|---|
| 브랜치 전략 | `main` + 작업별 짧은 브랜치 | 적용 기준 |
| 작업 단위 | 독립적으로 설명·검토·되돌릴 수 있는 변경 하나를 PR 하나로 묶기 | 적용 기준 |
| 커밋 메시지 | `타입(스코프): 주제`, Footer는 `Refs` 참조 전용 | 적용 기준 |
| `main` 반영 | PR → 작성자 외 사람 1명 이상 승인 → 사람이 Squash Merge | 적용 기준 |
| AI PR 리뷰 | CodeRabbit은 초기 Advisory, 사람 승인을 대체하지 않음 | 도입·검증 중 |
| CI | 실제 워크플로 실행을 검증한 뒤 필수 검사로 등록 | 도입 예정 |
| 이슈 상태 | Linear는 `ToDo` / `In Progress` / `Done`만 사용 | 적용 기준 |
| 이슈 동기화 | Linear ↔ GitHub Issues Two-way Sync로 같은 작업을 관리 | 적용·검증 완료 |
| PR 상태 자동화 | PR Open → `In Progress`, PR Merge → `Done` | 설정 완료, 전체 흐름 검증 대기 |
| 병합 이후 | 원격 작업 브랜치 자동 삭제, 다음 작업은 최신 `main`에서 새로 시작 | 저장소 설정 적용 |

## 협업 도구와 Source of Truth

| 도구 / 담당 | 책임 |
|---|---|
| Slack `#dev` | 팀 논의, Context 공유, Agent/Linear 호출 시작점 |
| Claude 등 Agent | Slack Thread 정리, GitHub 문서 수정, 설계 검토, 구현 보조 |
| `docs/` / `docs/adr/` | 확정된 요구사항·정책·설계·API·운영 규칙의 Source of Truth |
| Linear | 이슈·Acceptance Criteria·담당자·우선순위·일정·진행 상태 관리 |
| GitHub Issues | Linear와 Two-way Sync되는 동일 작업 기록 |
| GitHub | 코드, 브랜치, 커밋, PR, 리뷰, CI/CD와 변경 이력의 Source of Truth |
| CodeRabbit | GitHub PR의 자동 AI 1차 코드 리뷰. 초기에는 Advisory |
| 사람 리뷰어 | GitHub 문서·동기화된 Issue, 구현, 문서 영향을 함께 검토하고 최종 승인 |

Slack에만 남은 대화는 최종 작업 기준으로 보지 않는다. Agent가 Thread를 정리한 결과도 초안이다. 제품 요구사항·정책·설계를 새로 만들거나 변경할 때는 사람이 확정한 내용을 GitHub `docs/` / ADR 문서 PR로 반영하고 Human Review 후 Squash Merge한 다음, 병합된 `main` 문서를 기준으로 Linear Issue를 만든다. GitHub Issue는 Two-way Sync로 생성하며 두 이슈를 따로 작성하지 않는다.

이미 `main`에 확정된 요구사항을 그대로 구현하거나 제품 요구사항을 바꾸지 않는 버그 수정·리팩터링·테스트는 별도 문서 PR을 먼저 만들지 않는다.

## 기본 개발 워크플로우

| 단계 | 행동 | 확인할 결과 |
|---|---|---|
| 1. 논의 | Slack `#dev` Root Message와 Thread에서 논의 | 결정·미결정 사항이 분리됨 |
| 2. 확정 | 사람이 `[Human Confirm]`으로 최종 결정 작성 | Agent가 임의로 결정하지 않음 |
| 3. 문서 반영 | 요구사항·정책 변경이면 GitHub `docs/` 문서 PR 생성 | Human Review 후 Squash Merge |
| 4. 이슈 생성 | 병합된 `main` 문서를 기준으로 Linear 이슈를 `ToDo`로 생성 | Two-way Sync된 GitHub Issue 확인 |
| 5. 구현 | 최신 `main`에서 작업 브랜치 생성 | 이슈가 있는 작업만 실제 이슈 키 포함 |
| 6. PR | PR 본문에 문서·Linear·GitHub Issue 연결 | PR Open 시 `In Progress`로 전환되도록 설정 |
| 7. 리뷰 | CodeRabbit 자동 1차 리뷰 + Human Review 3종 체크 | 작성자 외 팀원 1명 이상 승인 |
| 8. 완료 | 사람이 Squash Merge | `Done` / `Closed` 자동화 설정, 실제 검증은 체크리스트 기준 |

## PR과 이슈 종료 원칙

커밋 Footer는 `Refs` 참조 전용으로 사용한다. 이슈 종료 자동화의 공식 진입점은 PR 본문이다.

- PR 하나가 이슈의 Acceptance Criteria 전체를 완료하면: `Fixes NSU-123` + `Closes #42`
- 하나의 이슈를 여러 PR로 나누면 중간 PR: `Refs NSU-123` + `Refs #42`
- 여러 PR 중 Acceptance Criteria를 최종 완료하는 마지막 PR: `Fixes NSU-123` + `Closes #42`

마지막 PR은 단순히 가장 늦게 생성된 PR이 아니라 연결된 이슈의 Acceptance Criteria 전체를 완료하는 변경을 의미한다. GitHub Issue가 중간 PR에서 조기에 닫히지 않도록 중간 PR에는 closing keyword를 사용하지 않는다.

자동 상태 규칙은 다음과 같이 설정되어 있다.

- Draft PR Open: 상태 변경 없음
- 일반 PR Open: `In Progress`
- PR 리뷰 요청 또는 활동: 상태 변경 없음
- PR Ready for merge: 상태 변경 없음
- PR Merge: `Done`

실제 PR Squash Merge 후 Linear와 GitHub Issue의 최종 상태가 기대대로 일치하는지에 대한 전체 검증은 [도입 체크리스트](08-도입-체크리스트.md)를 기준으로 한다. 검증 전에는 자동 종료를 완료된 사실처럼 표현하지 않는다.

## Human Review 필수 확인 3가지

1. **Requirement / Issue**: GitHub `docs/`의 확정 요구사항과 Issue의 Acceptance Criteria를 실제 구현이 충족하는가?
2. **Code**: 코드, 테스트, 보안, 권한, 예외 처리와 변경 영향이 적절한가?
3. **Documentation**: README, `docs/`, ADR을 수정해야 하는데 누락된 부분은 없는가?

## Linear 상태 규칙

| Linear 상태 | 전환 기준 | GitHub Issue |
|---|---|---|
| `ToDo` | 확정 문서를 기준으로 이슈 생성 | Open |
| `In Progress` | 연결된 일반 PR Open | Open |
| `Done` | 완료 대상 PR이 `main`에 Squash Merge되도록 자동화 설정 | Closed가 되도록 운영 |

`Backlog`, `Canceled`, `Duplicate`, `Approved`, `In Review`는 팀의 일반 작업 상태로 사용하지 않는다. 취소·중복 작업은 완료된 작업과 구분해 사유를 기록하고 팀이 정한 정리 절차를 따른다.

일반 작업은 동기화된 Linear / GitHub Issue를 연결한다. 오타·주석·간단한 문서 수정 같은 Level 0 작업은 이슈 없이 PR을 만들 수 있다. DB 스키마, 인증, 결제, 운영 환경, 호환성을 깨는 API 변경은 구현 전에 사람이 설계를 검토하고 필요하면 ADR을 작성한다.

`NSU-123` 같은 키는 형식 예시다. 실제 작업에서는 현재 Linear 팀의 실제 이슈 키를 사용하며, 없는 이슈 번호를 만들어 붙이지 않는다.
