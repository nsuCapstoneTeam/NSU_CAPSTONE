# 팀 규칙과 역할

## 먼저 읽는 팀 규칙

| 항목 | 운영 기준 | 상태 |
|---|---|---|
| 브랜치 전략 | `main` + 작업별 짧은 브랜치 | 적용 기준 |
| 작업 단위 | 독립적으로 설명·검토·되돌릴 수 있는 변경 하나를 PR 하나로 묶기 | 적용 기준 |
| 커밋 메시지 | `타입(스코프): 주제`, 제목 50글자 이내, 본문 한국어·72글자 이내 | 적용 기준 |
| `main` 반영 | PR → 작성자 외 사람 1명 이상 승인 → 사람이 Squash Merge | 적용 기준 |
| AI PR 리뷰 | CodeRabbit은 초기 Advisory, 사람 승인을 대체하지 않음 | 도입·검증 중 |
| CI | 실제 워크플로 실행을 검증한 뒤 필수 검사로 등록 | 도입 예정 |
| 이슈 상태 | Linear는 `ToDo` / `In Progress` / `Done`만 사용 | 적용 기준 |
| 이슈 동기화 | Linear ↔ GitHub Issues Two-way Sync로 같은 작업을 관리 | 검증 예정 |
| 병합 이후 | 원격 작업 브랜치 자동 삭제, 다음 작업은 최신 `main`에서 새로 시작 | 저장소 설정 적용 |

각 항목의 실제 절차는 [GitHub Flow와 브랜치](02-github-flow와-브랜치.md), [커밋 전략과 메시지](03-커밋-전략과-메시지.md), [로컬 설정과 일상 작업](04-로컬-설정과-일상-작업.md), [PR 작성과 리뷰](05-pr-작성과-리뷰.md), [CodeRabbit PR Review](10-coderabbit-pr-review.md)에서 다룬다.

## 협업 도구와 Source of Truth

| 도구 / 담당 | 책임 |
|---|---|
| Slack `#dev` | 팀 논의, Context 공유, Agent/Linear 호출 시작점 |
| Claude 등 Agent | Slack Thread 정리, GitHub 문서 수정, 설계 검토, 구현 보조 |
| `docs/` / `docs/adr/` | 확정된 요구사항·정책·설계·API·운영 규칙의 Source of Truth |
| Linear | 이슈·Acceptance Criteria·담당자·우선순위·일정·진행 상태 관리 |
| GitHub Issues | Linear와 Two-way Sync되는 동일 작업 기록 |
| GitHub | 코드, 브랜치, 커밋, PR, 리뷰, CI/CD와 변경 이력의 Source of Truth |
| CodeRabbit | GitHub PR의 자동 AI 1차 코드 리뷰. 초기에는 Advisory |
| 사람 리뷰어 | GitHub 문서·동기화된 Issue, 구현, 문서 영향을 함께 검토하고 최종 승인 |
| 저장소 관리자 | Organization 권한, 병합 방식, `main` Ruleset, GitHub App 및 CodeRabbit 설정 관리 |

Slack에만 남은 대화는 최종 작업 기준으로 보지 않는다. Agent가 Thread를 정리한 결과도 초안이다. 팀원이 확정한 내용은 먼저 GitHub `docs/` / ADR에 PR로 반영하고, 그 문서를 기준으로 Linear Issue를 만든다. GitHub Issue는 Two-way Sync로 생성하며 두 이슈를 따로 작성하지 않는다.

## 기본 개발 워크플로우

```text
Slack #dev에서 기능/문제 제시
        ↓
같은 Root Message의 Thread에서 팀 논의
        ↓
@Claude 등 Agent 호출
- 논의 요약
- 확정 / 미확정 사항 분리
- GitHub docs/ 변경
- 설계 검토
- Linear Issue 후보 제안
        ↓
사람이 Claude 결과 검토·확정
        ↓
문서 Branch → PR → Human Review → Squash Merge
        ↓
@Linear
- GitHub docs/를 기준으로 Issue / Acceptance Criteria 생성(ToDo)
- 담당자 / 우선순위 / 일정 반영
        ↓
Linear ↔ GitHub Issues Two-way Sync
- 제목 / Description / Acceptance Criteria 동일 유지
- 서로의 링크 확인
        ↓
최신 main에서 짧은 작업 브랜치 생성
        ↓
작업 시작 시 Linear In Progress
        ↓
AI Agent 또는 사람이 구현·검증
        ↓
GitHub Pull Request
        ↓
GitHub Actions CI(도입 완료 후) + CodeRabbit 자동 PR Review
        ↓
Human Review
- GitHub docs/와 Issue의 요구사항 / Acceptance Criteria 충족 확인
- 코드 / 테스트 / 보안 / 예외처리 확인
- README / docs/ / ADR 업데이트 필요 여부 확인
        ↓
작성자 외 사람 리뷰어 승인
        ↓
사람이 Squash Merge
        ↓
main 반영 + 원격 작업 브랜치 삭제
        ↓
Linear Done 자동 전환
        ↓
Two-way Sync로 GitHub Issue Closed
```

현재 GitHub Actions CI는 도입 예정이다. CI 도입 전에는 CodeRabbit Review와 Human Review를 사용하고, 실제 워크플로와 check 이름을 검증한 뒤 CI를 필수 검증 단계로 전환한다.

## Human Review 필수 확인 3가지

1. **Requirement / Issue**: GitHub `docs/`의 확정 요구사항과 Issue의 Acceptance Criteria를 실제 구현이 충족하는가?
2. **Code**: 코드, 테스트, 보안, 권한, 예외 처리와 변경 영향이 적절한가?
3. **Documentation**: README, `docs/`, ADR을 수정해야 하는데 누락된 부분은 없는가?

CodeRabbit은 이 검토를 보조하는 PR Reviewer이며 사람의 최종 판단을 대체하지 않는다. Linear ↔ CodeRabbit 직접 연동이나 Slack `@CodeRabbit` 호출은 공식 Workflow의 필수 단계로 사용하지 않는다.

핵심 운영 원칙은 **"Slack에서 논의하고, 확정 내용은 GitHub docs/에 남기며, Linear와 GitHub Issues는 같은 작업을 동기화하고, GitHub PR로 구현과 변경 이력을 검토한다"**이다.

## Linear 상태 규칙

| Linear 상태 | 사용 시점 | GitHub Issue |
|---|---|---|
| `ToDo` | 이슈가 생성되었지만 실제 작업을 시작하지 않음 | Open |
| `In Progress` | 담당자가 Branch를 만들고 실제 작업을 시작함 | Open |
| `Done` | 연결된 PR이 `main`에 Squash Merge됨 | Closed |

`Backlog`, `Canceled`, `Duplicate`, `Approved`, `In Review`는 사용하지 않는다. 취소되거나 중복된 작업은 이슈 상태를 늘리는 대신 이슈 본문/댓글에 사유를 남기고 팀이 정한 정리 방법을 따른다.

일반 작업은 동기화된 Linear / GitHub Issue를 연결한다. 오타·주석·간단한 문서 수정 같은 Level 0 작업은 이슈 없이 PR을 만들 수 있다. DB 스키마, 인증, 결제, 운영 환경, 호환성을 깨는 API 변경은 구현 전에 사람이 설계를 검토하고 필요하면 ADR을 작성한다.

`DEV-123` 같은 키는 형식 예시다. 실제 작업에서는 현재 Linear 팀의 실제 이슈 키를 사용하며, 없는 이슈 번호를 만들어 붙이지 않는다.
