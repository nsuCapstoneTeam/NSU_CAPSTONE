# ADR-001: 아티스트 신뢰성 V2의 계산 구조와 초기 파라미터

- 상태: **Accepted**
- 결정일: **2026-09-30**
- 관련 요구사항: `TRUST-143~154`
- 관련 이슈: NSU-18, NSU-19, NSU-20, NSU-32, NSU-39, NSU-53
- 상세 설계: [아티스트 신뢰성 모델 V2](../architecture/artist-reliability-v2.md)

> 이 ADR의 수치는 **V2 초기 정책값**이다.  
> PeerTrust, Beta Reputation System 등의 연구에서 그대로 도출된 상수가 아니며, 실제 플랫폼 데이터가 쌓이면 모델 버전을 올려 재조정할 수 있다.

---

## 1. 맥락

우리 프로젝트는 행사 조건과 아티스트 작업물을 분석해 설명 가능한 추천 결과를 제공한다.

하지만 다음 정보는 서로 의미가 다르다.

- 음악 의미 유사도, BPM, 리듬, 예산, 지역, 일정: **해당 행사와 얼마나 잘 맞는가**
- 공연 완료, 귀책 취소, 노쇼, 응답, 검증 후기: **약속을 얼마나 안정적으로 이행했는가**
- 실명확인, 외부 계정 연결, 저작권·실연 증빙: **누구이며 어떤 자격·권리를 확인했는가**

이를 하나의 점수에 섞으면 다음 문제가 생긴다.

1. 음악적으로 잘 맞는 것과 실제 공연 이행 신뢰성이 혼동된다.
2. 인증을 많이 받은 사용자가 자동으로 높은 신뢰성 점수를 받을 수 있다.
3. 거래 1건과 30건에서 나온 같은 점수를 동일하게 해석하게 된다.
4. 신규 아티스트가 이력 부족만으로 저신뢰로 취급될 수 있다.
5. 노쇼 같은 사건이 점수와 별도 패널티에서 중복 감점될 수 있다.
6. 최종 점수만 저장하면 왜 그 점수가 나왔는지 설명하거나 재계산하기 어렵다.
7. Spring Boot와 AI/Matching 서버 사이의 책임 경계가 흐려진다.

Linear SSOT v1.3은 Artist Reliability V2에서 매칭 적합도, 검증 정보, 신뢰성 점수, 확신 수준, 위험 신호를 분리하도록 요구한다.

---

## 2. 결정 요약

Artist Reliability V2는 다음 구조를 사용한다.

```text
플랫폼 도메인 사건
        ↓
신뢰 증거
        ↓
증거 가중치
├── 최근성
├── 행사 맥락
└── 증거 검증 수준
        ↓
영역별 Beta Reputation
├── 공연 이행 신뢰성
├── 준비·일정 준수 신뢰성
├── 소통 신뢰성
└── 거래 평판 신뢰성
        ↓
종합 신뢰성
        ↓
신뢰성 점수 + 확신 수준 + 위험 신호 + 산출 근거
```

핵심 결정은 다음과 같다.

- Matching Score와 Artist Reliability를 분리한다.
- Verification과 Reliability를 분리한다.
- 최종 점수보다 신뢰 증거를 먼저 저장한다.
- 네 개의 신뢰성 영역을 독립적으로 계산한다.
- 영역별 계산은 Beta Reputation을 기본 모델로 사용한다.
- Beta 사전분포는 `Beta(1, 1)`을 사용한다.
- 최근성 반감기는 365일로 시작한다.
- 종합 신뢰성 초기 가중치는 `45 / 20 / 15 / 20`을 사용한다.
- 신뢰성 점수와 확신 수준을 분리한다.
- 위험 신호는 별도로 관리하고 같은 사건을 이중 감점하지 않는다.
- Artist Reliability의 기준 원본과 계산 책임은 Spring Boot 백엔드가 가진다.
- Ranking 보정 공식은 이번 ADR에서 확정하지 않는다.

## 3. 매칭 적합도와 아티스트 신뢰성을 분리한다

두 값은 서로 다른 질문에 답한다.

```text
매칭 적합도
= 특정 행사 조건에 이 아티스트가 얼마나 잘 맞는가?

아티스트 신뢰성
= 이 아티스트가 약속된 활동을 안정적으로 이행했다는 근거가 얼마나 있는가?
```

따라서 Matching Score 원본에 Artist Reliability를 합쳐 저장하지 않는다.

아래 항목은 Artist Reliability에 포함하지 않는다.

- CLAP 음악 의미 유사도
- 장르 적합도
- BPM 적합도
- 리듬 적합도
- 공연 스타일 적합도
- 예산 및 출연료 적합성
- 지역 및 이동 조건
- 일정 가용성
- 예상 관객 및 매출
- 음악 실력이나 인기도

Ranking에서 신뢰성을 활용할 필요가 있더라도 별도의 파생 값으로 계산한다.

---

## 4. 검증 정보와 신뢰성 점수를 분리한다

다음 정보는 **검증 정보(Verification)** 로 관리한다.

- 실명 본인확인
- 외부 아티스트 계정 연결
- 저작권 보유 증빙
- 실연 참여 증빙
- 공식 발매 또는 공연 활동 증빙

이 값들은 아티스트의 신원·자격·권리 확인 결과이지, 공연을 안정적으로 수행했다는 행동 이력이 아니다.

따라서 다음 방식은 사용하지 않는다.

```text
저작권 검증 완료 → 신뢰성 +20점
외부 계정 연결 → 신뢰성 +10점
```

---

## 5. 최종 점수보다 신뢰 증거를 먼저 저장한다

다음과 같은 플랫폼 사건을 **신뢰 증거**로 저장할 수 있는 구조를 둔다.

- 공연 정상 완료
- 아티스트 귀책 취소
- 노쇼
- 사전 일정 확인
- 체크인 또는 현장 도착 확인
- 오퍼 기한 내 응답
- 늦은 응답
- 오퍼 무응답 만료
- 검증된 거래 후기

신뢰 증거는 가능한 경우 원본 Event / Offer / 향후 Booking·공연 데이터까지 추적 가능해야 한다.

### 5.1 귀책 주체

취소와 실패 사건은 최소 다음 귀책 주체를 구분한다.

- `ARTIST`
- `EVENT_PARTNER`
- `MUTUAL`
- `FORCE_MAJEURE`
- `PLATFORM`
- `OTHER`

아티스트 귀책이 아닌 사건은 아티스트의 자동 부정 근거로 계산하지 않는다.

---

## 6. 네 개의 신뢰성 영역

Artist Reliability는 다음 네 영역을 독립적으로 계산한다.

| 영역 | 의미 | 주요 근거 |
| --- | --- | --- |
| 공연 이행 신뢰성 | 실제 공연을 정상적으로 완료했는가 | 공연 완료, 아티스트 귀책 취소, 노쇼 |
| 준비·일정 준수 신뢰성 | 공연 전 합의된 절차와 시간을 지켰는가 | 사전 확인, 준비 절차, 체크인, 시간 준수 |
| 소통 신뢰성 | 필요한 요청에 안정적으로 응답했는가 | 기한 내 응답, 늦은 응답, 무응답 만료 |
| 거래 평판 신뢰성 | 검증된 실제 거래 상대의 평판이 어떠한가 | 실제 거래와 연결된 검증 후기 |

각 영역 점수는 별도로 보존하고, 종합 신뢰성을 계산할 때 초기 가중치를 적용한다.

---

## 7. Beta Reputation 기반 영역별 계산

### 7.1 초기 사전분포

V2 초기 사전분포는 다음과 같이 확정한다.

```text
α0 = 1
β0 = 1
```

즉 신규 아티스트의 사전분포는:

```text
Beta(1, 1)
```

이다.

아무 증거가 없을 때 내부 posterior mean은 0.5이지만, 사용자 화면에서 이를 곧바로 "신뢰성 50점"으로 노출한다는 의미는 아니다.

신규 아티스트의 사용자 표현은 **데이터 부족 / 낮은 확신**을 우선한다.

### 7.2 영역별 계산식

각 신뢰성 영역 `d`에서:

```text
S_d = Σ(w_e × x_e)
F_d = Σ(w_e × (1 - x_e))

α_d = 1 + S_d
β_d = 1 + F_d

R_d = 100 × α_d / (α_d + β_d)
```

여기서:

- `x_e = 1.0`: 성공
- `x_e = 0.0`: 실패
- `0 < x_e < 1`: 부분 성공
- `w_e`: 해당 신뢰 증거의 최종 가중치

공연 정상 완료는 성공 근거로, 아티스트 귀책 취소와 노쇼는 실패 근거로 처리한다.

부분 성공을 사용하는 구체 사건과 값은 해당 도메인 정책에서 별도로 정의할 수 있다.

## 8. 신뢰 증거 가중치

각 신뢰 증거의 최종 가중치는 다음 구조를 사용한다.

```text
w_e
= w_time
× w_context
× w_verification
```

### 8.1 최근성 가중치

최근 행동을 오래된 행동보다 더 크게 반영하기 위해 반감기 방식을 사용한다.

```text
w_time = 2 ^ (-d / 365)
```

- `d`: 사건 발생 후 경과 일수
- 초기 반감기: **365일**

예:

| 경과 시간 | 최근성 가중치 |
| --- | ---: |
| 현재 | 1.00 |
| 약 6개월 | 약 0.71 |
| 1년 | 0.50 |
| 2년 | 0.25 |

365일은 학술 논문에서 고정적으로 제시한 값이 아니라 **우리 프로젝트의 V2 초기 정책값**이다.

### 8.2 행사 맥락 가중치

모든 공연을 완전히 동일한 중요도로 취급하지 않기 위해 초기 맥락 등급을 다음과 같이 둔다.

| 행사 맥락 | 코드 예시 | 초기 가중치 |
| --- | --- | ---: |
| 일반 | `NORMAL` | **1.0** |
| 중요 | `IMPORTANT` | **1.2** |
| 핵심 | `CRITICAL` | **1.4** |

행사를 어느 등급으로 분류할지에 대한 세부 판정 규칙은 구현 정책에서 별도로 정의한다.

### 8.3 증거 검증 가중치

증거가 어떤 방식으로 확인되었는지에 따라 초기 가중치를 다음과 같이 둔다.

| 증거 검증 수준 | 예시 | 초기 가중치 |
| --- | --- | ---: |
| 플랫폼 자동 근거 | 상태 머신, 시스템 기록 | **1.0** |
| 양측 확인 근거 | 아티스트와 행사 관계자 모두 확인 | **0.9** |
| 단일 사용자 근거 | 한쪽 사용자만 제공한 정보 | **0.6** |

단일 사용자 근거라고 해서 항상 계산에 포함하는 것은 아니다.

먼저 해당 증거의 검증 상태가 **계산 포함 가능**으로 판단된 경우에만 이 가중치를 적용한다. 일방 주장만으로 강한 부정 신호를 자동 생성하지 않는다.

## 9. 종합 신뢰성 초기 가중치

V2의 종합 신뢰성 초기 가중치는 다음과 같이 확정한다.

| 영역 | 초기 가중치 |
| --- | ---: |
| 공연 이행 신뢰성 | **45%** |
| 준비·일정 준수 신뢰성 | **20%** |
| 소통 신뢰성 | **15%** |
| 거래 평판 신뢰성 | **20%** |

따라서 초기 종합 신뢰성은:

```text
R_raw
= 0.45 × R_performance
+ 0.20 × R_schedule
+ 0.15 × R_communication
+ 0.20 × R_reputation
```

으로 계산한다.

이 가중치는 논문에서 직접 도출된 값이 아니라 **객관적인 공연 이행 근거를 주관적인 평판보다 더 크게 반영하기 위한 V2 초기 제품 정책**이다.

실제 거래 데이터가 쌓이면 모델 검증을 거쳐 변경할 수 있다.

## 10. 확신 수준

신뢰성 점수와 데이터의 충분성은 별도로 관리한다.

### 10.1 유효 증거량

초기 구현에서 유효 증거량은 계산에 포함된 증거 가중치의 합으로 정의한다.

```text
N_eff = Σ(w_e)
```

### 10.2 확신 계수

초기 확신 계수는 다음과 같이 확정한다.

```text
C = N_eff / (N_eff + 5)
```

즉:

```text
K = 5
```

를 사용한다.

### 10.3 사용자 표시 구간

| 확신 계수 | 표시 |
| --- | --- |
| `0.00 <= C < 0.40` | **낮음** |
| `0.40 <= C < 0.70` | **보통** |
| `0.70 <= C <= 1.00` | **높음** |

예:

```text
신뢰성 점수: 88점
확신 수준: 높음
```

처럼 점수와 확신 수준을 함께 제공한다.

이 확신 공식과 임계값 역시 V2 초기 정책값이며, 향후에는 Beta posterior의 분산 또는 신뢰구간 폭을 이용한 방식과 비교할 수 있다.

## 11. 콜드 스타트

신규 아티스트는 플랫폼 이력이 없다는 이유만으로 저신뢰 아티스트로 처리하지 않는다.

`Beta(1, 1)` 사전분포 때문에 내부 기대값은 중립값 50이지만, 사용자에게 단순히 "신뢰성 50점"으로 보여주는 것은 데이터 부족과 낮은 성과를 혼동시킬 수 있다.

따라서 신규 아티스트는 다음 정보를 우선 표현한다.

```text
신뢰성 데이터: 부족
확신 수준: 낮음
플랫폼 공연 이력: 0건
```

본인확인이나 권리 검증 결과는 별도 Verification 정보로 함께 보여줄 수 있지만 신뢰성 점수의 가산점으로 사용하지 않는다.

---

## 12. 위험 신호

위험 신호는 신뢰성 점수와 별도로 관리한다.

초기 후보:

- 최근 노쇼
- 반복 아티스트 귀책 취소
- 반복 지각
- 반복 무응답
- 평판 조작 의심
- 계정 제재

중요한 원칙은 **이중 감점 금지**다.

예:

```text
노쇼 1건
→ 공연 이행 실패 근거로 반영
→ 위험 신호로 설명 가능
→ 별도 -30점 같은 고정 추가 감점은 하지 않음
```

위험 신호의 발생 임계값과 사용자 노출 방식은 이 ADR에서 확정하지 않는다.

---

## 13. Ranking 보정은 이번 ADR에서 확정하지 않는다

이전 검토에서 다음과 같은 신뢰성 랭킹 조정식이 후보로 논의된 적이 있다.

```text
50 + C × (R_raw - 50)
```

그러나 Beta 사전분포 자체가 적은 증거를 중립값 쪽으로 수축시키기 때문에, 확신 계수를 다시 곱하면 **증거량을 이중으로 반영할 가능성**이 있다.

따라서 위 식은 V2 공식 파라미터로 채택하지 않는다.

현재 결정은 다음과 같다.

- Matching Score와 Artist Reliability는 독립적으로 계산한다.
- Artist Reliability 원본을 Matching Score에 합쳐 저장하지 않는다.
- 랭킹 보정이 필요하면 별도의 파생 값으로 설계한다.
- 구체적인 보정 공식과 적용 범위는 별도 Human Decision에서 정한다.

---

## 14. Spring Boot와 AI/Matching 서버의 책임 경계

Artist Reliability의 기준 원본과 계산 책임은 **Spring Boot 백엔드**가 가진다.

### Spring Boot 백엔드

- Event / Offer / 사용자 / 검증 정보 관리
- 도메인 상태 변경
- 신뢰 증거 생성과 저장
- 귀책 주체 관리
- 증거 검증 상태 관리
- 신뢰성 계산
- 확신 수준 계산
- 위험 신호 판정
- 신뢰성 설명 근거 제공

### AI/Matching 서버

- CLAP 기반 음악 의미 유사도
- 음악 임베딩
- 오디오 특징 추출
- 음악/BPM/리듬 등 매칭 계산

AI/Matching 서버는 공연 완료, 취소, 노쇼, 응답 이력의 기준 원본을 소유하지 않으므로 Artist Reliability를 계산하지 않는다.

---

## 15. 현재 MVP와 후속 활성화 범위

### 현재 MVP에서 확정할 것

- 매칭 적합도와 Artist Reliability 분리
- Verification과 Reliability 분리
- 신뢰 증거 데이터 모델
- 신뢰성 계산 인터페이스
- V2 초기 계산 파라미터
- 신규 아티스트 데이터 부족 상태
- 추천 응답에서 적합 정보와 신뢰 정보 분리

### 거래·공연 기능 이후 실제 활성화

- 공연 정상 완료 근거
- 아티스트 귀책 취소
- 노쇼
- 공연 전 체크인
- 실제 거래 이력 기반 계산
- 검증된 거래 후기

현재 MVP에서 해당 사건이 발생하지 않는다면 파라미터는 확정하되 실제 점수 산출을 억지로 생성하지 않는다.

## 17. 아직 결정하지 않은 사항

다음 항목은 이 ADR의 승인 범위에 포함하지 않는다.

- 행사 맥락을 `NORMAL / IMPORTANT / CRITICAL`로 분류하는 세부 판정 규칙
- 부분 성공을 사용할 구체 사건과 각 `x_e` 값
- 위험 신호별 발생 임계값
- 위험 신호 사용자 노출 정책
- Artist Reliability의 Ranking 보정 여부와 공식
- 신규 아티스트의 최종 API/UI 표시 형식
- EVENT_PARTNER 신뢰성 세부 모델
- 실제 데이터 기반 파라미터 재학습·재조정 방법

## 18. 고려했지만 선택하지 않은 방식

### 18.1 단순 별점 평균

선택하지 않는다.

거래 횟수, 객관적 이행 여부, 데이터 충분성을 제대로 표현하기 어렵고 리뷰 조작에도 취약하다.

### 18.2 검증 완료에 고정 점수 부여

선택하지 않는다.

검증은 신원·자격·권리 확인이며 공연 이행 신뢰성과는 다른 개념이다.

### 18.3 Matching Score에 Reliability를 직접 합산

선택하지 않는다.

음악적 적합성과 운영 신뢰성은 별도 의사결정 축이다.

### 18.4 신규 아티스트를 0점 처리

선택하지 않는다.

데이터 부족과 부정적인 행동 이력을 구분해야 한다.

### 18.5 위험 사건별 고정 이중 패널티

선택하지 않는다.

동일 사건이 Beta 증거와 추가 감점에 동시에 들어가면 점수가 왜곡된다.

### 18.6 상시 위치 추적

V2 범위에서 선택하지 않는다.

필요한 경우 특정 시점의 동의 기반 체크인 정도를 후속 기능으로 검토한다.

### 18.7 EigenTrust 전체 그래프 및 GNN 기반 조작 탐지

V2 범위에서 선택하지 않는다.

졸업작품 규모와 현재 데이터량을 고려하면 초기 구현 비용이 크다.

---

## 19. 결과와 트레이드오프

### 장점

- 매칭 결과와 신뢰 결과의 의미가 명확하다.
- 검증 완료를 임의 점수로 바꾸지 않는다.
- 신규 아티스트의 콜드 스타트 불이익을 줄인다.
- 점수와 데이터 충분성을 분리해 보여줄 수 있다.
- 최종 결과의 원시 근거를 추적할 수 있다.
- 계산식을 변경해도 과거 증거로 재계산할 수 있다.
- Spring Boot와 AI/Matching 서버의 책임이 명확하다.

### 비용

- 단일 `reliability_score` 컬럼보다 데이터 모델이 복잡하다.
- 신뢰 증거 생성의 멱등성과 원본 추적이 필요하다.
- 귀책 주체와 검증 상태를 관리해야 한다.
- 계산 정책 버전을 관리해야 한다.
- 현재는 실제 거래 데이터가 부족하므로 초기 파라미터를 경험적으로 검증할 수 없다.

이 복잡도는 **설명 가능성, 재계산 가능성, 콜드 스타트 완화**를 위해 감수하는 비용으로 본다.

---

## 20. 검증 시나리오

구현 시 최소 다음 시나리오를 테스트한다.

1. 공연 정상 완료가 공연 이행 긍정 증거로 반영된다.
2. 행사 관계자 귀책 취소는 아티스트 부정 증거로 반영되지 않는다.
3. 아티스트 귀책 취소는 공연 이행 실패 증거로 반영된다.
4. 노쇼는 실패 증거와 위험 신호 후보가 되지만 이중 감점되지 않는다.
5. 1년 전 증거의 최근성 가중치는 0.5가 된다.
6. 동일 조건에서 `CRITICAL` 행사는 `NORMAL` 행사보다 더 큰 증거 가중치를 가진다.
7. 플랫폼 자동 근거가 단일 사용자 근거보다 높은 검증 가중치를 가진다.
8. 신규 아티스트의 내부 사전분포는 `Beta(1, 1)`이지만 사용자에게 저신뢰로 단정하지 않는다.
9. 신뢰성 점수와 확신 수준을 독립적으로 조회할 수 있다.
10. 동일 도메인 사건이 중복 신뢰 증거를 생성하지 않는다.
11. Matching Score 없이도 Artist Reliability를 독립적으로 계산할 수 있다.
12. Artist Reliability가 없어도 Matching Score 자체는 독립적으로 유지된다.
13. 점수 결과에서 사용된 원본 신뢰 증거를 추적할 수 있다.
14. 정책 파라미터가 변경되어도 원본 증거를 사용해 새 버전으로 재계산할 수 있다.

## 21. 근거

설계의 학술적 배경은 다음 연구를 참고한다.

- **PeerTrust** — 거래 횟수, 평가자 신뢰성, 거래 맥락, 시간 적응성
- **The Beta Reputation System** — 성공/실패 증거의 확률적 누적, 망각 개념
- **EigenTrust** — 평가자 신뢰성과 공모 공격에 대한 확장 관점
- **Survey of Attack and Defense Techniques for Reputation Systems** — 평판 시스템 공격·방어
- **Reputation Meta-analysis** — 온라인 시장에서 평판 정보와 거래 행동의 관계
- **Monitoring and Cold Start in Digital Platforms** — 신규 참여자의 이력 부족과 콜드 스타트 문제

이 연구들은 모델의 방향을 뒷받침하지만, 이 ADR의 `45/20/15/20`, 365일, `1.0/1.2/1.4`, `1.0/0.9/0.6`, `K=5` 같은 값 자체를 제시한 것은 아니다.

해당 값들은 우리 프로젝트의 **V2 초기 정책값**이다.

선행특허 조사는 추천과 운영 가능성, 지각·노쇼 등 실제 운영 지표의 중요성을 이해하기 위한 참고 자료로 사용했다.

이 ADR은 특허 권리범위나 침해 여부에 대한 법률 판단을 포함하지 않는다.
