# ADR-001: 아티스트 신뢰성 V2의 계산 구조와 책임 경계

- 상태: **Proposed**
- 날짜: 2026-09-30
- 관련 요구사항: `TRUST-143~154`
- 관련 이슈: NSU-18, NSU-19, NSU-20, NSU-32, NSU-39, NSU-53
- 상세 설계: [아티스트 신뢰성 모델 V2](../architecture/artist-reliability-v2.md)

## 1. 맥락

프로젝트는 행사 조건과 아티스트 작업물을 비교하여 설명 가능한 추천 결과를 제공한다.

기존 Trust Signal 설계는 실명 확인, 권리 증빙, 공연 완료, 취소, 노쇼 등 서로 성격이 다른 정보를 한 범주에서 다룰 가능성이 있었다. 이 상태로 구현하면 다음 문제가 생긴다.

1. 음악적으로 잘 맞는 것과 실제 공연을 안정적으로 수행하는 것이 같은 점수로 섞일 수 있다.
2. 본인확인이나 저작권 검증을 완료했다는 사실이 공연 이행 신뢰성과 혼동될 수 있다.
3. 별점 평균만으로는 거래 횟수와 데이터 부족을 설명하기 어렵다.
4. 신규 아티스트는 이력이 없다는 이유만으로 불리해질 수 있다.
5. 노쇼 같은 사건을 점수와 별도 패널티에서 중복 감점할 수 있다.
6. 최종 점수만 저장하면 점수의 근거를 나중에 설명하거나 재계산하기 어렵다.
7. Spring Boot와 AI/Matching 서버 사이의 책임 경계가 불명확해질 수 있다.

Linear SSOT v1.3은 Artist Reliability V2에서 매칭 적합도, 검증 정보, 신뢰성 점수, 확신 수준, 위험 신호를 분리하도록 요구한다.

---

## 2. 결정

### 2.1 매칭 적합도와 아티스트 신뢰성을 분리한다

다음 두 값은 독립적인 개념과 데이터로 관리한다.

```text
매칭 적합도
= 특정 행사 조건과 아티스트의 적합성

아티스트 신뢰성
= 플랫폼 활동을 안정적으로 이행했다는 근거
```

Matching Score 원본에 Artist Reliability를 합쳐 저장하지 않는다.

랭킹에 신뢰성 보정이 필요할 경우에도 별도의 파생 값으로 계산한다. 보정 공식과 적용 여부는 별도 Human Decision이 있기 전까지 확정하지 않는다.

### 2.2 검증 정보와 신뢰성 점수를 분리한다

실명확인, 외부 계정 연결, 저작권·실연·공식 활동 증빙은 Verification으로 관리한다.

이 정보는 Artist Reliability Score의 직접 가산점으로 사용하지 않는다.

### 2.3 최종 점수보다 신뢰 증거를 먼저 저장한다

공연 완료, 귀책 취소, 노쇼, 응답, 체크인, 검증 후기 등 플랫폼 사건을 **신뢰 증거**로 저장할 수 있는 구조를 둔다.

신뢰 증거는 가능한 경우 원본 Event / Offer / 향후 Booking·공연 데이터까지 추적 가능해야 한다.

### 2.4 신뢰성을 네 영역으로 분리한다

아티스트 신뢰성은 다음 네 영역을 독립적으로 표현한다.

1. 공연 이행 신뢰성
2. 준비·일정 준수 신뢰성
3. 소통 신뢰성
4. 거래 평판 신뢰성

최종 종합 신뢰성을 제공할 수 있지만, 영역별 점수도 함께 보존한다.

### 2.5 Beta Reputation을 확률 계산의 기본 기술안으로 사용한다

성공/실패/부분 성공 증거를 누적하는 기본 계산 구조로 Beta Reputation을 사용한다.

개념식은 다음과 같다.

```text
S = Σ(w × 성공 정도)
F = Σ(w × 실패 정도)

α = α0 + S
β = β0 + F

신뢰성 = α / (α + β)
```

다만 `α0`, `β0`, 영역별 가중치, 시간 감쇠 반감기 등 실제 파라미터는 이 ADR에서 확정하지 않는다.

### 2.6 신뢰성 점수와 확신 수준을 분리한다

같은 신뢰성 점수라도 증거가 1건인 경우와 30건인 경우를 동일하게 해석하지 않는다.

신뢰성 결과에는 최소 다음을 분리한다.

- 신뢰성 점수
- 확신 수준
- 위험 신호
- 산출 근거

신규 아티스트는 이력이 없다는 이유만으로 0점 또는 저신뢰 상태로 처리하지 않는다.

### 2.7 위험 신호를 별도 관리한다

노쇼, 반복 귀책 취소, 반복 지각, 반복 무응답, 평판 조작 의심 등은 별도 위험 신호로 관리한다.

이미 신뢰성 계산에 반영된 동일 사건에 대해 별도의 고정 감점을 다시 적용하지 않는다.

### 2.8 Artist Reliability의 기준 원본과 계산 책임은 Spring Boot 백엔드가 가진다

Spring Boot 백엔드는 Event, Offer, 사용자, 검증 정보와 플랫폼 상태 변경을 소유한다.

따라서 다음 책임을 Spring Boot 백엔드에 둔다.

- 신뢰 증거 생성과 저장
- 귀책 주체 관리
- 신뢰성 계산
- 확신 수준 계산
- 위험 신호 판정
- 신뢰성 설명 근거 제공

AI/Matching 서버는 음악 임베딩과 오디오 특징 기반 매칭 계산을 담당하며 Artist Reliability의 기준 원본을 계산하지 않는다.

### 2.9 현재 MVP와 실제 이력 기반 계산 활성화를 분리한다

현재 MVP에서는 다음을 우선 확정한다.

- 데이터 모델
- 인터페이스
- 매칭/검증/신뢰성 경계
- 신규 아티스트 데이터 부족 표현

실제 공연 완료, 취소, 노쇼, 체크인, 검증 거래 후기 기반 계산은 관련 거래·공연 기능 도입 후 활성화한다.

---

## 3. 결정하지 않은 사항

다음 항목은 이 ADR의 승인 대상에서 제외한다.

- 네 신뢰성 영역의 최종 가중치
- Beta 사전분포 파라미터
- 시간 감쇠 반감기
- 행사 중요도 가중치
- 증거 검증 수준별 가중치
- 확신 수준 최종 계산식
- 낮음/보통/높음 표시 임계값
- 위험 신호별 임계값
- 위험 신호 사용자 노출 정책
- Artist Reliability의 랭킹 보정 여부와 공식
- EVENT_PARTNER 신뢰성 세부 모델

이 값들은 실제 데이터, 사용자 표현 방식, 랭킹 정책을 추가로 검토한 뒤 별도 결정한다.

## 4. 결과

### 긍정적 결과

- 매칭 결과와 신뢰 결과의 의미가 명확해진다.
- 검증 완료 여부를 임의 점수로 환산하지 않게 된다.
- 신규 아티스트의 콜드 스타트 불이익을 줄일 수 있다.
- 최종 점수의 근거를 사용자에게 설명할 수 있다.
- 계산식을 변경해도 과거 증거로 재계산할 수 있다.
- 노쇼·취소 등 운영 데이터를 장기적으로 추천 품질 개선에 사용할 수 있다.
- AI 서버와 Spring Boot의 책임이 분명해진다.

### 비용과 복잡도

- 단일 `reliability_score` 컬럼보다 데이터 모델이 복잡해진다.
- 도메인 사건에서 신뢰 증거를 안정적으로 생성해야 한다.
- 귀책 주체와 증거 검증 상태를 관리해야 한다.
- 계산 버전과 파라미터 변경을 추적해야 한다.
- 실제 데이터가 쌓이기 전까지 신뢰성 모델을 충분히 검증하기 어렵다.

이 복잡도는 신뢰성 결과를 설명하고 재계산할 수 있게 하기 위한 의도적인 비용으로 본다.

## 5. 고려했지만 선택하지 않은 방식

### 5.1 단순 별점 평균

**선택하지 않는다.**

이유:

- 실제 거래 이행과 주관적 만족도를 구분하기 어렵다.
- 거래 1건과 30건의 차이를 제대로 표현하지 못한다.
- 리뷰 조작에 취약하다.

### 5.2 검증 완료 항목에 고정 보너스 부여

예:

```text
저작권 인증 +20
외부 계정 연결 +10
```

**선택하지 않는다.**

검증은 신원·자격·권리 확인이고 공연 이행 신뢰성과는 다른 개념이다.

### 5.3 Matching Score에 신뢰성 점수를 바로 합산

**선택하지 않는다.**

음악적으로 잘 맞는지와 안정적으로 공연할 근거가 있는지는 별도의 판단 축이다.

### 5.4 신규 아티스트를 0점 처리

**선택하지 않는다.**

데이터 부족을 부정적인 행동 이력으로 해석하면 콜드 스타트 편향이 발생한다.

### 5.5 위험 사건별 고정 이중 패널티

예:

```text
노쇼 → 실패 근거 반영
     → 추가 -30점
```

**선택하지 않는다.**

같은 사건을 두 번 감점하면 설명 가능성이 떨어지고 점수 왜곡이 커진다.

### 5.6 상시 위치 추적

**V2 범위에서 선택하지 않는다.**

행사 준비 확인이 필요하면 특정 시점의 동의 기반 체크인 정도를 후속 기능으로 검토한다.

### 5.7 EigenTrust 전체 그래프와 GNN 기반 조작 탐지

**V2 범위에서 선택하지 않는다.**

현재 졸업작품 규모에서는 구현 비용이 크며, 실제 거래 데이터가 충분히 쌓인 뒤 확장하는 편이 적절하다.

## 6. 구현 가이드

이 ADR이 승인되면 Spring 구현에서 다음 구조를 우선 검토한다.

```text
도메인 상태 변경
    ↓
신뢰 증거 생성
    ↓
신뢰 증거 저장
    ↓
신뢰성 계산
    ├── 공연 이행
    ├── 준비·일정
    ├── 소통
    └── 거래 평판
    ↓
신뢰성 스냅샷
    ├── 점수
    ├── 확신 수준
    ├── 위험 신호
    └── 산출 근거
```

구체적인 Entity, Table, DTO, 패키지 구조는 구현 이슈에서 확정한다.

## 7. 검증 방법

이 설계는 구현 시 다음 시나리오를 테스트할 수 있어야 한다.

1. 공연 정상 완료가 긍정 증거로 반영된다.
2. 행사 관계자 귀책 취소가 아티스트 부정 증거로 반영되지 않는다.
3. 아티스트 귀책 취소가 공연 이행 부정 증거로 반영된다.
4. 노쇼가 부정 증거와 위험 신호 후보로 표시되지만 이중 감점되지 않는다.
5. 신규 아티스트가 0점으로 표시되지 않는다.
6. 동일 도메인 사건이 중복 증거를 생성하지 않는다.
7. Matching Score를 계산하지 않아도 Artist Reliability를 독립적으로 조회할 수 있다.
8. Artist Reliability가 없어도 Matching Score 자체는 독립적으로 유지된다.
9. 점수 결과에서 사용된 원본 신뢰 증거를 추적할 수 있다.
10. 계산 파라미터가 바뀌었을 때 원본 증거를 이용해 재계산할 수 있다.

---

## 8. 근거

설계의 학술적 배경은 다음 연구를 참고한다.

- PeerTrust — 거래 횟수, 평가자 신뢰성, 거래 맥락
- The Beta Reputation System — 성공/실패 증거의 확률적 누적
- EigenTrust — 평가자 신뢰와 공모 공격에 대한 확장 관점
- Survey of Attack and Defense Techniques for Reputation Systems — 평판 시스템 공격·방어
- Reputation Meta-analysis — 온라인 시장에서 평판의 실증적 효과
- Monitoring and Cold Start in Digital Platforms — 신규 참여자의 콜드 스타트 문제

선행특허 조사는 추천과 운영 가능성, 지각·노쇼 등 실제 운영 지표의 중요성을 이해하는 참고 자료로 사용했다.

이 ADR은 특허 권리범위나 침해 여부에 대한 법률 판단을 포함하지 않는다.

## 9. 승인 시 후속 작업

- NSU-20: 계산 모델과 파라미터 설계 구체화
- NSU-32: 신뢰 증거 사건 입력 계약 구체화
- NSU-53: Spring 데이터 모델 및 응답 계약 설계
- NSU-39: 세부 신뢰 요소와 데이터 출처 정리
- 구현 이슈: 신뢰 증거 저장, 계산 엔진, 조회 API를 필요한 단위로 분리

PR 리뷰에서 이 ADR을 승인하면 상태를 `Accepted`로 변경한다.
