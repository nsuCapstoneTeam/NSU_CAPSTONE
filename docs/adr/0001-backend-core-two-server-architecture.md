# ADR-0001: Backend Core 2-서버 아키텍처

## 상태

Accepted

## 컨텍스트

아티스트-행사 매칭 플랫폼은 성격이 다른 두 종류의 작업을 동시에 요구한다.

- **전통적 웹 백엔드**: 사용자 인증(JWT), 도메인 CRUD, 파일 업로드, 트랜잭션·권한 관리 등
  안정적인 상태 관리와 일관성이 중요한 작업.
- **ML 추론**: CLAP 기반 오디오 임베딩 생성, 장르·분위기·에너지 분류, 코사인 유사도·매칭 점수
  계산 등 CPU/GPU 집약적이고 파이썬 생태계(PyTorch·transformers)에 의존하는 작업.

이 둘을 하나의 서버·하나의 언어로 묶으면 무거운 ML 라이브러리가 웹 프로세스에 얹혀 메모리·기동
시간이 폭증하고, 느린 추론이 API 응답 지연으로 직결되며, 자바에서 CLAP 계열 모델을 다루기도
어렵다. 벡터를 어디에 저장할지, 서버 간 통신을 무엇으로 할지, 임베딩을 동기로 처리할지도 함께
결정해야 한다.

## 결정

Backend Core를 **책임에 따라 두 서버로 분리**한다.

1. **Spring Boot 코어 서버** — 유일한 외부 진입점. JWT 인증, 도메인 CRUD, 파일 업로드→Object
   Storage, 하드 필터(SQL), 오케스트레이션, RDB+벡터 정본 영속화를 담당한다. 상태를 가진다.
2. **Python AI 매칭 서버** — 외부 비노출, 내부 네트워크 전용. CLAP 임베딩·분류·유사도 계산을
   담당하는 **무상태(stateless) 순수 추론기**. 어떤 정본 데이터도 보관하지 않는다.

부속 결정은 다음과 같다.

- **정본은 PostgreSQL에만** 둔다. Python은 무상태 → 수평 확장·재기동 자유.
- **벡터 저장소는 PostgreSQL + pgvector** (MVP).
- **오디오 임베딩은 비동기** 처리(`202 Accepted` + `PENDING`/`READY`/`FAILED`, MVP는 Spring `@Async`).
- **매칭은 2단계**: Spring/SQL 하드 필터로 후보 축소 → Python에서 소프트 매칭(유사도+가중 점수).
- **서버 간 통신은 REST/JSON**, 내부 네트워크 전용, 공유 시크릿 헤더 또는 mTLS 인증.
- **각 임베딩에 `modelVersion`** 을 저장해 버전 관리·재임베딩을 가능케 한다.

## 근거

- **관심사 분리**: 웹/도메인 로직과 ML 추론의 배포·확장·장애 특성이 완전히 다르므로 경계를
  나누면 각각을 독립적으로 최적화·확장할 수 있다.
- **무상태 추론기**: Python이 상태를 갖지 않으므로 부하가 몰리는 추론 계층만 자유롭게 스케일
  아웃하고, 언제든 재기동해도 데이터 정합성 문제가 없다.
- **생태계 적합성**: CLAP은 PyTorch·transformers 생태계에 있어 Python이 자연스럽고, 도메인/트랜잭션은
  Spring 생태계가 강하다.
- **담당 경계 정렬**: 서버 경계가 담당자(Seokyun / JinSol) 경계와 일치해 병렬 개발이 쉽다.

## 대안 및 기각 사유

| 대안 | 기각 사유 |
|---|---|
| **FAISS** (벡터 저장) | 라이브러리일 뿐 영속 저장소가 아니어서 정합성·영속성을 직접 구현해야 하고 정본과 이원화된다. MVP엔 과함 |
| **전용 벡터 DB** (Pinecone/Milvus 등) | 인프라·비용·운영 대상이 늘고 정본과 분리된다. MVP 규모엔 오버스펙 |
| **gRPC** (서버 간 통신) | 스키마·코드 생성·운영 복잡도 대비 이득이 적다. 내부 REST/JSON으로 충분. 초고성능 스트리밍 요구 시 재검토 |
| **동기 업로드** | CLAP 추론이 느려 사용자 대기·타임아웃·처리량 저하를 유발한다. 비동기 접수(`202`)로 대체 |
| **Python을 상태 저장소로 사용** | 무상태 원칙이 깨져 확장·재기동 자유가 사라지고 정본이 이원화된다 |

## 결과

**장점**

- 웹/도메인과 ML 추론을 독립적으로 개발·배포·확장할 수 있다.
- Python 추론 계층을 무상태로 유지해 수평 확장과 무중단 재기동이 쉽다.
- 정본이 PostgreSQL 한 곳에 모여 정합성 관리가 단순하다.
- pgvector로 하드 필터(SQL)와 벡터 검색을 한 트랜잭션에서 결합할 수 있다.

**트레이드오프**

- 서버가 둘로 나뉘어 네트워크 홉·배포 단위·관찰(로깅/추적) 복잡도가 늘어난다.
  → Resilience4j(timeout/retry/circuit-breaker)와 correlation-id 전파로 완화한다.
- 비동기 임베딩으로 인해 트랙이 `READY`가 되기 전까지 매칭에 쓸 수 없는 지연이 존재한다.
  → 상태(`PENDING`/`READY`/`FAILED`) 노출로 UX를 관리한다.
- pgvector는 초대규모에서 전용 엔진보다 성능 한계가 있다. → 규모 확대 시 인덱스(ivfflat/hnsw)
  도입, 그 이후 전용 벡터 DB 재검토.
