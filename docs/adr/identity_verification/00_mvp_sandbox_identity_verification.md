# ADR: MVP의 실명 본인확인은 테스트 채널로 한다

- 상태: **Proposed** (PR 리뷰에서 확정)
- 결정일: **2026-11-05** (사용자 결정)
- 관련: NSU-105(본인확인), NSU-127(PRIVATE 행사 열람 판정), NSU-128(댓글), NSU-129(시연 준비), NSU-89(곡 업로드·등록 정보 제출), [music_upload/01 곡 권리 검증](../music_upload/01_music_rights_verification.md), ADR `music_upload/02` §7 곡 업로드 자격(PR #186), [01 Trust Profile §4.3](../../api/01_trust_profile.md#43-verifications), [03 행사 API §4](../../api/03_events.md#4-열람-권한), SSOT `EVT-043`·`EVT-044`·`CMT-045`·`ART-027`·`AI-031`. 이 ADR이 기대는 SSOT 초안(v1.18, 팀 확인 전): ② `RIGHTS-024`·`ART-027` 간접 조건, ③ `TRUST-142` 실명 본인확인 표시, ④ `AUTH-009` 시연 예외, ⑤ `AUTH-006` 약관 동의 시점·시연 약관, `RIGHTS-023` 업로드 곡 조건

---

## Decision

**MVP는 실제 사용자의 실명을 확인하지 않는다.** 국내 본인확인기관(NICE 등)과 직접 계약하려면 사업자등록증이 필요한데, 팀에는 사업자등록이 없다. 대신 PortOne V2와 NHN KCP 테스트 채널, Mock 제공자로 운영과 같은 흐름을 구현하고, 시연 환경 전체에 테스트임을 알리는 배너를 띄운다. 시연 서버는 외부 가입을 받되, 공개되는 내용을 쓰는 기능은 팀 계정만 쓴다.

### 본인확인

| 항목 | 결정 |
|---|---|
| 본인확인 제공자 | 인터페이스 뒤에 Mock과 PortOne 테스트 연동(NHN KCP 테스트 채널)을 둔다(NSU-105). 운영 제공자는 실계약 뒤에 추가한다 |
| 제공자 설정 | 지금 만드는 환경은 시연(`DEMO`) 하나뿐이다. 운영(`PRODUCTION`) 환경은 이 ADR 범위 밖이다(아래 "운영 단계"). 제공자와 환경 설정에는 기본값이 없고, 둘 중 하나라도 없거나 환경이 `DEMO`가 아니면 서버가 시작하지 않는다(fail-closed). 서버 설정으로 고를 수 있는 제공자는 PortOne 테스트 연동 하나다. Mock은 설정 값이 아니라 자동화 테스트와 시드 스크립트가 코드로만 쓴다. 그래서 시연 중 KCP 창이 열리지 않아도 설정을 `MOCK`으로 바꿔 HTTP 본인확인을 Mock으로 돌릴 수 없고, 그런 값이면 서버가 시작하지 않는다. 예비 경로는 시드로 미리 만든 본인확인 계정이다 |
| 출처 결정 | 서버가 PortOne 재조회 응답의 `channel`로 출처를 정한다. 클라이언트가 보낸 값은 쓰지 않는다. 대조하는 값은 `SelectedChannel`의 필수 필드인 `type`·`pgProvider`·`pgMerchantId`다. `type = TEST`이고 `pgProvider`·`pgMerchantId`가 설정한 테스트 채널 값(NHN KCP, MID `AO6R1`)일 때만 받아 `SANDBOX`로 저장한다. 실연동(`LIVE`) 채널 응답은 받지 않는다. 선택 필드인 `key`는 응답에 있을 때만 설정한 채널 키와 같은지 더 본다. `channel`이 없거나 필수 필드가 하나라도 없거나 조건에 맞지 않으면 거절한다. 실제 테스트 응답에 어떤 필드가 오는지는 NSU-105 구현 첫 단계에서 한 번 호출해 확인한다. `MOCK`은 PortOne을 거치지 않고 시드 스크립트만 쓴다 |
| 시연의 본인확인 | PortOne 본인확인 창(NHN KCP 테스트 채널)을 실제로 띄운다. 휴대폰 인증 번호는 아무 6자리로 통과한다. 창을 열기 전에 "테스트 창입니다. 실제 이름·생년월일·휴대폰 번호를 넣지 마세요"를 보여 준다 |
| 테스트 본인확인 결과 | `SANDBOX` 결과는 확인했다는 사실, 출처, 확인 시각, 인증 시도 ID만 저장한다. 응답의 이름·생년월일·성별·휴대폰 번호·통신사·외국인 여부·CI·DI는 저장하지 않고 로그에도 남기지 않는다. 거절한 응답(`LIVE` 채널, 채널 값 불일치, 필수 필드 없음)도 같다. 실제 실명·CI가 들어올 수 있는 것은 오히려 이 경로다. 재조회 응답 전체, `verifiedCustomer`, `pgRawResponse`(같은 정보가 제공자 원문으로 들어 있다)는 로그·예외 메시지·저장 어디에도 넣지 않는다. 로그에는 인증 시도 ID와 거절 이유(채널 `type`처럼 사람을 가리키지 않는 값)만 남긴다 |
| 본인확인 요청 제한 | 본인확인 시작(인증 시도 기록을 만든다)과 완료(요청마다 PortOne 재조회를 부른다)를 합쳐 계정마다 1시간 10회(설정값, Asia/Seoul 정각부터 [시작, 끝))로 제한한다. 넘으면 `429 TOO_MANY_REQUESTS`와 `Retry-After`다(00 §8). 시도 기록을 만들지 않고 PortOne을 부르지 않는다. 카운터(Redis)를 쓸 수 없으면 `503 RATE_LIMIT_UNAVAILABLE`로 막는다(계약 §1.6) |
| Mock 본인확인 | HTTP로 고르는 경로를 만들지 않는다. 팀이 시드 스크립트로만 만든다. 로컬 개발도 같다. |
| 등록부 대조 시연 | Mock 본인확인 계정(팀원의 실명)으로 한다. `SANDBOX` 본인확인에는 저장된 이름이 없어서, 등록 정보를 내면 새 오류 `403 IDENTITY_NAME_UNAVAILABLE`이다. 본인확인을 다시 해도 풀리지 않으므로 `IDENTITY_VERIFICATION_REQUIRED`와 구분한다. 새 `code`는 `ErrorCode`에 더한다(00 §8). 등록 정보 제출 API와 `IDENTITY_VERIFICATION_REQUIRED`는 백엔드·프론트에 아직 구현되지 않아(2026-11-05 확인) 기존 클라이언트에 영향이 없다 |
| 대조할 등록곡 | 팀원의 등록곡을 쓴다. 그 팀원이 동의한다. 등록곡이 없으면 시연용 곡을 새로 등록한다. 그 곡은 업로드 규칙을 통과해야 한다. 팀원이 혼자 작사·작곡·편곡했고, 커버곡이 아니며, KOMCA·KOSCAP에 신탁하지 않았고, 작사·작곡·편곡 권리를 양도하거나 독점 계약하지 않은 곡이어야 한다(`RIGHTS-023`, SSOT v1.18 초안). v1.19 초안이 승인되면 아직 어디에도 발매하지 않은 곡이어야 한다. 이미 발매한 팀원 등록곡이면 시연용 곡을 새로 등록한다. 아니면 업로드가 `400`이라 등록부 대조 단계를 보여 줄 수 없다 |
| EVENT_PARTNER 화면 | Trust Profile `verifications`에 `IDENTITY`(실명 본인확인)를 맨 앞에 추가한다. 확인했다는 사실만 보여 주고 이름·생년월일·CI·출처는 내보내지 않는다([01 §4.3](../../api/01_trust_profile.md#43-verifications)) |
| 운영 단계 | 미룬다(2026-11-05 사용자 결정). MVP 뒤에도 졸업 작품 개발은 시연 환경에서 이어 간다. 운영을 시작할 때 새 ADR에서 사업자등록·본인확인 계약, 운영 제공자, `LIVE` 채널 검사, 운영 DB, 환경별 배너·공개 쓰기 설정을 정한다. 그 ADR이 지킬 원칙은 하나다. 시연 데이터(테스트 본인확인과 그것으로 얻은 `VERIFIED_ARTIST`·등록정보 일치·곡)는 운영 DB로 옮기지 않는다(music_upload/01 안전장치 3). 그래서 테스트 본인확인이 무효가 될 일이 없고, 그 아티스트의 곡을 따로 중단하지 않는다(NSU-105 "Eligibility와의 전제"의 두 번째 안) |

### 시연 서버

| 항목 | 결정 |
|---|---|
| 시연 서버 사용 | 실제 섭외에 쓰지 않는다. 행사·곡·PRIVATE 행사 내용은 팀이 만든 시연 데이터를 쓴다 |
| 외부 가입 | 받는다. 외부 사람은 가입, 테스트 본인확인, PUBLIC 행사 열람, 검색창 즉시 추천을 직접 써 본다. 즉시 추천을 어떤 역할이 쓸 수 있는지는 SSOT `AI-MATCH-050`에 따라 NSU-122가 정한다. 이 ADR은 쓸 수 있는 계정이면 `DEMO` 공개 쓰기 검사가 막지 않는다는 것만 정한다. PRIVATE 행사 열람은 아티스트 프로필·일정이 조건(`EVT-044`)에 맞아야 하는데, 외부 계정은 프로필·일정을 쓸 수 없어(공개 쓰기) 열 수 없다. PRIVATE 열람은 팀 계정인 아티스트 A로 보여 준다(2026-11-05 사용자 결정) |
| 공개 쓰기 | `DEMO`에서는 상태를 바꾸는 요청(`POST`·`PUT`·`PATCH`·`DELETE`)을 기본으로 막고, 서버 설정의 허용 목록(팀 시드 계정의 이메일)에 있는 계정만 통과시킨다. 허용 목록에는 팀이 가진 메일함의 주소(예: 팀 Gmail의 `+` 주소)만 넣고, 이메일 인증으로 가입한 계정만 허용 목록으로 판정한다. OAuth로 가입한 계정은 이메일이 같아도 허용 목록이 아니다. 판정은 쓰기 요청마다 `users`를 기본키로 한 번 읽어 이메일과 `password_hash` 유무(이메일 가입만 비밀번호가 있고, OAuth 가입 계정은 `null`이다)로 한다. 아직 아무도 쓰지 않은 주소를 넣어 두어도 외부 사람이 그 메일함을 만들어 먼저 가입할 수 없게 하기 위해서다. 다른 계정은 `403 DEMO_WRITE_NOT_ALLOWED`다. 기능마다 목록을 적지 않는다. 새 쓰기 기능(외부 링크 연동 NSU-37, 프로필 사진 NSU-130, 계정 정보 변경 NSU-131 등)이 생겨도 따로 막을 필요가 없게 하기 위해서다. 허용 목록에 없는 계정도 쓸 수 있는 경로는 다음뿐이다. 가입(이메일·휴대폰 인증, 약관 동의, 성인 확인, OAuth 가입 포함), 로그인·로그아웃·토큰 재발급, 실명 본인확인 시작·완료, 검색창 즉시 추천(NSU-122), 그리고 생기면 회원 탈퇴다. 즉시 추천의 결과 저장·곡 재생 방식은 NSU-122가 정하므로(`AI-MATCH-050`), 그 결정에 따라 허용 경로(재생 주소 발급 등)를 이 ADR에서 다시 맞춘다. 탈퇴를 막으면 외부 사람이 자기 정보를 지울 수 없다. `GET` 요청은 상태를 바꾸지 않는다. 예외는 02 §2.5 재생 주소 발급(재생 기록을 쓴다)이고, 즉시 추천의 재생 방식을 NSU-122에서 다시 맞출 때 이 필터와 함께 본다. 외부 서비스가 `GET`으로 돌아오는 OAuth 콜백도 코드만 받아 프론트로 넘기고, 저장은 프론트가 부르는 `POST`가 한다(외부 링크 연동 NSU-37 포함, 2026-11-05 사용자 결정). 그래서 메서드 기준 필터가 빠짐없이 막는다. 로그인·가입용 OAuth 콜백은 허용 경로(가입·로그인)다. 이 검사는 인증 다음, 본인확인 같은 다른 판정보다 먼저 한다. 그래서 허용 목록에 없는 계정은 본인확인 여부와 관계없이 `DEMO_WRITE_NOT_ALLOWED`를 받는다 |
| 인증 메시지 발송 한도 | SMS·이메일 인증 코드 발송에 세 가지 한도를 둔다. 정규화한 받는 번호·이메일마다 하루 5회(번호는 숫자만 받고 이메일은 소문자로 바꾼다. 대소문자·하이픈 같은 형식 변형으로 한도를 우회하지 못하게 하기 위해서다), 요청 IP마다 1시간 20회, 서버 전체 SMS 하루 300회·이메일 하루 80회다(이메일 전체 한도는 메일 발송 요금제의 하루 할당량보다 작게 둔다). `+`·점을 바꾼 이메일 주소는 다른 받는 곳이 되므로, 요청 IP마다 이메일 발송을 1시간 10회로 더 막는다(하루 창이면 공유 IP가 그날 내내 막혀 1시간 창으로 둔다). 이 한도가 없으면 IP 하나가 4시간 만에 이메일 전체 한도를 다 써 모든 이메일 가입을 막는다. 재전송 60초 쿨다운은 세션이 아니라 받는 곳 단위로 센다(세션을 여러 개 만들어 한 번호에 문자를 몰아 보내지 못하게). 넘으면 기존 `429 VERIFICATION_REQUEST_LIMIT_EXCEEDED`에 `Retry-After`(걸린 한도의 창이 끝날 때까지 남은 초. 하루 창은 다음 날 00:00 Asia/Seoul, 1시간 창은 다음 정각. 이메일 전체 한도만 Resend 하루 할당량의 초기화 시각(UTC 자정)에 맞춰 Asia/Seoul 09:00이다)를 붙인다. 한도·쿨다운에 걸려 거절된 요청은 세지 않는다. 확정 실패한 요청(제공자가 보내지 않았다고 응답)은 받는 곳 카운터만 되돌리고, 요청 IP·서버 전체 카운터와 60초 쿨다운은 남긴다. 제공자에 닿지 않은 실패(연결 실패, 보내기 전 예외)는 외부 호출이 없었으므로 요청 IP·서버 전체 카운터도 되돌린다(쿨다운은 남긴다). 제공자가 계속 거절하는 받는 곳으로 외부 호출을 끝없이 만들지 못하게 하기 위해서다. 시간 초과처럼 결과를 모르는 요청은 문자가 도착할 수 있으므로 센다. 같은 (받는 곳, IP) 쌍의 확인 시도도 하루 10회로 센다(세션을 바꿔 OTP를 추측하지 못하게, 받는 곳 하나로 세면 남이 오답으로 피해자를 잠글 수 있어 쌍으로 센다). 확인 시도를 다 쓴 쌍은 그날 발송도 막아, 다시 받아도 확인할 수 없는 문자에 비용과 하루 한도를 쓰지 않게 한다. 재전송이 확정 실패해도 이미 받은 코드는 그대로 쓸 수 있다. 확정 실패와 결과 모름을 나누기 위해 SMS도 SOLAPI SDK 대신 `RestClient`로 직접 부르고 timeout을 정한다(SDK는 상태 코드를 주지 않고 timeout이 50초로 고정이다). 기존 확인 5회는 그대로다. 60초 쿨다운에 걸린 응답에도 남은 쿨다운 초를 `Retry-After`로 붙인다. 수치는 설정값이라 시연 중에도 운영자가 설정을 바꾸고 서버를 다시 시작해 올릴 수 있다. CoolSMS 충전 금액도 비용 상한으로 둔다. 세 한도의 확인과 예약은 Redis Lua 스크립트 하나로 원자적으로 한다. IPv6 주소는 /64 대역 단위로 센다. 서버 전체 SMS·이메일 한도의 80%에 이르면 `WARN` 로그를 남기고 Slack `#dev`에 알린다(Incoming Webhook, URL은 저장소 밖 시크릿). 로그만으로는 운영자가 알 수 없기 때문이다. 카운터 키에는 번호·이메일·IP 원문 대신 기존 `hmac-secret`으로 만든 digest를 쓴다. 이메일은 로그인·가입 중복 확인·OAuth 가입·허용 목록 비교에서도 같은 소문자 정규형을 쓰고, DB에도 정규형만 둔다(계약 §1.3). 계약은 [signup-terms-and-send-limits.md](../../api/signup-terms-and-send-limits.md)이고, 구현은 가입 인증 코드 발송 제한을 다루는 NSU-123이 한다 |
| 개인정보 | 시연 서버에만 시연 서버 안내, 개인정보 수집·이용, 국외 이전을 서로 다른 필수 약관으로 나눠 가입 필수 약관(`SIGNUP_REQUIRED_TERMS`)에 넣는다(개인정보보호법 §22 동의 구분). 수집·이용 약관에는 수집 항목, 목적, 보유 기간(초기화 날짜), 동의를 거부할 권리와 거부하면 가입할 수 없다는 불이익(§15②), 처리 위탁(CoolSMS·Resend·PortOne·NHN KCP·AWS S3·서버 호스팅 업체)을 적는다. 필수 약관 ID는 `service`·`privacy`(모든 환경, `AUTH-006`)와 `demo-notice`·`overseas-transfer`(`DEMO`)로, 서버 설정과 화면 상수가 같은 값을 쓴다(계약 §1.1). 국외 이전 약관에는 Resend(미국)로 이메일 주소를 보낸다는 것과 이전 국가, 이전 일시·방법(인증 메일을 보낼 때마다 네트워크로), 받는 자와 연락처, 받는 자의 이용 목적(인증 메일 발송)과 보유·이용 기간, 거부 방법과 거부의 효과(이메일 인증이 필요한 가입을 할 수 없음)를 적는다(§28-8②). 제공자 이메일이 검증된 OAuth 가입은 인증 메일을 보내지 않아 국외 이전이 일어나지 않는데도 지금은 이 약관을 필수로 받는다. 필수 범위는 법률 검토에서 정한다(NSU-129). AWS 리전이 국외면 그것도 적는다. 이 고지 항목은 법률 검토 전이다. 처리방침 페이지로 연결한다. 약관 동의는 가입 세션을 만드는 요청에서 함께 받는다. 필수 약관이 빠지면 세션을 만들지 않고 기존 `400 REQUIRED_TERMS_NOT_AGREED`다. 그래서 이메일·휴대폰 번호를 받기 전에 동의가 있고, 인증 코드 발송도 동의 뒤다. OAuth 가입은 준비 요청(`POST /api/v1/auth/signup/artist/oauth/session`)에서 약관 동의를 받는다. 제공자에게서 받은 이메일·식별자는 그 전까지 OAuth 가입 세션(Redis, TTL 30분)에만 있고, 동의하지 않으면 그대로 사라진다. OAuth 로그인 자체가 그 값을 먼저 넘겨주므로 이 부분은 동의보다 먼저 받을 수밖에 없다. 휴대폰 번호는 준비 요청에서 동의와 함께 받으므로 동의 전에는 문자를 보내지 않는다. 중간에 그만둔 가입 세션의 이메일·번호는 세션 TTL(30분)이 지나면 Redis에서 사라지고 DB에 남지 않는다. 동의 기록(회원, 약관 ID·버전, 동의 시각)은 가입을 마칠 때 회원과 함께 DB에 저장한다. 가입 API 자체의 순서라 환경을 가리지 않고, 구현은 NSU-123이 한다. 처리방침에는 열람·정정·삭제 요청 창구(팀 메일 주소)를 적고, 요청을 받으면 NSU-129 담당자가 10일 안에 직접 처리한다(개인정보보호법 §35·§36). 회원 탈퇴 기능이 없어도 이 절차로 지운다. 수집 항목은 아래 표와 같다 |
| 공개 시작 조건 | 위 공개 쓰기 검사, OAuth `state`를 시작한 브라우저에 묶는 수정(지금은 `state`만 맞으면 다른 브라우저의 콜백·결과 코드도 받아, 공격자의 제공자 계정에 묶인 가입을 피해자가 끝낼 수 있다. ADR `authentication/00` Decision 7, [PR #206](https://github.com/nsuCapstoneTeam/NSU_CAPSTONE/pull/206). 2026-11-07 사용자 결정: 시연 OAuth를 끄지 않고 지금 고친다. 구현은 NSU-142([PR #208](https://github.com/nsuCapstoneTeam/NSU_CAPSTONE/pull/208), `__Host-NSU_OAUTH_BINDING` 쿠키: HttpOnly·Secure·SameSite=Lax·Path=/, 6분. 콜백과 결과 코드 교환도 묶음). 이 방식은 배포에서 다음을 갖춰야 동작한다: nginx 한 곳에서 화면과 `/api`를 같은 출처로 내보낸다, HTTPS·HTTP→HTTPS 전환·HSTS, 프록시가 `X-Forwarded-Proto`·`Host`를 넣고 앱은 `server.forward-headers-strategy=framework`를 켠다(프록시 없이 켜면 위조한 헤더를 믿으므로 앱 기본값이 아니라 배포 설정에서만 켠다), `OAUTH_BINDING_COOKIE_SECURE=true`), 발송 한도와 80% Slack 알림(Webhook 설정 확인), 가입 세션 생성·OAuth 시작·콜백 요청 제한(계약 §1.4), Redis `maxmemory`(기본 256MB)와 `noeviction`, 로그인 요청 제한(계약 §1.5), 저장소 밖 무작위 시크릿으로 둔 시드 계정 비밀번호, 본인확인 요청 제한, 신뢰하는 프록시가 넣은 값으로만 클라이언트 IP를 읽는 설정(잘못되면 모든 사용자가 IP 하나로 세어진다), 개인정보 약관과 동의 저장, 초기화 날짜, 초기화 runbook, 시연 환경 배너, 열람·정정·삭제 요청 창구, 검색창 즉시 추천의 요청 제한(NSU-122)이 모두 준비된 뒤에 시연 서버 주소를 외부에 알린다 |
| 테스트 표시 | 모든 화면 위에 배너를 늘 띄운다(예: "시연 환경입니다. 이 서버의 본인확인은 테스트 본인확인이라 실제 이름을 확인하지 않습니다."). 환경이 `DEMO` 하나뿐이라 켜고 끄는 설정을 두지 않는다. 운영 단계 ADR에서 백엔드가 알려 주는 환경 값으로 끄는 방법을 정한다 |
| 외부 가입 데이터 삭제 | 졸업 작품 최종 평가 다음 날 아래 "초기화 runbook"으로 시연 서버를 통째로 지운다(2026-11-05 사용자 결정). MVP 시연에서 가입한 외부 사람의 정보도 그날까지 보관한다. 가입 약관에 그 날짜를 적는다 |
| 리허설 | 시연마다 시드 스크립트로 본인확인 전 상태의 새 아티스트 A를 만든다. 리허설에서 본인확인한 A는 되돌리지 않고 다시 쓰지 않는다. A에 쓸 이메일 여러 개(팀이 가진 메일함의 `+` 주소, 예: `team+demo-artist-01`~`10`)를 허용 목록에 미리 넣어 두고, 시드는 아직 쓰지 않은 이메일로 A를 만든다. 그래서 시연마다 서버 설정을 바꾸지 않는다. 시드 계정 비밀번호는 저장소 밖의 무작위 시크릿으로 두고, 시드 스크립트·문서·로그에 적지 않는다. 허용 목록 계정은 이 비밀번호 하나로 지켜지고, 저장소와 이 ADR은 공개라 주소 형식이 알려져 있기 때문이다(로그인 요청 제한은 계약 §1.5) |

### 초기화 runbook

담당은 NSU-129 담당자다. 끝나면 단계마다 결과를 NSU-129에 남긴다.

1. 시연 서버를 내려 새 가입을 막는다.
2. DB와 Redis를 지운다. DB 백업과 스냅샷도 지운다.
3. 업로드 버킷의 객체와 이전 버전을 모두 지운다.
4. 애플리케이션·프록시 로그를 지운다.
5. 외부 서비스(CoolSMS 발송 기록, Resend 발송 기록, PortOne 본인인증 내역, NHN KCP 본인확인 기록)에서 지울 수 있는 기록을 지운다. 지울 수 없는 기록은 각 서비스의 보존 기간을 미리 처리방침에 적어 둔다(NSU-129에서 확인).
6. 다시 띄우기 전에 1~5단계가 끝났는지 확인한다.

### 시연 흐름

아티스트 A·B와 EVENT_PARTNER는 허용 목록에 있는 팀 시드 계정이다.

| 단계 | 화면·동작 | 보여 주는 것 |
|---|---|---|
| 1. 본인확인 전 | 아티스트 A로 로그인해 PRIVATE 행사 상세를 연다 | `404`. 곡 업로드는 `403 IDENTITY_VERIFICATION_REQUIRED`다. 가입·로그인에는 실명 본인확인이 필요 없다 |
| 2. 본인확인 | 마이페이지에서 PortOne 창(KCP 테스트)을 열고 휴대폰 인증을 마친다 | 서버가 PortOne에 결과를 다시 조회하고, 응답 채널이 테스트 채널이어서 출처 `SANDBOX`로 저장한다. 화면 위의 시연 배너가 테스트 본인확인임을 알린다 |
| 3. 열린 권한 | 같은 PRIVATE 행사 상세를 다시 열고, PUBLIC 행사에 댓글을 쓰고, 곡을 올린다 | `200`, 댓글 작성, 곡 업로드 |
| 4. 등록부 대조 | 팀원의 실명으로 Mock 본인확인한 아티스트 B가 그 팀원의 등록곡 등록번호를 낸다 | 한국저작권위원회 등록정보 API 호출, "등록부 저작자·권리자와 실명 일치" |
| 5. EVENT_PARTNER 화면 | EVENT_PARTNER가 A와 B의 Trust Profile을 연다 | A에는 `IDENTITY`, B에는 `IDENTITY`와 `COPYRIGHT` |

시연 준비(채널 설정, 시연 데이터, 리허설, 예상 질문)는 NSU-129에 있다.

## Context

- 용어는 [용어집](https://linear.app/nsu-capstone/document/용어집-context-475370673105)(2026-11-05 수정)을 따른다. Verified Artist는 실명 본인확인을 마친 `ACTIVE` Artist다. 테스트 채널이나 Mock으로 마친 것은 테스트 본인확인이고, 시연 서버에서만 실명 본인확인을 대신한다. 등록부 대조를 통과한 곡은 등록정보 일치이고, 권리 검증(`VERIFIED`)과 다르다.
- 실명 본인확인을 쓰는 곳은 네 곳이다.
  - 곡 업로드: `VERIFIED_ARTIST`만 곡을 올린다. 침해 신고가 왔을 때 책임을 물을 실명을 남기기 위해서다(ADR `music_upload/02` §7, PR #186, 2026-11-05). 시연 서버는 `SANDBOX` 결과의 이름·생년월일·CI를 저장하지 않으므로 `AUTH-009`의 최소 식별값을 남기지 못하고, 책임을 물을 실명도 남지 않는다. 대신 곡을 올릴 수 있는 계정을 팀 허용 목록으로 한정해 업로더를 특정한다("공개 쓰기").
  - 등록부 대조: 본인확인 이름을 등록부 저작자와 대조한다(music_upload/01, Trust Profile `COPYRIGHT`).
  - PRIVATE 행사 열람: 조건에 맞는 `VERIFIED_ARTIST`만 본다(`EVT-043`·`044`).
  - PUBLIC 행사 댓글: `VERIFIED_ARTIST`와 EVENT_PARTNER만 쓴다(`CMT-045`).
- 가입·로그인에는 실명 본인확인이 필요 없다(`AUTH-009`). AI 추천 조건(`AI-031` v1.17)과 Eligibility 판정([recommendation_eligibility/00](../recommendation_eligibility/00_eligibility_rules.md))도 `VERIFIED_ARTIST`를 직접 판정하지 않는다. 다만 곡 업로드에 실명 본인확인이 필요하므로, 본인확인을 하지 않은 아티스트는 곡이 없어 추천 후보가 되지 못한다. 실명 본인확인은 곡 업로드를 거쳐 사실상 추천 후보의 조건이다. 이 간접 조건을 `RIGHTS-024`·`ART-027`에 적은 문장은 SSOT v1.18 초안 ②(팀 확인 전)다.
- 2026-11-05 사업자 요건 조사 결과는 다음과 같다.

| 경로 | 사업자 없이 | 근거 |
|---|---|---|
| 본인확인기관(NICE 등)과 직접 계약 | 안 됨 | 필수 서류에 사업자등록증이 있다 |
| PortOne을 거친 실연동 | 테스트는 됨. 실연동은 확인하지 못함 | 콘솔 가입과 테스트 모드는 이메일로 된다. 실연동은 인증사 계약이다. 포트원의 결제(PG) 계약 안내는 계약 접수에 상호명과 사업자번호를 받는다. 본인인증 계약도 같은지는 공개 자료로 확인하지 못했다 |
| 카카오 로그인의 "이름" | 안 됨 | 개인정보 동의항목은 사업자 정보를 등록한 비즈 앱만 신청할 수 있다 |
| 네이버 로그인의 "이름" | 실명 보장 없음 | 2023년부터 가입할 때 실명 확인이 선택이다 |
| 모바일 신분증 검증 | 안 됨 | 민간 참여 모집 대상이 ISMS-P 인증 기업이었다(2024 보도) |
| 저작권 등록정보 API | 됨 | 공공데이터포털에서 무료로 쓰고, 개발 단계는 자동 승인이다 |

- 테스트 채널(2026-10-20 PortOne 콘솔·연동 안내에서 확인, NSU-105. 공개 문서 링크는 없다): NHN KCP 테스트 채널 MID `AO6R1`(SMS는 임의의 6자리), KG이니시스 통합인증 테스트 MID `MIIiasTest`, 토스인증 테스트 환경(가상 인물)이 있다. 다날은 계약 전에 테스트 연동정보를 주지 않는다.
- PortOne V2 본인인증 단건 조회 응답(`VerifiedIdentityVerification`)에는 `channel`(`SelectedChannel`)이 있고, `channel.type`은 `LIVE`(실연동)·`TEST`(테스트) 중 하나다. `channel`은 필수 필드가 아니다. `SelectedChannel` 안의 필수 필드는 `type`·`pgProvider`·`pgMerchantId`이고, `id`·`key`·`name`은 선택 필드다(PortOne V2 OpenAPI, 2026-11-05 조회).
- 2026-11-05 코드 상태:
  - 시연에 필요한 기능은 아직 구현되지 않았다. PRIVATE 행사는 등록자만 보도록 항상 거부하고(`DenyingCanViewPrivateEvent`), 댓글 코드는 없다.
  - 인증 코드 재전송 쿨다운은 가입 세션 단위뿐이다(`SignupRedisKeys.cooldown`). 가입 세션은 로그인 없이 만들 수 있어서, 세션을 새로 만들면 같은 번호로 계속 보낼 수 있다. 번호·IP·전체 한도는 없다.
  - 가입 필수 약관 동의는 가입 세션의 값으로만 남고 DB에 저장하지 않는다(`SignupVerificationService.agreeRequiredTerms`). 이 ADR이 바꾼다("개인정보", 계약 `signup-terms-and-send-limits.md` §1.1).
  - Spring 프로필 파일이 없다. 환경을 나누는 설정이 아직 없다.
  - SMS는 CoolSMS를 쓴다(2026-11-05 사용자 결정). CoolSMS GitHub 조직 페이지는 SOLAPI SDK를 100% 지원한다고 밝힌다. 그래서 `SolapiSmsSender`(SOLAPI 메시지 발송 API)를 계속 쓴다. 다만 안의 SDK 호출은 `RestClient` 직접 호출로 바꾼다(2026-11-06 사용자 결정, 계약 §1.2). CoolSMS 계정으로 실제로 보내지는지는 NSU-129 리허설에서 확인한다.
  - 인증 코드 발송(`sendEmailCode`·`sendPhoneCode`)은 약관 동의 여부를 보지 않는다. 동의는 가입을 마칠 때만 확인한다(`SignupRequiredConditionsValidator`). 이 ADR이 동의를 세션 생성 때 받도록 바꾼다("개인정보").
  - 프론트는 `VERIFICATION_REQUEST_LIMIT_EXCEEDED`를 "인증번호는 60초 뒤에 다시 받을 수 있어요."로 고정해 보여 준다(`frontend/src/features/auth/api/auth-api.js`). 백엔드는 `Retry-After`를 보내지 않는다.
  - 가입 인증 코드 발송 제한을 수신처 단위로 바꾸고 Redis 저장을 원자화하는 이슈가 이미 있다(NSU-123).

## Rationale

### 테스트 채널로 운영과 같은 흐름을 만든다

| 관점 | 테스트 채널 + Mock (채택) | 개인사업자 등록 후 실계약 | 실명 본인확인을 빼고 권한을 `ACTIVE` ARTIST로 |
|---|---|---|---|
| 정확성 | 실제 실명은 확인하지 않는다. 응답 채널로 출처를 정해 테스트 기록을 구분한다 | 실제 실명을 확인한다 | 곡 업로드·PRIVATE 열람·댓글 권한의 근거가 없다 |
| 보안 | 서버 재조회, 응답 채널 검사, 인증 시도 ID 묶기, 재사용 방지는 운영과 같다. 실연동(`LIVE`) 채널 응답은 받지 않는다 | 테스트 채널 안과 같다. CI·실명을 보관할 책임이 더해진다 | 이메일·휴대폰 인증만 한 계정이 PRIVATE 행사를 본다 |
| 성능 | 본인확인 1회마다 서버가 PortOne 결과 조회 1회를 기다린다 | 차이 없음 | 외부 호출이 없다 |
| 메모리 | 차이 없음 | 차이 없음 | 차이 없음 |
| 확장성 | 운영 단계 ADR에서 운영 제공자와 `LIVE` 채널 검사를 더하면 운영으로 간다 | 그대로 운영한다 | 운영할 때 권한 모델을 다시 설계해야 한다 |
| 운영 부담 | 운영 단계에서 운영 DB를 새로 만들고 시연 데이터를 옮기지 않는다 | 매출이 없어도 세금 신고, 인증사 정산, 개인정보 보관 | 없음 |
| 사용자 경험 | 시연에서 실제 인증 창을 보여 준다. 시연 배너가 테스트임을 알린다 | 실제 인증 | 인증 단계가 없다 |
| 비용 | 없음 | 인증 건당 요금 | 없음 |
| 구현량 | NSU-105 범위 | NSU-105 범위에 계약·심사 대응이 더해진다 | 가장 적다 |

- 실계약은 졸업작품 일정과 비용에 비해 무겁다.
- 실명 본인확인을 빼면 2026-09-17 지도교수 피드백의 핵심 질문("프로필의 아티스트가 실제 공연 가능한 사람인지 어떻게 검증할 것인가")에 답하지 못한다.
- 테스트 채널 안과 실계약 안은 흐름(창 열기 → 서버 재조회 → 인증 시도 ID 묶기)이 같다. 다른 점은 둘이다. 받는 응답 채널(`TEST` 채널 값과 운영 `LIVE` 채널 값)이 다르고, 운영에서는 `SANDBOX`에서 버리던 이름 등을 저장한다. 운영으로 갈 때 계약, 운영 제공자 설정, 운영 채널 값, 저장 항목이 더해진다.

### 출처는 응답 채널로 정한다

설정된 제공자만 보고 출처를 정하면, 시연 서버에 실연동 채널 값이 잘못 들어갔을 때 실제 본인확인 결과(실명·CI)가 `SANDBOX`로 들어오고 테스트 기록처럼 다뤄진다. 재조회 응답의 `channel`은 PortOne이 정하는 값이라 클라이언트가 바꿀 수 없다. 그래서 응답 채널이 설정한 테스트 채널일 때만 받고, 출처도 그 채널로 정한다. 대조는 `SelectedChannel`의 필수 필드(`type`·`pgProvider`·`pgMerchantId`)로 한다. 선택 필드인 `key`에만 기대면, `key`가 빠진 응답에서 시연 서버의 모든 본인확인이 거절된다. `channel`은 필수 필드가 아니므로, 없으면 판단할 수 없어 거절한다.

### 테스트 본인확인 결과는 저장하지 않는다

시연 서버는 외부 사람이 쓴다. KCP 테스트 창에는 실제 이름과 생년월일을 넣을 수 있다. 안내만으로는 막지 못하므로, 들어와도 남지 않게 한다.

| 관점 | 확인 사실만 저장 (채택) | 운영과 같이 저장 |
|---|---|---|
| 정확성 | 시연에 필요한 것(확인 여부, 출처)은 모두 남는다. `SANDBOX` 이름으로 하는 등록부 대조는 할 수 없다. 테스트 채널이 어떤 이름을 돌려주는지 공식 문서에 없어 원래 시연에 쓰지 않는다 | `SANDBOX` 이름으로도 대조를 시도할 수 있다 |
| 보안 | 외부 사람이 실명을 넣어도 서버에 남지 않는다 | 실명·생년월일·CI가 시연 서버 DB에 남는다 |
| 성능 | 차이 없음 | 차이 없음 |
| 메모리 | 차이 없음 | 차이 없음 |
| 확장성 | 시연 DB를 지울 때 `SANDBOX` 기록에는 지울 개인정보가 없다 | 시연 DB를 지울 때 본인확인 정보도 함께 확인해야 한다 |
| 운영 부담 | 처리방침에 본인확인 정보 보관을 적지 않아도 된다 | 본인확인 정보 보관을 처리방침에 적고 초기화 때 확인한다 |
| 사용자 경험 | 차이 없음 | 차이 없음 |
| 구현량 | 출처별로 저장 항목을 나누는 분기 1개 | 경로가 하나다 |

### 시연 서버에서 Mock을 HTTP로 열지 않는다

시연 서버는 외부에서 접속할 수 있다. Mock을 HTTP로 고를 수 있으면 누구나 원하는 이름으로 본인확인을 마치고 등록부 대조까지 통과한다. 화면에서 숨기는 것으로는 API 직접 호출을 막지 못한다. 그래서 Mock 본인확인은 시드 스크립트로만 만든다. Mock 계정의 등록부 대조도 허용 목록 계정만 할 수 있다.

### EVENT_PARTNER에게 실명 본인확인 사실을 보여 준다

실명 본인확인을 도입한 이유는 EVENT_PARTNER가 아티스트를 믿을 근거를 갖게 하는 것이다(2026-09-17 지도교수 피드백). 그런데 지금 실명 본인확인은 아티스트 쪽 권한(곡 업로드, PRIVATE 열람, 댓글)에만 쓰이고, Trust Profile에는 신원 항목이 없다. 용어집의 Verification은 "아티스트의 신원, 외부 계정, 작업물, 권리가 사실인지 확인한 결과"이므로 신원 항목이 정의에 들어맞는다.

| 관점 | `IDENTITY` 항목 추가 (채택) | 보여 주지 않기 |
|---|---|---|
| 정확성 | "실제 사람인가"를 EVENT_PARTNER 화면에서 바로 보여 준다 | 등록곡이 있는 아티스트만 `COPYRIGHT`로 간접적으로 드러난다 |
| 보안 | 확인했다는 사실만 내보내고 이름·생년월일·CI·출처는 내보내지 않는다 | 차이 없음 |
| 성능 | Trust Profile 일괄 조회에서 본인확인 기록 조회가 1회 늘어난다. 아티스트 수와 관계없이 일정하다 | 차이 없음 |
| 메모리 | 차이 없음 | 차이 없음 |
| 확장성 | 운영 본인확인으로 바뀌어도 계약이 같다 | 차이 없음 |
| 운영 부담 | 차이 없음 | 차이 없음 |
| 사용자 경험 | EVENT_PARTNER가 아티스트가 실존 인물로 확인됐는지 안다 | 알 수 없다 |
| 구현량 | 01 §4.3에 enum 값 1개(00 §3에 따라 하위 호환), 본인확인 기록을 읽는 `VerificationSource` 1개(01 §7) | 없음 |

### 테스트임은 시연 환경 배너로 알린다

시연을 보는 사람이 테스트 본인확인을 실제 실명 본인확인으로 읽지 않게 하기 위해서다. 기록마다 표시하지 않고 시연 환경 전체에 배너 하나를 띄운다.

지금 환경은 `DEMO` 하나이고, 그 안의 본인확인은 테스트 채널 응답(`SANDBOX`)과 시드 스크립트로 만든 Mock(`MOCK`)뿐이라 모두 테스트 본인확인이다. 실연동(`LIVE`) 응답은 받지 않는다(출처 결정). 그래서 환경 단위의 안내로 충분하고, 배너를 늘 띄우면 된다. 켜고 끄는 설정이 없으니 설정이 어긋나 배너가 꺼질 일도 없다.

| 관점 | 시연 환경 배너 (채택) | 기록마다 "(테스트)" 표시 |
|---|---|---|
| 정확성 | `DEMO`의 본인확인은 모두 테스트라 배너 하나로 정확하다 | 같다 |
| 보안 | 차이 없음 | 차이 없음 |
| 성능 | 차이 없음 | 차이 없음 |
| 메모리 | 차이 없음 | 차이 없음 |
| 확장성 | 본인확인에서 나온 표시(Trust Profile `COPYRIGHT` 등)가 늘어도 배너 하나로 덮는다 | 그런 표시마다 출처를 따라가야 한다 |
| 운영 부담 | 운영 단계에서 끄는 방법만 더한다 | 운영에서는 쓰이지 않는 필드와 코드가 남는다 |
| 사용자 경험 | 모든 화면 위에 같은 안내가 보인다 | 배지마다 "(테스트)"가 붙는다 |
| 구현량 | 배너 컴포넌트 1개. API와 Trust Profile 계약 변경이 없다 | Trust Profile `verifications`(01 §4.3)와 본인확인 상태 API에 출처 필드를 더하고, 화면 여러 곳을 고친다 |

### 시연 서버는 외부 가입을 받되 실제 섭외에 쓰지 않는다

심사위원과 다른 사람이 가입부터 직접 써 보게 하려고 외부 가입을 받는다(2026-11-05 사용자 결정).

시연 서버에서는 누구나 테스트 본인확인으로 Verified Artist가 된다. 그래서 "Verified Artist만 본다"는 PRIVATE 행사의 보호가 의미 없다. PRIVATE 행사를 포함한 행사·곡 내용은 팀이 만든 시연 데이터만 쓰고, 실제 섭외에는 쓰지 않는다.

외부 가입을 받으면 세 가지를 먼저 막아야 한다. 외부 계정이 공개 내용을 올리는 것(공개 쓰기), 인증 메시지를 한없이 보내는 것(발송 한도), 외부 사람의 개인정보를 근거 없이 보관하는 것(개인정보 약관·동의 저장·초기화)이다. 셋을 포함해 결정 표의 "공개 시작 조건"이 모두 준비되기 전에는 주소를 알리지 않는다.

| 관점 | 외부 가입 받기 (채택) | 시연 계정만 빌려주기 | 실제 개인정보를 하나도 넣지 않기 |
|---|---|---|---|
| 정확성 | 가입부터 실제 흐름으로 보여 준다 | 가입은 팀원만 보여 준다 | 실제 SMS를 보낼 수 없어 가입 흐름을 보여 주지 못한다 |
| 보안 | 외부인의 이메일·휴대폰 번호를 보관한다. 공개 쓰기 검사와 발송 한도로 남용을 막고, 약관에 보유 기간을 적고 초기화로 지운다 | 외부인의 개인정보가 없다 | 개인정보가 없다 |
| 성능 | 인증 코드 발송마다 Redis Lua 스크립트 호출이 1회(왕복 1회) 늘어난다 | 차이 없음 | 차이 없음 |
| 메모리 | 한도 카운터가 창(하루·1시간) 단위로 Redis에 생겼다 사라진다 | 차이 없음 | 차이 없음 |
| 확장성 | 발송 한도와 동의 저장은 운영 단계에서도 그대로 쓸 수 있다 | 차이 없음 | 차이 없음 |
| 운영 부담 | 처리방침 작성, 초기화 runbook, SMS 비용과 전체 한도 경고 로그 감시 | 시연마다 계정 준비 | 없음 |
| 사용자 경험 | 심사위원이 가입·본인확인·PUBLIC 열람·즉시 추천을 직접 써 본다. PRIVATE 열람·곡 업로드·행사 등록은 팀 계정으로 본다 | 만들어 둔 계정으로 써 본다 | 가입을 써 볼 수 없다 |
| 구현량 | 공개 쓰기 검사, 발송·요청 한도(계약 §1.2·§1.4·§1.5), 대기 challenge, SMS 어댑터 교체, 이메일 정규화 마이그레이션, 80% Slack 알림, 동의 저장 테이블, 약관 문구, 처리방침, runbook. 처음 잡은 약 2~3일보다 늘어난다. 다시 추정하는 것은 NSU-123·NSU-129다 | 시드 절차만 | 가입 시연을 위한 우회가 필요하다 |

### 공개 쓰기는 팀 계정만 한다

외부 계정이 곡과 행사를 올리면 시연 서버가 검증 없는 공개 음원·게시판이 된다. 곡 권리 신고 대응(NSU-104)은 아직 없다.

막는 방식은 기능 목록이 아니라 기본 거절이다. 쓰기 기능은 계속 늘어난다. 외부 링크 연동(NSU-37)에 더해 2026-11-05에만 프로필 사진(NSU-130)과 계정 정보 변경(NSU-131) 이슈가 새로 생겼다. 기능 목록으로 막으면 새 기능이 생길 때마다 목록을 고쳐야 하고, 하나를 빠뜨리면 외부 사람이 넣은 내용이 바로 공개된다. 허용 경로 목록(가입·로그인·본인확인·즉시 추천·탈퇴)은 거의 바뀌지 않는다.

| 관점 | 허용 목록 계정만 (채택) | 외부도 쓰고 NSU-104를 먼저 | 외부가 쓴 것은 본인에게만 보이기 |
|---|---|---|---|
| 정확성 | 공개 내용은 모두 팀 시연 데이터다 | 신고 전까지 검증 없는 내용이 공개된다 | 공개 내용은 팀 데이터뿐이다 |
| 보안 | 외부인이 남의 음원·행사·댓글을 올릴 수 없다 | 신고가 올 때까지 침해 음원이 재생될 수 있다 | 조회·추천 쿼리 하나라도 필터를 빠뜨리면 노출된다 |
| 성능 | 상태를 바꾸는 요청마다 `users` 기본키 조회 1회(이메일과 `password_hash` 유무). JWT에는 `sub`·`role`만 있어 토큰만으로는 판정할 수 없다. 시연 서버의 쓰기 요청은 드물어 부담이 작다 | 차이 없음 | 모든 조회·추천 쿼리에 조건이 붙는다 |
| 메모리 | 허용 목록(이메일 몇 개)을 설정에서 읽어 메모리에 둔다 | 차이 없음 | 차이 없음 |
| 확장성 | `DEMO` 전용 필터다. 운영 단계 ADR에서 끄는 방법을 정한다 | NSU-104는 운영에도 쓴다 | 운영에 필요 없는 조건이 모든 쿼리에 남는다 |
| 운영 부담 | 시드 계정이 바뀌면 허용 목록을 고친다 | 시연 기간 내내 신고를 지켜봐야 한다 | 새는 곳이 없는지 계속 확인해야 한다 |
| 사용자 경험 | 외부 사람은 업로드·행사 등록·댓글·프로필 입력을 해 볼 수 없다(`403`). 곡을 올리지 못하므로 어차피 추천 후보가 되지 않는다 | 외부 사람이 모든 기능을 써 본다 | 외부 사람이 모든 기능을 써 보지만 남에게 보이지 않는다 |
| 구현량 | 필터 1개와 허용 경로 목록, 설정 1개. 모든 비-GET 라우트를 나열해 검사하는 테스트 1개 | NSU-104 최소 기능(신고·즉시 중단)이 시연 전에 필요하다 | 가장 크다 |

### 인증 메시지 발송 한도

지금 재전송 쿨다운은 가입 세션 단위라서, 세션을 새로 만들면 같은 번호로 계속 보낼 수 있다. 외부 가입을 받으면 남의 번호로 문자를 계속 보내거나 SMS 비용을 써 버릴 수 있다.

| 관점 | 번호 하루·IP 1시간·SMS 전체 하루 (채택) | 번호·IP·전체 모두 하루 | 서버 전체 하루 한도만 | 세 한도 + CAPTCHA |
|---|---|---|---|---|
| 정확성 | 한 사람이 한도를 다 써도 다른 사람은 가입할 수 있다. 심사장 Wi-Fi처럼 IP 하나를 함께 써도 1시간 뒤 다시 열린다 | 공유 IP에서 10명 안팎이 가입하면 그 IP는 그날 내내 막힌다 | 한 사람이 하루 한도를 다 쓰면 그날 아무도 가입하지 못한다 | 채택안과 같다 |
| 보안 | 한 번호로 보내는 문자가 하루 5통을 넘지 않는다. 한 IP는 하루 최대 480회까지 보낼 수 있어 15시간이면 SMS 전체 한도(300통)를 채운다. 비용은 SMS 전체 한도와 충전 금액이 막고, 고갈은 80% Slack 알림을 받은 운영자가 대역을 막아 끊는다 | 한 IP가 하루 20회를 넘지 않는다 | 남의 번호로 하루 한도만큼 보낼 수 있다 | 자동화 남용까지 막는다 |
| 성능 | 발송마다 Redis Lua 스크립트 1회로 카운터 여러 개(계약 §1.2 표)를 확인하고 늘린다(왕복 1회, 외부 호출 없음) | 같다 | 카운터 1개 | 채택안에 CAPTCHA 검증 외부 호출 1회가 더해진다 |
| 메모리 | 창이 끝나면 사라지는 카운터 | 같다 | 카운터 1개 | 채택안과 같다 |
| 확장성 | 운영 단계에서도 그대로 쓸 수 있다. 수치만 설정으로 바꾼다 | 같다 | 운영에서는 부족하다 | 운영에도 쓸 수 있다 |
| 운영 부담 | CoolSMS 충전 금액이 마지막 상한이다. 시연 중 막히면 설정을 바꾸고 서버를 다시 시작해 올린다 | 같다 | 같다 | CAPTCHA 서비스 키 관리와 위탁 고지가 늘어난다 |
| 사용자 경험 | 가입 1건에 발송이 2회(이메일·SMS) 이상이라, 공유 IP 하나에서 1시간에 가입할 수 있는 사람은 10명 남짓이다. 막혀도 다음 정각에 풀린다. 심사장처럼 한 IP에서 여러 명이 동시에 가입하면 설정을 바꾸고 서버를 다시 시작해 IP 한도를 올린다 | 공유 IP의 사용자가 그날 가입하지 못한다 | 한도가 차면 정상 사용자도 막힌다 | 발송 전에 CAPTCHA를 푼다 |
| 구현량 | Redis 카운터(계약 §1.2 표)와 `Retry-After`, 80% Slack 알림 | 같다 | 카운터 1개 | 채택안에 프론트·백엔드 CAPTCHA 연동이 더해진다 |

- IP는 시연 서버 앞단에서 신뢰하는 프록시가 넣은 클라이언트 IP를 쓴다. 클라이언트가 보낸 `X-Forwarded-For`를 그대로 믿지 않는다.
- 하루의 기준은 Asia/Seoul 날짜이고, 1시간 창은 Asia/Seoul 정각에 시작한다. 창은 [시작, 끝)이다.
- 서버 전체 한도는 SMS와 이메일을 따로 센다. 이메일은 건당 비용은 작지만 메일 발송 요금제에 하루 할당량이 있어, 다 쓰면 그날 이메일 가입이 모두 `VERIFICATION_DELIVERY_FAILED`가 된다. 그래서 할당량보다 작은 이메일 전체 한도를 둔다. 창도 할당량과 같게 둔다. Resend Free는 하루 100통을 UTC 날짜로 세므로, Asia/Seoul 자정에 초기화하면 한 UTC 날짜에 80통 + 80통이 들어가 할당량을 넘는다.
- 세 한도를 모두 확인한 뒤 모두 통과할 때만 발송한다. 하나라도 걸리면 아무 카운터도 늘리지 않는다. 발송 결과가 확정 실패(제공자가 보내지 않았다고 응답)일 때만 예약한 받는 곳 키(날짜가 바뀌어도 예약 때의 키)를 되돌린다. 제공자 쪽 실패가 받는 곳 한도를 깎아 정상 사용자를 막지 않게 하기 위해서다. 요청 IP·서버 전체 카운터는 외부 호출 횟수를 세므로, 제공자에 닿은 확정 실패에서는 되돌리지 않는다(닿지 않은 실패는 외부 호출이 없었으므로 되돌린다). 닿은 실패까지 모두 되돌리면 수신 거부 번호처럼 늘 거절되는 받는 곳으로 한도에 닿지 않고 호출을 계속 만들 수 있다. 시간 초과처럼 결과를 모르면 실제로 보냈을 수 있으므로 보낸 것으로 센다.
- 확인과 증가는 Lua 스크립트 하나로 원자적으로 한다. 따로 읽고 늘리면, 같은 번호로 동시에 온 요청 여러 개가 모두 한도 아래로 읽혀 한도를 넘겨 보낸다.
- IPv4는 주소 하나, IPv6는 /64 대역을 한 IP로 센다. IPv6 사용자는 보통 /64 하나를 받아 그 안에서 주소를 마음대로 바꿀 수 있기 때문이다.
- 남은 위험: 서버 전체 SMS·이메일 한도는 채울 수 있다. IP 하나로도 SMS는 15시간(1시간 20통), 이메일은 8시간(1시간 10통)이면 다 쓴다. IP 여러 개(또는 /64 여러 개)면 더 빠르다. 그러면 그날 다른 사람이 인증을 받지 못한다. 휴대폰 인증은 모든 가입 방법의 필수 조건이라 SMS가 차면 모든 가입이 멈춘다. IP 하루 상한을 두면 공유 IP가 그날 내내 막히므로(버린 안) 두지 않고, 전체 한도의 80%에 이르면 `WARN` 로그와 Slack `#dev` 알림으로 운영자에게 알린다. 알림을 받은 운영자는 공격 대역을 막거나, 설정을 바꾸고 서버를 다시 시작해 한도를 올린다. 이메일 전체 한도는 Resend Free의 하루 100통을 넘겨 올릴 수 없다. 이메일 한도를 올려야 하면 하루 할당량이 없는 Resend Pro로 먼저 바꾼다(유료라 사용자 승인 뒤). SMS 비용은 CoolSMS 충전 금액이 막는다.
- 남은 위험: 제공자 장애(`5xx`, 읽기 timeout)면 사용자는 성공 응답을 받으면서 받는 곳 하루 5회를 쓴다. 채널마다 결과 모름·확정 실패가 10분에 5회를 넘으면 Slack `#dev`로 알린다(계약 §1.2). 알림을 받은 운영자는 다음을 한다. 1) 제공자 상태 페이지와 설정(키·발신 번호·도메인)을 확인한다. 2) 고친 뒤 관리 스크립트(NSU-123)로 장애 동안의 창에 쌓인 받는 곳·IP 카운터를 지운다. 3) 시연 중이면 리허설 체크리스트의 예비 경로(미리 가입해 둔 팀 계정)로 넘어간다. 제공자에 닿지 않은 실패(연결 실패, 보내기 전 예외)는 카운터를 모두 되돌리므로 이 절차가 필요 없다.
- 남은 위험: Redis가 멈추거나 `maxmemory`에 닿으면 발송·가입 세션 생성·OAuth·본인확인이 `503`으로 막힌다(fail-closed, 계약 §1.6). 로그인만 한도 없이 열린다. Redis를 되살리면 마지막 저장 뒤의 카운터가 사라질 수 있어, 그 창의 한도가 잠시 풀린다.
- 확인 시도 하루 한도는 (받는 곳, IP) 쌍으로 센다(2026-11-07 PR #205 CodeRabbit 리뷰, 사용자 결정). 받는 곳 하나로 세면 남이 피해자 번호로 세션을 만들어 오답 10번으로 그날 가입을 막을 수 있다. 쌍으로 세도 추측은 받는 곳 하루 발송 5회 × challenge별 확인 5회로 하루 25번(6자리 코드라 0.0025%)을 넘지 못한다.
- 남은 위험: 피해자와 같은 IP(공유 Wi-Fi 등)를 쓰는 사람은 여전히 오답 10번으로 그 번호를 그날 막을 수 있다. 피해자는 다른 네트워크에서 가입하거나, 처리방침의 요청 창구로 알리면 운영자가 관리 스크립트로 그 키를 지운다.

### 외부 가입 데이터는 날짜를 정해 통째로 지운다

시연 서버는 실제 서비스가 아니라서 통째로 지워도 잃을 것이 없고, 날짜 하나만 약속하면 되므로 지키기 쉽다. DB만 지우면 백업, 버킷의 이전 버전, 로그, 외부 서비스 기록에 개인정보가 남는다. 그래서 지울 곳을 runbook으로 정한다.

| 관점 | 날짜를 정해 통째로 초기화 (채택) | 가입 N일 뒤 계정별 삭제 | 탈퇴 기능으로 각자 삭제 |
|---|---|---|---|
| 정확성 | 약속한 날짜에 runbook의 모든 곳에서 지워진다 | 계정마다 약속한 날에 지워진다. 백업·로그는 따로 지워야 한다 | 탈퇴하지 않은 사람의 데이터가 남아 약속을 지키지 못한다 |
| 보안 | 시연 뒤 개인정보가 남지 않는다. 지울 수 없는 외부 기록은 처리방침에 미리 알린다 | DB는 같고, 백업·로그는 남기 쉽다 | 남을 수 있다 |
| 성능 | 차이 없음 | 예약 작업이 주기적으로 돈다 | 차이 없음 |
| 메모리 | 차이 없음 | 차이 없음 | 차이 없음 |
| 확장성 | 시연 서버에만 쓴다 | 운영에도 쓸 수 있지만 지금은 필요 없다 | 차이 없음 |
| 운영 부담 | 초기화 1회(runbook 6단계) | 예약 작업 감시 | 없음 |
| 사용자 경험 | 가입 화면에서 삭제 날짜를 미리 안다 | 가입마다 삭제 날짜가 다르다 | 직접 탈퇴해야 한다 |
| 구현량 | 삭제 코드가 없다. runbook, 약관 문구, 처리방침 | 예약 삭제 작업과 그 테스트 | 탈퇴 기능에 기댄다 |

### 등록부 대조 시연은 팀원의 등록곡으로 한다

등록부 대조는 본인확인 이름과 등록부 저작자 이름이 같아야 통과한다. `SANDBOX` 결과는 이름을 저장하지 않으므로, 대조는 Mock 본인확인 계정으로 한다. Mock 이름은 대조할 등록곡의 저작자인 팀원의 실명이다.

대조할 곡은 팀원의 등록곡이다. 공개 등록 정보를 쓰면 시연 서버가 외부에 열려 있어, 방문자가 곡 제목으로 등록부를 찾아 실존 저작자를 알아낼 수 있다. 그러면 "실명 일치" 표시가 동의도 받지 않은 그 사람을 우리 아티스트라고 주장하는 셈이 된다. 팀원의 등록곡을 쓰면 이름의 주인이 동의한 상태로 같은 흐름을 보여 줄 수 있다.

| 관점 | 팀원의 등록곡 (채택) | 시연 서버에서 등록부 조회도 Mock | 공개 등록 정보 |
|---|---|---|---|
| 정확성 | 실제 등록부 API로 실제 등록 저작물과 대조한다 | 실제 API를 부르지 않는다 | 실제 API로 대조하지만, 우리 아티스트는 그 저작자가 아니다 |
| 보안 | 이름의 주인(팀원)이 동의한다 | 실존 인물의 정보가 없다 | 동의 없이 실존 저작자가 우리 아티스트처럼 보인다 |
| 성능 | 차이 없음 | 등록부 외부 호출이 없다 | 차이 없음 |
| 메모리 | 차이 없음 | 차이 없음 | 차이 없음 |
| 확장성 | 차이 없음 | 시연 서버 전용 Mock 등록부가 하나 더 생긴다 | 차이 없음 |
| 운영 부담 | 등록곡이 없으면 새로 등록한다(처리 기간 7일, 수수료). 등록 뒤 공공데이터 API에 반영되는지 확인한다 | Mock 등록부 데이터를 관리한다 | 없음 |
| 사용자 경험 | 실제 흐름을 그대로 보여 준다 | 배너가 시연 데이터임을 알린다 | 방문자가 오해할 수 있다 |
| 구현량 | 없음 | Mock 등록부를 구현한다 | 없음 |

## Consequences

- NSU-105의 범위에 다음이 더해진다. 응답 채널 검사(`TEST` 채널만)와 채널로 정하는 출처, 출처별 저장 항목(`SANDBOX`는 확인 사실만), 기본값 없는 제공자·환경 설정과 시작 시 검사(`DEMO`가 아니면 시작하지 않음), Mock 시드 스크립트, 거절한 응답의 로그·저장 금지, 본인확인 시작·완료 요청 제한. `LIVE` 채널·운영 환경은 만들지 않는다. 담당은 김동엽이다(2026-11-05).
- NSU-123(가입 인증 코드 발송 제한)의 범위에 다음이 더해진다. 전체 목록과 테스트 기준은 [계약](../../api/signup-terms-and-send-limits.md)이 기준이다.
  - 발송 한도(받는 곳·확인 시도 하루, IP·IP별 이메일 1시간, SMS·이메일 전체 하루)를 Lua 스크립트 하나로 원자적으로 확인·예약, IPv6 /64 단위, 받는 곳 단위 쿨다운, 대기 challenge, `Retry-After`
  - 발송 결과 분류(SMS 어댑터를 `RestClient`로 교체), 80% 경고 로그와 Slack 알림, 제공자 장애 알림, 창 단위 카운터 초기화 관리 스크립트
  - Redis를 쓸 수 없을 때의 경로별 동작(`503 RATE_LIMIT_UNAVAILABLE` 등)과 카운터 명령 timeout 1초
  - 가입 세션 생성·OAuth 시작·로그인 요청 제한, Redis `maxmemory`·`noeviction`
  - 이메일 정규화(로그인·중복 확인·OAuth·허용 목록, DB 마이그레이션으로 `users.email` 소문자화와 `CHECK`)
  - 가입 세션 생성 때 약관 동의(필수 약관 구분 포함)와 가입 완료 때 동의 기록 저장(새 테이블, DB 마이그레이션)
  - 동시 요청에서 한도를 넘지 않는지는 Testcontainers Redis 통합 테스트로, 어댑터 분류는 로컬 HTTP 서버와 요청 팩토리 예외 주입으로 확인한다.
- NSU-129의 범위에 다음이 더해진다. 공개 쓰기 기본 거절 필터와 허용 경로 목록, 시연 서버 약관 문구(시연 안내·수집·이용·국외 이전)와 처리방침, 늘 보이는 시연 배너, 초기화 runbook 실행, 시연마다 새 아티스트 A를 만드는 시드 절차. 이슈를 나눌지는 NSU-129에서 정한다.
- 발송 한도와 동의 저장은 `DEMO` 전용이 아니라서, 가입 API를 고친다. 바뀌는 것 전체(약관 동의 시점, 약관 PUT 제거, 번호 형식, 발송·확인·세션 생성·OAuth·로그인 한도와 응답, `503 RATE_LIMIT_UNAVAILABLE` 새 공통 code, 이메일 정규화)는 [signup-terms-and-send-limits.md](../../api/signup-terms-and-send-limits.md) §2 표가 기준이다. 이미 구현된 가입 API와 화면을 깨는 breaking change다. 클라이언트가 이 저장소의 가입 화면뿐이라 `/api/v2`를 열지 않고, 백엔드(NSU-123)와 가입 화면(NSU-129)을 같은 배포로 낸다(00 §1 예외, 03 §12.1과 같은 방식). 약관 동의 시점과 시연 약관은 SSOT `AUTH-006`의 v1.18 초안 ⑤(팀 확인 전)에 기댄다.
- 공개 쓰기 검사는 `403 DEMO_WRITE_NOT_ALLOWED`를 새로 쓴다. 기본 거절이라 모든 쓰기 API에 해당한다. 그래서 기능별 계약마다 적지 않고 00 공통 규약에 `DEMO`에서만 나는 공통 오류로 한 번 적는다. 판정 순서는 인증 바로 다음이다. 00 §8에 공통 오류로 적었고, 03 §9, 02 §5, 04 §2.2·§3.2(검사 1-1), 05 §4에 그 순서를 넣었다. 기존 쓰기 API 테스트는 `DEMO` 필터가 들어가면 허용 목록 계정으로 요청하도록 고친다(NSU-129).
- PR #186(`music_upload/02` §7)은 2026-11-05 main에 머지됐고(`d508d02`), 이 브랜치는 그 위로 옮겼다(충돌 1건은 아래 기준으로 풀었다). 이 ADR은 §7을 근거로 쓰고, 두 PR이 `music_upload/01`을 함께 고치기 때문이다. 충돌을 풀 때 PR #186의 안전장치 4(`SANDBOX`는 `IDENTITY_NAME_UNAVAILABLE`)와 이 ADR의 안전장치 3(운영으로 옮기지 않음)을 둘 다 살린다. PR #187(NSU-48)과 #191(05 계약)은 2026-11-07 main에 머지됐고(`5f66f19`), 이 브랜치는 그 위로 다시 옮겼다. `recommendation_eligibility/00`의 버린 안 행 충돌은 #187의 사유(v1.17 `RIGHTS-023`·`RIGHTS-024` 근거)를 살리고, 이 ADR 링크와 `music_upload/01`을 고친 사실을 더해 풀었다. PR #186이 이 ADR에 맞춰 다음을 고쳤다(2026-11-05, `0cb9a91`·`2d0500b`·`8c67786`·`2574d1e`). `2574d1e`(02 §7 출처 판정을 이 ADR로 넘김, "운영 전환 때 무효"와 남은 결정 6을 "운영으로 옮기지 않음"으로, 04 §3.2, `music_upload/01`)도 머지에 들어갔다.
  - `music_upload/02` §7 "MVP 시연" 행: KCP 테스트 창(`SANDBOX`), Mock은 등록부 대조용 시드 계정만, `SANDBOX`의 등록 정보 제출은 `403 IDENTITY_NAME_UNAVAILABLE`
  - 04 §3.2 검사표·본문, §4 오류표, §5 테스트 기준과 `music_upload/01` 안전장치 4: 대조는 `MOCK` 이름만 쓰고, `SANDBOX`는 `403 IDENTITY_NAME_UNAVAILABLE`
- `IDENTITY_NAME_UNAVAILABLE`을 `ErrorCode`에 더하는 일은 등록 정보 제출 구현(NSU-89)이 한다.
- Trust Profile 계약(01 §4.3)에 `IDENTITY`를 추가했다. enum 값 추가라 하위 호환이다(00 §3). SSOT에는 `TRUST-142`에 v1.18 초안 ③으로 올렸다(팀 확인 전). 다만 그 초안은 실명 본인확인을 "추가 Trust Verification 후보" 목록에 넣었다. 용어집상 실명 본인확인은 Verified Artist의 조건이라 아티스트가 선택하는 Trust Verification이 아니다. 그래서 초안 ③의 위치는 SSOT에서 고쳐야 한다. 구현은 NSU-105가 한다. 01 §4.2에 "`COPYRIGHT`가 있으면 `IDENTITY`도 있다" 불변식을 넣었다. 등록정보 일치는 본인확인 이름이 있어야 생기기 때문이다. 01 §7에 Verification을 출처 도메인별 `VerificationSource`(NSU-105: `IDENTITY`, NSU-89: `COPYRIGHT`)로 읽어 합치는 구조를 적었다.
- 테스트 표시는 배너라서 Trust Profile 계약(01 §4.3)과 본인확인 상태 API에 출처 필드를 더하지 않는다. 환경 값 API도 만들지 않는다.
- 운영 단계는 새 ADR로 미룬다. 그 ADR이 정할 것은 사업자등록·본인확인 계약, 운영 제공자와 `LIVE` 채널 검사, 운영 DB(시연 데이터를 옮기지 않음), 환경 값과 배너·공개 쓰기 필터를 끄는 방법이다.
- 등록부 대조 시연에 쓸 팀원의 등록곡이 없으면 시연용 곡을 새로 등록한다. cros.or.kr에서 인증서로 접수하고, 처리 기간은 7일(신청서 서식 기준)이며 수수료가 든다. 등록 뒤 공공데이터 API에서 그 등록번호가 조회되는지 미리 확인한다(NSU-129).
- 곡 업로드는 `VERIFIED_ARTIST`만 한다(ADR `music_upload/02` §7, PR #186). 그래서 본인확인을 하지 않은 아티스트는 곡이 없어 Eligibility 후보가 되지 못한다(이 간접 조건 문장은 SSOT v1.18 초안 ②, 팀 확인 전). [recommendation_eligibility/00](../recommendation_eligibility/00_eligibility_rules.md)과 [music_upload/01](../music_upload/01_music_rights_verification.md)의 버린 안 사유를 이에 맞게 고쳤다.
- 시연 서버는 `SANDBOX` 결과의 이름·생년월일·CI를 남기지 않으므로 SSOT `AUTH-009`(v1.17.1 승인)의 최소 식별값을 시연에서 지키지 못한다. 이 예외는 SSOT `AUTH-009`에 v1.18 초안 ④로 적었다(팀 확인 전).
- 시연에 필요한 기능을 이슈로 나눴다. PRIVATE 열람 판정은 NSU-127, 댓글은 NSU-128, 시연 준비는 NSU-129다. 등록 정보 제출은 NSU-89다.
- SSOT v1.17(2026-11-05 Human Confirm)의 `ART-027`은 "Verified Artist"를 "`ACTIVE` ARTIST"로 읽는다. 그 근거 문장은 승인 뒤 v1.18 초안 ②로 고쳤다(팀 확인 전). 프로필 입력은 책임을 물을 실명이 필요한 행동이 아니어서, 본인확인 전에 프로필을 먼저 채울 수 있게 한다. 추천 후보가 되려면 곡이 있어야 하므로 실명 본인확인은 곡 업로드를 거쳐 사실상 필요하다는 점도 함께 적었다.
- 프론트 체험판의 `ARTIST_VERIFIED`("아티스트 인증")와 "작업물 권리 확인" 배지를 계약에 맞춰 바꾼다(NSU-129).
- 아티스트용 행사 목록 API가 없어서, 시연은 PRIVATE 행사 상세 주소로 보여 준다. 목록 API를 만들지는 NSU-127 설계에서 정한다.

| 한 채널에서 10분 안에 결과 모름·확정 실패 6번째 | Slack `#dev` 알림 한 번 |
| 서버 전체 SMS 또는 이메일 한도의 80% | Slack `#dev`에 한 번 알림이 오고, 알림에 번호·이메일·IP가 없다 |
| 시드 스크립트·저장소 | 시드 계정 비밀번호가 없다 |
| Mock 본인확인을 고르는 HTTP 요청 | 그런 엔드포인트가 없다 |
| 제공자나 환경 설정 없이, 또는 환경을 `DEMO`가 아닌 값으로 서버 시작 | 시작하지 않는다 |
| 제공자 설정을 `MOCK`(또는 PortOne 테스트가 아닌 값)으로 서버 시작 | 시작하지 않는다 |
| 허용 목록 주소로 OAuth 가입한 계정이 곡 업로드 | `403 DEMO_WRITE_NOT_ALLOWED`(이메일 인증 가입 계정만 허용 목록) |
| OAuth 가입 준비 요청에 필수 약관이 없음 | `400 REQUIRED_TERMS_NOT_AGREED`, 문자를 보내지 않는다 |
| 이메일 하루 81번째 발송 요청 | `429`, `Retry-After`는 다음 09:00(Asia/Seoul)까지 |
| 발송 제공자 응답이 시간 초과 | 카운터를 되돌리지 않는다 |
| Redis 한도 카운터 키 | 번호·이메일·IP 원문이 없다 |
| 처리방침 | 열람·정정·삭제 요청 창구가 있고, 요청을 10일 안에 처리한 기록이 NSU-129에 있다 |
| 같은 번호로 하루 6번째 인증 코드 요청(가입 세션을 새로 만들어도) | `429 VERIFICATION_REQUEST_LIMIT_EXCEEDED`, `Retry-After` |
| 같은 IP에서 1시간 안 21번째 요청, 서버 전체 하루 301번째 SMS 요청 | 같다. IP 한도의 `Retry-After`는 다음 정각까지다 |
| 한도·쿨다운에 걸려 거절된 요청 | 어느 카운터도 늘지 않고 기존 코드는 그대로 유효하다(시간 초과는 센다) |
| 제공자에 닿은 확정 실패(`4xx`) | 받는 곳 카운터만 되돌린다. 요청 IP·서버 전체 카운터와 쿨다운은 남아, 늘 거절되는 받는 곳으로 반복해도 한 IP의 제공자 호출은 1시간 20회 이하다. 이미 받은 코드는 그대로 유효하다 |
| 같은 번호로 세션 두 개를 만들어 60초 안에 각각 발송 | 두 번째는 `429`(쿨다운은 받는 곳 단위) |
| 같은 IP에서 `+` 주소를 바꿔 가며 1시간 안 이메일 11번째 발송 | `429`, `Retry-After`는 다음 정각까지 |
| 한 IP에서 확인 시도 하루 10회를 다 쓴 번호로 같은 IP에서 발송 요청 | `429 VERIFICATION_ATTEMPT_LIMIT_EXCEEDED`, 문자를 보내지 않는다 |
| 다른 IP에서 피해자 번호로 오답 10번을 넣은 뒤 피해자가 자기 IP에서 가입 | 발송·확인이 된다 |
| 대문자가 섞인 이메일로 가입한 뒤 같은 값으로 로그인 | 로그인된다 |
| 번호를 `010-1234-5678`처럼 형식만 바꿔 세션 생성 | `400 VALIDATION_ERROR` |
| 같은 번호로 가입 세션 여러 개에서 인증 코드 요청 50건을 동시에(Testcontainers Redis) | 정확히 1건만 발송된다(받는 곳 쿨다운). 쿨다운을 0초로 둔 테스트 설정에서는 정확히 5건(하루 한도) |
| 같은 /64 대역의 다른 IPv6 주소들에서 1시간 안 21번째 요청 | `429` |
| 필수 약관 동의 없이 가입 세션 생성 요청 | `400 REQUIRED_TERMS_NOT_AGREED`, 세션을 만들지 않고 문자·메일을 보내지 않는다 |
| 가입 세션을 만들고 30분 동안 가입을 마치지 않음 | Redis에서 세션의 이메일·번호가 사라지고 DB에 없다 |
| 허용 목록 밖 계정의 `GET` 요청 전체 | 02 §2.5 재생 주소 발급(재생 기록)을 빼면 상태가 바뀌지 않는다(외부 링크 연동 저장은 `POST`). 재생 주소 발급은 NSU-122에서 다시 맞춘다 |
| 외부 사람이 시연 서버에 가입 | 가입 화면에 시연 서버임, 수집 항목, 보유 기간, 처리 위탁이 보이고, 동의 기록이 DB에 저장된다 |
| 모든 화면 | 시연 환경 배너가 보인다 |
| 리허설 다음 본 시연 | 시드로 만든 새 아티스트 A가 본인확인 전 상태다 |
| 졸업 작품 최종 평가 다음 날 초기화 뒤 | DB·Redis·백업·버킷 이전 버전·로그에 외부 가입 데이터가 없고, runbook 단계별 결과가 NSU-129에 있다 |
