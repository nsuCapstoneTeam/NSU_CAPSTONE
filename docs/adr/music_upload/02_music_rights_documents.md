# ADR: 곡 권리 서류 — 아티스트가 준비하고 서버는 검증만 한다

- 상태: **Proposed** (PR 리뷰에서 확정)
- 결정일: **2026-11-05** (김동엽). 2026-11-02 초안(운영자가 이용허락 범위를 검토한 뒤 이용 시작)을 대체한다
- 관련: [PR #150](https://github.com/nsuCapstoneTeam/NSU_CAPSTONE/pull/150), [00 곡 업로드 검사](./00_music_upload_validation.md), [01 곡 권리 검증](./01_music_rights_verification.md), [04 곡 API §2](../../api/04_music.md), SSOT v1.17 초안 `RIGHTS-016`·`017`·`023`·`161`, `ADMIN-095`, `STORAGE-102`, NSU-89·103·104

## 1. 결정 요약

**저작권 관련 서류는 아티스트가 모두 준비한다. 서버는 업로드 때 서류가 갖춰졌는지와 파일 형식만 검증하고, 서류의 진위와 허락 범위는 판단하지 않는다. 권리 문제는 신고가 오면 정해진 절차로 즉시 중단해 처리한다.**

| 단계 | 누가 | 할 일 |
|---|---|---|
| 1. 업로드 전 준비 | 아티스트 | 곡의 권리 관계를 확인한다. 아티스트 말고 권리를 가진 사람이 있으면 권리자별 이용허락서(서식 02 또는 같은 범위의 기존 계약서)를 받아 둔다 |
| 2. 업로드 때 검증 | 서버 | 권리 확인·이용 동의(서식 01의 화면판) 문구 버전, 제3자 권리가 있을 때 이용허락서 첨부 여부와 개수, 서류 파일의 형식(PDF·JPEG·PNG)과 크기(파일당 5MiB)를 검사한다. 통과하면 바로 저장하고 분석·추천·재생에 쓴다 |
| 3. 신고 대응 | 플랫폼 | ① 신고 수령인 공지 ② 즉시 중단(재생 주소·추천·분석 모두) ③ 신고자와 업로더 양쪽 통보 ④ 소명하면 재개 ⑤ 반복 침해 계정 정지 |

- **곡은 실명 본인확인을 마친 아티스트(`VERIFIED_ARTIST`)만 올린다**(2026-11-05). 서류의 진위는 보지 않는 대신, 침해 신고가 왔을 때 책임을 물을 실명이 남게 한다. 시연 방식은 7절에 있다.
- 운영자는 서류를 심사하지 않는다. "검증 통과"는 형식 검사를 통과했다는 뜻이며, 권리의 존재를 인증하지 않는다.
- 이 결정은 법적 위험을 줄이는 운영 방식이다. 서류를 받았다는 이유만으로 플랫폼의 책임이 없어지지는 않는다(4절).
- API 계약은 [04 곡 API §2](../../api/04_music.md)(`hasThirdPartyRights`, `licenseFiles`)에 있다. 신고 대응은 NSU-104로 구현한다.

## 2. 왜 이 문제가 생겼는가

우리 서비스는 아티스트의 곡을 분석해 행사 요청과 **음악 유사도**가 높은 곡을 추천한다. EVENT_PARTNER는 행사를 등록하고 아티스트를 섭외하는 사용자다. 이 사용자는 추천된 곡을 듣고 섭외 여부를 판단한다.

이 과정에는 서로 다른 사용이 들어간다.

| 서비스가 하는 일 | 필요한 허락 |
|---|---|
| 음원 파일을 받아 서버에 보관 | 파일 제출·복제·보관 |
| CLAP으로 음악의 특징을 분석 | 필요한 파일 처리, 특징 벡터 생성·저장, 음악 유사도 계산 |
| 추천 결과에서 미리듣기 제공 | 해당 구간을 EVENT_PARTNER에게 재생·전송 |

CLAP은 이 설계에서 음악과 행사 요청을 비교하는 기존 모델이다. **추론**은 모델로 입력을 분석하는 작업이고, **embedding(특징 벡터)**은 비교에 쓰는 숫자 묶음이다. 업로드한 곡으로 모델을 새로 학습시키거나 파인튜닝하는 작업은 허락 범위에 포함하지 않는다.

따라서 "노래를 들을 수 있다", "아티스트가 올렸다", "AI 분석에만 쓴다"는 설명 하나로 세 가지 사용의 권한이 모두 해결되지는 않는다. 이용허락을 받는 경우에도 실제 사용 방법과 조건이 그 범위 안에 있어야 한다. [저작권법 제46조](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0046&lsiSeq=285693&urlMode=lsScJoRltInfoR)

## 3. 검토 과정

### 3.1 권리 보증과 등록부 자동 대조

[기존 권리 설계](./01_music_rights_verification.md)는 아티스트에게 권리 보증을 받고, 등록한 곡은 공적 등록부와 자동으로 대조하는 방식이다. 운영자가 곡마다 서류를 읽어야 하는 부담을 줄이려는 선택이었다.

확인하는 사실에는 한계가 있다.

- **권리 보증:** 아티스트가 사용할 권리가 있다고 약속한 것이다. 실제 권리를 증명한 것은 아니다.
- **등록정보 일치:** 등록번호·제목·이름 등이 일치한 것이다. 제출한 녹음 파일이 그 곡인지, 녹음물과 반주까지 사용할 수 있는지는 별도 문제다.
- **외부 계정 연결:** 그 계정에 접근할 수 있음을 확인한 것이다. 계정에 게시된 모든 음악의 권리를 갖고 있다는 뜻은 아니다.

그래서 기존 설계도 등록부 대조만으로 `VERIFIED`를 주지 않도록 구분했다. 다만 커버곡처럼 다른 사람의 권리가 들어간 곡을 "커버곡" 표시와 보증만으로 받는 점이 남았다.

### 3.2 샘플 길이로 해결되는지

짧은 미리듣기의 길이 제한을 검토했다. 업로드 ADR에는 KOMCA의 무료 홍보용 스트리밍 규정을 참고해 56~60초를 제안한 배경이 남아 있다.

하지만 **"30초 이하면 자유 이용", "60초 이하면 적법"이라는 일반 기준으로 사용할 수는 없다.** 공정이용은 목적, 저작물의 성격, 사용한 부분의 비중·중요성, 시장에 미치는 영향 등을 함께 판단한다. 짧다는 사실만으로 결론을 낼 수 없다. [저작권법 제35조의5](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=05&joNo=0035&lsiSeq=285693&urlMode=lsScJoRltInfoR)

특정 사용료 면제 규정도 우리 서비스와 대상 곡에 실제로 적용되는지 확인해야 한다. 그 규정의 숫자만 가져와 원곡·실연·녹음물의 모든 권리나 서버 분석까지 허락된 것으로 보지 않는다. 이 ADR은 해당 면제가 우리 서비스에 적용된다고 결정하지 않는다.

따라서 길이는 분석 품질과 전송량을 위한 제품 조건으로 관리하고, 이용 권한은 서류로 따로 다룬다. 업로드 길이는 서버 협의 013과 SSOT `AI-033`에서 정한다.

### 3.3 YouTube에서 가져와 분석하고 링크로 들려주는 방식

검토한 흐름은 "아티스트가 YouTube에 게시 → 서버가 음원을 다운로드해 CLAP 분석 → 추천 결과에는 YouTube 링크 제공"이었다. 미리듣기를 외부 플랫폼에 맡기면 직접 음원을 전송하는 부담을 줄일 수 있다고 보았다.

하지만 다음 두 문제는 남는다.

1. YouTube에서 재생할 수 있다는 사실이 우리 서버의 다운로드·보관·분석 허락을 뜻하지 않는다.
2. YouTube API 정책은 사전 서면 승인 없는 영상 콘텐츠의 다운로드·저장 등을 제한하고, 오디오와 비디오 구성요소를 분리하는 행위도 금지한다. 아티스트의 동의와 YouTube의 API 이용 조건은 각각 확인해야 한다. [YouTube API 개발자 정책 III.E.1·III.I.7](https://developers.google.com/youtube/terms/developer-policies)

그래서 **분석용 파일은 아티스트가 적법하게 확보한 파일을 직접 제출하는 방향**을 택했다. 외부 링크나 공식 플레이어는 미리듣기의 선택지가 될 수 있지만, 서버의 음원 추출을 허용하는 근거로 사용하지 않는다.

### 3.4 운영자가 이용허락 범위를 검토하는 방식 (2026-11-02 초안)

11-02 초안은 아티스트가 서류를 준비하고, 운영자가 서명자의 권한·파일과 서류의 일치·허락 범위를 확인한 뒤 분석·추천·재생을 시작하는 3단계를 택했다. 서류를 준비하게 하는 것만으로는 그 서류가 이 서비스의 사용 방법을 허락하는지 알 수 없다는 이유였다.

이 방식은 검토 담당자, 보완·거절 기준, 검토 대기 상태가 필요하다. 검토 결과를 플랫폼의 권리 판단으로 볼 여지도 생긴다. 2026-11-05 사용자는 운영자 검토를 두지 않고, 아티스트가 서류를 모두 준비하고 서버는 검증만 하는 방식을 택했다.

### 3.5 서류를 받는 형태

| 관점 | 운영자 검토 (11-02 초안) | A 전자 동의 + 제3자 이용허락서 첨부 (채택) | B 모든 서류를 파일로 첨부 | C 보증만 받고 서류는 아티스트 보관 |
|---|---|---|---|---|
| 정확성 | 파일과 권리자·허락 범위를 사람이 연결해 본다. 위조·누락은 남는다 | 제3자 권리가 있는 곡은 이용허락서가 없으면 올라가지 않는다. 진위는 보지 않는다 | A와 같다. 본인 서명 파일이 늘어도 서버가 내용을 읽지 못해 확인 수준은 같다 | 서류가 실제로 있는지 서버가 모른다. 신고가 와야 확인한다 |
| 보안·개인정보 | 민감한 서류 열람 권한과 기록이 필요하다 | 이용허락서(실명·서명)를 비공개로 보관한다. 열람 API는 없고 삭제 기한을 둔다 | 모든 곡의 서명 파일을 보관해 개인정보 보관량이 가장 많다 | 서버에 서류가 없다 |
| 성능 | 사람 검토 대기가 생긴다 | 제3자 권리가 있는 곡만 파일 수신이 늘어난다(파일당 5MiB 이하) | 모든 업로드에서 파일 수신이 늘어난다 | 늘어나는 것이 없다 |
| 메모리 | 차이 없음 | 차이 없음(임시 파일로 받는다) | 차이 없음 | 차이 없음 |
| 확장성 | 검토량이 늘면 담당자가 병목이 된다 | S3 저장량이 조금 늘어난다 | 저장량이 늘어난다 | 차이 없음 |
| 운영 부담 | 검토·보완·거절 업무가 필요하다 | 서류 보관·삭제를 관리한다. 검토 업무는 없다 | A와 같고 양만 많다 | 신고가 오면 서류를 요청하고 기다려야 한다 |
| 사용자 경험 | 아티스트가 검토를 기다린다 | 자작곡은 동의만, 제3자 권리가 있는 곡만 파일을 첨부한다 | 모든 곡에 서명 파일을 준비해야 한다 | 가장 빠르다 |
| 구현량 | 검토 상태·권한·기록·이용 기능 연결이 필요하다 | 중간(첨부 파트와 서류 저장) | 중간 | 적다(문구만 바뀜) |

A를 택한 이유는 다음과 같다.

- **정확성:** 제3자 권리가 있는 곡을 서류 없이 분석·재생하는 경우를 업로드 단계에서 막는다. C는 이를 막지 못한다.
- **사용자 경험:** 자작곡은 동의만으로 올린다. B는 모든 곡에 서명 파일을 요구한다.
- **개인정보:** 서류를 받는 곡을 제3자 권리가 있는 곡으로 좁힌다.
- **운영 부담:** 운영자 검토 없이 처리할 수 있다.

## 4. 법적 근거와 남는 위험

2026-11-05에 2026-10-29 시행 저작권법(법률 제21595호) 조문을 확인했다. 법률 자문이 아니다.

**진위 확인 의무는 없다.** 온라인서비스제공자는 서비스 안의 침해를 모니터링하거나 적극적으로 조사할 의무가 없다(제102조 제3항). 그래서 서버가 서류의 진위와 허락 범위를 판단하지 않는 설계 자체는 법 위반이 아니다.

**면책을 받으려면 아래 요건을 모두 갖춰야 한다** (제102조 제1항 제3호, 저장 서비스).

| 요건 | 우리 서비스에서 할 일 |
|---|---|
| 송신을 먼저 시작하지 않고, 저작물이나 받는 사람을 고르지 않음. 반복 침해자의 계정을 해지하는 방침을 두고 실제로 지킴 | 반복 침해 계정 정지(NSU-104). 추천이 "고르는 것"에 해당하는지는 불확실하다 |
| 침해를 통제할 수 있다면, 그 침해로 직접적인 금전 이익을 얻지 않음 | 지금은 무료라 해당할 일이 적다. 유료화할 때 다시 본다 |
| 침해를 알았거나 명백한 정황을 알면 즉시 중단 | 신고가 오면 바로 재생·추천·분석을 멈춘다 |
| 신고를 받을 사람을 지정해 공지 | 신고 수령인 공지 |

여기에 제103조 절차가 붙는다. 신고를 받으면 즉시 중단하고 신고자와 업로더에게 알린다(제2항). 업로더가 정당한 권리를 소명하면 재개 예정일을 신고자에게 알리고 그날 재개한다. 신고자가 그 전에 소송을 제기했다고 알리면 재개하지 않는다(제3항).

**신고 시 중단으로도 면책되지 않는 경우가 있다.**

1. **알게 된 뒤의 책임:** 침해를 안 때부터 신고를 받기 전까지 생긴 책임은 면제되지 않는다(제103조 제5항 단서). 업로드 때 "커버곡"이라는 답을 받고도 원곡의 허락 없이 분석·재생하면 "명백한 정황"으로 볼 여지가 있다.
2. **플랫폼이 직접 하는 이용:** 면책 조항은 다른 사람의 복제·전송으로 생긴 침해에 관한 것이다. CLAP 분석(파일 복제, embedding 생성)은 플랫폼이 직접 하는 일이라 면책 대상이 아닐 수 있다. 한국에는 정보분석(TDM) 예외 조항이 없고, 공정이용(제35조의5)에 해당하는지도 불확실하다.

그래서 **제3자 권리가 있는 곡은 그 권리자의 이용허락서를 업로드 조건으로 둔다.** 아티스트 본인의 권리는 동의로 해결된다. 커버곡의 원곡이나 MR·샘플처럼 제3자에게 있는 권리는 그 권리자의 허락이 있어야 한다.

약관으로 아티스트에게 책임을 넘겨도 권리자(제3자)에 대한 플랫폼의 책임은 없어지지 않는다. 사업자의 고의·중과실 책임을 면제하는 약관 조항은 무효다(약관의 규제에 관한 법률 제7조). 그래서 서식은 확인 내용이 사실과 다를 때의 아티스트 책임을 적되, 모든 책임을 아티스트에게 넘기는 문구를 쓰지 않는다.

추천이 면책 요건을 깨는지, AI 분석이 복제에 해당하는지는 상용화 전에 전문가에게 확인한다([01](./01_music_rights_verification.md) "상용화 전 할 일"과 같다).

## 5. 어떤 곡을 받는가

받는 기준은 "자작곡인지 커버곡인지"라는 이름이 아니라 **제출한 녹음 파일에 아티스트 말고 권리를 가진 사람이 있는지**다. 서버는 이 구분을 판단하지 않는다. 아티스트가 제3자 권리 여부를 고르고, 있으면 이용허락서를 올린다.

| 예시 | 제3자 권리 | 아티스트가 준비할 서류 |
|---|---|---|
| 혼자 작사·작곡·연주·녹음한 자작곡 | 없음(양도·신탁·독점계약이 없을 때) | 업로드 화면의 동의만 |
| 다른 사람이 공동 창작·연주한 자작곡 | 있음 | 공동 권리자·실연자의 이용허락서 |
| 직접 연주·녹음한 커버곡 | 있음(원곡의 작사·작곡) | 원곡 권리자의 이용허락서. 편곡·개사가 있으면 그 변경 허락도 포함 |
| MR·비트·샘플을 사용한 곡 | 있음 | 소재 권리자의 이용허락서, 또는 이 서비스의 이용을 포함하는 라이선스 계약서 |
| 보호기간이 끝난 원곡을 직접 연주·녹음한 곡 | 새 편곡·실연·녹음물에 남의 권리가 없으면 없음 | 업로드 화면의 동의만 |
| 남이 가진 상업 발매 Master를 그대로 올리는 곡 | 있음(Master) | Master 권리자의 이용허락서 |

- 아티스트 한 명의 서명만으로 다른 권리자의 허락이 생기지는 않는다.
- 신탁한 곡은 아티스트가 동의해도 전송 권리가 신탁단체에 있다. 서버는 신탁 여부를 자기 신고로 기록하고, 플랫폼은 상용화 전 KOMCA 사전 신고·협의로 재생 근거를 마련한다([01](./01_music_rights_verification.md)).
- 이용허락서는 서비스의 이용 범위(보관, CLAP 분석·추천, 서비스 내 미리듣기) 전체를 허락해야 한다. 서버는 곡마다 다른 허락 범위를 적용하지 못하기 때문이다. 그렇지 않은 곡은 올리지 않는다.

## 6. 운영

### 1단계 — 업로드 전 준비 (아티스트)

아티스트는 자기 권리와 다른 사람의 권리를 구분한다. 필요한 권리자의 허락은 음원을 올리기 전에 받는다. 허락서에는 대상 파일·구간, 서비스에서 할 일, 기간·지역·대가가 드러나야 한다. 권한이 불분명하면 올리지 않는다.

### 2단계 — 업로드 때 서버 검증

서버는 다음만 검사한다. 통과하면 바로 저장하고 AI 임베딩을 요청하며, 추천과 미리듣기에 쓴다.

- 올리는 아티스트가 실명 본인확인을 마쳤는지(`VERIFIED_ARTIST`, 아니면 `403 IDENTITY_VERIFICATION_REQUIRED`)

- 권리 확인·이용 동의 문구가 지금 버전인지
- 제3자 권리가 있다고 고른 곡에 이용허락서가 1개 이상 있는지(최대 5개)
- 이용허락서가 PDF·JPEG·PNG이고 파일당 5MiB 이하인지(파일 내용으로 판별)
- 음원의 형식·크기·길이([00](./00_music_upload_validation.md))

서명한 사람의 권한, 파일과 허락서의 일치, 허락 범위는 판단하지 않는다. 빈 서식이나 서명 없는 파일도 형식이 맞으면 통과한다. 서류에 적힌 이용 기간도 읽거나 추적하지 않는다. 그 확인은 서류를 준비한 아티스트의 책임이며(서식 01), 권리 문제는 3단계로 처리한다.

이용 범위는 **기존 CLAP 모델의 추론과 음악 유사도 추천**이다. 모델 학습·파인튜닝, 음성 복제, 생성형 콘텐츠 제작, 음원·embedding 판매는 포함하지 않는다.

### 3단계 — 신고 대응 (플랫폼, NSU-104)

1. **신고 수령인 공지:** 복제·전송 중단 요구를 받을 담당자와 연락처를 서비스에 공지한다(제103조 제4항).
2. **즉시 중단:** 신고를 받으면 그 곡을 바로 멈춘다.
   - 재생: 새 재생 주소를 발급하지 않는다. 이미 발급한 재생 주소(최대 10분 유효, 서버 협의 014)도 바로 쓸 수 없게 한다. 끊는 방법은 NSU-104에서 정한다(예: 원본을 격리 경로로 옮김).
   - 추천: 추천 후보와 다시 보기에서 뺀다.
   - 분석: AI 분석 요청과 재분석을 멈추고, 그 곡을 AI 검색 후보로 보내지 않는다.
3. **양쪽 통보:** 중단 사실을 신고자(권리주장자)와 곡을 올린 아티스트에게 알린다(제103조 제2항).
4. **소명하면 재개:** 아티스트가 정당한 권리를 소명해 재개를 요구하면, 재개 요구 사실과 재개 예정일을 신고자에게 알리고 그날 재개한다. 예정일 전에 신고자가 소송을 제기했다고 알리면 재개하지 않는다(제103조 제3항).
5. **반복 침해 계정 정지:** 중단이 확정된 곡이 정해진 수를 넘은 계정은 정지한다(제102조 제1항 제1호 다목).

운영자는 신고 내용의 옳고 그름을 판단하지 않고 위 순서대로 처리한다. 신고부터 재개까지의 시각과 당사자를 기록한다. 중단 기록은 곡을 지워도 (아티스트, 파일 SHA-256) 단위로 남고 정식 재개로만 풀린다([01](./01_music_rights_verification.md)). 허락 만료·철회도 같은 흐름으로 처리한다. 서버가 이용 기간을 추적하지 않으므로, 만료·철회는 권리자나 아티스트가 알려 온 때(서식 01·02의 종료 요청 또는 신고)부터 즉시 중단 대상이다. 알린 뒤에도 쓰면 "알게 된 뒤의 책임"(4절)이 생기기 때문이다.

## 7. 업로드 자격과 시연 방식 (2026-11-05 결정)

**실제 서비스에서는 사업자등록 뒤 본인확인 서비스를 계약해, 실명 본인확인을 마친 아티스트만 곡을 올리게 한다.** 사용자가 확인한 바로는 지금 쓸 수 있는 본인확인 API가 모두 사업자등록 번호를 요구한다. 그래서 MVP에서는 실제 본인확인을 붙이지 않는다.

| 구분 | 방식 |
|---|---|
| 실제 서비스 | 사업자등록 → 본인확인 서비스 계약 → 실명 본인확인을 마친 아티스트만 업로드 |
| MVP 시연 | 시연용 더미 계정을 만들고 Mock 본인확인으로 `VERIFIED_ARTIST`가 되게 한다. PortOne + NHN KCP 테스트 채널은 열 수 있지만 실제 검증은 하지 않고 테스트 응답만 준다. 응답 데이터가 실제와 다를 수 있다 |

- 서버는 업로드 때 서류를 검증하지 않고, 권리 문제는 신고가 오면 6절 3단계로 처리한다(1절과 같다).
- 시연용 본인확인 결과는 출처(`MOCK`·`SANDBOX`)를 남기고, 운영 전환 때 무효로 한다([01](./01_music_rights_verification.md) 본인확인 출처 안전장치).
- 본인확인 구현은 NSU-105다. 곡 업로드(NSU-89)는 NSU-105의 본인확인 결과를 읽으므로, NSU-105 전에는 시연 계정용 Mock 본인확인 구현이 먼저 있어야 한다.

## 9. 준비한 서식과 읽는 순서

권리서식은 `docs/곡_권리_서식_샘플/`에 있다. 링크는 저장소 안의 상대 경로다.

| 읽는 순서 | 문서 | 쓰는 사람과 용도 |
|---|---|---|
| 1 | [작성 및 제출 안내](../../곡_권리_서식_샘플/00_작성_및_제출_안내.md) | 아티스트와 운영자가 준비할 서류, 서버 검증 항목, 신고 절차를 확인한다 |
| 2 | [곡 업로드 권리 확인 및 이용 동의서](../../곡_권리_서식_샘플/01_곡_업로드_권리_확인_및_이용_동의서.md) | 아티스트가 권리 관계를 밝히고 자기 권리의 이용을 허락한다. 업로드 화면에서 전자 동의로 받는다 |
| 3 | [곡 비독점적 이용허락서](../../곡_권리_서식_샘플/02_곡_비독점적_이용허락서.md) | 제3자 권리자 또는 적법한 대리인이 이용을 허락한다. 아티스트가 받아 업로드 때 파일로 올린다 |

아티스트가 필요한 권리를 모두 보유한다면 서식 02를 작성할 필요가 없다. 제3자의 권리가 있으면 서식 02나 같은 범위를 확인할 수 있는 기존 계약서를 올린다. **비독점적 이용허락**은 정한 범위에서 서비스를 이용할 수 있게 하는 계약이며, 저작권 소유권을 플랫폼에 넘기는 계약이 아니다.

세 파일은 2026-10-22 작성하고 2026-11-05 고친 법률 검토용 샘플이다. 서비스명·법적 운영 주체·연락처·기간·대가·보관 조건 등의 빈칸을 확정하고 법률 검토를 받아야 배포용 문서로 쓸 수 있다. 이 경로에는 빈 서식만 두며, 사용자가 작성한 개인정보와 서명·권리 증빙은 저장소에 넣지 않는다.
