# ADR: EVENT_PARTNER 프로필 API

- 상태: **Proposed** (PR 리뷰에서 확정)
- 결정일: **2026-11-05** (NSU-50 설계 세션, 김동엽). 같은 날 설계 리뷰(Claude 적대적 리뷰, Codex 한도로 대신함) 지적을 반영했다
- 관련: [05 EVENT_PARTNER 프로필 API](../../api/05_event_partner_profile.md), [00 공통 규칙 §1·§7](../../api/00_conventions.md), [03 행사 API §3.3·§5.4·§7](../../api/03_events.md), [ADR event_management/01 지역 코드 표준](../event_management/01_region_code_standard.md), SSOT v1.17.1(최종 승인) `MVP-125`·`AUTH-160`·`SEC-120`·`DM-060`, NSU-50, NSU-56(화면), NSU-119(아티스트 프로필), NSU-130, NSU-131

---

## Decision

EVENT_PARTNER가 자기 프로필을 조회·수정·삭제하는 API를 `/api/v1/me/event-partner-profile`에 둔다.

1. **필드**: 담당자 이름(필수, 1~40자), 소속·단체명(선택, 60자 이하), 소개(선택, 700자 이하), 주요 행사 종류(행사의 `eventType` 코드 0~3개), 주요 활동 지역(시·도 2자리 또는 시·군·구 5자리 코드 0~3개).
2. **저장**: 새 테이블 `event_partner_profiles`. `user_id`가 PK이면서 `users.id` FK다(1:1). 목록 두 개는 `VARCHAR[]` 배열과 `CHECK`로 저장한다(`events.genres`와 같은 방식).
3. **프로필 행의 생성 시점**: 가입할 때 만들지 않는다. 처음 `PUT`할 때 만든다. 행이 없으면 `GET`은 `200`과 빈 값(`name: null`, 목록 `[]`, `updatedAt: null`)이다.
4. **수정**: `PUT` 전체 교체. 처음 저장할 때 동시에 요청이 와도 `INSERT … ON CONFLICT (user_id) DO UPDATE` 한 문장으로 처리한다.
5. **삭제**: `DELETE`는 행을 지우고 `204`다. 행이 없어도 `204`다. 지운 뒤 `GET`은 저장 전과 같은 빈 값이다.
6. **동시 수정**: 버전 비교 없이 나중 저장이 이긴다.
7. **경로**: 역할별 경로를 쓴다. 아티스트 프로필(NSU-119)에는 `/api/v1/me/artist-profile`을 제안한다. NSU-119 설계에서 확정한다.
8. **지역**: 시·도 코드와 시·군·구 코드를 함께 받고, 서버가 정규화해 저장한다. 같은 지역은 한 가지 표현으로만 저장된다(05 §2).
   - 시·군·구가 함께 고른 시·도 안에 있으면 시·도로 합친다.
   - 시·군·구가 하나뿐인 시·도(세종 `36`·`36110`)는 시·도 코드로 저장한다.
   - 중복을 하나로 합친다.

## Context

SSOT는 마이페이지 범위로 "EVENT_PARTNER 프로필·일정 관리"(`MVP-125`)만 적고 필드를 정하지 않았다. `AUTH-160`은 EventPartnerProfile을 Auth/User와 다른 도메인 책임으로 두고, 프로필 상태를 `users`에 중복 저장하지 않게 한다. EVENT_PARTNER의 일정은 등록한 행사이며 행사 API(03, NSU-54)가 다룬다.

체험판 화면(NSU-56, `frontend/src/features/my-page/components/profile-tab.jsx`)은 담당자 이름·소개·소속·주요 행사 유형·주요 행사 지역·프로필 사진을 브라우저에 저장한다. 행사 유형과 지역은 한국어 이름 하나를 고르는 단일 선택이고, 지역은 임시 목록 `['서울', '경기', '부산']`이다. 서버에 연결할 때 화면은 코드 0~3개를 고르는 다중 선택으로 바뀐다.

`users` 테이블은 인증 정보(이메일·비밀번호 해시·휴대폰·역할·상태)만 가진다. 가입할 때 담당자 이름을 받지 않으므로 가입 직후에는 프로필 정보가 없다.

아티스트 프로필 API(NSU-119)는 아직 설계 전이다. 그 이슈가 근거로 든 ADR(`recommendation_eligibility/00`)은 프로필 테이블을 NSU-12가 화면과 함께 설계한다고 적는다. 그래서 이 ADR의 경로·저장 방식은 NSU-119에 대한 제안이다.

EVENT_PARTNER 프로필은 표시 정보다. 추천 Eligibility나 순위에 쓰지 않는다. 다른 사용자(아티스트)에게 보여 주는 조회는 아직 없다.

## Rationale

### 필드

| 관점 | 채택: 화면 기준(사진 제외) | 최소(이름·소속·소개) | 화면 기준 + 공개 연락처 칸 |
|---|---|---|---|
| 정확성 | 기존 분류 값을 재사용해 행사 API와 같은 허용 목록으로 검증 | 같음 | 연락처 형식 검증 규칙이 새로 필요 |
| 보안·개인정보 | 담당자 이름은 개인정보다. 자유 입력(소속·소개)에도 개인정보가 들어갈 수 있다 | 같음 | 연락처를 구조화해 모으므로 수집 항목과 노출 범위를 정해야 함 |
| 성능·메모리 | 차이 없음 | 차이 없음 | 차이 없음 |
| 확장성 | 종류·지역을 나중에 아티스트에게 행사를 추천할 때 신호로 쓸 수 있음 | 나중에 컬럼 추가 | 화면 기준과 같음 |
| 운영 부담 | 낮음 | 가장 낮음 | 개인정보 문의 대응 |
| 사용자 경험 | 체험판의 칸을 모두 서버에 저장(선택 방식은 다중 선택으로 바뀜) | 체험판의 칸 2개가 저장되지 않음 | 칸이 늘어남 |
| 구현량 | 중간 | 작음 | 큼 |

목록 상한 3개는 행사 희망 장르(1~3개)에 맞췄다. 연락처 칸을 뺀 이유는 연락처 공유를 막기 위해서가 아니다. SSOT `DM-060`이 DM에서 외부 연락처 공유를 허용하므로, 연락처는 필요할 때 DM으로 주고받으면 되고 프로필에 구조화해 모을 필요가 없다(`SEC-120` 최소 수집).

### 저장 위치

| 관점 | 채택: 새 테이블 + 배열 | `users`에 컬럼 추가 | 새 테이블 + 목록별 자식 테이블 |
|---|---|---|---|
| 정확성 | 종류는 DB `CHECK`. 지역은 배열이라 FK가 없어서 앱이 `regions`로 검증하고, 개편 때 배열 이전 규칙(아래 Consequences)이 필요 | 역할별 `CHECK`가 복잡해짐 | 지역도 FK로 보장 |
| 보안 | 계정 정보와 분리(`AUTH-160`) | 비밀번호 해시와 같은 행이라 응답에 섞일 위험. `AUTH-160`과 어긋남 | 채택안과 같음 |
| 성능 | PK 단건 조회 1번 | PK 단건 조회 1번 | 조회 3번 또는 조인. 수정 때 자식 행을 지우고 다시 넣음 |
| 메모리 | 차이 없음 | 차이 없음 | 차이 없음 |
| 확장성 | NSU-119가 `artist_profiles`로 같은 패턴을 쓸 수 있음 | 역할마다 컬럼이 쌓임 | 지역 역검색에 유리(지금은 필요 없음) |
| 운영 부담 | 새 테이블이라 락 위험 없음. 개편 마이그레이션에 배열 이전이 더해짐 | `users` `ALTER` | 테이블 3개 |
| 사용자 경험 | 차이 없음 | 차이 없음 | 차이 없음 |
| 구현량 | 작음 | 작음 | 큼 |

ADR event_management/01은 "앱 안의 정적 파일로 목록 관리"를 DB가 잘못된 코드를 막지 못한다는 이유로 기각했다. 이 설계도 배열에는 FK가 없어 같은 약점을 일부 갖는다. 목록 자체는 `regions` 테이블에 두고, 형식은 `CHECK`로, 존재는 앱 검증과 개편 마이그레이션의 점검 쿼리로 막는다. 지역으로 역검색하는 기능이 생기면 자식 테이블로 옮긴다.

### 생성 시점과 수정 방식

| 관점 | 채택: 첫 `PUT` 때 생성, 없으면 `200` + 빈 값 | 없으면 `404` | 가입할 때 빈 행 생성 |
|---|---|---|---|
| 정확성 | "아직 입력 안 함"을 `updatedAt: null`로 구분 | `404`가 "계정 없음"과 헷갈림 | 담당자 이름에 `NOT NULL`을 걸 수 없음 |
| 보안 | 차이 없음 | 차이 없음 | 가입 흐름 2곳(일반·OAuth)을 바꿈 |
| 성능 | 조회 1번. 첫 저장 경쟁은 upsert 한 문장 | 같음 | 가입 트랜잭션에 INSERT 1번 추가 |
| 메모리 | 차이 없음 | 차이 없음 | 입력하지 않은 사용자도 행을 가짐 |
| 확장성 | NSU-119도 같은 규칙을 쓸 수 있음 | 같음 | 역할이 늘 때마다 가입 흐름 변경 |
| 운영 부담 | 낮음 | 낮음 | 기존 가입자 백필 |
| 사용자 경험 | 프론트가 분기 없이 빈 폼을 그림 | 프론트가 `404`를 따로 처리 | 채택안과 같음 |
| 구현량 | 작음 | 작음 | 큼 |

`PUT`을 고른 이유는 화면이 항상 전체 입력값을 보내기 때문이다. `PATCH`의 "`null`이 지우라는 뜻인지, 그대로 두라는 뜻인지" 모호함이 없고, 같은 요청을 다시 보내도 저장 값이 같다.

첫 저장 경쟁은 upsert 한 문장으로 처리한다. "찾고 없으면 저장"(JPA `findById` → `save`)은 두 요청이 모두 "없음"을 보고 INSERT해 PK 충돌이 나므로, 충돌을 잡아 다시 시도하는 코드가 필요하다.

### 삭제

| 관점 | 채택: `DELETE` 추가 | 탈퇴 설계로 미룸 |
|---|---|---|
| 정확성 | 삭제 뒤 상태가 저장 전 상태와 같아 불변식이 하나로 유지 | 해당 없음 |
| 보안·개인정보 | 정보주체가 담당자 이름·자유 입력을 지울 수 있음(개인정보보호법 §36) | 탈퇴 기능 전까지 삭제 요구에 응할 수단이 없음 |
| 성능 | `DELETE` 1문장 | 차이 없음 |
| 메모리 | 차이 없음 | 차이 없음 |
| 확장성 | 탈퇴 처리도 같은 삭제를 부를 수 있음 | 탈퇴 설계가 처음부터 만듦 |
| 운영 부담 | 수동 삭제 요청 대응이 필요 없음 | 삭제 요청을 DB에서 직접 처리해야 함 |
| 사용자 경험 | 마이페이지에서 지울 수 있음 | 이름을 지울 수 없음(`name` 필수) |
| 구현량 | 작음(엔드포인트 1개) | 없음 |

### 경로

| 확장성 | 공개 조회를 열 때 `/event-partners/{id}/profile`로 이름이 이어짐 | 역할이 늘면 oneOf가 늘어남 |

| 사용자 경험 | 응답 타입이 고정 | 응답 타입을 역할로 다시 가름 |

### 지역 단위와 정규화

| 관점 | 채택: 시·도 또는 시·군·구, 서버 정규화 | 시·도 또는 시·군·구, 겹치면 `400` | 시·군·구 5자리만 | 시·도 2자리만 |
|---|---|---|---|---|
| 정확성 | 같은 지역이 한 가지 표현으로만 저장. 세종도 하나 | 겹침은 막지만 단독 `36`과 단독 `36110`이 둘 다 저장돼 같은 지역이 두 표현 | "서울 전체"를 상한 3개 안에 표현할 수 없음 | 세부 지역을 표현할 수 없음 |
| 보안 | 차이 없음(허용 목록 검증) | 차이 없음 | 차이 없음 | 차이 없음 |
| 성능·메모리 | 차이 없음(최대 3개 정리) | 차이 없음 | 차이 없음 | 차이 없음 |
| 확장성 | 나중에 지역으로 비교할 때 표현이 하나라 비교가 단순 | 두 표현을 함께 다뤄야 함 | NSU-119 제안과 달라짐 | NSU-119 제안과 달라짐 |
| 운영 부담 | 개편 마이그레이션도 같은 정규화를 적용 | 개편 뒤 겹침이 생기면 그 행의 저장이 막힘 | 시·군·구만 이전 | 시·도만 이전 |
| 사용자 경험 | 두 단계 선택에서 겹쳐 골라도 저장되고, 응답에 정리된 값이 보임 | 겹치게 고르면 이유를 알 수 없는 `400`(필드 정보 없음, ADR-007 §4.2) | 시·도 전체를 고를 수 없음 | 세부 지역을 고를 수 없음 |
| 구현량 | 중간 | 중간 | 작음 | 작음 |

정규화는 요청 값을 바꿔 저장한다. 응답이 정리된 값을 돌려주므로 화면은 응답으로 다시 그린다.

## Consequences

- `V7__create_event_partner_profiles_table.sql`이 새 테이블을 만든다. 기존 테이블을 바꾸지 않는다. 롤백은 테이블을 지우는 forward 마이그레이션이다(PR 설명에 적는다).
- **행정구역 개편 때의 배열 이전**: ADR event_management/01의 "목록 변경과 저장된 코드 이전을 마이그레이션 하나로"를 이 배열에도 적용한다.
  - 각 코드를 새 코드로 바꾼 뒤 05 §2의 정규화(중복 합침, 시·도 안의 시·군·구 합침, 시·군·구 하나뿐인 시·도)를 다시 적용한다. 예: 2026-07 광주·전남 통합(`29`·`46` → `12`) 때 `["29", "46"]`은 `["12"]`, `["29", "46110"]`은 `["12"]`가 된다.
  - 하나가 둘 이상으로 나뉘어 3개를 넘으면, 그 시·도 코드로 합친다.
  - 같은 마이그레이션 끝에서 "저장된 코드가 모두 `regions`의 `code` 또는 `province_code`에 있다"를 확인하는 점검 쿼리를 실행하고, 어긋나면 마이그레이션을 실패시킨다.
  - 이전을 빠뜨리면 사라진 코드가 남고, 화면이 받은 값을 그대로 보낸 `PUT`이 `400`이 된다. 위 점검이 이를 막는다.
- 테이블은 사용자의 역할을 검사하지 못한다. EVENT_PARTNER만 행을 만드는 것은 API의 역할 제한이 보장한다.
- 행사 종류 허용 값이 `ck_events_event_type`과 이 테이블의 `CHECK` 두 곳에 있다. 값을 더할 때 두 `CHECK`를 같은 마이그레이션에서 고친다. 한쪽만 고치면 앱 검증을 통과한 값이 DB에서 거절돼 `500`이 된다. 두 `CHECK`가 `EventType`과 같은지 확인하는 테스트를 둔다(05 §6).
- 프로필 응답에는 이메일·휴대폰이 없다. 다만 소속·소개에 사용자가 연락처를 적을 수는 있다. 다른 사용자용 조회를 열 때 이 점을 고려해 노출할 필드를 정한다.
- 화면과 서버를 함께 배포한다. 필드를 더하면, 그 필드를 모르는 이전 화면이 저장할 때 새 필드가 지워질 수 있다.
- **받아들인 위험: 계정 상태**. JWT는 role claim만 보고 계정 상태를 보지 않는다. 상태 검사는 로그인 시점(`LoginPrincipal.isEnabled`)에만 있다. 그래서 정지된 사용자가 만료 전 토큰으로 프로필을 고칠 수 있다. 행사 API도 같다. 토큰 발급 뒤 상태 반영은 Auth/User 도메인(00 §7, `AUTH-160`)이 정한다.
- 탈퇴할 때 프로필을 지우는 연동과 보유기간은 탈퇴 기능을 설계할 때 정한다. 그때 이 API의 삭제를 다시 쓸 수 있다. FK는 `ON DELETE`를 두지 않는다(사용자 행은 상태로만 탈퇴를 표시한다). 개인정보처리방침의 수집 항목에 담당자 이름을 더하는 일은 PR 설명에 후속 작업으로 적는다.

## Excluded

| 뺀 것 | 이유 | 이어서 할 곳 |
|---|---|---|
| 프로필 사진 | 백엔드에 S3 의존성이 없다. 아티스트 사진, 추천 응답의 `profileImageUrl`과 저장 방식을 한 번에 정한다 | NSU-130 |
| 이메일·휴대폰 조회·변경 | 재인증이 필요한 인증 영역이다. 프로필과 다른 자원이다(`AUTH-160`) | NSU-131 |
| 다른 사용자에게 보여 주는 프로필 조회 | NSU-50 범위가 아니다. 공개할 필드는 그때 정한다 | 필요할 때 새 이슈 |
| EVENT_PARTNER 일정 | 일정은 등록한 행사이며 행사 API가 다룬다 | 03, NSU-54 |
| 버전 비교(낙관적 잠금) | 위 "동시 수정" | 필드가 접근 제어에 쓰이면 |
| 공개 연락처 칸 | 위 "필드" | 없음 |

## Reused

- 분류 값 `EventType`과 그 허용 목록(03 §3.3), 지역 목록 `regions`(03 §7)
- 배열 + `CHECK` 저장 방식(`events.genres`, `Event.java`의 `@JdbcTypeCode(SqlTypes.ARRAY)`)
- 역할 제한과 호출자 식별(`MyEventController`의 `@PreAuthorize`, `@AuthenticationPrincipal Jwt`)
- 오류 형식 `ErrorCode`·`ErrorResponse`·`GlobalExceptionHandler`(ADR-007). 새 `code`는 없다

## Rejected Alternatives

- **`users` 컬럼 추가**: 계정 정보와 표시 정보가 섞이고 `AUTH-160`과 어긋난다.
- **목록별 자식 테이블**: 지역 FK를 얻지만 지금은 역검색이 필요 없어 조회·수정 비용만 는다.
- **가입할 때 빈 행 생성**: 담당자 이름에 `NOT NULL`을 걸 수 없고 가입 흐름 2곳을 바꿔야 한다.
- **`PATCH`**: `null`의 의미가 모호하다. 화면은 항상 전체 값을 보낸다.
- **`/api/v1/me/profile` 공통 경로**: 역할 분기가 서비스 안으로 들어가고 응답 타입이 역할마다 달라진다.
- **겹치는 지역을 `400`으로 거절**: 같은 지역의 두 표현이 남고, 두 단계 선택에서 이유를 알 수 없는 오류가 난다.
- **삭제를 탈퇴 설계로 미룸**: 그동안 삭제 요구에 응할 수단이 없다.
