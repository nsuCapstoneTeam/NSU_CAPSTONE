# ADR: 지역 코드 표준

- 상태: **Proposed** (PR 리뷰에서 확정)
- 결정일: **2026-10-18** (NSU-54·58 설계 세션)
- 관련: [03 행사 API §7](../../api/03_events.md#7-지역-목록), [00 공통 규칙 §2](../../api/00_conventions.md#2-명명), SSOT `EVT-042`·`AI-MATCH-051`·`SEARCH-049`, NSU-12·48·54

---

## Decision

행사 지역과 아티스트의 이동 가능 지역은 시·군·구 단위로 나타내고, 코드는 행정안전부 법정동코드의 앞 5자리(시·군·구 코드)를 문자열로 쓴다.

```text
regionCode = "11680"   (서울특별시 강남구)
앞 2자리   = "11"      (서울특별시)
```

- 단위는 자치구·시·군, 세종특별자치시, 제주의 행정시(제주시·서귀포시)다. 일반구가 있는 시(수원시 등)는 시 하나로 본다.
- 백엔드가 목록을 갖고 값을 검사하며, `GET /api/v1/regions`로 시·도별 시·군·구 목록을 내려준다.
- 목록은 DB의 지역 테이블에 마이그레이션으로 넣고, 행사의 지역 코드는 이 테이블을 참조한다(외래 키). 행정구역이 개편되면 목록 변경과 저장된 코드 이전을 마이그레이션 하나로 처리한다(2026-10-18 구현 계획 결정).
- 이 코드는 00 §2의 enum 규칙(UPPER_SNAKE)에 대한 예외다. 다른 분류 값(행사 종류, 공연 형태, 장르)은 UPPER_SNAKE 코드이고, 목록을 API 문서에 적는다.

## Context

Eligibility의 지역 조건(`REGION_REACHABLE`, `AI-MATCH-051` "행사 지역 이동 가능 여부")은 행사의 지역을 아티스트 프로필의 이동 가능 지역과 비교한다. 그래서 두 쪽이 같은 지역 목록을 써야 한다. `AI-MATCH-051`은 분류 값 목록을 Event·Artist Profile 설계에서 정하라고 한다.

지금 프런트의 지역 선택지는 서울·경기·부산 3개뿐이다. 행사의 "장소"는 자유 입력이고, "지역"은 판정과 검색(`SEARCH-049` Region)에 쓰는 분류 값이다.

## Rationale

**시·군·구 단위.** 같은 시·도 안에서도 이동 부담이 크게 다르다. 경기 북부와 남부, 경북 동해안과 내륙이 그런 예다. 시·군·구 단위면 아티스트가 실제로 갈 수 있는 곳을 고를 수 있어, 이동 판정이 정밀해진다.

| 단위 | 장점 | 단점 |
|---|---|---|
| 시·도 16개 | 경계가 분명하고 고르기 쉽다 | 같은 시·도 안의 이동 거리 차이를 무시한다 |
| 광역권 6개 | 가장 고르기 쉽다 | 부산과 안동이 같은 영남이 되는 등 판정이 거칠다 |
| 시·군·구 약 230개 | 이동 판정이 정밀하다 | 목록 관리와 선택 화면의 부담이 크다 |
| 프런트 3개 | 지금 화면 그대로다 | 다른 지역 행사를 등록할 수 없다 |

**공인 코드.** 시·군·구 코드를 고르는 세 방식을 비교했다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 법정동코드 앞 5자리 | 코드를 새로 만들지 않는다. 이름이 같은 구(중구 6곳 등)도 코드로 구분된다. 앞 2자리로 시·도를 안다. 개편 때 공인 코드 변경을 따라가면 된다 | UPPER_SNAKE 규칙의 예외다 |
| 직접 만든 UPPER_SNAKE(`SEOUL_GANGNAM`) | 00 규칙을 그대로 따른다 | 약 230개 코드를 직접 만들고, 이름이 같은 구의 구분 규칙이 필요하다 |
| 시·도 코드 + 시·군·구 이름 | 목록 관리가 작다 | 판정이 시·도까지만이라 시·군·구를 쓰는 이유가 사라진다 |

**목록 API.** 다른 분류 값은 수가 적고 거의 바뀌지 않아 문서와 프런트의 표로 충분하다. 지역은 약 230개이고 행정구역 개편으로 바뀐다. 문서·프런트·백엔드 세 곳에 복제하면 개편 때 세 곳을 함께 고쳐야 하므로, 백엔드 한 곳에서 내려준다.

## Consequences

- API의 지역 코드는 숫자 문자열이다(00 §2 예외). 클라이언트는 이름을 `GET /api/v1/regions`에서 얻는다.
- 행정구역이 개편되면 목록을 갱신하고 저장된 코드를 옮겨야 한다. 옮기는 방법은 정하지 않았다. 예: 2023년 군위군이 경상북도에서 대구광역시로 옮겨 갔다. 강원(`42`→`51`)과 전북(`45`→`52`)은 특별자치도 출범으로 시·도 코드가 바뀌었다. 2026년 7월에는 광주광역시(`29`)와 전라남도(`46`)가 전남광주통합특별시(`12`)로 합쳐졌다.
- 목록은 법정동코드 전체자료로 만들고, 그 기준일을 함께 관리한다.
- 아티스트가 이동 가능 지역을 고를 선택지가 많다. "서울 전체" 같은 시·도 단위 선택(앞 2자리)과 판정 규칙은 NSU-12·48에서 정한다.
- 프런트는 지역 선택을 시·도 → 시·군·구 두 단계로 바꾼다.

## Rejected Alternatives

- **시·도 16개**: 고르기 쉽지만 같은 시·도 안의 이동 부담 차이를 판정하지 못한다.
- **광역권 6개**: 판정이 가장 거칠고, 행사 지역이 권역으로만 남는다.
- **프런트 3개로 시작**: 다른 지역에서 열리는 행사를 등록할 수 없다.
- **직접 만든 UPPER_SNAKE 코드**: 00 규칙에는 맞지만, 약 230개 코드를 직접 만들어 세 곳에 두고 개편 때마다 함께 고쳐야 한다.
- **앱 안의 정적 파일로 목록 관리**: 마이그레이션은 가볍지만, DB가 잘못된 코드를 막지 못하고 개편 때 저장된 코드를 옮길 근거가 데이터와 따로 논다.
- **시·도 코드 + 시·군·구 이름**: 시·군·구가 판정에 쓰이지 않아 정밀한 이동 판정이라는 목적을 이루지 못한다.
