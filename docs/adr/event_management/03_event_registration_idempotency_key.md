# ADR: 행사 등록 멱등 키

- 상태: **Proposed** (PR 리뷰에서 확정)
- 결정일: **2026-10-18** (NSU-99 설계 세션)
- 관련: [03 행사 API §5.3.1·§9·§12.1](../../api/03_events.md), [00 공통 규칙 §2·§8](../../api/00_conventions.md), [02 행사 소프트 삭제](./02_event_soft_delete.md), NSU-99, NSU-100(요청 제한), NSU-97(삭제한 행사의 보관), [IETF `Idempotency-Key` 헤더 초안 draft-07](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07)

---

## Decision

행사 등록(`POST /api/v1/events`)은 `Idempotency-Key` 헤더를 반드시 받는다. 같은 등록자가 같은 키로 다시 보내면 행사를 새로 만들지 않는다.

- 값은 따옴표 없는 소문자 하이픈 표기 UUID다. 버전은 묻지 않는다. 화면은 등록 화면마다 키를 한 번 만들고(`crypto.randomUUID()`), 다시 보낼 때 같은 키를 쓴다.
- 키와 본문 해시를 `events` 행에 함께 저장하고, `(event_partner_id, idempotency_key)`에 유니크 제약을 건다. 키는 행이 있는 동안 기억한다.
- 같은 키로 다시 오면 지금의 행사를 `201`로 돌려준다. 그 행사를 삭제했으면 `404 EVENT_NOT_FOUND`, 본문이 다르면 `422 IDEMPOTENCY_KEY_REUSED`다.
- 같은 키의 요청이 동시에 오면 유니크 제약이 한 요청만 저장하게 한다. 나중 요청은 먼저 온 요청의 트랜잭션이 끝날 때까지 기다린 뒤 결과를 받는다.
- INSERT 전의 키 조회는 다시 보낸 요청에 빨리 답하기 위한 것이고, 중복은 유니크 제약이 막는다. INSERT가 유니크 위반을 만나면 키로 다시 조회해 `201`·`404`·`422`로 응답하며, `500`으로 끝내지 않는다.
- 등록이 DB에서 기다리거나 실행하는 시간에는 상한(설정값, 기본 3초)을 둔다. 같은 키의 처리 중인 요청을 기다리는 시간도 여기에 든다. 넘으면 저장하지 않고 `503 EVENT_REGISTRATION_UNAVAILABLE`로 응답한다.
- 시작 시각 검사(`EVENT_START_IN_PAST`)는 같은 키의 경쟁을 정리한 뒤, 행사를 새로 만드는 요청에만 한다. 키를 INSERT로 먼저 선점하고 같은 트랜잭션에서 시작 시각을 검사해, 지났으면 롤백한다.

## Context

- PR #130의 행사 계약을 검토했을 때, 응답이 끊겨 다시 보낸 등록이 행사를 하나 더 만든다는 지적이 나왔다. 수정과 취소는 다시 보내도 결과가 같고, 다시 보낸 삭제는 `404`를 받아 화면이 성공으로 처리한다(03 §5.6). 중복을 만드는 요청은 등록뿐이다.
- 등록은 행 하나를 저장하는 짧은 트랜잭션이다. AI 서버 같은 외부 호출이 없다.
- 지금 이 API를 호출하는 화면이 없다. 프런트의 행사 화면은 아직 브라우저 저장소를 쓴다.
- 백엔드는 Redis를 로그인·가입·인증 저장소에 쓴다. 정기 작업 스케줄러는 없다.
- 멱등 키 헤더의 참고 문서인 IETF 초안(draft-07)은 2026-04-18에 만료됐고 RFC가 되지 않았다. 초안은 키가 없으면 `400`, 같은 키에 다른 본문이면 `422`, 처리 중이면 `409`를 권한다.

## Rationale

### 키를 필수로 둔다

| 기준 | 필수 | 선택 |
|---|---|---|
| 다시 보낸 요청의 중복 | 생기지 않는다 | 키 없이 보내면 생긴다 |
| 서버 처리 경로 | 하나 | 키 있음·없음 두 갈래 |
| 나중에 바꾸는 비용 | 없다 | 필수로 바꿀 때 화면을 다시 고치는 breaking change다 |

호출하는 화면이 없는 지금이 필수로 도입하는 비용이 가장 작다.

### 키를 행사 행에 저장한다

| 기준 | `events` 행 | 별도 테이블, 24시간 | Redis, 24시간 TTL |
|---|---|---|---|
| 더하는 것 | 열과 유니크 인덱스 | 테이블, 만료된 키를 지우는 정리 작업(스케줄러 신규) | 없음 |
| 기억하는 기간 | 행이 있는 동안 | 24시간 | 24시간 |
| 다음 날 다시 보낸 요청 | 같은 행사 | 중복 행사 | 중복 행사 |
| 저장 도중 서버가 멈출 때 | 행사와 키가 한 행이라 함께 남거나 함께 없다 | 같은 트랜잭션이면 왼쪽과 같다 | DB와 Redis가 어긋날 수 있어 "처리 중" 상태와 복구가 필요하다 |

행사와 키를 한 행에 두면 INSERT 하나가 키를 원자적으로 선점하고, 정리 작업 없이 행이 있는 동안 키를 기억한다. 다른 생성 API가 멱등 키를 받게 되면 그 API의 테이블에 같은 열을 더한다.

### 동시 요청은 유니크 제약으로 기다리게 한다

PostgreSQL은 커밋되지 않은 행과 유니크 키가 겹치는 INSERT를 그 트랜잭션이 끝날 때까지 기다리게 한다. 먼저 온 트랜잭션이 커밋하면 유니크 위반이 되고, 롤백하면 충돌이 없다([PostgreSQL 18 문서, Index Uniqueness Checks](https://www.postgresql.org/docs/18/index-unique-checks.html)). 그래서 나중 요청은 유니크 위반을 만나면 저장된 행사를 읽어 돌려주고, 먼저 온 요청이 롤백했으면 이어서 저장한다. 평소 기다리는 시간은 행 하나를 저장하는 트랜잭션의 길이이고, 길어질 때를 위한 상한은 아래에 둔다.

| 기준 | 유니크 제약으로 기다림 | 처리 중이면 `409`(Redis 분산 락) |
|---|---|---|
| 평소 등록 | 키 조회와 INSERT | 여기에 Redis 왕복 2번(락 잡기·풀기)이 더해진다 |
| 겹친 두 번째 요청 | 기다린 뒤 `201`. 상한을 넘으면 `503` | 바로 `409`. 화면이 다시 보내야 한다 |
| 필요한 장치 | 유니크 제약 | Redis 락과 유니크 제약. 락 TTL이 지나거나 Redis가 락을 잃으면 두 번째 요청이 DB까지 오기 때문이다 |
| Redis 장애 | 영향 없다 | 등록을 막을지 따로 정해야 한다 |

Redis 락은 처리 중에 외부 호출이 있어 DB 트랜잭션 하나로 묶을 수 없을 때 맞는다. 추천 생성은 AI 서버를 호출하므로 Redis 잠금과 `409 RECOMMENDATION_IN_PROGRESS`를 쓴다(02 §5.1). 등록은 이 조건에 해당하지 않는다.

화면은 응답을 받기 전에 다시 보내지 않는다(03 §5.3.1). 그래도 화면이 시간 초과로 다시 보낸 요청은 서버가 아직 처리 중인 먼저 보낸 요청과 겹칠 수 있으므로, 서버의 동시 요청 처리는 따로 필요하다.

기다림에는 서버 쪽 상한을 둔다. 먼저 온 트랜잭션이 잠금 대기나 DB 지연으로 멈추면, 같은 키의 요청들이 DB 연결을 붙잡은 채 함께 멈춰 기본 풀 10개를 다 쓸 수 있다. 화면의 재시도 횟수 제한은 서버에서 이미 기다리는 요청을 끊지 못한다. 지금 DB 설정에는 대기 상한이 없고, PostgreSQL의 `lock_timeout`·`statement_timeout`도 기본값으로는 꺼져 있다. 상한을 넘은 요청은 롤백하고 `503`으로 끝내 연결을 돌려준다. `409`가 아니라 `503`인 이유는, 화면이 이미 `5xx`를 받으면 같은 키로 다시 보내므로 새로 처리할 응답이 없기 때문이다.

시작 시각 검사를 키 확인 뒤에만 두면, 먼저 보낸 요청이 저장하고 커밋하기 전에 시작 시각이 지난 경우 다시 보낸 요청이 그 행을 보지 못하고 `400 EVENT_START_IN_PAST`로 끝난다. 그 뒤 먼저 보낸 요청이 커밋하면 행사는 생겼는데 화면은 실패로 안다. 그래서 키를 INSERT로 먼저 선점해 같은 키의 경쟁을 정리하고, 새로 만드는 요청에만 시작 시각을 검사한다.

### 키 값은 따옴표 없는 UUID다

IETF 초안은 값을 RFC 8941 String(`"…"`)으로 정한다. 이 API를 호출하는 쪽은 우리 화면 하나이고 초안은 만료됐으므로, 화면이 `crypto.randomUUID()`의 값을 그대로 보내는 형식을 택했다. 따옴표로 감싼 값은 `400 VALIDATION_ERROR`다. 키 없음 `400`과 다른 본문 `422`는 초안을 따른다.

UUIDv7은 요구하지 않는다. 키는 기본 키가 아니고 유니크 인덱스의 앞 열이 등록자라서, 키의 시간 순서가 인덱스 성능에 주는 이점이 없다. v7에 든 시각은 사용자 기기의 시계라서 서버가 쓰지 않는다. v4는 브라우저에 내장돼 있고 프런트가 이미 쓴다.

### 본문은 정규화한 값의 해시로 비교한다

검증과 정규화를 마친 본문(`EventContent`)의 모든 필드로 SHA-256 해시를 만들어 키와 함께 저장한다. 앞뒤 공백, 필드 순서, `genres` 순서, 빈 선택정보와 `null`처럼 화면이 다르게 보내도 같은 행사가 되는 차이는 같은 본문으로 본다. 키를 기록한 뒤 행사를 수정해도 비교 기준은 처음 등록한 본문이다.

### 다시 보낸 요청에는 지금의 행사를 돌려준다

처음 응답을 따로 저장하지 않고, 키로 찾은 행사의 지금 상태를 돌려준다. 결과가 행사 행 자체라서 응답을 저장할 곳이 필요 없고, 그 사이의 수정·취소가 반영된 값을 화면이 받는다. 행사를 삭제했으면 다른 API와 같이 `404`다(ADR 02).

## Consequences

- V6 마이그레이션으로 `events`에 키와 본문 해시 열, `(event_partner_id, idempotency_key)` 유니크 인덱스를 더한다. 머지된 V5는 고치지 않는다. V6 전에 만든 행에는 키가 없다(`NULL`).
- 등록의 검사 순서가 `400`(키·본문) → 키 확인과 선점(처리 중이면 기다림, 상한을 넘으면 `503`) → 새로 만드는 요청만 `400 EVENT_START_IN_PAST` → 커밋이 된다. 시작 시각이 지났으면 롤백하므로 키는 기록되지 않는다. 먼저 보낸 요청이 저장된 뒤(커밋 전 포함) 시작 시각이 지나도, 다시 보낸 요청은 `201`을 받는다.
- 소프트 삭제한 행사의 키도 기억하므로, 그 키로 다시 보내면 `404`다. NSU-97에서 완전 삭제를 도입하면, 완전히 지운 뒤에는 같은 키로 새 행사가 만들어진다. 완전 삭제는 보관 기간이 지난 뒤의 일이라 그때 같은 키로 다시 보내는 화면은 없다고 본다.
- 본문 해시에 들어가는 필드가 바뀌면(필드 추가 등), 배포 전에 보낸 요청을 배포 뒤에 다시 보낼 때 `422`가 될 수 있다. 배포 직후 짧은 시간의 재전송만 해당한다.
- 등록 트랜잭션의 DB 시간 상한(기본 3초)은 트랜잭션 안에서 PostgreSQL `lock_timeout`·`statement_timeout`을 설정하거나(`SET LOCAL`) 트랜잭션 시간 제한으로 구현한다. 상한을 넘으면 `503`이고, 화면은 간격을 늘려 가며 3번까지 같은 키로 다시 보낸다(03 §5.3.1).
- 같은 키의 요청이 한꺼번에 몰리면 행사는 1건이지만, 기다리는 요청마다 DB 연결을 잡는다(기본 풀 10개). 키를 바꿔 가며 보내는 대량 등록은 멱등 키로 막지 못한다. 둘 다 사용자별 요청 제한(NSU-100, SSOT `SEC-118`)으로 다룬다.
- 화면이 다른 출처에서 API를 부르게 되면 CORS 허용 헤더에 `Idempotency-Key`를 넣는다. 지금은 Vite 프록시로 같은 출처다.
- 호출하는 화면이 없어 `/api/v2`를 열지 않고 v1을 바꾼다(00 §1의 예외, 03 §12.1).

## Reused

- 키 형식 검사: `EventController`의 `eventId` 정규식(소문자 하이픈 표기 UUID)
- 오류 응답: `ErrorCode`·`BusinessException`·`GlobalExceptionHandler`(ADR-007). 새 code는 `IDEMPOTENCY_KEY_REUSED` 하나다
- 중복 방지와 동시 요청 처리: PostgreSQL 유니크 제약. 새 의존성은 없다
- 본문 해시 계산: `EventFingerprint`의 방식(길이를 앞에 붙인 정규 문자열의 SHA-256). `EventFingerprint` 자체는 추천 입력 필드만 담아 본문 비교에 쓸 수 없다
- 화면의 키 생성: 브라우저 `crypto.randomUUID()`(프런트가 이미 쓴다)

## Rejected Alternatives

- **키 선택**: 키 없이 다시 보낸 요청은 여전히 중복을 만들고, 처리 경로가 둘이 된다.
- **별도 테이블에 24시간 보관**: 다른 API와 함께 쓸 수 있지만, 테이블과 정리 작업이 늘고 24시간 뒤의 재전송은 중복을 만든다.
- **Redis에 24시간 TTL로 보관**: 정리 작업은 없지만, DB와 따로 저장돼 서버가 도중에 멈추면 키와 행사가 어긋난다.
- **상한 없는 기다림**: 먼저 온 트랜잭션이 멈추면 같은 키의 요청들이 DB 연결 풀을 다 쓸 수 있고, 커밋 전에 시작 시각이 지나면 성공한 등록이 실패로 보인다(2026-10-18 Codex 설계 리뷰).
- **처리 중인 같은 키에 `409 IDEMPOTENCY_REQUEST_IN_PROGRESS`(Redis 분산 락)**: 같은 키의 폭주를 DB 앞에서 거절하지만, 평소 요청마다 Redis 왕복이 늘고 화면에 재시도 처리가 필요하다. 키를 바꾼 폭주는 막지 못한다.
- **IETF 초안의 따옴표 문법**: 화면이 값을 따옴표로 감싸야 하고 빠뜨리기 쉽다. 초안은 만료됐다.
- **UUIDv7 요구**: 이 키에서는 시간 순서의 이점이 없고, 화면에 라이브러리가 필요하다.
- **처음 응답을 저장해 그대로 돌려주기**: 응답을 저장할 곳이 더 필요하고, 그 사이 바뀐 행사를 화면이 모르게 된다.
- **다시 보낸 응답임을 알리는 헤더(`Idempotent-Replayed` 등)**: 화면이 처음 응답과 구분할 필요가 없다.
- **등록 요청 제한을 함께 도입**: 쓰기 API 전체에 한 번 설계해 적용하도록 NSU-100으로 넘겼다.
