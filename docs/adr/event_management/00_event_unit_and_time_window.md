# ADR: 행사 단위와 시간대

- 상태: **Proposed** (PR 리뷰에서 확정)
- 결정일: **2026-10-18** (NSU-54·58 설계 세션)
- 관련: [03 행사 API §2·§3.2·§5.2](../../api/03_events.md), SSOT `EVT-042`·`DOMAIN-108`·`BOOKING-059`·`AI-MATCH-051`·`ART-029`, NSU-54

---

## Decision

행사 1건은 EVENT_PARTNER가 아티스트 1팀을 섭외하려고 등록하는 공연 1건이며, 이어진 시간대 하나를 갖는다.

```text
시간대 = startDate + startTime ~ endDate + endTime   (Asia/Seoul 벽시계 값)
0 < 종료 − 시작 ≤ 24시간
1 ≤ performanceMinutes ≤ (종료 − 시작)의 분
```

- 시간대는 아티스트가 비워 둬야 하는 구간이다. 공연시간(`performanceMinutes`)은 그 안에서 실제로 무대에 서는 길이다.
- 가용 일정 판정은 시간대 전체를 쓴다. 아티스트는 시간대 전체가 비어 있어야 추천 후보가 된다.
- 자정을 넘기는 시간대는 종료 날짜(`endDate`)를 다음 날로 적는다.
- "행사 일정"은 별도 리소스가 아니라 행사의 시간대 필드다. 여러 날이나 여러 팀이 필요한 행사는 행사를 여러 건 등록한다.
- 등록·수정한 값의 시작은 지금보다 뒤여야 한다. 행사가 시작하면(시작 ≤ 지금) 수정·취소·추천 생성을 막고, 상태는 `OPEN`으로 둔다.

## Context

NSU-54는 "행사 일정 CRUD"와 "행사 정보 CRUD"를 나눠 적었다. 그러나 행사를 쓰는 다른 요구사항과 계약은 모두 행사 하나에 날짜 하나를 전제한다.

| 근거 | 내용 |
|---|---|
| SSOT `EVT-042` | Event Date 1개, 공연 시작시간·종료시간 1개씩 |
| SSOT `DOMAIN-108`·`BOOKING-059` | `MATCHED`는 행사 단위 상태이고, 매칭 성사는 행사와 아티스트 한 쌍에 대해 정한다 |
| SSOT `AI-MATCH-051` | Eligibility는 "행사 날짜 공연 가능 여부"를 판정한다 |
| 02 §4.3, 서버 협의 014 결정 4 | 추천 snapshot과 지문이 행사 날짜 하나를 쓴다 |
| 프런트 NSU-56 | 행사마다 `date` 1개, `startTime`, `endTime`을 저장한다 |

`EVT-042`에는 공연 시작시간, 공연 종료시간, 공연시간이 모두 필수로 있지만 셋의 관계는 정해져 있지 않았다. 프런트도 세 값을 따로 받고, 종료가 시작보다 늦은지만 확인한다.

공연 형태에 DJ가 있어 자정을 넘기는 심야 공연이 실제로 생긴다. 프런트는 시각을 `'HH:MM'` 문자열로 비교하므로 22:00~02:00 같은 시간대를 입력할 수 없었다.

## Rationale

**행사 1건 = 공연 1건.** 행사 아래에 회차를 두는 2단 구조를 함께 검토했다. 이틀 축제의 1일차 밴드와 2일차 DJ처럼 회차마다 공연 형태와 예산이 다르면, 행사 필드 대부분이 회차로 내려간다. 그러면 추천, Eligibility, 지문, Offer, `MATCHED`를 모두 회차 단위로 다시 정해야 한다. 여러 행사를 묶는 축제 단위는 나중에 행사에 필드를 더해 붙일 수 있으므로, 지금의 단일 단위가 그 길을 막지 않는다.

**시간대와 공연시간을 따로 둔다.** 아래처럼 무대에 서는 순서가 정해지지 않은 공연이 있다.

| 예 | 시간대 | 공연시간 |
|---|---|---|
| 결혼식 축가 | 12:00~13:00(예식) | 5분 |
| 기업 만찬 공연 | 18:00~21:00 | 30분 |
| 축제 밴드 공연 | 19:00~19:40 | 40분 |

시작~종료를 무대 시간으로 보고 공연시간을 계산하면 위의 두 경우를 표현할 수 없다. 세 값을 관계 검사 없이 받으면 "시간대 1시간, 공연시간 300분" 같은 값이 저장되고, 추천과 Offer가 그 값을 그대로 쓴다. `ART-029`는 추천할 때 날짜와 시간 충돌을 확인하라고 정한다. 정확한 무대 순서를 모르므로 시간대 전체로 판정한다.

**종료 날짜를 따로 둔다.** 자정 넘김을 다루는 세 방식을 비교했다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 같은 날 안에서만 | 날짜 하나로 판정·정렬이 끝난다 | 심야 공연을 23:59에서 잘라야 한다 |
| 종료 ≤ 시작이면 다음 날로 해석 | 필드가 그대로다 | 다음 날이라는 사실이 값에 드러나지 않는 암묵 규칙이다 |
| 종료 날짜 필드 | 시간대가 값에 그대로 드러난다 | `EVT-042` 개정(v1.16)과 지문 필드 추가가 필요하다 |

**시간대는 24시간 이하다.** 시간대는 아티스트가 비워 둬야 하는 구간이다. 그래서 사흘짜리 시간대에는 사흘을 모두 비운 아티스트만 후보가 된다. 사흘 중 하루만 공연하는 행사를 이렇게 등록하면 의도와 다르게 후보가 줄어든다. 여러 날 머무는 공연은 날마다 나눠 등록하는 편이 판정과 맞는다.

**날짜와 시:분을 네 필드로 나눈다.** 프런트의 입력 칸, `EVT-042`, Offer(`BOOKING-058`)의 공연일·공연시간이 모두 날짜와 시각을 따로 다룬다. `HH:mm` 형식으로 분 단위가 강제된다. `startAt`·`endAt`을 00의 시각 형식(`+09:00`, 초 단위)으로 받으면 API의 시각 형식이 하나로 통일된다. 대신 프런트가 값을 합쳐 보내고 나눠 보여 줘야 하며, 초와 오프셋을 따로 검사해야 한다.

**시작 시각 기준으로 잠근다.** 끝난 행사로 추천을 만들면 AI 비용만 들고 쓸 데가 없다. 시작한 행사의 조건을 바꾸면 이미 진행 중인 섭외와 어긋난다. 상태를 새로 두지 않고 시각만으로 판단하므로 `DOMAIN-108`의 `CLOSED`(모집 마감인지 행사 종료인지 정해지지 않음)를 지금 정하지 않아도 된다.

## Consequences

- SSOT v1.16에서 `EVT-042`의 Event Date를 시작·종료 날짜로 나누고, `AI-MATCH-051`의 "행사 날짜 공연 가능 여부"를 "행사 시간대 공연 가능 여부"로 바꾼다.
- 02 §4.3의 지문 필드에 종료 날짜를 더한다(03 §8.3).
- 프런트는 `date`를 시작·종료 날짜로 나눈다. "공연 시작 시간"·"공연 종료 시간" 라벨은 시간대 뜻으로 읽히도록 고친다.
- 여러 날이나 여러 팀이 필요한 행사는 같은 내용을 여러 번 입력한다. 행사 복제는 화면 기능으로 덜 수 있다.
- 진행 중인 행사(시작 ≤ 지금 < 종료)는 내 행사 목록의 지난 행사(`PAST`)에 들어가고 잠긴다.
- "지금"은 서버 시계의 Asia/Seoul 시각이다. 화면을 열어 둔 사이에 시작 시각이 지나면 저장이 `400 EVENT_START_IN_PAST` 또는 `409 EVENT_ALREADY_STARTED`로 거절된다.

## Rejected Alternatives

- **행사 + 일정(회차) 2단**: 여러 날 축제를 한 번에 관리할 수 있지만, 회차마다 다른 조건 때문에 필드 대부분이 회차로 내려가고 추천·Eligibility·Offer·`MATCHED`를 회차 단위로 다시 정해야 한다.
- **날짜 1개, 섭외 여러 팀**: 한 무대의 여러 팀을 1건으로 등록하지만, 행사 단위 `MATCHED`의 뜻을 다시 정해야 하고 팀마다 다른 공연 형태·예산을 표현할 수 없다.
- **무대 시간 = 시작~종료**: 값이 어긋날 일은 없지만 "18~21시 중 30분" 같은 공연을 표현할 수 없다.
- **세 값 독립, 관계 검사 없음**: 가장 단순하지만 서로 맞지 않는 값이 저장되어 추천과 Offer에 그대로 쓰인다.
- **같은 날 안에서만 / 종료 ≤ 시작이면 다음 날**: 위 비교표를 보라.
- **여러 날 허용(상한 7일) / 상한 없음**: 기간 전체를 비운 아티스트만 후보가 되어 "며칠 중 하루" 행사와 혼동되고, 상한이 없으면 입력 실수도 그대로 저장된다.
- **`startAt`·`endAt`**: API의 시각 형식은 하나가 되지만, 화면 입력과 구조가 달라지고 초·오프셋 검사가 더 필요하다. 오프셋 없는 `YYYY-MM-DDTHH:mm`은 00의 시각 형식과 비슷하지만 다른 형식이 생겨 헷갈린다.
- **시작 시각 제한 없음**: 끝난 행사로 추천 비용을 쓰고, 이미 끝난 행사를 취소하는 것처럼 뜻이 없는 동작이 남는다.
- **잠금 + 끝나면 `CLOSED`**: 상태만 보고 판단할 수 있지만, `CLOSED`의 뜻을 지금 정해야 하고 예약 작업이나 조회 때의 계산이 필요하다.
