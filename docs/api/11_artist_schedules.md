# 아티스트 공연 가능 일정 API

ARTIST가 자기 공연 가능 일정을 조회·추가·수정·삭제하는 API다. 추천 Eligibility의 일정 조건(`SCHEDULE_AVAILABLE`)이 같은 저장 값을 읽는다.

- 구현 이슈: NSU-120(GitHub #176). Eligibility 일정 창구 연결(NSU-34)도 이 이슈가 한다
- 요구사항: SSOT v1.17.1(최종 승인) `ART-029`(Artist Availability, 상태 4개), `ART-027`(관리 주체 `ACTIVE` ARTIST), `AI-MATCH-051`(일정 조건), `EVT-042`(행사 시간대), `SEC-120`(개인정보 최소화)
- 결정 기록: [artist_schedule/00 아티스트 공연 가능 일정 API](../adr/artist_schedule/00_artist_schedule_api.md)
- 관련 계약: [09 아티스트 프로필 API](./09_artist_profile.md)(같은 모양의 쓰기 계정 확인과 잠금), [03 행사 API](./03_events.md) §3.2(행사 시간대), [05 EVENT_PARTNER 프로필 API](./05_event_partner_profile.md) §2(문자열 규칙)
- 용어: [용어집 (CONTEXT)](https://linear.app/nsu-capstone/document/용어집-context-475370673105). SSOT의 Artist Availability를 "공연 가능 일정"이라 부른다. 코드와 경로는 schedule이다(ADR 결정 12)
- 공통 규칙: [00_conventions.md](./00_conventions.md). 에러 형식과 공통 `code`는 [ADR-007](../adr/ADR-007-spring-backend-global-exception-handling.md)을 따른다. Scalar 태그 이름은 `공연 가능 일정`이다(00 §10.1 목록에 더한다)

> 상태: 2026-11-28 NSU-120 설계 세션에서 정했다. 설계 리뷰 중이다(2회차 뒤 길이 하한을 없애고 하루 상한을 더함).

## 0. 범위

| 이 문서가 정한다 | 이 문서가 정하지 않는다 |
|---|---|
| 자기 일정의 조회·추가·수정·삭제(§1~§4) | 다른 사용자(EVENT_PARTNER 등)의 일정 열람 |
| 필드, 검증 규칙, 겹침 규칙, 하루 상한(§2·§3) | 추천 판정식(ADR recommendation_eligibility/00) |
| 응답 상태와 오류, 검사 순서(§4) | 섭외 성사가 `BOOKED`를 쓰는 규칙(Offer 설계) |
| 저장과 동시성, 탈퇴할 때 일정 파기, 추천이 읽는 값(§5) | 탈퇴 기능 자체(NSU-167), 요청 제한(NSU-100) |
| 로그(§6), 화면이 바꿀 것(§8), 테스트 기준(§9) | 반복 일정, 공휴일 표시 |

## 1. 엔드포인트

| 동작 | 메서드·경로 | 호출 주체 | 성공 |
|---|---|---|---|
| 내 일정 조회 | `GET /api/v1/me/artist-schedules?from={날짜}&to={날짜}` | ARTIST | `200` + 목록(§3) |
| 일정 추가 | `POST /api/v1/me/artist-schedules` | `ACTIVE` ARTIST | `201` + 추가한 일정 목록(§3) |
| 일정 수정 | `PUT /api/v1/me/artist-schedules/{artistScheduleId}` | `ACTIVE` ARTIST | `200` + 일정(§3) |
| 일정 삭제 | `DELETE /api/v1/me/artist-schedules/{artistScheduleId}` | ARTIST(계정 상태 무관) | `204` |

- 모든 요청에 `Authorization: Bearer {accessToken}`이 필요하다(00 §7).
- 대상은 토큰의 `sub` 사용자다(00 §1). 본문에 `artistId`·`userId`를 넣어도 무시한다.
- `artistScheduleId`는 서버가 만든 일정 `id`(§3)다. 정규형 UUID(8-4-4-4-12자리, 대소문자 구분 없음)만 받는다. `1-2-3-4-5` 같은 축약형은 `400 INVALID_ARTIST_SCHEDULE_ID`다(09 §1의 `artistId`와 같은 검사).
- 추가는 일정 1~7개를 한 번에 받는다. 모두 저장하거나 하나도 저장하지 않는다. 화면의 주간 폼이 한 주의 여러 요일을 한 번에 더하기 때문이다.
- 추가 응답에는 `Location` 헤더가 없다. 여러 일정을 만들고, 한 건 조회 경로가 없기 때문이다.
- 수정은 일정 한 건의 전체 교체(`PUT`)다. 일정 이름을 빼면 일정 이름을 지운다. 화면의 수정 폼이 일정의 모든 필드를 함께 보내므로 부분 수정(`PATCH`)은 두지 않는다.
- 삭제는 지운 일정이 없어도 `204`다. 없는 일정과 다른 사용자의 일정도 `204`이고 아무것도 지우지 않는다. 같은 삭제를 다시 보내도 결과가 같다.
- 추가는 멱등 키를 받지 않는다. 그래서 추가는 다시 보내도 안전한 요청이 아니다. 응답을 받지 못하면(연결 끊김·시간 초과) 화면은 같은 요청을 자동으로 다시 보내지 않고 그 기간을 다시 읽어 그린다. 다시 읽은 빈 결과가 저장 실패를 뜻하지는 않는다(§8, ADR "멱등 키를 두지 않는 이유"). 같은 일정을 곧바로 다시 보내면 겹침 규칙으로 `409`가 되지만, 그 사이 다른 기기에서 그 일정을 옮겼으면 원래 시간에 새 일정이 생긴다.
- 일정 한 건 조회와 다른 사용자의 일정 열람은 없다(ADR Excluded).
- 이 API는 REST 성숙도 2단계로 설계한다. 응답에 링크(HATEOAS)를 넣지 않는다.

## 2. 요청

### 2.1 조회 파라미터

| 파라미터 | 형식 | 필수 | 규칙 |
|---|---|---|---|
| `from` | 날짜(00 §4) | O | 조회 첫날 |
| `to` | 날짜 | O | 조회 마지막 날(포함). `from` 이상이고, `from`부터 `to`까지 42일 이하 |

- 조회 구간은 `[from 00:00, to 다음 날 00:00)`이다(`Asia/Seoul`). 이 구간과 겹치는 일정을 돌려준다.
- 구간과 맞닿기만 한 일정은 빠진다. 끝이 `from 00:00`인 일정과 시작이 `to 다음 날 00:00`인 일정이다.
- 구간에 걸친 일정은 자르지 않고 그대로 돌려준다. 예: `from = 2026-12-01`이면 `2026-11-30 22:00 ~ 2026-12-01 02:00` 일정이 나온다.
- 42일은 월간 화면의 6주 칸이다. 43일 이상은 `400 VALIDATION_ERROR`다.
- 날짜는 `2000-01-01`부터 `2099-12-31`까지다(§2.2와 같다).
- 파라미터가 빠졌거나, 형식이 틀렸거나, 없는 날짜(`2026-02-30`)이거나, `from`이 `to`보다 늦으면 `400 VALIDATION_ERROR`다. 서버가 문자열로 받아 직접 검사하므로 `ProblemDetail`이 나가지 않는다(03 §6의 `period`와 같은 방식).

### 2.2 일정 본문 (추가·수정)

추가는 `{"items": [일정, …]}`을, 수정은 일정 하나를 본문으로 보낸다. 일정의 필드는 둘이 같다.

| 필드 | 타입 | 필수 | 규칙 |
|---|---|---|---|
| `startDate` | 날짜 | O | 시작 날짜 |
| `startTime` | 시:분 | O | 시작 시각(분 단위) |
| `endDate` | 날짜 | O | 끝 날짜. 같은 날 끝나면 `startDate`, 자정을 넘기면 다음 날 |
| `endTime` | 시:분 | O | 끝 시각(분 단위). `24:00`은 받지 않는다 |
| `status` | enum | O | `AVAILABLE`(가능), `HOLD`(보류), `UNAVAILABLE`(불가) |
| `title` | 문자열 \| `null` | | 일정 이름. 30자 이하. 빠지거나 `null`이거나 비면 일정 이름이 없다 |

```text
시작 = startDate + startTime   (Asia/Seoul 벽시계 값, 오프셋 없음)
끝   = endDate + endTime
시작 < 끝,  끝 − 시작 ≤ 24시간
```

| 예 | 시작 ~ 끝 | 결과 |
|---|---|---|
| 저녁 | 2026-12-12 18:00 ~ 2026-12-12 22:00 | 통과 |
| 짧은 틈 | 2026-12-12 19:00 ~ 2026-12-12 19:20 | 통과(20분) |
| 1분 | 2026-12-12 19:00 ~ 2026-12-12 19:01 | 통과 |
| 자정을 넘김 | 2026-12-12 22:00 ~ 2026-12-13 02:00 | 통과 |
| 하루 종일 | 2026-12-13 00:00 ~ 2026-12-14 00:00 | 통과(24시간) |
| 하루 끝을 `24:00`으로 | 2026-12-12 18:00 ~ 2026-12-12 24:00 | `400`. 2026-12-13 `00:00`으로 보낸다 |
| 정각·30분이 아닌 시각 | 2026-12-12 19:40 ~ 2026-12-12 20:10 | 통과 |
| 24시간 초과 | 2026-12-13 00:00 ~ 2026-12-14 00:30 | `400` |
| 시작 = 끝 | 2026-12-12 20:00 ~ 2026-12-12 20:00 | `400` |
| 끝이 시작보다 이름 | 2026-12-12 20:00 ~ 2026-12-12 18:00 | `400` |

- 날짜·시:분·상태는 서버가 문자열로 받아 직접 검사한다. 형식이 틀리거나(`"18:00:00"`, `"2026/12/12"`, `"25:00"`), 없는 날짜(`2026-02-30`)이거나, 목록에 없는 상태면 `400 VALIDATION_ERROR`다. 소문자 `available`도 목록에 없는 값이다(03 §3.1과 같은 방식, ADR-007 §4.4).
- `BOOKED`(확정)는 받지 않는다(`400 VALIDATION_ERROR`). 섭외가 성사되면 서버가 쓸 값이다. 시간을 막으려면 `UNAVAILABLE`을 쓴다(ADR 결정 3).
- 날짜는 `2000-01-01`부터 `2099-12-31`까지다. 범위 밖은 `400 VALIDATION_ERROR`다. 지난 날짜도 받는다.
- 시작 < 끝과 길이 24시간 이하는 `Asia/Seoul` 규칙으로 바꾼 시점으로 검사한다. DB `CHECK`와 같은 기준이다. 위 날짜 범위의 `Asia/Seoul`에는 일광 절약 시간이 없어 벽시계 차이와 결과가 같다.
- 분은 `00`~`59` 모두 받는다. 30분 단위는 화면이 고르는 방식이고 서버 규칙이 아니다. 서버와 DB는 같은 규칙(분 단위, 시작 < 끝, 24시간 이하)을 지킨다. 길이 하한은 없다. 30분보다 짧은 빈 시간(예: 막힌 일정 사이의 `19:00~19:20`)도 적을 수 있어야 그 시간의 짧은 행사에서 추천될 수 있기 때문이다. 그래서 운영자나 섭외 성사가 넣은 `19:40~20:10` 일정도 같은 시간 그대로 상태만 바꿔 수정할 수 있다(ADR "시간 단위와 길이").
- `title`:
  - 05 §2의 문자열 규칙과 같다. 앞뒤 공백·보이지 않는 글자를 지운 뒤 유니코드 코드포인트 수로 센다. 31자 이상이면 `400 VALIDATION_ERROR`다. 지운 결과를 저장한다.
  - 보이는 글자가 없으면 일정 이름 없음(`null`)으로 저장한다. 오류가 아니다. 화면이 빈 일정 이름 칸을 그대로 보내도 되게 하기 위해서다.
  - NUL 문자나 짝 없는 서로게이트가 있으면 `400 VALIDATION_ERROR`다.
- 추가 본문의 `items`:
  - 1~7개다. 키가 빠지거나, `null`이거나, `[]`이거나, 8개 이상이면 `400 VALIDATION_ERROR`다. 원소가 `null`이어도 같다.
  - 한 항목이라도 검증에 걸리면 아무것도 저장하지 않는다.
- JSON 문법 오류나 필드 타입으로 바꿀 수 없는 값(`items` 자리에 객체 등)은 Spring 표준 400(`ProblemDetail`)이다(05 §2와 같다).
- 본문 바이트 크기 상한은 이 API가 따로 두지 않는다. 본문을 객체로 읽기 전의 크기 제한은 모든 JSON API에 공통인 문제라 전역 장치(앞단 프록시와 앱의 본문 크기 상한, 별도 이슈)가 맡는다. `items` 7개 상한은 객체로 읽은 뒤의 검증이고, 읽는 동안의 메모리를 제한하지 않는다(ADR Consequences).
- 서버가 정하는 필드(`id`)와 모르는 필드는 무시한다. 수정은 본문의 `id`가 아니라 경로의 `artistScheduleId`를 고친다.
- OpenAPI 문서의 요청 `status` 허용 값은 세 개(`AVAILABLE`, `HOLD`, `UNAVAILABLE`)다. 00 §10.1은 허용 값을 enum으로 가리키라고 한다. 요청이 받는 값은 enum(`ArtistScheduleStatus`)의 일부라서 세 값을 적는 예외로 둔다. 테스트가 이 세 값을 enum에서 `BOOKED`를 뺀 값과 맞춘다(§9).

### 2.3 겹침 규칙

- 같은 아티스트의 일정끼리는 상태와 관계없이 겹칠 수 없다.
- 구간은 `[시작, 끝)`이다. 한 일정의 끝과 다른 일정의 시작이 같으면(맞닿음) 겹침이 아니다.
- 겹치면 `409 ARTIST_SCHEDULE_OVERLAP`이고 아무것도 바뀌지 않는다. 다음은 모두 같은 응답이다.
  - 새 일정이 저장된 일정과 겹친다. 전날 밤에 시작해 자정을 넘긴 일정도 포함한다.
  - 추가 본문의 항목끼리 겹친다.
  - 수정한 일정이 자기의 다른 일정과 겹친다.
- 수정은 그 일정의 옛 구간과 겹쳐도 된다. 예: `18:00~22:00`을 `20:00~23:00`으로 바꾼다.
- 다른 아티스트의 일정과는 겹쳐도 된다.
- 같은 시간의 상태를 바꾸려면 그 일정을 수정한다. 한 시간에 두 상태를 함께 둘 수 없다.
- 응답은 어느 일정과 겹쳤는지 알려 주지 않는다(`{code, message}`만). 화면은 다시 조회해 그린다(§8).

### 2.4 하루 일정 수 상한

- 한 아티스트가 같은 날에 시작하는 일정은 96개까지다. 날은 `startDate`(`Asia/Seoul` 날짜)다. 자정을 넘는 일정은 시작한 날에 센다.
- 추가나 수정으로 어느 날이 97개가 되면 `409 ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED`이고 아무것도 바뀌지 않는다. 추가는 한 항목이라도 걸리면 전부 저장하지 않는다.
- 수정은 시작 날짜를 바꿀 때만 센다. 이미 96개인 날의 일정을 같은 날 안에서 고치는 것은 된다.
- 한 항목이 상한과 겹침에 함께 걸리면 상한 쪽(`ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED`)이다.
- 상한은 DB가 모든 작성 경로에 지킨다(§5.1). 화면 사용자는 보통 닿지 않는다(ADR "하루 일정 수 상한과 아티스트별 잠금"). 상한이 42일 조회를 4,033건 이하로 묶는다.

## 3. 응답 본문

일정 하나는 다음 필드를 갖는다. `title`은 OpenAPI 스키마에도 `null`을 허용 타입으로 적는다(00 §10, 요청 본문의 `title`도 같다).

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | UUID 문자열 | 일정 ID(UUIDv7). 서버가 만든다. 수정·삭제 경로의 `artistScheduleId`다 |
| `startDate` | 날짜 | 시작 날짜 |
| `startTime` | 시:분 | 시작 시각 |
| `endDate` | 날짜 | 끝 날짜 |
| `endTime` | 시:분 | 끝 시각 |
| `status` | enum | `AVAILABLE`, `HOLD`, `BOOKED`, `UNAVAILABLE` |
| `title` | 문자열 \| `null` | 일정 이름 |

| 응답 | 본문 |
|---|---|
| 조회 `200` | `{"items": [일정, …]}`. 시작 시각 오름차순이다. 일정이 없으면 `items: []`다 |
| 추가 `201` | `{"items": [일정, …]}`. 요청 `items`와 같은 순서다 |
| 수정 `200` | 일정 하나. 저장한 값이다(앞뒤 공백을 지운 일정 이름 등). 화면은 이 값으로 다시 그린다 |

불변식:

- 시작 < 끝, `끝 − 시작 ≤ 24시간`이고 시각은 분 단위다(초가 없다). 같은 날 시작하는 일정은 96개 이하다. `endTime`에 `24:00`은 나오지 않는다. DB가 모든 행에 지킨다(§5.1).
- 한 아티스트의 일정끼리 겹치지 않는다. 그래서 목록에 시작 시각이 같은 일정이 없다.
- `title`은 `null`이거나, 보이는 글자가 있는 30자 이하 문자열이다.
- 분은 `00`·`30`이 아닐 수 있다(`19:40` 등). 화면은 30분 단위로 고르지만, 운영자 SQL이나 뒤에 생길 섭외 성사가 넣은 일정, 다른 클라이언트가 넣은 일정은 다른 분일 수 있다. 화면은 어떤 분이든 그린다.
- `BOOKED`는 지금 운영자 SQL로만 생긴다. `BOOKED` 일정도 수정·삭제할 수 있다. 수정 본문은 `BOOKED`를 받지 않으므로 수정하면 다른 상태가 된다. 시간은 그대로 둘 수 있다(예: `19:40~20:10` `BOOKED` → 같은 시간 `UNAVAILABLE`). 섭외 성사 기능이 생기면 `BOOKED` 일정의 수정·삭제 규칙은 그 설계가 정한다(ADR Consequences).
- enum 값은 늘어날 수 있다(00 §3). 화면은 모르는 상태를 받아도 실패하지 않는다.
- 이메일·휴대폰·사용자 ID는 담지 않는다.

## 4. 응답 상태와 오류

오류 본문은 ADR-007의 `{code, message}`다. `VALIDATION_ERROR`는 어느 필드가 틀렸는지 알려 주지 않는다(ADR-007 §4.2). 새 `code`는 다섯 개다.

| `code` | HTTP | 뜻 |
|---|---|---|
| `INVALID_ARTIST_SCHEDULE_ID` | 400 | `artistScheduleId`가 정규형 UUID가 아니다(00 §8 `INVALID_{대상}`) |
| `ARTIST_SCHEDULE_NOT_FOUND` | 404 | 수정할 일정이 없거나 다른 사용자의 일정이다 |
| `ARTIST_SCHEDULE_OVERLAP` | 409 | 자기 다른 일정과 겹친다(§2.3) |
| `ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED` | 409 | 같은 날 시작하는 일정이 96개를 넘는다(§2.4) |
| `ARTIST_SCHEDULE_BUSY` | 503 | 잠금을 3초 안에 잡지 못했거나 교착으로 끊겼다(§5.2) |

| 상황 | HTTP | `code` |
|---|---|---|
| 토큰 없음·만료·서명 오류 | 401 | `AUTHENTICATION_REQUIRED` |
| 시연 서버(`DEMO`)에서 허용 목록 밖 계정의 추가·수정·삭제 | 403 | `DEMO_WRITE_NOT_ALLOWED` |
| EVENT_PARTNER가 부름 | 403 | `ACCESS_DENIED` |
| 추가·수정에서 계정이 `ACTIVE`가 아님(`SUSPENDED`, 또는 아래의 `WITHDRAWN`) | 403 | `ACCESS_DENIED` |
| 수정·삭제의 `artistScheduleId`가 정규형 UUID가 아님 | 400 | `INVALID_ARTIST_SCHEDULE_ID` |
| 조회 파라미터나 본문의 검증 실패(§2) | 400 | `VALIDATION_ERROR` |
| JSON 문법 오류, 필드 타입으로 바꿀 수 없는 값 | 400 | 없음. Spring 표준 `ProblemDetail`(ADR-007 §4.4) |
| 수정할 일정이 없거나 다른 사용자의 일정 | 404 | `ARTIST_SCHEDULE_NOT_FOUND` |
| 자기 다른 일정과 겹침 | 409 | `ARTIST_SCHEDULE_OVERLAP` |
| 같은 날 시작하는 일정이 96개를 넘음 | 409 | `ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED` |
| 추가·수정·삭제에서 잠금 하나를 3초 안에 잡지 못함, 또는 교착으로 끊김. 아무것도 바뀌지 않는다. `Retry-After`는 붙이지 않는다 | 503 | `ARTIST_SCHEDULE_BUSY` |
| 서버 오류 | 500 | `INTERNAL_SERVER_ERROR` |

검사 순서:

- 조회: `401` → `403`(역할) → `400 VALIDATION_ERROR`(파라미터) → `200`
- 추가: `401` → `403 DEMO_WRITE_NOT_ALLOWED` → `403 ACCESS_DENIED`(역할) → `403 ACCESS_DENIED`(계정 상태) → `400 VALIDATION_ERROR`(본문) → `409`(항목마다 하루 상한, 겹침 순) → `201`
- 수정: `401` → `403 DEMO_WRITE_NOT_ALLOWED` → `403 ACCESS_DENIED`(역할) → `400 INVALID_ARTIST_SCHEDULE_ID` → `403 ACCESS_DENIED`(계정 상태) → `400 VALIDATION_ERROR`(본문) → `404` → `409`(하루 상한, 겹침 순) → `200`
- 삭제: `401` → `403 DEMO_WRITE_NOT_ALLOWED` → `403 ACCESS_DENIED`(역할) → `400 INVALID_ARTIST_SCHEDULE_ID` → `204`
- 추가·수정·삭제는 잠금을 3초 안에 잡지 못하면 그 자리에서 `503 ARTIST_SCHEDULE_BUSY`다. 잠금을 잡는 곳은 계정 상태 확인(`users` 행), 본문 검증 뒤의 아티스트별 잠금, 저장 문장이다(§5.2).

순서의 이유:

- 역할은 `SecurityConfig`의 URL 규칙이 본문을 읽기 전에 막는다. 그래서 EVENT_PARTNER가 깨진 JSON을 보내도 `403`이다. 컨트롤러의 `@PreAuthorize`는 두 번째 방어선이다(09 §4.1과 같다).
- 계정 상태는 본문 검증보다 먼저다(09 §4.1과 같다). 그래서 정지된 아티스트가 틀린 본문을 보내도 `400`이 아니라 `403`이다.
- `INVALID_ARTIST_SCHEDULE_ID`는 컨트롤러가 트랜잭션을 열기 전에 검사한다. 그래서 정지된 아티스트가 틀린 `artistScheduleId`로 수정해도 `400 INVALID_ARTIST_SCHEDULE_ID`다.
- JSON 문법·타입 오류(`ProblemDetail`)는 본문을 객체로 읽는 단계에서 나므로 `INVALID_ARTIST_SCHEDULE_ID`와 계정 상태 검사보다 먼저 나올 수 있다.
- `404`와 `409`는 수정 문장 하나가 정한다. 대상 행이 없으면 상한과 겹침을 검사하지 않고 `404`다. 상한은 행을 넣기 전의 트리거가, 겹침은 그 뒤의 배제 제약이 검사하므로 상한이 먼저다.
- 다른 사용자의 일정은 없는 일정과 같은 응답이다(수정 `404`, 삭제 `204`). 다른 사람의 일정 ID가 있는지 드러내지 않는다.
- 시연 서버 검사(00 §8)는 인증 바로 다음이다. 이 검사는 전역 필터(NSU-158)가 하며 2026-11-28 기준 아직 구현되지 않았다. 조회는 이 검사를 받지 않는다. NSU-158이 끝나기 전에는 이 쓰기 API를 외부에서 접속할 수 있는 시연 서버에 배포하지 않는다(09 §4.1과 같다).
- 삭제와 조회는 계정 상태를 보지 않는다. 정보주체가 자기 정보를 지우는 요구(개인정보보호법 §36)를 막지 않기 위해서다(09 §4.1과 같다).

탈퇴한 계정(`WITHDRAWN`):

- NSU-167 D3은 탈퇴한 계정의 요청을 인증 단계에서 `401`로 거절한다. D3이 들어간 뒤에는 탈퇴가 끝난 다음 시작한 요청이 모든 메서드에서 `401`이다. 이 API에 오기 전에 끝난다.
- `403 ACCESS_DENIED`(계정 상태)는 인증을 통과한 뒤 `users` 행 잠금에서 탈퇴를 본 추가·수정이다. 탈퇴와 겹친 요청(§5.3)이 여기에 해당한다.
- D3이 들어가기 전에는 탈퇴한 계정의 유효한 토큰도 인증을 통과한다. 그때 추가·수정은 `403`, 삭제는 `204`, 조회는 `200`(빈 목록)이다. D3을 넣는 NSU-167이 이 테스트(§9 "계정 상태")를 `401`로 바꾼다.

## 5. 저장과 동시성

### 5.1 저장

- 저장은 `artist_schedules` 테이블이고 한 행이 일정 한 건이다. `user_id`가 `users.id`를 참조한다(FK에 `ON DELETE` 없음). 시각은 `timestamptz`다(ADR 결정 8, 설계 상세 "마이그레이션 스케치").
- DB가 지키는 것:
  - `title`을 뺀 모든 칸의 `NOT NULL`
  - 시작 < 끝, 길이 24시간 이하, 시작·끝이 분 단위(초 이하가 0)(`CHECK`)
  - 상태 4개(`CHECK`)
  - 일정 이름이 공백만이 아님(`CHECK`), 30자 이하(`VARCHAR(30)`)
  - 같은 아티스트의 겹침 금지(`EXCLUDE USING gist`, 확장 `btree_gist`)
  - 새 행은 `ACTIVE` ARTIST에게만 들어간다(삽입 가드 트리거, §5.3)
  - 같은 날 시작하는 일정 96개 이하(삽입 가드와 같은 `BEFORE INSERT` 트리거, 시작 날짜를 바꾸는 수정의 트리거, §2.4). 트리거가 아티스트별 잠금을 잡은 뒤 센다. 세기가 잠금 뒤의 새 스냅숏에 기대므로 `READ COMMITTED`가 아닌 트랜잭션의 추가와 시작 날짜 변경은 거절한다
- 서버만 지키는 것: 날짜 범위, 요청의 `BOOKED` 거절, 일정 이름의 보이지 않는 글자 규칙이다.
- 길이 규칙과 하루 상한은 모든 작성 경로(API, 운영자 SQL, 뒤에 생길 섭외 성사)에 같다. 그래서 응답 크기와 판정 조회 범위가 DB로 묶인다.
  - 24시간 상한: 일괄 조회(§5.4)가 이 상한으로 조회 범위를 묶는다. 판정의 정확성 조건이다.
  - 하루 상한: 42일 조회는 많아야 4,033건(42일 × 96 + 범위 앞에 걸친 1건)이다. 페이지네이션을 두지 않는 근거다. 길이 하한은 두지 않는다(§2.2).
  - 분 단위: 응답의 `HH:mm`이 저장 값을 그대로 나타낸다. 초가 있으면 같은 분 안의 일정이 길이 0으로 보일 수 있다.
- 추가는 한 트랜잭션에서 1~7행을 넣는다. 수정은 `UPDATE … WHERE id = :artistScheduleId AND user_id = :me` 한 문장이고, 0행이면 `404`다. 삭제는 `DELETE … WHERE id = :artistScheduleId AND user_id = :me` 한 문장이다.
- 버전 비교는 두지 않는다(09 §5와 같은 방침). 같은 일정을 두 화면에서 고치면 나중 저장이 이긴다.

### 5.2 잠금과 동시성

- 추가·수정은 한 트랜잭션에서 차례로 다음을 한다.
  1. `SET LOCAL lock_timeout = '3s'`
  2. `ArtistWriteAccess.require(me)`: `users` 행을 `FOR SHARE`로 잠그며 `ACTIVE` ARTIST인지 확인한다(NSU-119)
  3. 본문 검증
  4. 아티스트별 잠금: `SELECT pg_advisory_xact_lock(hashtextextended('artist_schedules:' || :me, 0))`. 같은 아티스트의 추가·수정이 여기서 한 줄로 선다
  5. 저장 문장
- 삭제는 1 다음에 삭제 문장만 실행한다. `users` 행도 아티스트별 잠금도 잡지 않는다.
- 잠금 순서는 모든 추가·수정에서 `users` → 아티스트별 잠금 → `artist_schedules`다. 운영자 SQL의 INSERT도 트리거가 같은 순서로 잡는다. 일정을 넣거나 고치는 운영자 트랜잭션은 runbook대로 `users` 행 `FOR SHARE`와 아티스트별 잠금을 이 순서로 먼저 잡는다. 탈퇴 절차(§5.3)는 `users` → `artist_schedules`이고 아티스트별 잠금을 잡지 않는다.
- 잠금 대기는 09 §5와 같다. 보장하는 것은 잠금 획득 시도 하나당 3초다. 요청 전체의 대기 시간에는 상한을 두지 않는다. 이 API에서 기다리는 곳은 넷이다.
  - `users` 행: 같은 사용자의 탈퇴·정지 같은 상태 변경이 끝나지 않았다.
  - 아티스트별 잠금: 같은 아티스트의 다른 추가·수정(운영자 SQL의 INSERT 포함)이 끝나지 않았다.
  - 겹치는 미커밋 일정: 아티스트별 잠금을 먼저 잡지 않은 운영자 UPDATE가 고친 행과 겹친다. 배제 제약이 그 트랜잭션의 끝을 기다린다. 커밋되면 `409`, 롤백되면 저장한다.
  - 같은 일정 행: 그 일정의 다른 수정·삭제가 끝나지 않았다.
- 한 잠금이라도 3초를 넘으면(SQLState `55P03`) `503 ARTIST_SCHEDULE_BUSY`이고 아무것도 바뀌지 않는다. 교착으로 끊겨도(`40P01`) 같다. 교착은 아티스트별 잠금을 먼저 잡지 않은 운영자 UPDATE와 엮일 때만 생긴다(ADR "겹침 규칙과 일관성 장치"). 운영자 `psql`이나 탈퇴 트랜잭션이 행을 오래 잡아도 요청이 연결과 스레드를 무한정 쥐지 않게 하기 위해서다.
- 겹침은 SQLState `23P01`이고 제약 이름이 `ex_artist_schedules_no_overlap`일 때 `409 ARTIST_SCHEDULE_OVERLAP`이다. 하루 상한은 SQLState `23514`이고 제약 이름이 `ck_artist_schedules_daily_limit`일 때 `409 ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED`다. 다른 DB 오류는 `500`이다.

| 동시에 일어난 일 | 결과 |
|---|---|
| 같은 아티스트의 겹치는 두 추가 | 아티스트별 잠금으로 차례로 진행한다. 하나는 `201`, 뒤 요청은 앞 요청의 커밋 뒤에 검사해 `409`이고 아무것도 저장되지 않는다. 앞 요청이 롤백되면 뒤 요청이 저장된다. 앞 요청이 3초 넘게 잠금을 쥐면 뒤 요청은 `503`이다 |
| 서로 겹치는 항목을 엇갈린 순서로 넣는 두 추가 | 위와 같다. 교착이 없다. 먼저 잠금을 잡은 쪽이 `201`, 다른 쪽이 `409`다 |
| 하루 상한 직전(95개)인 날에 두 추가 | 차례로 진행한다. 하나는 `201`(96개), 다른 하나는 `409 ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED`다. 97개가 되지 않는다 |
| 잠금을 먼저 잡지 않은 운영자 쓰기와 추가·수정·탈퇴 | 추가·수정이나 탈퇴가 운영자 트랜잭션의 끝(고친 행과 겹치거나 같은 행, 또는 탈퇴가 쥔 `users` 행)을 기다린다. 서로를 기다리면 교착이고 PostgreSQL이 한쪽을 끊는다. 요청이 끊기면 `503`이고 아무것도 바뀌지 않는다. 탈퇴가 끊기면 탈퇴 전체가 롤백되고 탈퇴 절차가 다시 실행한다(NSU-167). runbook은 일정을 넣거나 고치기 전에 `users` 행과 아티스트별 잠금을 이 순서로 먼저 잡아 이 경우를 피한다 |
| 같은 일정의 두 수정 | 둘 다 `200`이고 나중에 커밋된 값이 남는다 |
| 같은 일정의 수정과 삭제 | 수정이 먼저 커밋되면 삭제가 그 일정을 지운다. 삭제가 먼저 커밋되면 수정은 `404`다 |
| 계정 상태 확인 직후 정지 | 정지 UPDATE가 추가·수정의 커밋을 기다린다. 저장은 남는다. 정지된 아티스트는 추천에서 계정 조건으로 빠진다 |
| 정지가 먼저 `users` 행을 잡음 | 추가·수정이 정지의 커밋을 기다린 뒤 `403`이다 |
| 추가·수정과 탈퇴 | §5.3. 어느 순서든 탈퇴한 사용자의 일정은 남지 않는다 |
| 저장 중의 조회와 일괄 조회(추천) | 커밋된 일정만 본다 |

### 5.3 탈퇴할 때 일정 파기

- 탈퇴하면 일정을 즉시 지운다(NSU-167 D2). 삭제 트리거를 두지 않고 탈퇴 절차가 지운다(NSU-167 D4).
- "탈퇴한 사용자의 일정이 남지 않는다"는 두 장치가 함께 지킨다.
  - 삽입 가드 트리거: `artist_schedules`에 행을 넣기 전에(`BEFORE INSERT`), 같은 트랜잭션에서 그 사용자의 `users` 행을 `FOR SHARE`로 잠그고 `ACTIVE` ARTIST가 아니면 거절한다. API, 운영자 SQL, 뒤에 생길 섭외 성사 등 작성 경로와 관계없이 적용된다. API는 `ArtistWriteAccess`가 먼저 같은 행을 잠그므로 트리거는 기다리지 않는다.
  - 탈퇴 절차의 순서(아래)
- 트리거는 지우지 않고 새 행만 막는다. D4의 "트리거는 프로필에만"은 파기 트리거에 대한 결정이라 이 가드와 겹치지 않는다(ADR 결정 11).
- 탈퇴 절차는 `READ COMMITTED` 트랜잭션에서 다음 순서로 한다. 운영자 runbook도 같은 순서다.
  1. `users.status`를 `WITHDRAWN`으로 바꾼다.
  2. `DELETE FROM artist_schedules WHERE user_id = :id`를 실행한다.
- 이 순서면 저장과 탈퇴가 겹쳐도 행이 남지 않는다.
  - 저장이 먼저 `users` 행을 잡으면 탈퇴의 UPDATE가 저장의 커밋을 기다린다. 그 뒤의 `DELETE`는 커밋된 일정을 보고 지운다.
  - 탈퇴가 먼저 잡으면 저장이 탈퇴의 커밋을 기다린 뒤 `403`이다.
  - 운영자 SQL처럼 `ArtistWriteAccess`를 거치지 않는 INSERT도 가드 트리거가 `users` 행을 잠그므로 같은 두 경우로 나뉜다. 탈퇴가 먼저 커밋됐으면 INSERT가 거절된다.
  - 일정 `UPDATE`는 가드를 거치지 않고 `users`를 잠그지 않는다. 그래서 운영자 UPDATE와 탈퇴는 일정 행 하나만 두고 기다리며 교착이 없다. 소유자(`user_id`)를 바꾸는 UPDATE는 거절한다(ADR "탈퇴 시 파기").
- 순서를 바꾸거나(삭제 → 상태 변경) `REPEATABLE READ` 이상으로 돌리면, 기다리는 동안 커밋된 일정이 남을 수 있다.
- 일정 모듈에 탈퇴용 공개 메서드는 없다. 탈퇴 절차가 위 SQL을 직접 실행한다(ADR 결정 11).
- NSU-167 전에는 탈퇴 기능이 없다. 그 전에 운영자가 SQL로 상태를 `WITHDRAWN`으로 바꾸면 같은 트랜잭션에서 위 `DELETE`도 실행한다.
- 탈퇴 트랜잭션이 `users` 행을 쥐는 동안의 일정 저장은 `503 ARTIST_SCHEDULE_BUSY`로 끝날 수 있다. 정상 동작이다.

### 5.4 추천 Eligibility가 읽는 값

- 추천은 일정 모듈의 공개 일괄 조회 `ArtistSchedules.findByArtistIds(artistIds, from, to)`로 읽는다. 어댑터 `SavedArtistScheduleReader`가 결과를 `ScheduleSlot`으로 바꾼다. 빈 구현 `EmptyArtistScheduleReader`는 지운다(ADR 결정 9·10).
- 일괄 조회는 Eligibility ADR의 창구 전제를 지킨다.
  - `[from, to)`와 겹치거나 맞닿는 일정을 아티스트 수와 관계없이 한 문장으로 읽는다.
  - `from`·`to`와 돌려주는 시작·끝은 `Asia/Seoul` 벽시계다. `Event.ZONE`으로 바꿔 조회하고, 같은 시간대로 되돌린다.
  - 일정이 없는 아티스트는 키가 없다. 지도와 목록은 null이 아니고 수정할 수 없다. 목록은 시작 순이다.
  - 조회에 실패하면 예외를 던진다. 빈 결과로 바꾸지 않는다.
- 일괄 조회는 일정 이름과 일정 ID를 돌려주지 않는다.

| 저장 값(행사 시간대 기준) | 추천에서 |
|---|---|
| `AVAILABLE` 일정을 맞닿은 것까지 이어 붙여 시간대 전체를 덮고, 시간대와 겹치는 다른 상태가 없음 | `SCHEDULE_AVAILABLE` 통과 |
| 시간대와 겹치는 `HOLD`·`BOOKED`·`UNAVAILABLE`이 있음 | `SCHEDULE_BLOCKED`로 빠진다 |
| 일정이 없거나, `AVAILABLE`이 시간대 일부만 덮음 | `SCHEDULE_NOT_COVERED`로 빠진다 |

- 판정식은 Eligibility ADR이 정하고 이 문서는 바꾸지 않는다. 일정은 프로필 다음에 보므로, 프로필이 없는 아티스트는 `PROFILE_MISSING`으로 먼저 빠진다.

## 6. 로그와 개인정보

- 일정(시간·상태)과 일정 이름은 아티스트의 개인정보다. 로그에 남지 않는다. 장치는 새로 만들지 않고 09 §6과 같은 장치(로그 ADR `logging/00` Decision 7·8)를 쓴다.
  - 이 모듈의 로그 문장은 잠금 대기 초과·교착 WARN 하나다. 아티스트 ID와 SQLState만 남긴다.
  - 검증은 실제 출력 바이트로 한다(§9 "운영 관측").
- 응답은 이메일·휴대폰·사용자 ID를 담지 않는다.
- 일정은 본인만 본다. 다른 사용자에게는 추천 결과의 통과 조건(`SCHEDULE_AVAILABLE`)으로만 드러난다. 그 행사 시간대에 된다는 사실만 드러나고, 다른 시간의 일정과 일정 이름은 드러나지 않는다.
- 처리방침(NSU-165)의 수집 항목에 공연 가능 일정(시간, 상태, 일정 이름)을 더한다. 지난 일정의 보유 기간도 그때 정한다. 실사용자에게 열기 전에 끝낸다.

## 8. 화면이 바꿀 것

체험판 화면(`frontend/src/features/my-page/availability.js`, `components/availability-panel.jsx`·`week-add-form.jsx`)은 일정을 브라우저(`localStorage`)에 저장한다. 서버에 연결할 때 다음이 바뀐다.

| 체험판 | 서버 연결 뒤 |
|---|---|
| 브라우저 저장 | 주·월을 열 때 그 기간을 `GET`으로 읽는다(주 7일, 월 35·42일). 추가는 `POST`, 수정은 `PUT`, 삭제는 `DELETE`이고 응답으로 다시 그린다 |
| 화면이 만든 일정 ID(`crypto.randomUUID()`) | 응답의 `id`를 쓴다 |
| 하루 안의 `date`·`start`·`end` | `startDate`·`startTime`·`endDate`·`endTime`. 같은 날 끝나면 `endDate = startDate`다 |
| 끝 `24:00` | 다음 날 `00:00`으로 보낸다(`endDate`를 하루 뒤로). 응답의 다음 날 `00:00`은 그날의 `24:00`으로 그린다 |
| 하루 종일(`allDay`) | `00:00` ~ 다음 날 `00:00`으로 보낸다. 서버는 `allDay`를 저장하지 않는다. 응답이 이 모양이면 하루 종일로 그린다 |
| 같은 날 안의 겹침 확인 | 그대로 둔다. 서버가 날을 넘는 겹침까지 막는다. `409 ARTIST_SCHEDULE_OVERLAP`을 받으면 그 기간을 다시 읽어 그리고 "다른 일정과 시간이 겹칩니다"를 보여 준다. |
| 주간 폼의 여러 요일 추가 | 고른 요일을 `items` 하나로 보낸다(최대 7개). `400`·`409`면 아무것도 저장되지 않았다 |
| 자정을 넘는 일정 없음 | 응답에 자정을 넘는 일정이 올 수 있다(운영자나 다른 기기가 넣은 것). 두 날에 걸쳐 그린다 |
| `BOOKED`(확정)를 고르지 않음 | 그대로 둔다. 응답의 `BOOKED`는 표시한다. `BOOKED` 일정을 수정하려면 다른 상태를 고른다. 시간은 그대로 보내도 된다 |
| 응답을 받지 못함(연결 끊김·시간 초과, 새로 생김) | 추가·수정·삭제가 저장됐는지 알 수 없다. 같은 요청을 자동으로 다시 보내지 않는다. 그 기간을 다시 읽어 그린다. 다시 읽은 결과는 조회한 순간의 일정일 뿐이다. 원래 요청이 아직 처리 중이면 그 뒤에 커밋될 수 있으므로, 빈 결과를 저장 실패로 안내하지 않는다. "저장 여부를 확인하지 못했습니다. 목록을 확인해 주세요"를 보여 주고, 사용자가 다시 추가하면 그 요청을 보낸다. 앞 요청이 그 사이 저장됐으면 겹쳐 `409`이고 같은 일정이 두 번 생기지 않는다. 다시 보낸 추가는 그 사이 다른 기기에서 옮긴 일정을 원래 시간에 다시 만들 수 있다(ADR "멱등 키를 두지 않는 이유") |
| `409 ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED`(새로 생김) | 아무것도 저장되지 않았다. "하루에 일정을 96개까지 둘 수 있습니다"를 보여 준다 |
| `503 ARTIST_SCHEDULE_BUSY`(새로 생김) | 저장·삭제가 되지 않았다. 입력값을 그대로 두고 "잠시 후 다시 시도해 주세요"를 보여 준다. 자동으로 다시 보내지 않는다 |

- 정지된 계정의 추가·수정은 `403 ACCESS_DENIED`다. 삭제와 조회는 된다.
- 화면의 시간 선택(`08:00`~`24:00`, 30분)은 그대로 써도 된다. 서버는 분 단위 시각을 모두 받고 길이 하한이 없다.
- 정각·30분이 아닌 일정(섭외 성사·운영자의 `BOOKED`) 옆에는 30분보다 짧은 틈이 생긴다. 화면은 그 틈을 채울 수 있게 옆 일정의 시작·끝 시각도 고를 수 있게 한다. 예: `18:30~19:00` 불가와 `19:20~19:50` 확정 사이의 `19:00~19:20` 가능. 시간 선택을 바꾸는 시점은 화면 담당이 정한다. 바꾸기 전에는 그런 틈에서 추천되지 않는다.
- 일정 이름 칸(`maxLength={30}`)은 UTF-16 단위로 세므로 서버(코드포인트)보다 엄격하다. 그대로 둬도 `400`이 나지 않는다.

## 9. 테스트 기준

DB가 관여하는 경우(배제 제약, `CHECK`, 동시 요청, 잠금, 조회 횟수)는 실제 PostgreSQL(Testcontainers)로 확인한다.

**내 일정 API**

| 대상 | 경우 |
|---|---|
| 역할 | 토큰이 없으면 `401`. EVENT_PARTNER의 조회·추가·수정·삭제는 `403 ACCESS_DENIED`이고 행이 생기거나 바뀌거나 지워지지 않는다. 깨진 JSON을 보내도 `403`이다 |
| 계정 상태 | `SUSPENDED` 아티스트의 유효한 토큰으로 한 추가·수정은 `403 ACCESS_DENIED`이고 행이 그대로다. 검증에 걸리는 본문을 보내도 `400`이 아니라 `403`이다. 같은 토큰의 삭제는 `204`이고 일정이 지워진다. 조회는 `200`이다. `WITHDRAWN` 아티스트의 추가는 `403`이고 행이 생기지 않는다(NSU-167 D3 전의 동작. D3을 넣으면 `401`로 바꾼다, §4 "탈퇴한 계정") |
| 추가 | 두 항목(토요일 `18:00~22:00` `AVAILABLE`과 일정 이름, 일요일 하루 종일 `UNAVAILABLE`)의 추가는 `201`이다. 응답 `items`는 요청 순서이고 서버가 만든 `id`가 있다. 이어서 한 조회와 값이 같다 |
| 모두 또는 전무 | 7개 중 7번째가 저장된 일정과 겹치면 `409`, 1번째 항목과 겹치면 `409`, 검증에 걸리면 `400`이다. 세 경우 모두 행 수가 그대로다 |
| 개수 | `items`가 빠짐·`null`·`[]`·8개이거나 원소가 `null`이면 `VALIDATION_ERROR`이며 `ProblemDetail`이 아니다. 1개와 7개는 통과 |
| 시간 | §2.2 표의 경우마다 결과가 표와 같다. 그 밖에 `25:00`, `"18:00:00"`, `"2026/12/12"`, `2026-02-30`, `1999-12-31`, `2100-01-01`은 `VALIDATION_ERROR`. `2000-01-01`, 지난 날짜, `19:40~20:10`, `23:59` 시작은 통과 |
| 상태 | `BOOKED`, 없는 값, 소문자 `available`, `null`, 빠짐은 `VALIDATION_ERROR`. 세 값은 통과 |
| 일정 이름 | 30자는 통과, 31자는 `VALIDATION_ERROR`. 앞뒤 공백은 지워 저장된다. 공백만·폭 없는 공백만·빠짐·`null`은 `title: null`로 저장된다(오류 아님). NUL 문자는 `VALIDATION_ERROR`. 이모지 30개는 통과. 보이지 않는 글자 규칙은 05 §6과 같다 |
| 겹침 | 저장된 `18:00~22:00`이 있을 때 `20:00~23:00` 추가는 상태가 달라도 `409 ARTIST_SCHEDULE_OVERLAP`이고 행이 그대로다. 맞닿은 `22:00~23:00`은 통과. 다른 아티스트는 같은 시간도 통과. 전날 `22:00`~이날 `02:00` 일정이 있으면 이날 `01:00~03:00`은 `409`, `02:00~03:00`은 통과 |
| 수정 | 일정 이름을 뺀 수정은 일정 이름을 지운다. 자기 옛 구간과 겹치는 새 구간(`18:00~22:00` → `20:00~23:00`)은 `200`. 다른 자기 일정과 겹치면 `409`이고 두 일정이 그대로다. 다른 아티스트의 일정 ID와 없는 ID는 `404 ARTIST_SCHEDULE_NOT_FOUND`이고 다른 아티스트의 일정이 그대로다. 본문의 `id`는 무시된다. SQL로 넣은 `19:40~20:10` `BOOKED` 일정을 같은 시간의 `UNAVAILABLE`로 바꾸는 수정은 `200`이고 시간이 그대로다 |
| 삭제 | 자기 일정은 `204`이고 지워진다. 다른 아티스트의 일정 ID는 `204`이고 그 일정이 남는다. 없는 ID와 이미 지운 ID도 `204` |
| 경로 형식 | `1-2-3-4-5`와 `abc`는 수정·삭제 모두 `400 INVALID_ARTIST_SCHEDULE_ID`. 대문자로 쓴 정규형 UUID는 통과 |
| 조회 | 조회 기간과 겹치는 일정만 시작 순서로 나온다. 끝이 `from 00:00`인 일정과 시작이 `to` 다음 날 `00:00`인 일정은 빠진다. 전날 밤에 시작해 `from`에 걸친 일정은 그대로 나온다. 42일은 통과, 43일은 `VALIDATION_ERROR`. `from > to`, 파라미터 빠짐, 형식 오류, 없는 날짜, 범위 밖 날짜는 `VALIDATION_ERROR`이며 `ProblemDetail`이 아니다. 일정이 없으면 `items: []`. 일정의 키가 모두 있다(`title: null` 포함) |
| 본인만 | 두 아티스트의 일정이 서로의 조회에 나오지 않는다 |
| 운영자 SQL 일정 | SQL로 넣은 `BOOKED`와 `19:40` 같은 분의 일정이 조회에 그대로 나온다 |
| 무시하는 필드 | 본문의 `id`·`artistId`·`userId`와 모르는 필드는 결과에 영향이 없다 |
| 형식 오류 | 깨진 JSON과 `items` 자리의 객체는 Spring 표준 400(`ProblemDetail`) |
| 응답 유실 뒤 조회 | 추가 트랜잭션의 커밋을 보류한 채 같은 기간을 조회하면 그 일정이 없다. 커밋 뒤 다시 조회하면 나온다. 같은 일정을 다시 추가하면 `409`다(화면 복구 기준 §8의 근거) |
| 운영 관측 | 잠금 대기 초과 `503`의 WARN 로그에 아티스트 ID와 SQLState가 남는다(양성 대조). 가짜 일정 이름을 넣은 추가 성공, 검증 실패(31자 일정 이름), 겹침 `409`, 깨진 JSON 흐름에서 배포 설정 인코더의 실제 출력 바이트에 그 일정 이름이 없다(`LogPrivacyIntegrationTest`와 같은 방식) |

**저장과 DB**

| 대상 | 경우 |
|---|---|
| DB 제약 | 직접 INSERT에서 `user_id`·`start_at`·`end_at`·`status`의 `NULL`, 시작 = 끝, 뒤집힌 구간, 24시간 초과, 초가 있는 시작·끝, 허용 밖 상태, 공백만인 일정 이름, 31자 일정 이름, 같은 아티스트의 겹치는 행을 거절한다. 맞닿은 행, 다른 아티스트의 겹치는 행, `BOOKED`, `19:40` 같은 분, 1분짜리 행은 받는다 |
| 허용 값 일치 | 상태 `CHECK`가 허용하는 값이 `ArtistScheduleStatus` 값 전체와 같다 |
| 동시 추가 | 같은 아티스트에 서로 겹치는 일정을 하나씩 담은 추가 두 개를 배리어로 같은 순간에 출발시키고 20번 되풀이한다(매번 행을 지운다). 매번 행은 1개이고, 하나는 `201`, 다른 하나는 `409 ARTIST_SCHEDULE_OVERLAP`이다. `503`·`500`은 없다(아티스트별 잠금으로 교착이 없다) |
| 차례 추가 | 앞 추가가 커밋된 뒤 겹치는 추가를 보내면 `409`이고 행이 그대로다 |
| 미커밋 일정 기다림 | 다른 연결이 겹치는 일정을 넣고 커밋하지 않으면 추가는 기다린다. 그 연결이 커밋하면 `409`, 롤백하면 `201`이다 |
| 엇갈린 추가 | 추가 [A, B]와 [B와 겹치는 B′, A와 겹치는 A′]를 배리어로 같은 순간에 출발시키고 20번 되풀이한다. 매번 한 요청만 `201`이고 다른 요청은 `409`다. `503`(교착)은 없다 |
| 운영자 UPDATE와 교착 | 다른 연결이 아티스트별 잠금 없이 일정 R을 `UPDATE`(같은 날 안에서 시간 변경)하고 커밋하지 않은 채, R의 새 구간과 겹치는 추가 요청을 다른 스레드에서 시작한다. 요청이 기다리는 것을 `pg_stat_activity`로 확인한 뒤 그 연결이 같은 아티스트의 새 행을 INSERT한다(트리거가 아티스트별 잠금을 기다린다). PostgreSQL이 어느 쪽을 끊든 결과는 둘 중 하나다. 요청이 끊기면 `503 ARTIST_SCHEDULE_BUSY`이고(`500`이 아니다) 요청의 행이 없다. 그 연결이 끊기면 R이 옛 값으로 돌아가고 요청은 `201`이다. runbook대로 그 연결이 먼저 잠금을 잡으면 교착 없이 요청이 기다린 뒤 끝난다 |
| 운영자 수정·추가와 탈퇴 | 운영자를 흉내 낸 연결이 runbook대로 `users` 행 `FOR SHARE` → 아티스트별 잠금을 잡고 일정 R을 `UPDATE`한 채, 다른 연결에서 탈퇴(상태 UPDATE → 일정 `DELETE`)를 시작한다. 탈퇴가 기다리는 것을 확인한 뒤 운영자 연결이 새 일정을 INSERT하고 커밋한다. 두 트랜잭션이 모두 끝나고(교착 없음) 최종 일정은 0건이다. runbook을 어긴 경우(잠금 없이 R을 `UPDATE` → 탈퇴 시작 → INSERT)는 PostgreSQL이 한쪽을 `40P01`로 끊고, 어느 쪽이 끊겨도 탈퇴를 다시 실행하면 최종 일정이 0건이다 |
| 추가와 탈퇴 겹침 | 두 DB 연결. 탈퇴는 `READ COMMITTED`에서 상태 UPDATE 뒤 일정 `DELETE`를 흉내 낸다. (1) 탈퇴 UPDATE의 커밋을 보류한 채 추가를 다른 스레드에서 시작하면 기다린다. 탈퇴가 `DELETE`까지 실행하고 커밋하면 추가는 `403 ACCESS_DENIED`이고 행이 없다. (2) 추가가 `users` 행을 잡고 일정을 넣은 뒤 커밋을 보류한 채(테스트용 트랜잭션) 탈퇴 UPDATE를 시작하면 기다린다. 추가를 커밋하면 탈퇴가 이어서 `DELETE`를 실행하고, 커밋한 뒤 행이 없다 |
| 추가와 정지 겹침 | (2)와 같은 방식으로 정지(`SUSPENDED`)하면 정지가 추가의 커밋을 기다리고 일정이 남는다 |
| 삽입 가드 | 직접 INSERT에서 `WITHDRAWN`·`SUSPENDED` 아티스트, EVENT_PARTNER, 없는 사용자의 행을 거절한다. `user_id`를 다른 사용자로 바꾸는 UPDATE를 거절한다. `SET`에 기존 `user_id`를 그대로 넣은 UPDATE는 통과한다. 다른 연결이 그 사용자의 `users` 행을 UPDATE한 채 커밋하지 않으면 직접 INSERT가 기다린다 |
| 운영자 SQL과 탈퇴 겹침 | 운영자처럼 `ArtistWriteAccess` 없이 직접 INSERT하는 연결로 위 (1)·(2)를 되풀이한다. (1) 탈퇴가 먼저 `users` 행을 잡고 `DELETE`까지 실행한 뒤 커밋하면 INSERT가 거절되고 행이 없다. (2) INSERT가 먼저 커밋을 보류하면 탈퇴 UPDATE가 기다리고, INSERT 커밋 뒤 탈퇴의 `DELETE`가 지워 행이 없다 (3) 운영자 연결이 `UPDATE … SET user_id = <기존 값>, status = …`로 일정 행을 잡고 커밋을 보류한 채 탈퇴를 시작하면, 탈퇴는 `users` UPDATE를 마치고 `DELETE`에서 기다린다. 교착 없이 운영자 UPDATE가 커밋되면 탈퇴의 `DELETE`가 지워 행이 없다 |
| 잠금 대기 상한 | 다른 연결이 그 사용자의 `users` 행을 UPDATE한 채 커밋하지 않으면 추가·수정은 약 3초 뒤 `503 ARTIST_SCHEDULE_BUSY`이고(`500`이 아니다) 행이 그대로다. 다른 연결이 그 일정 행을 잠근 채(`SELECT … FOR UPDATE`) 있으면 수정·삭제가 같은 `503`이다. 겹치는 미커밋 일정을 3초 넘게 쥐어도 추가가 같은 `503`이다. 다른 연결이 그 아티스트의 아티스트별 잠금을 쥔 채 있으면 추가·수정이 같은 `503`이고, 삭제와 조회는 기다리지 않는다. 잠금을 풀면 다음 요청은 성공한다 |
| 하루 상한 | 어느 날(`Asia/Seoul`)에 95개를 넣은 뒤 1개 추가는 `201`, 다음 1개는 `409 ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED`이고 행 수가 그대로다. 95개인 날에 그날 항목 2개와 다른 날 항목 1개를 담은 추가는 `409`이고 아무것도 저장되지 않는다. 다음 날은 통과. 그날 `23:59` 시작은 그날, 다음 날 `00:00` 시작은 다음 날로 센다. 96개인 날로 시작 날짜를 옮기는 수정은 `409`, 96개인 날 안에서 시간을 바꾸는 수정은 `200`. 상한과 겹침에 함께 걸리는 항목은 `DAILY_LIMIT_EXCEEDED` |
| 하루 상한 경쟁 | 95개인 날에 서로 겹치지 않는 한 건짜리 추가 두 개를 배리어로 같은 순간에 출발시키고 20번 되풀이한다. 매번 그날 행은 96개이고, 하나는 `201`, 다른 하나는 `409 ARTIST_SCHEDULE_DAILY_LIMIT_EXCEEDED`다 |
| 하루 상한 DB | 직접 INSERT로 97번째 행을 넣으면 SQLState `23514`, 제약 이름 `ck_artist_schedules_daily_limit`으로 거절한다. 한 문장으로 여러 행을 넣어도 앞 행까지 센다(95개인 날에 2행 INSERT는 거절). 운영자처럼 직접 UPDATE로 시작 날짜를 96개인 날로 옮기면 거절, 같은 날 안의 시간 변경과 상태 변경은 통과. `REPEATABLE READ`·`SERIALIZABLE` 트랜잭션의 직접 INSERT와 시작 날짜 변경 UPDATE는 개수와 관계없이 SQLState `25000`으로 거절, 같은 날 안의 수정은 통과 |
| 임시 표로 속이기 | 운영자 연결이 같은 이름의 임시 표 `users`(대상 사용자를 `ACTIVE` ARTIST로 넣음)와 `artist_schedules`(비어 있음)를 만든 뒤, 실제로는 `WITHDRAWN`인 사용자의 일정을 INSERT하면 삽입 가드가 거절한다. 실제로 96개인 날에 INSERT하면 `ck_artist_schedules_daily_limit`으로 거절한다 |
| 일정 표 복원 | `ACTIVE`·`SUSPENDED`·`WITHDRAWN` 아티스트와 없는 사용자의 행이 섞인 덤프를 ADR "마이그레이션 스케치"의 복원 절차로 되돌린다. `ACTIVE`·`SUSPENDED`의 행만 들어가고, 커밋 뒤 `trg_artist_schedules_before_insert`가 켜져 있다. 복원으로 어느 날이 96개를 넘으면 전체가 롤백된다. 복원 트랜잭션이 아티스트별 잠금을 잡지 않는다(`pg_locks`에 `advisory` 행이 없다) |
| 아티스트별 잠금 키 | 앱이 잡는 잠금과 트리거가 잡는 잠금이 같은 키다. 요청이 잠금을 쥔 채 멈춘 동안(테스트용 지연), 다른 연결의 직접 INSERT가 `pg_locks`의 같은 advisory 키에서 기다린다 |
| 마이그레이션 | 다른 연결이 `users` 행을 UPDATE한 채 커밋하지 않으면 마이그레이션은 `lock timeout`으로 실패한다(FK가 `users`에 락을 건다). 테스트는 파일을 버전 번호가 아니라 설명(`create_artist_schedules`)으로 찾는다. 머지 직전에 번호를 바꿔도 테스트를 고치지 않게 하기 위해서다 |

**추천 Eligibility**

| 대상 | 경우 |
|---|---|
| 시간대 변환 | 행사 시간대 `2026-12-12 19:00~21:00`(KST)와 겹치는 `BOOKED`가 조회되어 판정이 실패한다(`SCHEDULE_BLOCKED`). 벽시계를 UTC로 바꿔 조회하는 구현이면 이 테스트가 실패한다 |
| 경계 | `[from, to)`에 맞닿는 일정(끝 = `from`, 시작 = `to`)이 조회된다. 끝이 `from` 30분 전인 일정은 조회되지 않는다. `from` 24시간 전에 시작해 `from`에 끝나는 24시간 일정이 조회된다 |
| 지도 | 일정이 없는 아티스트는 키가 없다. 지도는 null이 아니고 수정할 수 없다. 빈 입력은 SQL 없이 빈 지도다. 인자나 원소가 null이면 `NullPointerException`, `from`이 `to`보다 늦으면 `IllegalArgumentException`이다 |
| 조회 횟수 | 아티스트 1명과 100명의 `filter()`가 같은 수의 SQL 문장을 쓰고, `artist_schedules` 조회는 `filter()`마다 1번이다 |
| 판정 | 프로필을 갖춘 아티스트와 실제 DB 일정으로 행사 시간대 `19:00~21:00`을 판정한다. `AVAILABLE` `18:00~20:00`과 `20:00~22:00`(맞닿음)은 통과. `18:00~20:00`만 있으면 `SCHEDULE_NOT_COVERED`. `AVAILABLE` `18:00~20:00`과 `HOLD` `20:00~22:00`은 `SCHEDULE_BLOCKED`. 일정이 없으면 `SCHEDULE_NOT_COVERED`. 짧은 틈: `UNAVAILABLE` `18:30~19:00`, `AVAILABLE` `19:00~19:20`, `BOOKED` `19:20~19:50`이면 행사 시간대 `19:00~19:20`은 통과한다(설계 리뷰 2회차 지적의 회귀 테스트) |
| 상태 대응 | `ArtistScheduleStatus`의 모든 값이 `ScheduleStatus`의 같은 이름으로 바뀐다 |
