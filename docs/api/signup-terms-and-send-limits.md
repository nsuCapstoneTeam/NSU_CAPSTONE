# 가입 약관 동의 시점과 인증 코드 발송 한도

가입 세션을 만들 때 필수 약관 동의를 함께 받고, 인증 코드 발송에 하루·1시간 한도를 둔다. 가입 세션 생성·OAuth 시작·로그인에도 요청 제한을 두고, 이메일은 저장과 비교를 모두 소문자로 한다. 이미 구현된 가입 API를 바꾸는 계약이다.

- 상태: **백엔드 필수 구현·자동 검증 반영, 통합 배포 전**(2026-11-10). 약관·정규화·요청 제한·알림·관리 스크립트·Redis 메모리/시간 설정을 구현했다. 실제 Webhook 주입·제공자 응답 확인·배포 환경 검증과 프론트 NSU-129는 별도다. 이 문서 전체가 배포 완료된 것은 아니다.
- 구현 이슈: NSU-123(백엔드), NSU-129(가입 화면)
- 근거: ADR [identity_verification/00](../adr/identity_verification/00_mvp_sandbox_identity_verification.md) "개인정보"·"인증 메시지 발송 한도"(2026-11-05 결정). 약관 동의 시점과 시연 약관 2종은 SSOT `AUTH-006`의 v1.18 초안 ⑤(팀 확인 전)에 기댄다. 승인본 `AUTH-006`(v1.17.1)은 "서비스 이용약관 동의·개인정보처리방침 동의"다
- 함께 보는 계약: [artist-oauth-signup.md](./artist-oauth-signup.md)(OAuth 가입 준비·최종 가입)

## 1. 바뀌는 API

### 1.1 가입 세션 생성에 약관 동의를 함께 받는다

| API | 바뀌는 것 |
|---|---|
| `POST /api/v1/auth/signup/artist/session` | 요청 본문에 `agreements`(필수)를 더하고, `phone`은 숫자 정규형만 받으며 `email`은 서버가 소문자로 정규화한다(§1.3) |
| `POST /api/v1/auth/signup/event-partner/session` | 같다 |
| `POST /api/v1/auth/signup/artist/oauth/session` | 같다 |
| `PUT /api/v1/auth/signup/{artist,event-partner}/session/required-terms-agreement` | 없앤다. 동의는 위 세션 생성에서만 받는다 |

```json
{
  "email": "artist@example.com",
  "phone": "01012345678",
  "agreements": [
    { "id": "service", "version": "v1" },
    { "id": "privacy", "version": "v1" },
    { "id": "demo-notice", "version": "v1" },
    { "id": "overseas-transfer", "version": "v1" }
  ]
}
```

- `agreements`의 항목 모양은 지금의 약관 동의 API와 같다(`id`, `version`).
- 필수 약관 ID는 다음과 같다. 서버 설정 `SIGNUP_REQUIRED_TERMS`와 화면의 약관 상수(`REQUIRED_TERM_VERSIONS`)는 이 표와 같은 값을 쓴다. 버전을 올리면 설정과 화면을 같은 배포로 바꾼다.

| `id` | 내용 | 환경 |
|---|---|---|
| `service` | 서비스 이용약관 | 모든 환경(SSOT `AUTH-006`) |
| `privacy` | 개인정보 수집·이용(항목, 목적, 보유 기간, 처리 위탁, 동의 거부권과 불이익). 승인본 `AUTH-006`의 "개인정보처리방침 동의"를 개인정보보호법 §15·§22에 맞춰 수집·이용 동의로 받는다. SSOT 문구 반영은 팀 확인 전이다 | 모든 환경(SSOT `AUTH-006`) |
| `demo-notice` | 시연 서버 안내(실제 섭외에 쓰지 않음, 초기화 날짜, 테스트 본인확인) | `DEMO`만 |
| `overseas-transfer` | 개인정보 국외 이전(Resend, 미국) | 국외 이전이 있는 환경. 지금은 `DEMO` |

- 기본 환경은 위 2종만, `SPRING_PROFILES_ACTIVE=demo`로 명시적으로 켠 `demo` Spring 프로필은 위 4종을 `SIGNUP_REQUIRED_TERMS`에 설정한다. 버전 기본값은 없고 환경별 필수 ID 누락·중복·알 수 없는 ID는 기동 실패다.
- 서버 설정의 필수 약관이 하나라도 빠지거나 버전이 다르면 `400 REQUIRED_TERMS_NOT_AGREED`이고, 세션을 만들지 않고 메일·문자를 보내지 않는다. 같은 `id`가 두 번 오거나 모르는 `id`가 오면 기존 `400 TERMS_AGREEMENT_INVALID`다.
- 서버는 동의를 받은 시각(세션 생성 요청을 처리한 시각)을 약관 ID·버전과 함께 가입 세션(Redis)에 둔다. OAuth 가입은 OAuth 가입 세션에 같은 값을 둔다. 최종 가입(`POST /api/v1/auth/signup/{역할}`, `POST /api/v1/auth/signup/artist/oauth`)이 성공할 때 그 값을 그대로 회원과 함께 DB에 저장한다. 동의 시각은 가입 완료 시각이 아니다.
- 중간에 그만둔 세션은 세션 TTL(30분)이 지나면 Redis에서 사라지고 DB에 동의 기록이 생기지 않는다.
- OAuth 가입 준비의 재요청은 `agreements`도 비교한다. 같으면 `200`, 다르면 다른 필드가 다를 때와 같은 `400 VALIDATION_ERROR`다.

### 1.2 인증 코드 발송에 한도와 `Retry-After`를 둔다

대상: `POST /api/v1/auth/signup/{artist,event-partner}/session/{email,phone}-verification/send`

| 한도 | 단위 | 기본값 | 창 |
|---|---|---|---|
| 받는 곳 | 정규화한 번호·이메일 하나(§1.3) | 하루 5회 | Asia/Seoul 날짜 |
| 확인 시도 | 정규화한 번호·이메일과 요청 IP(IPv6는 /64)의 쌍 하나. 살아 있는 challenge에 대한 오답만 센다 | 하루 10회 | Asia/Seoul 날짜 |
| 요청 IP | IPv4 주소 하나, IPv6 /64 대역 하나 | 1시간 20회 | Asia/Seoul 정각부터 [시작, 끝) |
| 요청 IP의 이메일 발송 | IPv4 주소 하나, IPv6 /64 대역 하나 | 1시간 10회 | Asia/Seoul 정각부터 [시작, 끝) |
| 서버 전체 | SMS | 하루 300회 | Asia/Seoul 날짜 |
| 서버 전체 | 이메일 | 하루 80회 | Asia/Seoul 09:00부터 다음 날 09:00까지 [시작, 끝) |
| 재전송 쿨다운 | 정규화한 받는 곳·채널 | 60초 | 마지막 발송 요청부터 60초 |

- 넘으면 기존 `429 VERIFICATION_REQUEST_LIMIT_EXCEEDED`다(확인 시도 한도는 기존 `429 VERIFICATION_ATTEMPT_LIMIT_EXCEEDED`). 응답 헤더 `Retry-After`에 걸린 한도의 창이 끝날 때까지 남은 초를 준다. 여러 한도에 걸리면 가장 늦게 풀리는 값이다. 60초 쿨다운에 걸려도 남은 초를 준다.
- 요청 IP는 서버가 해석한 원격 주소를 쓴다. 리버스 프록시 뒤에 배포할 때는 프록시가 외부에서 들어온 전달 헤더를 제거하고 신뢰할 수 있는 클라이언트 주소를 설정해야 한다. 백엔드 직접 접근을 막고, 서로 다른 클라이언트가 실제로 별도 IP 한도로 계산되는지 배포 환경에서 확인한다.
- 재전송 쿨다운은 지금의 가입 세션 단위에서 받는 곳 단위로 바꾼다. 세션을 여러 개 만들어 한 번호에 몇 초 안에 문자를 여러 통 보내지 못하게 하기 위해서다. 정상 사용자가 세션을 새로 만들어도 최대 60초만 기다린다.
- 요청 IP의 이메일 발송 한도는 `+`·점을 바꾼 주소(`me+1@…`, `m.e@…`)를 받는 곳 한도로 막을 수 없어서 둔다. 이런 주소는 서로 다른 받는 곳으로 센다. 이 한도가 없으면 IP 하나가 1시간 20회씩 4시간이면 이메일 전체 한도 80회를 다 써서, 다음 09:00까지 모든 이메일 인증을 막는다. 이 한도가 있으면 IP 하나가 이메일 전체 한도를 다 쓰는 데 8시간이 걸린다. 그 사이에 80% 알림(아래)을 받은 운영자가 그 대역을 막는다. 창을 하루가 아니라 1시간으로 두는 것은, 심사장 Wi-Fi처럼 IP 하나를 여러 명이 쓸 때 그날 내내 막지 않기 위해서다(ADR "버린 안"의 IP 하루 창). 가입 1건은 이메일 발송 1회와 SMS 발송 1회이므로, 공유 IP 하나에서 1시간에 가입할 수 있는 사람은 요청 IP 한도(1시간 20회) 때문에 재전송이 없을 때 10명이다(20 ÷ 2로 계산한 값이고, 실제 시연장 인원을 잰 값이 아니다). 이메일 한도는 그보다 먼저 걸리지 않지만, 재전송이 많으면 먼저 걸린다. 그래서 시연 당일 설정값을 리허설 체크리스트에 둔다(NSU-129).
- 확인 시도 한도는 세션을 새로 만들어도 이어진다. 지금의 challenge별 확인 5회는 그대로 두고, 같은 (받는 곳, IP) 쌍의 하루 합계를 따로 센다. 세션을 바꿔 OTP를 계속 추측하지 못하게 하기 위해서다.
- 받는 곳 하나로만 세지 않는 이유: 그러면 남이 피해자 번호로 세션을 만들어 오답 10번을 넣어 피해자의 가입을 그날 막을 수 있다(2026-11-07 PR #205 CodeRabbit 리뷰, 사용자 결정). 쌍으로 세면 남의 IP에서 넣은 오답은 피해자를 막지 못한다. IP를 바꿔 가며 추측해도 받는 곳 하루 발송 5회와 challenge별 확인 5회 때문에 받는 곳 하나에 하루 최대 25번(6자리 코드라 0.0025%)만 추측할 수 있다.
- 확인 시도 하루 한도를 다 쓴 (받는 곳, IP) 쌍은 발송도 막는다. 발송 요청도 `429 VERIFICATION_ATTEMPT_LIMIT_EXCEEDED`이고 `Retry-After`는 걸린 한도 중 가장 늦게 풀리는 시각까지 남은 초다(이 한도만이면 다음 자정, 이메일 전체 한도도 함께 걸려 있으면 다음 09:00). 제공자를 부르지 않고 어느 카운터도 늘리지 않는다. 다시 받아도 그날은 확인할 수 없으므로, 문자 비용과 받는 곳 하루 5회를 쓰지 않게 하기 위해서다. 확인 요청이 하루 한도에 걸렸을 때도 같은 `Retry-After`를 준다. challenge별 확인 5회에 걸린 `429`에는 지금처럼 `Retry-After`가 없다. 화면은 `Retry-After`가 있으면 하루 한도로, 없으면 challenge별 한도로 안내한다(§2). 한 번의 오답이 두 한도를 함께 채우면(하루 10번째 오답이 그 challenge의 5번째 오답) 하루 한도로 응답한다. 다시 받아도 그날은 확인할 수 없기 때문이다.
- 기본값은 설정값이다. 시간 설정 이름·검증 조건은 [backend README](../../backend/README.md#가입-인증-알림과-시간-설정)에 있다. 설정을 바꾸면 서버를 다시 시작해야 반영된다. 이메일 전체 한도는 메일 발송 요금제의 하루 할당량보다 작게 둔다.
- 할당량 계산은 시연 전용 Resend 계정을 쓰고 받는 메일(inbound)을 쓰지 않는다는 전제다. Resend 할당량은 계정 단위이고 받은 메일도 센다.
- 이메일 전체 한도의 창은 메일 발송 제공자의 하루 할당량 창과 같아야 한다. [Resend Free](https://resend.com/docs/knowledge-base/account-quotas-and-limits)는 하루 100통이고, UTC 날짜(Asia/Seoul 09:00)에 초기화된다. 창을 Asia/Seoul 자정으로 두면 Asia/Seoul 09~24시에 80통, 00~09시에 80통이 한 UTC 날짜에 들어가 할당량을 넘는다. 그러면 로컬 한도가 남아 있어도 Asia/Seoul 09시까지 이메일 인증이 실패한다. 월 할당량 3,000통도 80통 × 31일 = 2,480통이라 넘지 않는다. 하루 할당량이 없는 유료 요금제로 바꾸면 이 한도는 비용 상한으로만 남는다. 받는 곳·확인 시도·SMS 전체 한도는 Asia/Seoul 날짜 그대로다.
- 세션 확인, 60초 쿨다운, 한도 확인과 예약, challenge 발급을 Redis Lua 스크립트 하나(지금의 challenge 발급 스크립트를 넓힌다)로 원자적으로 한다. 어느 하나라도 걸리면 아무 카운터도 늘리지 않고 기존 challenge도 그대로 둔다. 그래서 쿨다운에 걸린 두 번째 클릭은 하루 한도를 쓰지 않고, 한도에 걸린 요청은 이미 받은 코드를 무효로 만들지 않는다. 이 스크립트는 여러 키를 한 번에 쓰므로 단독 Redis(클러스터 아님)를 전제로 한다. Redis Cluster나 서버리스 Redis로 옮기면 키를 한 슬롯에 모으는 hash tag 설계를 다시 한다.
- 새 challenge는 발송 결과가 나올 때까지 대기 challenge로 둔다. 기존 challenge는 지우지 않는다. 지금의 발급 스크립트는 발급할 때 기존 challenge를 먼저 지우므로 이 부분을 바꾼다. 보냄·결과 모름이면 스크립트 하나로 대기 challenge가 기존 challenge를 바꾼다. 확정 실패면 대기 challenge만 지운다. 그래서 재전송이 실패해도 이미 받은 코드는 그대로 쓸 수 있다. 확인 요청은 복구 시간이 지나기 전에는 대기 challenge를 보지 않는다.
  - 대기 challenge는 발급 번호(`generationId`)로 구분한다. 승격은 현재 대기 코드의 발급 번호가 일치할 때만 한다. 확정 실패가 뒤늦게 기록되면 그 발급 번호가 일치하는 대기 코드나 보존 코드만 정리한다. 두 발송이 겹쳐도(쿨다운 0초 테스트 설정 등) 옛 발송의 결과가 새 코드를 덮거나 지우지 않는다.
  - 발송 결과가 기록되지 않았지만 이미 확인에 쓸 수 있는 대기 코드가 있으면, 새 발급 전에 별도로 보존한다. 만료 시각과 오답 횟수는 그대로 적용한다. 새 코드 발송이 확정 실패하면 기존 활성 코드와 보존한 코드는 계속 쓸 수 있다. 새 코드가 정상적으로 승격되면 보존한 코드도 정리한다.
  - 새 코드의 결과 기록도 유실되면, 복구 대기 시간부터 활성 코드와 가장 최근의 확인 가능한 대기 코드만 후보로 삼는다. 이후 새 코드의 확정 실패가 기록되면 아직 보존 중인 이전 대기 코드를 남은 유효기간 동안 다시 쓸 수 있다. 보존하는 대기 코드는 세션·채널별로 한 개다.
  - Redis에 예약만 남고 발송 시도가 기록되지 않은 건은 15초 뒤 정리한다. 다음 확인·발급 요청에서 대기 코드와 예약 카운터를 한 번만 정리하고 쿨다운은 유지한다. 환불 정보는 OTP와 별도로 원래 카운터가 모두 만료될 때까지 보관한다. 발급 요청은 현재 한도에 걸린 미발송 예약을 먼저 찾아 정리하므로 OTP가 만료됐거나 가입 세션이 바뀌어도 복구할 수 있다. 예약 응답이 유실돼 제공자를 부르지 못해도 기존 코드는 유효하다.
  - 발송 시도 뒤 15초(읽기 timeout 10초 + 여유)가 지나도 결과가 기록되지 않으면 기존 코드는 그대로 둔다. 확인 요청에서 기존 코드가 맞지 않거나 없으면 대기 코드도 검증한다. 대기 코드는 일치할 때만 사용할 수 있고, 활성 코드를 먼저 비교하고 틀린 후보마다 해당 challenge와 (받는 곳, IP) 쌍의 하루 오답 횟수를 각각 1회 늘린다. 두 후보가 모두 틀리면 하루 오답은 2회다. 각 후보 비교 전에 코드별·하루 잔여 한도를 확인한다. 하루 한 번만 남았을 때 활성 코드가 틀리면 대기 코드는 비교하지 않고 `429 VERIFICATION_ATTEMPT_LIMIT_EXCEEDED`와 자정까지의 `Retry-After`로 끝낸다. 코드별 한도만 소진하면 `Retry-After`는 없다. 결과가 기록되지 않은 발송의 카운터는 유지한다.
  - 제공자가 확정 실패를 반환한 뒤 Redis 정리 또는 쿨다운 조회가 실패해도 `503 VERIFICATION_DELIVERY_FAILED`로 응답한다. 남은 쿨다운을 확인할 수 없으면 `Retry-After`를 생략한다.
- 카운터 키에는 정규화한 번호·이메일과 IP 대신 기존 `hmac-secret`으로 만든 digest를 쓴다. 키의 TTL은 그 창이 끝나는 시각에서 10분 뒤다. 그래서 하루 키는 다음 날 00:10(이메일 전체 키는 다음 09:10), 1시간 키는 다음 정각 10분 뒤에 사라진다.
- 서버 전체 한도(SMS·이메일)의 80%에 이르면 `WARN` 로그를 남기고 Slack `#dev`에 알린다. 로그만으로는 운영자가 알 수 없기 때문이다.
  - 알림은 Slack Incoming Webhook으로 보낸다. Webhook URL은 시크릿이라 저장소 밖 설정으로 넣는다. 값이 없으면 시작할 때 `WARN` 로그를 남기고 알림만 보내지 않는다(로컬 개발·테스트). 시연 서버에 값이 있는지는 공개 시작 조건에서 확인한다.
  - 창(채널·날짜)마다 한 번 보낸다. 전송이 실패하면 그 창의 다음 발송 때 다시 보낸다(창마다 성공한 한 번). 알림에는 채널, 창, 현재 값, 한도만 넣고 번호·이메일·IP는 넣지 않는다.
  - 알림 전송은 발송 요청과 따로 한다(기본 전체 timeout 3초). 단일 작업자·대기 큐 32개로 자원을 제한하며 큐 포화·Redis 장애는 WARN을 남긴다. 장애 횟수는 채널·창별 누적값으로 보존해 다음 작업에서 병합하고, Redis 응답 유실 재시도는 중복 집계하지 않는다. Redis 반영 전 프로세스 종료나 창 보존 시간을 넘는 장애 시 집계가 누락될 수 있다. 알림이 실패해도 발송 결과에 영향이 없다. Slack 접수 뒤 응답 유실이나 Redis 성공 기록 실패 시에는 재시도로 중복될 수 있다.
  - 받은 운영자가 할 일(대역 차단, 한도 조정, Resend Pro 전환)은 ADR "남은 위험"에 있다.
- 제공자 장애도 같은 Slack으로 알린다. 채널마다 결과 모름·확정 실패가 10분 고정 창(Asia/Seoul)에서 5회를 넘으면, 그 창에 한 번 알린다(전송 규칙은 위와 같다). 5xx·읽기 timeout이면 사용자는 성공 응답을 받으면서 받는 곳 하루 한도를 쓰기 때문에, 운영자가 바로 알아야 한다.
- 카운터 키는 `signup:limit:v2:{한도 종류}:{창 시작 epoch초}:{digest}` 꼴로 둔다. 제공자 장애나 설정 오류가 끝난 뒤 운영자는 관리 스크립트(NSU-123)로 한도 종류와 창을 골라 그 창의 키를 지운다. 받는 곳·이메일 하나만 풀 때는 스크립트가 정규화와 digest 계산을 대신한다. 키 이름이 digest라 운영자가 손으로 찾을 수 없기 때문이다. 조회가 기본이고 실제 초기화에는 `--apply --quiesced`가 필요하다. 복구 대기 시간이 지난 미발송 예약은 초기화 전에 환불한다. 관련 예약을 아직 정리할 수 없으면 초기화를 거절한다. 실행 절차와 옵션은 [backend README](../../backend/README.md#가입-한도-카운터-관리)에 있다.

발송 결과는 셋으로 나눈다.

| 결과 | 예 | 응답 | challenge·쿨다운 | 카운터 |
|---|---|---|---|---|
| 보냄 | 제공자가 접수함 | 지금의 성공 응답 | 대기 challenge가 기존 challenge를 바꾼다. 쿨다운을 남긴다 | 센다 |
| 확정 실패 | 제공자가 거절함(아래 분류표), 요청이 제공자에 닿지 않음 | `503 VERIFICATION_DELIVERY_FAILED`, `Retry-After`는 남은 쿨다운 초 | 대기 challenge만 지운다. 기존 challenge와 60초 쿨다운은 남긴다 | 받는 곳 카운터를 되돌린다. 요청 IP·서버 전체 카운터는 제공자에 닿았으면 세고, 닿지 않았으면 되돌린다(아래) |
| 결과 모름 | 읽기 시간 초과, 응답을 받다 끊김, 빈 응답, 제공자 `5xx` | 지금의 성공 응답 | 대기 challenge가 기존 challenge를 바꾼다(코드가 도착할 수 있다). 쿨다운을 남긴다 | 센다. `WARN` 로그 |
| 분류 밖 예외(보내기 전) | 요청을 보내기 전에 난 런타임 예외(요청 직렬화, 서명 생성 등) | `500 INTERNAL_SERVER_ERROR` | 확정 실패와 같다 | 확정 실패와 같다. `ERROR` 로그 |
| 분류 밖 예외(보낸 뒤) | 요청을 보낸 뒤에 난 런타임 예외(응답 해석 등) | 지금의 성공 응답 | 결과 모름과 같다(제공자가 접수했을 수 있다) | 결과 모름과 같다. `ERROR` 로그 |

어댑터는 제공자 응답을 다음처럼 나눈다. 두 어댑터 모두 Spring `RestClient`로 제공자 REST API를 직접 부르고, 연결 timeout 3초·읽기 timeout 10초(설정값)를 둔다.

| 상황 | SMS(`SolapiSmsSender`, SOLAPI) | 이메일(`ResendEmailSender`, Resend) |
|---|---|---|
| 보냄 | `2xx`이고 실패 목록(`failedMessageList`)이 비었다 | `2xx`이고 응답에 `id`가 있다 |
| 확정 실패 | `4xx`(잔액 부족, 형식 오류, 인증 실패, `429` 포함), `2xx`이지만 보낸 메시지가 모두 실패 목록에 있다 | `4xx`(`429` 포함) |
| 확정 실패(닿지 않음) | 연결 거부, 이름 풀이 실패, 연결 timeout | 같다 |
| 결과 모름 | `5xx`, 읽기 timeout, 응답 중 끊김, 본문을 읽을 수 없거나 `failedMessageList`가 없는 `2xx` | `5xx`, 읽기 timeout, 응답 중 끊김, `id`가 없는 `2xx` |

- 요청 팩토리는 `JdkClientHttpRequestFactory`(JDK `HttpClient`)를 쓴다. 연결 timeout은 `HttpConnectTimeoutException`, 읽기 timeout은 그 밖의 `HttpTimeoutException`으로 와서 예외 타입으로 나눌 수 있다. `HttpURLConnection` 기반 팩토리는 둘 다 `SocketTimeoutException`이라 메시지 문자열로만 나눌 수 있다.
- 어댑터는 요청을 보내기 전과 보낸 뒤를 나눠, 보낸 뒤에 난 예외는 모두 결과 모름으로 던진다. 제공자 응답 모양이 바뀌어도 문자는 가는데 코드를 지우는 일이 없게 하기 위해서다.

- SMS는 SOLAPI SDK(`DefaultMessageService`)를 쓰지 않는다. SDK는 `4xx`와 `5xx`를 모두 상태 코드 없는 `SolapiUnknownException`으로 던져 확정 실패와 결과 모름을 나눌 수 없다. timeout도 50초로 고정이라 요청 스레드를 최대 50초 붙잡는다. 인증 헤더(HMAC-SHA256 서명)는 SDK의 `Authenticator`와 같은 형식으로 만든다. 엔드포인트와 응답 본문은 SDK가 부르는 메시지 발송 API와 같다. 잔액 부족·수신 거부가 `4xx`로 오는지 `2xx`의 실패 목록으로 오는지는 NSU-123 첫 단계에서 테스트 계정으로 확인한다. 어느 쪽이든 확정 실패다.
- 어댑터는 확정 실패와 결과 모름을 다른 예외로 던진다. 지금은 둘 다 `VerificationDeliveryException`이다.
- 로그와 예외 메시지에는 제공자 응답 본문 원문, 번호, 이메일을 넣지 않는다. 상태 코드와 제공자 오류 코드만 남긴다.
- 받는 곳 카운터는 제공자가 그 받는 곳으로 접수했거나 접수했을 수 있는 메시지를 센다(`2xx`는 접수일 뿐 배달 확인이 아니다). 그래서 확정 실패를 되돌려 정상 사용자가 제공자 쪽 문제(잔액 부족 등) 때문에 하루 한도를 잃지 않게 한다. 요청 IP와 서버 전체 카운터는 외부 호출 횟수를 센다. 제공자에 닿은 확정 실패(`4xx`, 전체 실패 목록)에서는 되돌리지 않고 쿨다운도 남긴다. 제공자에 닿지 않은 실패(보내기 전 예외, 연결 거부, 이름 풀이 실패, 연결 timeout)는 외부 호출이 없었으므로 요청 IP·서버 전체 카운터도 되돌린다. 쿨다운은 남아 같은 받는 곳으로 몰아 보내지 못한다. 제공자가 계속 거절하는 받는 곳(수신 거부 등)으로 반복 요청해도 한 받는 곳은 60초에 1번, 한 IP는 1시간 20번, 서버 전체는 하루 한도를 넘겨 외부 호출을 만들지 못한다.
- 되돌릴 때는 예약 때 쓴 키를 그대로 쓰고, 키가 있을 때만 줄인다. 키가 이미 사라졌으면 아무것도 하지 않는다. 그래서 TTL 없는 키가 새로 생기지 않는다.
- 결과 모름에서 코드가 도착하지 않으면, 사용자는 60초 뒤 다시 받는다. 그 요청도 하루 한도에서 센다.

### 1.3 번호와 이메일 정규화

한도가 대소문자·하이픈 같은 형식 변형으로 우회되지 않도록, 세션 생성 때 `phone`은 정규형만 받고 `email`은 서버가 정규화한다. `+`·점을 바꾼 이메일 주소는 다른 받는 곳이다. 이 경우는 요청 IP의 이메일 발송 한도가 막는다(§1.2).

- `phone`: 숫자만, `^01[016789][0-9]{7,8}$`. 하이픈·공백·`+82`가 섞인 값은 `400 VALIDATION_ERROR`다. 화면이 보내기 전에 숫자만 남긴다.
- `email`: 앞뒤 공백을 지우고 전체를 소문자로 바꾼 값을 저장·발송·digest에 쓴다.
- 이메일을 비교하는 곳은 모두 같은 정규화를 쓴다. 저장값만 소문자이고 비교는 원문이면, 대문자가 섞인 주소로 가입한 사람이 같은 주소로 로그인하지 못하고(`401 INVALID_LOGIN_CREDENTIALS`), 제공자 이메일의 대소문자만 다른 OAuth 가입이 중복 확인을 통과해 같은 메일함의 계정이 둘 생긴다(`AUTH-158`).

| 비교하는 곳 | 지금 | 바꾼 뒤 |
|---|---|---|
| 로그인(`POST /api/v1/auth/login`) | 입력 원문으로 `findByEmail` | 입력을 정규화한 뒤 찾는다 |
| 이메일 가입 중복 확인 | 세션 값으로 `existsByEmail` | 세션 값이 이미 정규형이다 |
| OAuth 가입 중복 확인·저장 | 제공자 이메일 원문 | 제공자 이메일을 정규화한 뒤 확인·저장한다 |
| `DEMO` 허용 목록 | 설정 값과 비교 | 설정 값과 회원 이메일을 모두 정규화해 비교한다 |

- 로컬 부분(`@` 앞)까지 소문자로 바꿔 저장·발송한다. 표준(RFC 5321)은 로컬 부분의 대소문자를 구분할 수 있게 하지만, 실제 메일 서비스(Gmail·네이버·다음·Outlook 등)는 구분하지 않는다. 대소문자를 구분하는 메일 서버의 주소는 지원하지 않는다(2026-11-07 PR #205 CodeRabbit 리뷰, 사용자 결정). 저장값을 하나로 두어 중복 가입과 로그인 실패를 막기 위해서다.
- 배포 전에 발급된 OAuth 세션의 검증 이메일은 가입 준비에서 정규화한다. 새 약관 동의 정보가 없는 이미 연결된 구형 세션은 `SIGNUP_SESSION_INVALID`로 재시작을 안내한다.
- DB의 `users.email`은 정규형만 둔다. DB 마이그레이션으로 기존 값을 `lower(btrim(email))`로 바꾸고 `CHECK (email = lower(btrim(email)))`를 더한다. 앞뒤 공백이 남은 행이 있으면 정규화한 주소의 중복 확인이 그 행을 찾지 못하기 때문이다. 그러면 기존 `UNIQUE (email)`이 대소문자·앞뒤 공백을 구분하지 않는 유일성이 된다. 마이그레이션 전에 `lower(btrim(email))`이 같은 중복 행이 있는지 확인한다. 있으면 마이그레이션이 실패하므로 먼저 손으로 정리한다(시연 DB는 팀 계정뿐이다).

### 1.4 Redis에 키를 만드는 공개 경로의 요청 제한

인증 없이 부를 수 있고 요청마다 Redis에 키를 만드는 경로가 셋 있다. 가입 세션 생성은 TTL 30분 해시를, OAuth 시작(`GET /api/v1/auth/oauth/authorization/{provider}`)은 TTL 5분 인가 요청 키를 만든다(`auth.oauth.authorization-request-ttl`). OAuth 콜백은 실패해도 TTL 1분 결과 키를 만든다(`RedisOAuthResultStore.saveError`). 제한이 없으면 반복 요청으로 Redis 메모리를 채울 수 있다. 메모리가 차면 가입·OAuth 상태 저장이 함께 실패한다.

| 대상 | 단위 | 기본값 | 창 |
|---|---|---|---|
| §1.1의 세 세션 생성 API를 합쳐서 | IPv4 주소 하나, IPv6 /64 대역 하나 | 1시간 30회 | Asia/Seoul 정각부터 [시작, 끝) |
| OAuth 시작과 OAuth 콜백(제공자를 합쳐서) | 같다 | 1시간 30회 | 같다 |

- 세션 생성 한도를 넘으면 `429 TOO_MANY_REQUESTS`와 `Retry-After`다(00 §8, 인증 코드 발송이 아니므로 공통 code). 세션을 만들지 않는다.
- OAuth 시작·콜백은 브라우저가 직접 여는 주소라 화면 코드가 `429` 본문을 읽지 못한다. 그래서 한도를 넘으면 지금의 OAuth 오류 처리(`OAuthFrontendRedirectService`)처럼 프론트 주소로 `302` 리다이렉트하고 `error=TOO_MANY_REQUESTS`와 `retryAfter=<초>`를 쿼리로 붙인다. 이 리다이렉트는 결과 키(`saveError`)를 거치지 않으므로 Redis 키를 만들지 않는다. 인가 요청 키도 만들지 않는다.
- 카운터 키와 TTL은 §1.2와 같은 방식이다. 기본값은 설정값이다.
- 검사 순서: OAuth 시작·콜백 제한은 `GET` 요청에만 건다. 시연 쓰기 차단(`403 DEMO_WRITE_NOT_ALLOWED`, 00 §8)은 인증 다음이다. 그래서 토큰 없는 쓰기 요청은 이 필터들보다 먼저 `401`을 받는다(ADR `authentication/00` Decision 6, [PR #206](https://github.com/nsuCapstoneTeam/NSU_CAPSTONE/pull/206)). 세션 생성·로그인 제한은 원래 공개 경로(토큰 없이 부르는 `POST`)에 건다. 이 필터들을 구현할 때 #206이 넣는 필터 목록 테스트를 함께 갱신한다.
- Redis는 `maxmemory 256mb`(설정값, 호스트 메모리 안에서 Redis·JVM·PostgreSQL 몫을 나눈 값)와 `maxmemory-policy noeviction`으로 둔다. `maxmemory`가 없으면(Redis 기본값 0) `noeviction`은 효과가 없고, Redis가 호스트 메모리를 다 써 커널이 Redis·JVM·PostgreSQL 중 하나를 종료할 수 있다. `noeviction`은 메모리가 차도 한도 카운터를 지우지 않고 쓰기를 거절하게 한다. 다른 정책이면 카운터가 지워져 한도가 풀린다.

### 1.5 로그인 요청 제한

`DEMO`의 공개 쓰기 허용 목록(팀 계정)은 그 계정의 비밀번호 하나로 지켜진다. 로그인(`POST /api/v1/auth/login`)에 제한이 없으면 비밀번호를 계속 추측할 수 있고, 없는 계정에도 bcrypt를 돌리므로 요청을 쏟아부어 CPU를 채울 수 있다.

| 대상 | 단위 | 기본값 | 창 |
|---|---|---|---|
| 로그인 요청 | IPv4 주소 하나, IPv6 /64 대역 하나 | 1시간 30회 | Asia/Seoul 정각부터 [시작, 끝) |
| 로그인 실패 | 정규화한 이메일(§1.3)과 요청 IP(IPv6는 /64)의 쌍 하나 | 1시간 10회 | 같다 |

- 두 한도는 비밀번호를 확인하기 전에 본다. 실패 슬롯은 검증 전에 예약하고 성공하면 원래 창의 슬롯을 반납한다. 동시에 진행 중인 인증도 실패 슬롯을 사용하므로 동시 요청이 실패 한도를 넘어 bcrypt를 실행하지 않는다. 넘으면 `429 TOO_MANY_REQUESTS`와 `Retry-After`이고 bcrypt를 돌리지 않는다. 기본값은 설정값이다.
- 로그인 실패를 이메일 하나로만 세면, 공개된 팀 주소로 10번 틀려 누구나 시연 계정을 잠글 수 있다. 그래서 (이메일, IP) 쌍으로 센다. 남의 IP에서 넣은 실패는 팀의 로그인을 막지 못한다. IP를 바꿔 가며 추측하는 것은 로그인 요청 IP 한도와 무작위 시크릿 비밀번호가 막는다.
- 시드 계정 비밀번호는 저장소 밖의 무작위 시크릿으로 두고, 시드 스크립트·문서·로그에 적지 않는다.

### 1.6 Redis를 쓸 수 없을 때

이 계약의 한도 카운터는 모두 Redis에 있다. Redis가 멈추거나, 응답이 늦거나, `maxmemory`에 닿아 쓰기를 거절하면(`noeviction`) 카운터를 읽고 쓸 수 없다. 경로마다 다음처럼 한다.

| 경로 | 동작 | 응답 | 이유 |
|---|---|---|---|
| 인증 코드 발송(§1.2) | 막는다(fail-closed). 제공자를 부르지 않는다 | `503 VERIFICATION_DELIVERY_FAILED`, `Retry-After` 없음 | 한도 없이 보내면 문자 비용과 남의 번호 폭탄을 막지 못한다. challenge도 Redis라 어차피 확인할 수 없다 |
| 가입 세션 생성·OAuth 시작·콜백(§1.4) | 막는다 | 세션 생성은 `503 RATE_LIMIT_UNAVAILABLE`, OAuth는 `error=RATE_LIMIT_UNAVAILABLE`로 리다이렉트 | 세션·인가 요청 자체가 Redis에 있어 어차피 만들 수 없다 |
| 본인확인 시작·완료(ADR 본인확인 요청 제한) | 막는다. PortOne을 부르지 않는다 | `503 RATE_LIMIT_UNAVAILABLE` | PortOne 재조회 남용을 막는다 |
| 로그인(§1.5) | 한도 검사 없이 비밀번호를 확인한다(fail-open). `WARN` 로그 | 평소와 같다 | Redis가 멈춘 동안에도 팀이 로그인할 수 있게 한다. 그동안은 비밀번호 추측과 bcrypt 남용을 막지 못한다 |

- 가입 인증 발송 전 세션 조회·미발송 예약 복구·새 예약·발송 시작은 하나의 전체 800ms 기한을 공유한다. 한 번의 발급에서 처리할 복구 건수는 제한하며, 남은 복구 대상 때문에 발급을 끝낼 수 없으면 같은 발송 실패 응답을 반환한다. 전용 연결의 연결 200ms·명령 250ms는 로컬·같은 배포망에서 검증할 초기값이며 각 호출은 명령 한도와 전체 기한의 남은 시간 중 짧은 시간까지만 기다린다. Redis 장애 시 발송 API는 1초 안에 `503 VERIFICATION_DELIVERY_FAILED`를 반환하고 제공자 호출은 0건이어야 한다. 기한을 넘긴 응답 경로에서는 `cancel()`이나 쿨다운 조회를 기다리지 않는다. 늦은 Redis 명령·응답은 제공자 호출을 시작하지 않으며 예약은 기존 복구 경로에 맡기고 불확실한 카운터는 보수적으로 유지한다. 전역 Redis 설정은 바꾸지 않는다.
- 다른 카운터 명령의 timeout 기준은 1초다. NSU-101에서 Redis 명령 timeout을 정할 때 이 경로들은 1초 이하로 둔다. Lettuce 기본값(60초)이면 Redis가 멈춘 동안 요청 스레드를 60초씩 붙잡는다.
- `RATE_LIMIT_UNAVAILABLE`(`503`)은 새 공통 `code`다. 00 §8 표에 더한다.
- 02 §2.5·04의 요청 제한은 Redis에 접속할 수 없으면 서버 메모리 카운터로 넘어간다. 이 계약은 그 방식을 쓰지 않는다. 서버 메모리 카운터는 재시작하면 사라지고, 위 경로들은 막아도 사용자가 잠시 뒤 다시 하면 된다.

## 2. breaking change

**이미 구현된 가입 API와 화면을 바꾸는 breaking change다(2026-11-06 사용자 승인).** 00 §1은 v1 안에서 기존 클라이언트를 깨는 변경을 하지 않고 `/api/v2`를 열도록 정한다. 이 API를 부르는 클라이언트는 이 저장소의 가입 화면 하나뿐이다. 그래서 `/api/v2`를 열지 않고, 백엔드(NSU-123)와 가입 화면 변경(NSU-129)을 같은 배포로 낸다(00 §1의 예외, [03 §12.1](./03_events.md#121-등록-멱등-키와-불리언-이름-nsu-99-2026-10-18)과 같은 방식). 둘 중 하나만 배포하면 가입이 모두 실패하므로, 배포 순서를 나누지 않는다. 배포는 시연 서버를 외부에 공개하기 전에 한다. 배포 직후 이미 열려 있던 옛 화면은 가입이 실패하므로 새로고침을 안내한다.

| 바뀌는 것 | 전 | 후 | 화면이 할 일 |
|---|---|---|---|
| 약관 동의 시점 | 세션을 만든 뒤 `PUT …/required-terms-agreement` | 세션 생성 본문의 `agreements` | 이메일·휴대폰 입력과 함께 약관 동의를 받아 세션 생성에 보낸다. 약관 PUT을 부르지 않는다 |

| 필수 약관 | `service`·`privacy` | §1.1 표(`DEMO`는 `demo-notice`·`overseas-transfer` 추가) | 체크박스를 표대로 두고 상수를 맞춘다 |

| 발송 `429` | 60초 쿨다운만 | 하루·1시간 한도도 같은 `code` | "60초 뒤" 고정 문구 대신 `Retry-After`로 남은 시간을 보여 준다 |

## 3. 테스트 기준

Redis 카운터와 Lua 스크립트의 원자성은 Testcontainers Redis로 시험한다. 어댑터의 발송 결과 분류 중 상태 코드·본문·읽기 지연은 로컬 HTTP 서버로 시험한다. 연결 거부는 아무도 듣지 않는 로컬 포트로 만든다. 연결 timeout과 이름 풀이 실패는 로컬 HTTP 서버로 만들 수 없으므로, `RestClient`의 요청 팩토리가 그 예외(`HttpConnectTimeoutException`, `UnknownHostException`)를 던지게 바꿔 시험한다. Testcontainers는 Redis·PostgreSQL만 띄운다.

| 확인 | 기대 결과 |
|---|---|
| 세 세션 생성 API에 `agreements` 없이 또는 필수 약관 하나를 빼고 요청 | `400 REQUIRED_TERMS_NOT_AGREED`, 세션·메일·문자 없음 |
| 같은 `id`를 두 번, 또는 모르는 `id`를 보냄 | `400 TERMS_AGREEMENT_INVALID` |
| 필수 약관을 모두 넣어 세션 생성 뒤 최종 가입 | DB의 동의 기록이 요청한 ID·버전과 같고, 동의 시각이 세션 생성 시각과 같다 |
| 세션을 만들고 30분 동안 가입을 마치지 않음 | Redis에서 세션이 사라지고 DB에 동의 기록·번호가 없다 |
| `phone`이 `010-1234-5678`, `+821012345678`, ` 01012345678` | `400 VALIDATION_ERROR` |
| `Artist@Example.com`과 `artist@example.com`으로 세션 여러 개에서 발송 | 같은 받는 곳으로 세어 하루 6번째가 `429` |
| 같은 번호로 가입 세션 여러 개에서 발송 요청 50건을 동시에(Testcontainers Redis) | 정확히 1건만 보낸다(받는 곳 쿨다운) |
| 쿨다운을 0초로 둔 테스트 설정에서 같은 번호로 발송 요청 50건을 동시에(Testcontainers Redis) | 정확히 5건만 보낸다(받는 곳 하루 한도의 원자성) |
| 60초 안에 같은 받는 곳으로 다시 발송(같은 세션, 또는 세션을 새로 만들어) | `429`, `Retry-After`는 남은 쿨다운 초. 하루 카운터는 늘지 않고 기존 코드는 그대로 유효하다 |
| 하루 한도에 걸린 발송 요청 | `429`. 어느 카운터도 늘지 않고 기존 코드는 그대로 유효하다 |
| 같은 IP(IPv6는 같은 /64)에서 1시간 안 21번째, SMS 하루 301번째, 이메일 하루 81번째 | `429 VERIFICATION_REQUEST_LIMIT_EXCEEDED`, `Retry-After`는 그 창이 끝날 때까지 |
| 같은 IP에서 같은 받는 곳으로 세션을 바꿔 가며 살아 있는 challenge에 하루 10번째 오답, 그 뒤의 확인 요청 | 10번째 오답부터 `429 VERIFICATION_ATTEMPT_LIMIT_EXCEEDED`, `Retry-After`는 다음 자정까지(지금의 challenge별 한도처럼 한도에 닿는 오답에서 바로 걸린다) |
| challenge가 없는 세션에서 확인 요청을 반복 | 지금의 응답(`VERIFICATION_CODE_EXPIRED` 등)이고, 받는 곳 하루 확인 카운터가 늘지 않는다 |
| 제공자가 `4xx`로 거절(제공자에 닿은 확정 실패) | `503 VERIFICATION_DELIVERY_FAILED`, `Retry-After`는 남은 쿨다운 초. 대기 challenge는 지우고, 받는 곳 카운터만 되돌린다. 요청 IP·서버 전체 카운터와 쿨다운은 남는다 |
| 코드 A를 받은 뒤 재전송이 확정 실패하고 A로 확인 | 확인에 성공한다 |
| 다른 IP에서 피해자 번호로 오답 10번을 넣은 뒤 피해자가 자기 IP에서 발송·확인 | 발송되고 맞는 코드로 확인된다(확인 시도는 (받는 곳, IP) 쌍으로 센다) |
| 쿨다운 0초 테스트 설정에서 같은 세션의 발송 A·B가 겹치고 B가 먼저 끝난 뒤 A가 끝남 | A는 대기 challenge를 바꾸지 않는다. B의 코드로 확인된다 |
| Redis에 예약을 저장한 뒤 응답이 유실됨 | `503`, 제공자 호출 없음. 15초 뒤 복구에서 예약 카운터를 한 번만 되돌리고 기존 코드는 유지한다 |
